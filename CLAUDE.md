# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

LoyalPro — loyalty program platform for beauty salons integrated with YClients CRM. Three components share one repo:

- **`backend/`** — Node.js/Express API server (port 3001). Serves both the staff web frontend and the mobile client app.
- **`frontend/`** — Vanilla JS single-page app for salon staff. Served as static files by the backend.
- **`mobile/`** — Expo/React Native app for end clients (loyalty card, bonus balance).

## Architecture

### Backend structure
- `server.js` — entry point: sets up Express, mounts routes, starts cron jobs
- `config.js` — all env vars and constants in one place
- `db.js` — two PostgreSQL pools: `pool`/`db` (main app DB) and `botPool`/`botDb` (Telegram bot DB on Beget)
- `migrations.js` — runs `ALTER TABLE … ADD COLUMN IF NOT EXISTS` style safe migrations on startup
- `routes/index.js` — mounts all routers; handles JWT auth inline for `/api/*` routes
- `routes/webhook.js` — YClients webhook at `/yclients/webhook.v2/:companyId` (no JWT, responds 200 immediately then processes async)
- `services/loyalty.js` — cashback calculation, sync from YClients, bonus accrual logic
- `services/yclients.js` — all YClients REST API calls; has in-memory cache for product/service trees
- `services/home-care.js` — "домашний уход" (home care) goods catalog sync
- `services/segments.js` — client segmentation refresh
- `services/staff.js` — staff data sync
- `services/portfolio.js` — pure helpers (filename templating, reorder validation, URL absolutize) shared by admin route + mobile API. No DB/HTTP — unit-tested in `portfolio.test.js`

### Auth & roles
JWT in `Authorization: Bearer <token>` header (or `?token=` for downloads). Roles: `owner > admin > specialist`. Specialists can only access `/api/home-care`, `/api/auth`, `/api/template-settings`. Public routes (no JWT): `/api/auth/login`, `/api/auth/register`, `/api/app-settings`.

Mobile clients use a separate auth path: `routes/mobile-auth.js` + `routes/mobile-client.js` under `/api/mobile/`.

### CORS
Managed in `server.js`. The whitelist is set via `ALLOWED_ORIGINS` env var (comma-separated) or falls back to hardcoded defaults. To add an origin, set `ALLOWED_ORIGINS` in the environment — do not edit the hardcoded list unless adding a permanent default.

### Cron jobs (all TZ: Europe/Moscow)
- `0 10 * * *` — birthday bonuses
- `0 */3 * * *` — YClients sync + goods categories sync
- `0 * * * *` — staff data sync

### Database
PostgreSQL (Beget cloud, SSL). Uses `pg` pool directly — no ORM. Helper `db` object wraps pool with `.query`, `.one`, `.many`, `.any`, `.oneOrNone`. All schema changes go through `migrations.js` using `IF NOT EXISTS` / `DO NOTHING` patterns — never destructive.

### Frontend (staff SPA)
`frontend/js/app.js` — entry, router, init  
`frontend/js/core/` — api.js, auth.js, nav.js, theme.js, utils.js  
`frontend/js/pages/` — one file per page (dashboard, clients, records, staff, segments, settings, home-care, users, portfolio)

API calls go through `core/api.js` which attaches JWT from localStorage automatically.

### Multi-salon
All DB tables have `salon_id` FK to `salons`. Every API route resolves the salon from `req.user.salon_id`. Never run queries without scoping to `salon_id`.

## Tools

### Portfolio module (До/После)
"Before/after" gallery for the mobile client app, managed by salon admins under Settings → Mobile App → Портфолио работ.

**Tables (`migrations.js`):**
- `portfolio_categories` — `id, salon_id, title, cover_photo_url, display_order, is_published, created_at, updated_at`. `cover_photo_url DEFAULT ''` is a sentinel — categories created without a cover are publishable only after upload.
- `portfolio_items` — `id, salon_id, category_id, staff_id (nullable, ON DELETE SET NULL), title, description, photo_after_url (NOT NULL), photo_before_url (nullable), display_order, created_at, updated_at`.
- Indexes: `(salon_id, display_order)` on categories, `(salon_id, category_id, display_order)` on items, partial `(salon_id, staff_id) WHERE staff_id IS NOT NULL` on items.

**Admin API (`routes/portfolio.js`, mounted at `/api/portfolio`, `requireRole('owner','admin')`):**
- `GET/POST/PUT/DELETE /categories[/:id]` — list with `items_count`, create (empty cover sentinel), update title/`isPublished` (refuses publish without cover), cascade-delete with file cleanup.
- `POST /categories/:id/cover` — multipart cover upload, replaces old file on success.
- `PUT /categories/reorder` — batch `display_order` (declared **before** `:id` to avoid path-matcher collision).
- `GET /categories/:id/items`, `POST /items` (multipart `after` required + `before` optional), `PUT /items/:id` (text only), `POST /items/:id/photos` (replace either or both), `DELETE /items/:id/before` (clear before-photo), `DELETE /items/:id` (cascade files).
- `PUT /items/reorder` — same-category guard (Set over `category_id`); also declared **before** `/items/:id`.

**Mobile API (`routes/mobile-client.js`, `mobileAuth`):**
- `GET /api/mobile/client/portfolio/categories` — published categories with items_count > 0, scoped to client's salon. URLs absolutized.
- `GET /api/mobile/client/portfolio/categories/:id` — items in a published category, embeds `specialist:{id,name,photoUrl}|null`. Photo precedence: `custom_photo_url` (trimmed) > `avatar_url` > null.
- `GET /api/mobile/client/portfolio/by-staff/:staffId` — items attributed to a staff member, only from published categories, ordered `created_at DESC`.

**Multer config:** `memoryStorage()` (so the row id can be embedded in the filename), 5 MB cap, image-only filter. Files written to `frontend/uploads/portfolio_{cat,item}_<id>[_(after|before)]_<ts>.<ext>`. `safeUnlink` swallows ENOENT and only acts on `/uploads/...` paths.

**Frontend:** `frontend/js/pages/portfolio.js` — two-level admin SPA (categories grid → items grid in a category) with HTML5 drag-drop reorder on both levels and create/edit modals. Stub `staff-profile-modal` shape reused via shared classes (`stg-section`, `btn-pri`, `fg`/`fl`).

- Минимальный срок до визита (`services/agent/lead-time.js`, чистый модуль, тесты `agent-lead-time.test.js`): день в день — старт не раньше now+2ч; заявка в 22:00+ (мск) на завтра — старт не раньше 12:00; ночная заявка (00:00–06:59) на сегодня — тоже не раньше 12:00. Применяется в выдаче слотов (`get_available_slots`/`get_parallel_slots`/`get_sequential_slots`; в якорном режиме фильтруются только добавляемые звенья) И write-guard'ом в `create_booking`/`reschedule_booking` (ответ `too_soon` с корректирующим hint — иначе клиент обошёл бы фильтр, назвав раннее время сам). `book_chain` наследует guard через хендлер create-booking. Промпт-правило «МИНИМАЛЬНЫЙ СРОК ДО ВИЗИТА» в Сценарии 2.
- Слот всегда считается под КОНКРЕТНУЮ услугу: `service_yc_id` в `get_available_slots` **обязателен** (как в parallel/sequential). Без него длительность неизвестна и старты считались сеткой 30 мин — инцидент 2026-07-31: предложено 11:30 перед чужой записью в 12:00, а записывалась 60-минутная услуга → YClients «Выбранное время недоступно» уже ПОСЛЕ согласования с пациентом. Провал записи именно по времени (`TIME_UNAVAILABLE_RE` в `tools/create-booking.js`) детерминированно перезапрашивает слоты и кладёт в ответ `slot_unavailable:true` + `available_slots` (свежие реальные старты этой услуги) — модель предлагает альтернативу только оттуда, а не из устаревшей выдачи. Промпт больше НЕ диктует причину отказа: фраза «это время только что заняли» была прописана в правиле и уходила пациенту как выдумка (причина отказа системе неизвестна).
- Альтернативный специалист при пустых слотах: если у запрошенного мастера на дату слотов нет, `get_available_slots` САМ проверяет других исполнителей этой услуги (из `staffList` каталога, до 3, минус скрытые парами `service-filter`) и возвращает `alternative_staff:[{staff_yc_id,name,slots}]` + `hint`; если проверены ВСЕ и пусто у всех — `no_alternative_staff:true`. Промпт-правило «АЛЬТЕРНАТИВНЫЙ СПЕЦИАЛИСТ»: не отвечать «времени нет», а в том же сообщении предложить имя+время альтернативы; «нет ни у кого» — только при `no_alternative_staff:true`. - Плотная запись — какое из свободных времён Мила называет первым (`services/agent/slot-density.js`, чистый модуль, тесты `agent-slot-density.test.js` + `agent-slots-offer.test.js`; спеки `docs/superpowers/specs/2026-08-06-agent-slot-density-design.md` и `…-08-07-…-v2-…`): рядом с ПОЛНЫМ хронологическим `slots` едет короткий `offer_slots` (в одномастерной выдаче, у каждого элемента `staff_options`/`alternative_staff` и на пути повторного предложения после отказа YClients). Полный `slots` остаётся источником `allowedTimes` reply-guard'а и нужен, когда пациент просит другое время. Занятость мастера считается из УЖЕ загруженной сетки `/timetable/seances` (`seancesToBusy`) — ни одного лишнего запроса в YClients, и перерыв/блокировка кресла тоже годятся в анкор; ГОТЧА: сетка ограничена сменой, поэтому её края анкорами НЕ становятся (на это есть тест — иначе слот в начале смены снова побеждал бы). Критерий (утверждён салоном): минимум мёртвого времени до/после ближайшей занятости, при равенстве — слот, примыкающий ВТОРОЙ стороной, потом раньше по времени. **Кап — одно время на КАЖДЫЙ КРАЙ занятости** (`anchor` = `b<конец блока>`/`a<начало блока>`): полезных времён у блока ровно два — вплотную ПЕРЕД началом и сразу ПОСЛЕ конца. Иначе топ-2 по стоимости давал соседние окошки одного куска: инцидент 2026-08-07 — на дне Пери (занято 12:00–12:30 и 14:00–21:00) Мила предложила «13:00 и 13:30», а 13:00 оставляет между записями дыру в шаг сетки; теперь это «12:30 и 13:30». Занятости нет вовсе → прежние самые ранние, и это путь ДЕГРАДАЦИИ (сетка не ответила): `busyKnown` требует, чтобы сетка была получена И НЕПУСТА — пустая означает «мастер не работает / молчание API», и выдать её за свободный день нельзя. РЕАЛЬНО свободный день (ни одной записи) — отдельная ветка `chooseOffer`: времени НЕ называем вовсе (`free_day:true`, `offer_slots` пуст), потому что в пустом дне любое время рвёт его на две дыры; промпт-правило «ДЕНЬ СВОБОДЕН ЦЕЛИКОМ» спрашивает половину дня, ответ пациента возвращается параметром `day_part` (`morning` <14:00 / `afternoon` ≥14:00 / `evening` ≥17:00 — границы утверждены, вечер и вторая половина намеренно пересекаются; незнакомое значение фильтром НЕ считается). При заданном `day_part` `free_day` не выставляется НИКОГДА (иначе вопрос по кругу), `day_part` сужает ТОЛЬКО `offer_slots`, в пустом дне отдаются края половины (`pickEdgeSlots`), в названной половине пусто → `day_part_empty:true` + время из остального дня. В перечислении специалистов у мастера с `free_day` времени не называем («свободно в течение дня»), оговорка ДОПИСЫВАЕТСЯ к базовому хинту (смешанный день). Память: `shownTimes` рендерит `offer_slots` (а не начало `slots` — иначе в журнал попадёт время, которого пациент не слышал), при `free_day` — факт «весь день свободен, время не называла», `day_part` идёт в строку журнала. Промпт-правила подкреплены ТЕЛЕМЕТРИЕЙ в reply-guard (`offer_bypass` — время из `slots` мимо `offer_slots`; `free_day_time` — время там, где положен вопрос о половине дня): ТОЛЬКО лог, без переписывания — время, названное САМИМ пациентом, модель обязана подтверждать, и глушить такую реплику значило бы повторить дефект анти-ложь-guard'а 04.08. `get_parallel_slots`/`get_sequential_slots`/`get_available_dates` плотность не считают.

Промпт-правило «ВЫБОР СПЕЦИАЛИСТА ДЕЛАЕТ ПАЦИЕНТ» требует перечислить всех одним сообщением (имя+должность+1–2 времени) и спросить «к кому удобнее», цену в этот момент не называть и не утверждать, что это все специалисты клиники; «Любой специалист — сама выбери любого» теперь срабатывает, ТОЛЬКО когда пациент САМ так сказал. ЗАЧЕМ: промпт разрешал модели взять исполнителя самой, и пациент молча получал одного мастера — при том что цена зависит от мастера (у главврача выше). ПУСТАЯ выдача разведена на ЧЕТЫРЕ разных ответа, и путать их нельзя: `filtered:true` (услуга или все пары скрыты админкой — «предлагать нельзя вообще»), `error: ERR_STAFF_UNREACHABLE` (не достучались НИ ДО ОДНОГО), `HINT_STAFF_PARTIAL` (проверены не все), и только при `reachable === total` — `no_staff_available:true` («у всех занято»). Тот же водораздел обязателен и на НЕПУСТОЙ выдаче: хинт «эту услугу ведёт один специалист» (`HINT_STAFF_SINGLE`) — утверждение обо ВСЕХ исполнителях, поэтому он разрешён только при `reachable === checked === total`, иначе `HINT_STAFF_ONE_OF_PARTIAL` («время нашлось у одного из ПРОВЕРЕННЫХ, единственным его не объявляй»). Вердикт диспетчер ставит в `finally`, а не после цепочки ветвлений (упавшая на середине серии отправка уходит в общий catch, а вердикт нужен и там), при частичной доставке — `false`; реплики модели уходят через ЕДИНУЮ точку `deliverReplies` именно затем, чтобы новая ветка отправки не забыла выставить флаг — забытый флаг = молчаливый `false` = Мила повторяет уже сказанное, включая приветствие. `delivered IS NULL` в таблице означает два РАЗНЫХ случая (прогон упал до вердикта / вердикт не дошёл); выжимка трактует оба как «не показано», но при разборе журнала это стоит помнить. Сделанные записи техническим гейтом не защищены (write-события живут в памяти все 48 ч при любом `delivered`), поэтому за них отвечает правило блока: администратор мог перенести или отменить запись в CRM, и перед подтверждением пациенту даты/времени/самого факта записи модель обязана свериться с `list_client_bookings`. PII не рендерится ни из аргументов вызова, ни из полей результата: выделенные экстракторы безопасны тем, что явно перечисляют показываемые поля, а фолбэк для НЕИЗВЕСТНОГО инструмента (`fmtResultScalars`) прогоняет через тот же фильтр имён (`client_phone/client_name/comment` + паттерн `phone|client_name|full_name|e-?mail`) и аргументы, и скаляры результата — иначе он был бы «безопасен» лишь случайно. Хронология одного хода: все события попытки уходят одним INSERT с `DEFAULT NOW()`, `created_at` у них совпадает — порядок восстанавливает тай-брейк по исходному индексу строки; без него разделение на write/read ВСЕГДА ставило запись впереди чтения и журнал врал модели «сначала записала, потом посмотрела историю». `dropped` означает РОВНО «срезано капом» (оркестратор логирует это как срез) — события, о которых экстрактору нечего сказать, в счётчик не идут. Всё в `tool-events.js` строго best-effort, КРОМЕ `loadRecent`: её ошибка намеренно не глотается — ловит оркестратор своим fail-open (ход идёт без блока памяти). Аварийный рычаг — `AGENT_TOOL_MEMORY=false` (по умолчанию память ВКЛЮЧЕНА): флаг гасит РОВНО чтение выжимки в промпт, запись журнала идёт при любом его значении — форензика нужна независимо от того, показываем ли память модели (переименовать таблицу нельзя: `migrations.js` вернёт её на рестарте). Форензика — сырой jsonb в таблице, хранение 30 дней, чистка кроном `40 4 * * *` (там же, где журнал авторства; сбой чистки логируется WARN — молчащий крон означал бы бессрочное хранение сырых input/result). `sequential-offers`/`pending-replies` журнал не заменяет, они живут рядом. Живая проверка — `scripts/agent-tool-memory-e2e.js` (платный LLM, реального сообщения никому не отправляет: `send` застаблен): проверяет не только что времена всплыли в ответе второго хода, но и что блок «ЖУРНАЛ» реально попал в его системный промпт — иначе тест был бы зелёным по совпадению, часть времён модель может взять из собственной прошлой реплики в транскрипте.

Готча: правка старой записи в YClients перевыстреливает вебхук годы спустя, enrollment создаётся с `scheduled_at` в прошлом, а воркер арендует по `scheduled_at <= NOW()` без нижней границы → такое касание уходит немедленно. Защиты от протухших касаний нет.
- Таблицы (`migrations.js`): `care_programs` (conditions jsonb) → `care_touches` (delay_days, send_time, intent_text, text_mode) → `care_enrollments` (статусы `active|completed|declined|escalated|superseded|stopped`) → `care_touch_sends` — очередь+журнал в одной таблице (статусы `scheduled|sent|skipped|cancelled|failed`). DELETE программы каскадом уносит enrollments и весь журнал.
- Зачисление (`services/care/enroll.js`, хук в `routes/webhook.js` на resource=record): визит состоялся = `attendance=1` ИЛИ `paid_full=1` — НЕ кэшбэчный критерий «оплачено деньгами»: визит с оплатой бонусами тоже заслуживает заботы. `classifyRecordEvent` ПЕРВЫМ проверяет un-enroll (`status='delete'` / `deleted` / `attendance=-1` — предоплаченная неявка несёт `paid_full=1` одновременно с `attendance=-1`) → гасит активные цепочки записи. Повторный подходящий визит supersede'ит прежний активный enrollment той же программы по ДАТЕ ВИЗИТА, а не по порядку вебхуков (правка старой записи может перевыстрелить вебхук годы спустя — без сравнения `visit_at` она глушила бы живую цепочку). Дедуп — UNIQUE (program_id, yclients_record_id); self-heal: ретрай вебхука дозаполняет касания enrollment'а, вставленного до падения процесса. Телефон нормализуется `normalizePhoneKey`, ЧС клиента блокирует зачисление.
- Воркер (`services/care/worker.js`, тик 15с, guard от наслоения тиков — медленный прогон не пускает следующий): LEASE_SQL арендует до 5 due-строк `FOR UPDATE SKIP LOCKED` + attempts при аренде; колонки касания берутся СКАЛЯРНЫМИ ПОДЗАПРОСАМИ в RETURNING — JOIN на цель UPDATE в PG запрещён («invalid reference to FROM-clause entry»), юнит-моки db.any валидность SQL не проверяют → после правок LEASE_SQL обязателен живой EXPLAIN на дев-БД (SQL экспортируется именно для этого). Порядок детерминированных проверок до LLM: enrollment активен → программа включена → env-гейт агента → `isAllowed` (ОБЩИЙ гейт Милы: ЧС/режим/расписание) → диалог не на операторе → анти-спам «1 касание в день» (сдвиг scheduled_at на +24ч от max(scheduled_at, now()), не skip) → повторный визит по условиям программы (fail-open при сбое YClients) → care-проход. Таймаут LLM 60с (< backoff аренды 120с); maxTokens — дефолт провайдера `AGENT_MAX_TOKENS` (инцидент 2026-08-03: ручной бюджет 1200 съедался reasoning-токенами gemini, JSON обрезался finish=length → `llm_no_json` и ВСЕ касания молча скипались).
- ОКНО РАСПИСАНИЯ НА КАСАНИЯ НЕ РАСПРОСТРАНЯЕТСЯ (2026-08-06): воркер зовёт гейт как `isAllowed(salonId, phone, { ignoreSchedule: true })` — опция гасит РОВНО сужение окном (`scheduleEnabled && !opts.ignoreSchedule` в `agent-settings.js`), чёрный список, режим whitelist и тумблер агента действуют в полном объёме. ЗАЧЕМ: окно проектировалось для ВХОДЯЩИХ («когда Мила отвечает клиентам»), а время касания задаёт САМ салон в программе (`send_time`) — это уже решение о том, когда писать пациенту. Прежний defer на сутки (фикс 2026-08-03) чинил терминальный skip, но при ПОСТОЯННОМ окне (ночное 22:00–09:30 на проде + касание в 11:00) сдвиг на +24ч сохраняет время суток → касание не уходило НИКОГДА и вечно висело scheduled в дашборде. Ветка `outside-schedule` в воркере оставлена СТРАХОВКОЙ (defer + WARN): при откате опции или подменённом гейте терминальный skip сжёг бы цепочку молча — at-most-once второго шанса не даёт. Тесты — `agent-settings-allowed.test.js` (окно нулевой длины `'10:00'-'10:00'`, чтобы «вне окна» было верно в любой момент прогона) + тест в `care-worker.test.js`, что боевой `defaultDeps.isAllowed` передаёт флаг (правка «унифицируем вызовы гейта» вернула бы дефект молча).
- ФИКС 2026-08-03 (интеграционное ревью): env kill-switch (`CHATPUSH_AGENT_ENABLED`) выключен — касание ОТКЛАДЫВАЕТСЯ на сутки тем же механизмом, что анти-спам (`deferTouch`: сдвиг scheduled_at, attempts=0), а НЕ терминальный skip: иначе цепочка молча сгорала бы навсегда (at-most-once, второго шанса нет), пока админ держит Милу выключенной на проде. Прочие причины гейта (whitelist/blacklist/disabled per-salon) — это «клиенту/салону нельзя», а не «сейчас нельзя», остаются терминальным skip как раньше. РЕШЕНИЕ: enrollment, остановленный эскалацией (`status='escalated'`), после «Вернуть боту» НЕ возобновляется — новая цепочка начнётся только со следующего подходящего визита.
- Доставка AT-MOST-ONCE (пропущенное касание дешевле дубля живому пациенту): mark-before-send — sent-маркер пишется ДО отправки условным `UPDATE … WHERE status='scheduled'`; условие — ФИНАЛЬНЫЙ гейт: арендованный enrollment_status в LIMIT-5 батче устаревает (stop_program по строке A уже отменил строку B того же enrollment). Флаги `delivered`/`terminalWritten` в catch: доставлено → статус НЕ откатывается никогда; терминальный skipped/cancelled записан → не перезаписывается; отправки не было → откат в scheduled с чисткой sent_at, после 3 попыток — failed. Любой терминальный исход последнего касания завершает enrollment (`maybeCompleteChain`) — иначе зомби-active в дашборде.
- care-проход: `buildCarePrompt` (`care-prompt.js`) — транскрипт и имя клиента КЛИЕНТ-КОНТРОЛИРУЕМЫ, всё проходит `sanitizeLine`/`sanitizeName` покомпонентно (перевод строки в сообщении пациента не может подделать реплику «Мила: …» отдельной строкой). `parseCareDecision` (`decision.js`) fail-safe: не-JSON / нестроковый `text` (массив коэрсился бы в правдоподобный текст) / пусто / >1500 символов / bidi-контролы → skip, не отправка. Действие `escalate` — осложнение в переписке: касание не шлём, диалог на оператора (зеркало `tools/escalate-to-operator.js`: upsert agent_dialogs + `emitAgentStatus`), эскалация ДО остановки цепочки — если упала, ретрай её повторит, а не потеряет. Ответы пациента на касание обрабатывает ОСНОВНОЙ агент (обычный вебхук-путь со всеми мед-границами); `rememberPending` подмешивает касание в транскрипт до эха Chatpush, для whatsapp — persist-on-send в chatpush_messages.
- Режим текста касания (`care_touches.text_mode`, дефолт `free`): `free` — `intent_text` это ЗАГОТОВКА СМЫСЛА, текст пишет Мила; `strict` — `intent_text` уходит ГОТОВЫМ ТЕКСТОМ (менять смысл, сокращать, дописывать эмодзи и вопросы запрещено, разрешена только подстановка обращения по имени; лимит санитизации поднят 400→1200 символов). Решение «слать ли вообще» в strict остаётся за LLM — мед-правила, эскалация при осложнении, skip при жалобе и stop_program работают как в свободном режиме (готовый текст не должен ложиться поверх «у меня отёк»). Неизвестный режим трактуется как `free`. UI — чипы «✍️ Мила пишет сама / 📋 Готовый текст» в редакторе касания.
- API `/api/care` (`routes/care.js`, owner/admin; JWT-поля `req.user.salonId`/`userId` — НЕ `salon_id`!): programs CRUD+toggle, дашборд `GET /enrollments` (next_touch_at/last_sent_at), журнал `GET /enrollments/:id/sends` (LEFT JOIN care_touches — touch_id NULL после удаления касания из программы), `POST /enrollments/:id/stop`, `POST /preview` (сухой прогон). Фронт — `frontend/js/pages/care.js` (страница «Забота»). Живые проверки: `scripts/care-e2e.js` (реальный LLM + РЕАЛЬНАЯ отправка на номер; чистка уносит sent-журнал каскадом, поэтому повторный прогон в тот же день отправит ещё раз — анти-спам свой прошлый прогон не увидит), `scripts/care-ui-e2e.js` (UI) и `scripts/care-preview-e2e.js` (превью + режим текста, API и UI; ничего не отправляет).
- Превью выборки (`services/care/preview.js`, `POST /api/care/preview`, кнопка «👁 Выборка» в карточке программы и в редакторе): «кто попал бы, если бы программа работала последние N дней» (1–90, дефолт 30). Нужно потому, что зачисление ЧИСТО СОБЫТИЙНОЕ — бэкфилла нет, и у только что созданной программы дашборд пуст: без превью не отличить «условия кривые» от «подходящих визитов не было». Тянет `/records/{cid}` за период и гоняет ТОТ ЖЕ `evaluateRule` и тот же критерий `isVisitCompleted`, что и enroll.js — расхождение превью с боевым отбором есть баг, правки условий идут в оба места. Ничего не пишет в БД и не отправляет. `matchVisits` чистая (тесты `care-preview.test.js`), сеть и ЧС — в маршруте; строки помечаются `skipReason` (`no_phone`/`blacklist`/`superseded` — из нескольких визитов клиента дожила бы цепочка только от самого позднего). Тело принимает либо `programId` (условия из БД), либо `conditions`+`touches` (черновик в редакторе, программа ещё не сохранена). Пустая карта категорий → `catMapFailed:true` в ответе (иначе «никто не подошёл» читается как «условия не те»).

### Напоминания о повторном визите
Отдельный модуль рядом с «Заботой», не её часть: правило = условия отбора визита (тот же формат `{logic, items}` и тот же `evaluateRule`, что у care-программ) + задержка в днях + текст (свободный или готовый) + необязательные ступени бонуса по балансу карты. На каждый подходящий состоявшийся визит заводится строка `reminder_queue` — очередь и журнал в одной таблице, статусы `scheduled|sent|skipped|cancelled|failed`.

- Таблицы (`migrations.js`): `reminder_rules` (conditions jsonb, delay_days, send_time, text_mode, text, attribution_days, bonus_enabled, bonus_tiers jsonb, backfill_max_per_day) → `reminder_queue` (якорь визита: anchor_record_id/anchor_visit_at/anchor_staff_name/anchor_services, бонусная тройка balance_before/bonus_tier/bonus_accrued/bonus_txn_ok, атрибуция conversion_record_id/converted_at/visited_at, source `webhook|backfill`) → `reminder_suppressions` (анти-повтор, UNIQUE(rule_id, phone)). `reminder_queue.rule_id` — **`ON DELETE SET NULL`**, в отличие от каскада «Заботы»: история «кому что по какому правилу» обязана пережить удаление правила, отсюда денормализованный `rule_title`. Строки удалённого правила (`rule_id IS NULL`, ещё `status='scheduled'`) join воркера не вернёт и они висели бы вечно — их гасит `ORPHAN_SQL` (`UPDATE … SET status='cancelled'` на каждом тике, до аренды).
- Планирование ЧИСТО СОБЫТИЙНОЕ (хук в `routes/webhook.js` на `resource=record`, `services/reminders/enroll.js`, свой try/catch — падение не должно ронять «Заботу» и кэшбэк) — бэкфилла нет, у только что созданного правила очередь пуста. Критерий «визит состоялся» и классификация события переиспользуют `care/enroll.js` (`isVisitCompleted`, `classifyRecordEvent`): un-enroll (отмена/неявка/удаление) проверяется ПЕРВЫМ, потому что предоплаченная неявка несёт `paid_full=1` одновременно с `attendance=-1`. «Аналогичная услуга» (клиент уже записан/уже приходил повторно) — это ПОПАДАНИЕ ПОД ТЕ ЖЕ УСЛОВИЯ ПРАВИЛА, а не совпадение конкретной услуги: правило на категорию «Лазерная эпиляция» считает аналогичной запись на любую услугу категории. Снятие флага анти-повтора визитом стоит ДО планирования новой строки (иначе новая строка упёрлась бы в собственный `muted` от прошлого цикла) и бьёт только по `reminder_suppressions.source='auto'` — ручной отказ клиента (`source='manual'`) визитом не снимается, только человеком. Защита от вебхука не по порядку — двусторонняя, как в «Заботе»: (1) если по правилу+телефону уже есть ЖИВАЯ строка от БОЛЕЕ ПОЗДНЕГО визита, планирование по более старому визиту пропускается целиком (проверяется первой, раньше un-mute и cancel-stale); (2) прежние запланированные строки от БОЛЕЕ РАННИХ визитов отменяются при планировании новой. Дедуп — `UNIQUE(rule_id, anchor_record_id)`.
- Общий предикат «визит ДЕЙСТВИТЕЛЬНО состоялся» — `visitReallyHappened` в `services/reminders/eligibility.js` (голого `isVisitCompleted` мало по тем же двум причинам, что у un-enroll выше: предоплаченная неявка и удалённая-но-с-живым-attendance запись). Экспортирован ОДИН на оба потребителя — событийный планировщик (`enroll.js`) и разовый догон (`backfill.js`) — чтобы они не могли молча разъехаться в критерии.
- Бонусная часть (`services/reminders/bonus.js` + `tiers.js`) — ГЛАВНЫЙ ИНВАРИАНТ: наружу не бросает никогда, любой сбой (нет карты нужного типа, YClients не ответил, начисление упало) деградирует в ступень `no_bonus`, и сообщение уходит без единого слова про бонусы — клиент не должен прочитать про бонусы, которых у него нет. Карта — СТРОГО типа, настроенного в салоне (`salon.yclients_card_type_id`, как `services/loyalty.js` и `routes/clients.js`), а не «с максимальным балансом»: у клиента могут быть карты других программ (например samosale), и начисление на чужую карту необратимо. Тип не настроен → `no_bonus` без единого вызова YClients. Следствие: `SELECT` салона в `defaultDeps.applyBonus` воркера обязан тянуть `yclients_card_type_id` — забытое поле молча выключает бонусы навсегда. Ступени (`pickTier`) — порог `up_to` ИСКЛЮЧАЮЩИЙ (ступень ловит баланс строго меньше своего порога), последняя ступень с `up_to:null` — «весь остаток»; начисление НЕОБРАТИМО, поэтому вызывающий обязан звать `applyBonus` не более одного раза на строку. Защита в воркере — НАМЕРЕНИЕ, записанное ДО вызова YClients: `UPDATE … SET bonus_tier='pending' WHERE id=$1 AND bonus_tier IS NULL`, и `applyBonus` зовётся, только если пометка легла. Одной проверки «`bonus_accrued IS NULL`» после начисления НЕ хватает: `ycAccrueCard` — ручная транзакция без ключа идемпотентности, и падение процесса (или обрыв БД) между успешным начислением и записью результата вернуло бы строку в `scheduled` с пустым `bonus_accrued`, а следующая аренда начислила бы деньги ВТОРОЙ раз. Строка, найденная в состоянии `pending`, трактуется как `no_bonus` (про сумму, которой может не быть, клиенту не говорим) + WARN в лог: прошлая попытка оборвалась ровно в этом окне, карту клиента надо проверить руками.
- Воркер (`services/reminders/worker.js`, тик 60с, тот же `_tickInFlight`-guard от наслоения, что в «Заботе»). Порядок внутри строки: детерминированные гейты → **бонусы** (считаются рано, потому что текст обязан содержать ФАКТИЧЕСКИ начисленную сумму, а не обещание; от двойного начисления защищает пометка `bonus_tier='pending'` ДО вызова YClients) → рендер текста (шаблон в `strict`, LLM-проход в `free`) → reply-guard → **захват строки условным `UPDATE … WHERE status='scheduled'`** (`SET status='sent'`) вплотную перед `sendMessage` → отправка → персист. Захват стоит ПОСЛЕДНИМ, а не сразу после аренды: ранний захват (как в первой версии плана) означал, что падение процесса (OOM, `pm2 restart`) между захватом и реальной отправкой оставляет строку `sent` без единого отправленного сообщения — `LEASE_SQL` арендует только `scheduled`, и такая строка терялась бы навсегда, выглядя в дашборде отправленной. Запас по времени: `LLM_TIMEOUT_MS` 60с строго меньше `RETRY_BACKOFF_S` 120с (тот же запас, что в care-воркере) — таймаут-ретрай не пересечётся с ещё живым прошлым вызовом в окне аренды; защита ПРОЦЕССНАЯ (один PM2-инстанс), не распределённая — при горизонтальном масштабировании нужен явный distributed lock или больший backoff. `LEASE_SQL` — тот же приём, что в «Заботе»: колонки правила берутся скалярными подзапросами в RETURNING (JOIN на цель UPDATE в PG запрещён), юнит-моки SQL не проверяют → после правок обязателен живой EXPLAIN на дев-БД.
- В режиме `free` воркер ПЕРЕИСПОЛЬЗУЕТ care-промпт (`buildCarePrompt`) — отдельного промпта для напоминаний нет, `intent_text` для него собирается уже с подставленными цифрами (`renderReminderText`). Care-промпт инструктирует модель отвечать не только `send`, а ещё `escalate` и `stop_program` (`care/decision.js`), и оба варианта обязаны быть реально обработаны, а не просто схлопнуты в «текст пуст»: `escalate` (осложнение после процедуры) — касание НЕ отправляется, диалог переводится на оператора (`escalateDialog`, тот же приём, что `tools/escalate-to-operator.js`: upsert `agent_dialogs` + `emitAgentStatus`), строка `skipped`; `stop_program` (просьба «не пишите мне») — ставится флаг анти-повтора с `source='manual'` (визитом НЕ снимается — см. выше) и строка `cancelled`. Причина от модели (`decision.reason`) пишется в `decision_reason`, а не тонет в общей формулировке. Маркер `[сообщение администратора клиники]` (`OPERATOR_MARK` из `agent/history.js`) срезается из транскрипта ПЕРЕД передачей в care-промпт (`stripOperatorMark`, посимвольно с начала каждой строки серии) — care-промпт про эту пометку не знает и отдал бы её клиенту дословно.
- Гейты воркера ДО бонусов и текста, по порядку: правило включено → env-гейт агента (выключен → `deferRow`, не терминально) → `isAllowed(salonId, phone, { ignoreSchedule: true })` — ОБЩИЙ гейт Милы (ЧС/режим/тумблер), но ночное окно расписания на плановые напоминания НЕ распространяется (симметрично «Заботе»: время задаёт сам салон в `send_time`); неожиданный `outside-schedule` вопреки `ignoreSchedule` — страховка, `deferRow` + WARN, а не терминальный skip → диалог не на операторе (эскалация Милы или ручная пауза — `deferRow` с `bumpDefers=true`, предел терпения `MAX_OPERATOR_DEFERS=3`, дальше терминальный skip: ждать бесконечно нельзя, напоминание протухнет по смыслу) → анти-повтор (`reminder_suppressions.muted`) → анти-спам «1 плановое сообщение в день» → живые проверки по YClients-записям (`hasFutureMatchingBooking` на будущих и на состоявшихся-после-визита записях; fail-open при сбое API — тот же размен, что в «Заботе»).
- Общий анти-спам `services/messaging/daily-limit.js` — «1 плановое сообщение клиенту в день», СЧИТАЕТ ОБЕ очереди (`care_touch_sends` UNION `reminder_queue`) одним запросом: две независимые очереди со своими воркерами легко сложились бы в два сообщения одному человеку в одно утро («как самочувствие» от «Заботы» и «пора повторить» от напоминаний). Это ЧТЕНИЕ ПЕРЕД ДЕЙСТВИЕМ без блокировки, не гарантия: два тика на один телефон, попавшие в одно окно, оба увидят «сегодня не слали» и оба отправят — размен осознанный (пропущенное сообщение хуже редкого дубля), окно сужено mark-before-send в обеих очередях, но не закрыто.
- Атрибуция конверсии (`services/reminders/attribution.js`, `handleAttribution` в `enroll.js`, зовётся на ЛЮБОМ событии записи, не только на состоявшемся визите): клиент создал новую запись под условия ТОГО ЖЕ правила → засчитывается отправленному напоминанию (`conversion_record_id`), а состоявшийся визит по уже засчитанной записи проставляет `visited_at`. Из нескольких подходящих отправленных строк побеждает САМАЯ СВЕЖАЯ (`pickAttributionRow` сортирует по `sent_at DESC`) — именно последнее напоминание вероятнее всего и привело клиента. Окно атрибуции берётся из `attribution_days` самого правила (граница включающая), строки с `rule_id IS NULL` (правило удалено) в атрибуции не участвуют — сверять новую запись не с чем.
- Догон по базе (`services/reminders/backfill.js`, чистые функции без БД/сети + `routes/reminders.js` для сети) — «кому ушло бы напоминание, если бы правило работало последние N дней» (1–90). Нужен по той же причине, что превью «Заботы»: планирование чисто событийное, у только что созданного правила дашборд пуст, без догона не отличить «условия кривые» от «подходящих визитов ещё не было» — и в отличие от «Заботы» догон не просто показывает выборку, а РЕАЛЬНО СТАВИТ строки в очередь (раздельные `POST .../backfill/preview` и `POST .../backfill`). Отбор гоняет ТОТ ЖЕ `evaluateRule` и ТОТ ЖЕ `visitReallyHappened`, что и боевой планировщик. Раскладка по дням (`spreadOverDays`, кап `backfill_max_per_day`) СОРТИРУЕТ СТРОКИ ПО ДАТЕ ВИЗИТА ПО ВОЗРАСТАНИЮ — решение владельца салона: первым напоминание получает тот, кто НЕ БЫЛ ДОЛЬШЕ ВСЕХ, а не тот, кто был недавно, он самый просроченный по смыслу правила. Это ОТДЕЛЬНАЯ сортировка от «свежие сверху» в `matchBackfillVisits` — та нужна только для дедупликации (`skipReason:'superseded'`: из нескольких визитов клиента дожила бы строка только от самого позднего), и с сортировкой отправки не совпадает. Ручка `POST /rules/:id/backfill` (`routes/reminders.js`) при потолке 5000 записей (25 страниц YClients) делает ПАКЕТНУЮ вставку (`insertQueueBatch`, пачки по 500 — с запасом от лимита PostgreSQL в 65535 параметров запроса) и ОДИН общий запрос на резолв клиентов (`resolveClients`) вместо двух запросов на строку: построчные SELECT/INSERT на 5000 записей упирались в 60-секундный `proxy_read_timeout` nginx, и админ видел 504 при уже успешно вставленных строках. Защита от повторного запуска — `backfillInFlight` (Set по id правила, `409` при двойном клике/двух администраторах) — ПРОЦЕССНАЯ, не распределённая, тот же класс, что `_tickInFlight` воркера. Падение в середине пачки не прячет, сколько строк УЖЕ легло: число вставленных идёт прямо в текст ошибки (общий `api()` фронта теряет остальные поля тела ответа, читает только `j.error`).
- Валидация правила (`parseRuleBody` в `routes/reminders.js`, вынесена на верхний уровень модуля ради юнит-теста `reminders-routes.test.js` без HTTP/БД) — недоверчивая: суммы ступеней бонусов уходят реальными деньгами на карту клиента, неизвестное действие ступени или сумма ≤0 при `action='accrue'` отвергаются, а не молча игнорируются; кап числа ступеней — 20 (тот же кап, что на касания «Заботы» в `routes/care.js`).
- Тестовая отправка правила на свой номер (`POST /rules/:id/test`, кнопка «🧪 Тест» в карточке правила, чистый `services/reminders/test-send.js` + `worker.processTestRow`): сообщение уходит РЕАЛЬНО и ТЕМ ЖЕ `processOne`, что в бою — иначе тест ничего не доказывал бы о боевом пути. ЗАЧЕМ отдельно от догона: догон показывает только ВЫБОРКУ визитов, а текст (в режиме `free` его пишет Мила живым LLM-проходом) и ступень бонусов считаются лишь в момент отправки, и до включения правила «в массы» проверить их нечем — очередь у нового правила пуста, планирование чисто событийное. Тестовая строка ставится в БУДУЩЕЕ (`TEST_LEAD_MS`, час) и `source='test'`: боевой тик арендует только `scheduled_at <= NOW()`, поэтому перехватить её он не может, а забирает её адресная аренда `LEASE_ONE_SQL` (по id, БЕЗ условия due). Оба варианта аренды собираются ОДНИМ `buildLeaseSql` — набор колонок `RETURNING` это контракт со всем `processOne`, и разъехавшиеся копии означали бы, что тест гоняет строку с другим набором полей (закреплено тестом). Строку, оставшуюся `scheduled` (гейт отложил её), `processTestRow` в `finally` гасит в `cancelled`: иначе через час её арендовал бы БОЕВОЙ воркер и отправил бы то же сообщение по-настоящему, уже с боевыми deps. Отличий от боевого прогона ровно четыре (`buildTestDeps`), и все — про то, что тест не портит боевое состояние клиента: анти-повтор не ставится и прошлый не мешает (тест повторяем), дневной лимит не применяется, живые записи клиента («уже записан» / «уже пришёл») тест не отменяют, бонусы по умолчанию считаются СУХИМ прогоном (`applyBonusDry`: баланс карты читается по-настоящему и ступень выбирается по нему — иначе тест не показал бы, что именно начислилось бы и каким текстом ступени, — но транзакция подменена пустышкой, `txnOk=null`, причина строки «ТЕСТ: бонусы РЕАЛЬНО НЕ начислялись»). Боевое начисление — только явной галочкой (необратимо). Остаются в силе: гейт Милы (ЧС/режим/тумблер — «этому номеру нельзя», и тест не повод), пауза оператора, reply-guard; ВЫКЛЮЧЕННОЕ правило тестируется (`rule_enabled` перекрывается) — его для того и тестируют. ГОТЧА, стоившая живого прогона: телефоны в `clients` лежат в разных формах (`+79200255591`), а ключ канонизирован — точное сравнение промахивалось, и тест уходил без имени и БЕЗ `yclients_client_id`, то есть с молча выключенными бонусами; карточка ищется суффиксным LIKE (`resolveTestClient`, та же защита «только полный номер, 10+ цифр», что в `identity.resolveClient`), а id клиента YClients резолвится ОДИН раз и идёт и в якорь, и в бонусы. Якорь теста — последний СОСТОЯВШИЙСЯ визит из YClients (`pickAnchorVisit`, признаки те же, что у `visitReallyHappened`); визитов нет → дата из `delay_days` правила, `{услуга}`/`{мастер}` пустые, и ответ ручки это явно сообщает. ## Key constraints

- **Webhook handler must respond 200 immediately** before any async processing — YClients retries on timeout.
- **Advisory locks** are used in `processRecordEvent` to prevent race conditions on duplicate webhook deliveries — do not remove them.
- **Cashback accrual rule** — бонусы начисляются **только** если визит оплачен полностью деньгами: без применения бонусов и без скидок. Если клиент использовал бонусы или скидку — кэшбэк не начисляется (`finances_operation` type check в loyalty service).
- **`db.one` vs `db.oneOrNone`** — both exist, but they are byte-for-byte the same implementation (`db.js`: `return r.rows[0] || null`) — `one` does **not** throw on a missing row, it silently returns `null` just like `oneOrNone`. Code written expecting `one` to throw will instead keep running with `null` and blow up later as an unrelated `TypeError` (`Cannot read properties of null …`) far from the real cause. Treat both as `oneOrNone` and check the result explicitly wherever "not found" must be handled.
- **Timezone** — server runs TZ=Europe/Moscow. All date arithmetic must be Moscow-local. Use `AT TIME ZONE 'Europe/Moscow'` in SQL when comparing dates.
