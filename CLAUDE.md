# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

LoyalPro — loyalty program platform for beauty salons integrated with YClients CRM. Three components share one repo:

- **`backend/`** — Node.js/Express API server (port 3001). Serves both the staff web frontend and the mobile client app.
- **`frontend/`** — Vanilla JS single-page app for salon staff. Served as static files by the backend.
- **`mobile/`** — Expo/React Native app for end clients (loyalty card, bonus balance).

## Architecture

### Backend structure
- `server.js` — entry point: sets up Express, mounts routes, starts cron jobs
- `config.js` — all env vars and constants in one place
- `db.js` — two PostgreSQL pools: `pool`/`db` (main app DB) and `botPool`/`botDb` (Telegram bot DB on Beget)
- `migrations.js` — runs `ALTER TABLE … ADD COLUMN IF NOT EXISTS` style safe migrations on startup
- `routes/index.js` — mounts all routers; handles JWT auth inline for `/api/*` routes
- `routes/webhook.js` — YClients webhook at `/yclients/webhook.v2/:companyId` (no JWT, responds 200 immediately then processes async)
- `services/loyalty.js` — cashback calculation, sync from YClients, bonus accrual logic
- `services/yclients.js` — all YClients REST API calls; has in-memory cache for product/service trees
- `services/home-care.js` — "домашний уход" (home care) goods catalog sync
- `services/segments.js` — client segmentation refresh
- `services/staff.js` — staff data sync
- `services/portfolio.js` — pure helpers (filename templating, reorder validation, URL absolutize) shared by admin route + mobile API. No DB/HTTP — unit-tested in `portfolio.test.js`

### Auth & roles
JWT in `Authorization: Bearer <token>` header (or `?token=` for downloads). Roles: `owner > admin > specialist`. Specialists can only access `/api/home-care`, `/api/auth`, `/api/template-settings`. Public routes (no JWT): `/api/auth/login`, `/api/auth/register`, `/api/app-settings`.

Mobile clients use a separate auth path: `routes/mobile-auth.js` + `routes/mobile-client.js` under `/api/mobile/`.

### CORS
Managed in `server.js`. The whitelist is set via `ALLOWED_ORIGINS` env var (comma-separated) or falls back to hardcoded defaults. To add an origin, set `ALLOWED_ORIGINS` in the environment — do not edit the hardcoded list unless adding a permanent default.

### Cron jobs (all TZ: Europe/Moscow)
- `0 10 * * *` — birthday bonuses
- `0 */3 * * *` — YClients sync + goods categories sync
- `0 * * * *` — staff data sync

### Database
PostgreSQL (Beget cloud, SSL). Uses `pg` pool directly — no ORM. Helper `db` object wraps pool with `.query`, `.one`, `.many`, `.any`, `.oneOrNone`. All schema changes go through `migrations.js` using `IF NOT EXISTS` / `DO NOTHING` patterns — never destructive.

### Frontend (staff SPA)
`frontend/js/app.js` — entry, router, init  
`frontend/js/core/` — api.js, auth.js, nav.js, theme.js, utils.js  
`frontend/js/pages/` — one file per page (dashboard, clients, records, staff, segments, settings, home-care, users, portfolio)

API calls go through `core/api.js` which attaches JWT from localStorage automatically.

### Роутинг по hash (`core/nav.js`)
Открытая страница живёт в `location.hash` (`#clients`, `#chat/<ключ диалога>`) — до 10.08.2026 адрес не менялся вовсе, и F5 (а на телефоне это единственный способ «обновить») выбрасывал на стартовую страницу роли, у владельца на Дашборд. `navTo(p, opts)` пишет hash, `hashchange` возвращает переход обратно в приложение — отсюда бесплатно работают «Назад»/«Вперёд» браузера. Детали, которые легко сломать:
- **Свой же hash узнаём по `_navPage`**: он обновляется ВНУТРИ `navTo` ДО записи в hash, поэтому событие от собственной записи видит `page === _navPage` и страницу не перезагружает. Без этого каждый клик по меню грузил бы раздел дважды.
- **Хвост после `/`** отдаётся странице через `window._deepLinkArg`; сегодня он есть только у чата. `navTo` хвост СОХРАНЯЕТ (`careOpenChat` из «Заботы» ставит `#chat/<номер>` и сразу зовёт `navTo('chat')` — срезанный хвост потерял бы диалог), а клик по пункту меню — наоборот, стирает (`nav(el)` → `{reset:true}`, «в начало раздела»).
- **`_navAllowed(p)`** — раздел, недоступный роли, из адреса НЕ открывается: hash переживает выход из аккаунта, и оставшийся от администратора `#users` открыл бы специалисту на том же телефоне чужой раздел. Источник правды — уже отфильтрованное `applyRoleNav` меню `#mainNav`; `medical-cert` проверяется по своему родителю `cert-requests`. При отказе адрес возвращается на текущую страницу через `replaceState` (разошедшийся с экраном hash сломал бы следующее «Назад» и F5).
- **Стартовая страница** пишется `history.replaceState`, а не присваиванием hash: иначе первое «Назад» просто перезагружало бы её.
- `document.body.dataset.page` — ключ текущей страницы на `<body>`, им пользуется мобильная вёрстка чата.

### Чат на телефоне (≤700px)
Один экран — одна панель: список диалогов ИЛИ переписка, переключает класс `.chat-show-dialog` на `.chat-layout` (+ `body.chat-dialog-open`, он прячет шапку страницы). Возврат — кнопка `.chat-back` («‹ К списку чатов», на десктопе `display:none`) и «Назад» браузера: оба ведут в `chatCloseDialog()`, и оба состояния отражены в адресе. До 10.08.2026 тут было простое «в столбик» (список с `max-height:280px` и переписка под ним, обе со своим скроллом ВНУТРИ скролла `.content`) — на телефоне это не листалось, палец попадал во вложенный скролл, а выхода из переписки не было вовсе.
- Порог 700px продублирован в CSS (`features.css`) и в JS (`CHAT_MOBILE_MAX` в `chat.js`) — менять только ВМЕСТЕ, вёрстка и логика обязаны переключаться одновременно.
- Высота считается КАСКАДОМ, без JS: `body[data-page="chat"] .content` теряет внешний скролл и становится flex-колонкой, страница и `.chat-layout` тянутся `flex:1`. Поэтому и нужен `data-page` — иначе скролл пришлось бы гасить всем страницам. `min-height:560px` у `.chat-layout` на мобиле обязательно сбрасывается в `0`, иначе flex не даёт панели сжаться.
- `loadChat()` ПЕРЕОТКРЫВАЕТ диалог из адреса принудительно (`_chatActiveKey = null` перед `openChatDialog`): `hashchange` успевает сработать раньше загрузки списка, и композер тогда остаётся с заглушкой без каналов отправки.
- Мелочи, найденные живым прогоном, а не тестами: инлайновый `style="display:flex"` на шапке страницы перебивал правило, которое её прячет (стили переехали в `.chat-page-head`); фокус в поле ввода при открытии диалога на телефоне не ставится (выехала бы клавиатура поверх переписки); подсказка про Enter/Shift+Enter и длинная подпись «Отвечает оператор (бот молчит)» на узком экране обрезались — обе укорочены.
- Живая проверка — `scripts/chat-mobile-e2e.js` (headless-Chrome 390×844, ничего не отправляет): список листается, диалог открывается на весь экран, возврат кнопкой и «Назад», F5 внутри диалога, F5 на произвольной странице, переход «Забота» → чат, чужой раздел в адресе, и отдельной вкладкой — что десктоп не сломан. Скриншоты в `/tmp/chat-mobile-*.png`.

### Multi-salon
All DB tables have `salon_id` FK to `salons`. Every API route resolves the salon from `req.user.salon_id`. Never run queries without scoping to `salon_id`.

### Portfolio module (До/После)
"Before/after" gallery for the mobile client app, managed by salon admins under Settings → Mobile App → Портфолио работ.

**Tables (`migrations.js`):**
- `portfolio_categories` — `id, salon_id, title, cover_photo_url, display_order, is_published, created_at, updated_at`. `cover_photo_url DEFAULT ''` is a sentinel — categories created without a cover are publishable only after upload.
- `portfolio_items` — `id, salon_id, category_id, staff_id (nullable, ON DELETE SET NULL), title, description, photo_after_url (NOT NULL), photo_before_url (nullable), display_order, created_at, updated_at`.
- Indexes: `(salon_id, display_order)` on categories, `(salon_id, category_id, display_order)` on items, partial `(salon_id, staff_id) WHERE staff_id IS NOT NULL` on items.

**Admin API (`routes/portfolio.js`, mounted at `/api/portfolio`, `requireRole('owner','admin')`):**
- `GET/POST/PUT/DELETE /categories[/:id]` — list with `items_count`, create (empty cover sentinel), update title/`isPublished` (refuses publish without cover), cascade-delete with file cleanup.
- `POST /categories/:id/cover` — multipart cover upload, replaces old file on success.
- `PUT /categories/reorder` — batch `display_order` (declared **before** `:id` to avoid path-matcher collision).
- `GET /categories/:id/items`, `POST /items` (multipart `after` required + `before` optional), `PUT /items/:id` (text only), `POST /items/:id/photos` (replace either or both), `DELETE /items/:id/before` (clear before-photo), `DELETE /items/:id` (cascade files).
- `PUT /items/reorder` — same-category guard (Set over `category_id`); also declared **before** `/items/:id`.

**Mobile API (`routes/mobile-client.js`, `mobileAuth`):**
- `GET /api/mobile/client/portfolio/categories` — published categories with items_count > 0, scoped to client's salon. URLs absolutized.
- `GET /api/mobile/client/portfolio/categories/:id` — items in a published category, embeds `specialist:{id,name,photoUrl}|null`. Photo precedence: `custom_photo_url` (trimmed) > `avatar_url` > null.
- `GET /api/mobile/client/portfolio/by-staff/:staffId` — items attributed to a staff member, only from published categories, ordered `created_at DESC`.

**Multer config:** `memoryStorage()` (so the row id can be embedded in the filename), 5 MB cap, image-only filter. Files written to `frontend/uploads/portfolio_{cat,item}_<id>[_(after|before)]_<ts>.<ext>`. `safeUnlink` swallows ENOENT and only acts on `/uploads/...` paths.

**Frontend:** `frontend/js/pages/portfolio.js` — two-level admin SPA (categories grid → items grid in a category) with HTML5 drag-drop reorder on both levels and create/edit modals. Stub `staff-profile-modal` shape reused via shared classes (`stg-section`, `btn-pri`, `fg`/`fl`).

### AI-агент: управление и гейт допуска
- **МОРАТОРИЙ НА НОВЫЕ ПРОМПТ-ПРАВИЛА (принцип, зафиксирован 10.08.2026 по итогам диагностики):** системный промпт Милы — ~39k токенов префикса и >100 правил; каждое новое правило снижает соблюдение старых, и промпт-only защита проигрывала живым прогонам МНОГОКРАТНО (greeting 1/3, care-skip 6/6, дубли вызовов 9/ход при явном запрете). Новые поведенческие дефекты закрываются ТОЛЬКО детерминированно: гейтами/guard'ами в коде, хинтами в ответах инструментов, дописками оркестратора. Править существующее правило (уточнить, снять противоречие) можно; ДОБАВЛЯТЬ новое — только если детерминированного пути нет, с обоснованием в коммите.
- `services/agent-gate.js` — чистые хелперы: `normalizePhoneKey` (РФ `8→7`), `decideGate` (порядок: enabled → чёрный список → режим/белый). Юнит-тесты `agent-gate.test.js`.
- Расписание: `agent_settings.schedule_enabled/schedule_start/schedule_end` ('HH:MM', мск). Окно **только сужает** допуск — вне окна режим принудительно `whitelist` (reason `outside-schedule`), внутри действует выбранный режим. Окно через полночь поддержано (`start > end`), начало включительно, конец исключительно; битые границы → расписание игнорируется (fail-open). Отсечка жёсткая по часам: диалог, начатый в окне, после его конца бот не продолжает.
- `services/agent-settings.js` — настройки (`agent_settings`) и списки номеров (`agent_number_rules`); `isAllowed(salonId, phone)` объединяет их через `decideGate` (fail-closed без `salonId`). Номера хранятся каноничными (нормализуются при записи в `addNumberRule`).
- `routes/agent-settings.js` (`/api/agent`, owner/admin) — тумблер, режим `all|whitelist`, CRUD номеров.
- `routes/chatpush-webhook.js` зовёт `isAllowed` перед авто-ответом. Два уровня: env `CHATPUSH_AGENT_ENABLED` (глобальный kill-switch) И per-salon настройки из админки.
- Фронт: модалка «⚙️ Агент» на странице «Чат» (`frontend/js/pages/agent-settings.js`).
- **Только личная переписка**: в ГРУППОВЫХ чатах Мила молчит всегда (рабочие группы салона, чаты с несколькими участниками) — сообщения сохраняются и видны в «Чате», отвечает там только человек. Гейт `services/agent/group-chat.js` (чистый модуль, тесты `agent-group-chat.test.js`) стоит в двух местах: `routes/chatpush-webhook.js` (не ставит в очередь) и `dispatcher.enqueue/process` (второй уровень). Признак группы: явный `chat_type` от Chatpush (`person` → личка, любое другое непустое значение → группа; шлют tdlib и MAX, WhatsApp — нет), иначе разбор `chat_id` (`-…` у tdlib/MAX, `…@g.us`/`@broadcast` у WhatsApp, `g:…` — ключ диалога админки). ЗАЧЕМ гейт: в группе Chatpush присылает chat_id группы И номер УЧАСТНИКА, а ключ диалога у диспетчера — `phone || chat_id`, поэтому сообщение из рабочей группы уводило Милу в ЛИЧНУЮ переписку с этим участником (она читала его личный транскрипт и отвечала ему в личку). Гейт намеренно ШИРЕ, чем `services/chat.isGroupChatId`: тот зеркалит `DIALOG_KEY_SQL` и выражение индекса `idx_chatpush_messages_dialogkey2` — расширять его нельзя без пересборки индекса.
- Номер собеседника берётся СТРОГО с той стороны, где стоит клиент (`envelope` в `services/chatpush.js`, тесты в `chat.test.js`): у ИСХОДЯЩЕГО — только `recipient_phone_number`, у ВХОДЯЩЕГО — только `sender_phone_number`. Перекрёстных фолбэков быть не может: вторая сторона в обоих случаях — НАШ инстанс, и его номер клиентом не бывает. Симметричная половина дефекта живёт в MAX: он кладёт свой номер в `recipient_phone_number` даже у входящих с неизвестным номером отправителя (6 событий на проде — диалоги `27331166`, `55303820`), и прежний фолбэк уводил туда уже сообщения КЛИЕНТА. В ГРУППЕ номер участника лежит в `sender_phone_number` и правилом не затрагивается (наш собственный номер там законен — администратор пишет в рабочую группу со своего аккаунта), поэтому разовая склейка истории трогает входящие только в ЛИЧНЫХ чатах. Инцидент 2026-08-10 (диалог `298342940`, tdlib, «darialyaskalo»): у собеседника в Telegram номер скрыт, Chatpush прислал `recipient_phone_number: null`, фолбэк подставил номер клиники `79250177778` — и ключ диалога (`DIALOG_KEY_SQL`: phone, иначе chat_id) у входящих и исходящих РАЗЪЕХАЛСЯ: сообщения клиента под `298342940`, ответы администратора под `79250177778`. В «Чате» переписка выглядела монологом клиента, а ответы 31 разного чата (129 строк tdlib + 61 max) свалились в ОДИН фантомный диалог с номером клиники. Побочно тем же промахивалась пауза «ответил оператор»: `pauseKey = msg.phone || msg.chatId` в `routes/chatpush-webhook.js` ставил `agent_dialogs` на фантомный ключ, то есть настоящий диалог клиента оставался БЕЗ паузы и Мила могла вклиниться в разговор, который уже вёл человек (в самом инциденте она промолчала лишь потому, что 11:15–11:32 мск — вне ночного окна). Историю склеил разовый `scripts/fix-dialog-phone-keys.js` (собственный номер не хардкодит — берёт из `chatpush_events` как `sender_phone_number` исходящих; гасит `phone` и удаляет фантомную строку `agent_dialogs`).
- Номер клиента, ставший известен ПОСРЕДИ переписки, подтягивается к прежним сообщениям чата (`chat-persist.adoptPhoneForChat`, зовётся из `routes/chatpush-webhook.js` после сохранения, тесты `chat-persist.test.js`): Telegram/MAX скрывают номер, пока клиент не пришлёт его текстом, поэтому ключ диалога прыгает с `chat_id` на `phone` и одна переписка живёт в «Чате» ДВУМЯ диалогами — начало под `chat_id`, продолжение под номером (на проде так были расщеплены 6 чатов, склеены вторым проходом `scripts/fix-dialog-phone-keys.js`; чат с НЕСКОЛЬКИМИ разными номерами скрипт пропускает — какой из них принадлежит собеседнику, из данных не следует). Группы не трогаются: там `phone` — номер УЧАСТНИКА, свой у каждого сообщения, а ключ и так строится от `chat_id`. Альтернатива «ключ по `chat_id` для tdlib/MAX» ОТВЕРГНУТА (решение салона 10.08): она требует пересборки `idx_chatpush_messages_dialogkey2` и расщепила бы клиентов, которые сейчас склеены между WhatsApp и Telegram по одному номеру.
- Диалоги на операторе (`agent_dialogs.status='escalated'` — и эскалация Милы, и ручная пауза `operator_reply`) в списке чатов подсвечены красным и закреплены СВЕРХУ; внутри группы порядок обычный, по свежести. `GET /api/chat/dialogs` отдаёт `agentStatus`/`escalatedReason`; смена статуса рассылается SSE-событием `agent_status` (`chat-events.emitAgentStatus`) из трёх мест: `tools/escalate-to-operator.js`, `pauseAgent` и `POST /dialogs/:key/agent`. Порядок списка считает ТОЛЬКО фронт (`frontend/js/pages/chat-dialog-sort.js`, чистый модуль + `node --test`) — список перестраивается локально по SSE, и второй экземпляр правила в `ORDER BY` пришлось бы чинить в двух местах. Живые проверки: `scripts/chat-escalation-e2e.js` (контракт+SSE), `scripts/chat-escalation-visual.js` (headless-Chrome: всплытие и подсветка без перезагрузки, скриншоты обеих тем).
- Минимальный срок до визита (`services/agent/lead-time.js`, чистый модуль, тесты `agent-lead-time.test.js`): день в день — старт не раньше now+2ч; заявка в 22:00+ (мск) на завтра — старт не раньше 12:00; ночная заявка (00:00–06:59) на сегодня — тоже не раньше 12:00. Применяется в выдаче слотов (`get_available_slots`/`get_parallel_slots`/`get_sequential_slots`; в якорном режиме фильтруются только добавляемые звенья) И write-guard'ом в `create_booking`/`reschedule_booking` (ответ `too_soon` с корректирующим hint — иначе клиент обошёл бы фильтр, назвав раннее время сам). `book_chain` наследует guard через хендлер create-booking. Промпт-правило «МИНИМАЛЬНЫЙ СРОК ДО ВИЗИТА» в Сценарии 2.
- Слот всегда считается под КОНКРЕТНУЮ услугу: `service_yc_id` в `get_available_slots` **обязателен** (как в parallel/sequential). Хронология одного хода: все события попытки уходят одним INSERT с `DEFAULT NOW()`, `created_at` у них совпадает — порядок восстанавливает тай-брейк по исходному индексу строки; без него разделение на write/read ВСЕГДА ставило запись впереди чтения и журнал врал модели «сначала записала, потом посмотрела историю». `dropped` означает РОВНО «срезано капом» (оркестратор логирует это как срез) — события, о которых экстрактору нечего сказать, в счётчик не идут. Всё в `tool-events.js` строго best-effort, КРОМЕ `loadRecent`: её ошибка намеренно не глотается — ловит оркестратор своим fail-open (ход идёт без блока памяти). Аварийный рычаг — `AGENT_TOOL_MEMORY=false` (по умолчанию память ВКЛЮЧЕНА): флаг гасит РОВНО чтение выжимки в промпт, запись журнала идёт при любом его значении — форензика нужна независимо от того, показываем ли память модели (переименовать таблицу нельзя: `migrations.js` вернёт её на рестарте). Форензика — сырой jsonb в таблице, хранение 30 дней, чистка кроном `40 4 * * *` (там же, где журнал авторства; сбой чистки логируется WARN — молчащий крон означал бы бессрочное хранение сырых input/result). `sequential-offers`/`pending-replies` журнал не заменяет, они живут рядом. Живая проверка — `scripts/agent-tool-memory-e2e.js` (платный LLM, реального сообщения никому не отправляет: `send` застаблен): проверяет не только что времена всплыли в ответе второго хода, но и что блок «ЖУРНАЛ» реально попал в его системный промпт — иначе тест был бы зелёным по совпадению, часть времён модель может взять из собственной прошлой реплики в транскрипте.

- Запись на конкретный препарат, которого пациент НЕ называл, переспрашивается детерминированно (`services/agent/generic-booking-guard.js` — чистый модуль, тесты `agent-generic-booking-guard.test.js` + `agent-create-booking-generic.test.js`): инцидент 2026-07-31 — пациент попросил «биоревитализацию», модель молча оформила «Revi Silk 1 ml»; правило «ПРЕПАРАТ/ФИЛЛЕР/ЗОНУ НЕ УТОЧНЯЕМ» держалось только на промпте. `create_booking` на ветке проверки услуги зовёт `check` и при попадании возвращает hint-ответ `generic_service_hint` с `service_yc_id` обобщённой услуги (тот же приём, что `too_soon`); обход — явный аргумент схемы `patient_named_service:true`, он же покрывает законный случай «пациент назвал бренд кириллицей» («стилаж»). Судим ТОЛЬКО по ЛАТИНСКИМ токенам ≥3 букв в названии услуги («ml», «gr» отсекаются длиной) и сверяем их с текстом сообщений пациента (`toolCtx.patientText` — пересчитывается КАЖДОЙ попыткой, как `attachments`, чтобы перегенерация видела свежую серию): зоны ботулинотерапии — русские слова со склонением («лба» при услуге «Лоб+Межбровье»), стем-сверка давала бы ложные срабатывания на самом частом ЛЕГАЛЬНОМ пути, а каждое ложное — лишний проход провайдера. `GUARDED_GENERICS` — ПРОИЗВОДНЫЙ список от `GENERIC_SERVICE_TITLES` минус `UNIT_PRICE_SERVICE_TITLE` (новое обобщённое направление не должно молча оставлять guard слепым; Ботулакс исключён осмысленно — там уточняется ЗОНА, латинская эвристика к ней неприменима). Guard МОЛЧИТ в двух случаях, и оба — fail-open: обобщённой услуги нет в каталоге (правило невыполнимо — она попадает туда только `allow`-галочкой, см. пункт про `GENERIC_SERVICE_TITLES`) и у неё ПУСТОЙ `staff` — hint отправил бы модель на её `service_yc_id`, а следующая проверка `create_booking` («мастер выполняет услугу») выдала бы ВТОРОЙ невыполнимый hint, то есть пинг-понг; запись на конкретный препарат лучше тупика. `book_chain` guard НЕ наследует, и это тоже правка по ревью: план утверждал, что `ctx` туда не передаётся, — на деле передавался насквозь, поэтому `patientText` вырезается ЯВНО (`linkCtx`). Причина: в схеме `book_chain` нет `patient_named_service`, обход был бы невыполним, а вариант стыковки пациент подтверждает ЦЕЛИКОМ («давайте первый вариант» после показа названий услуг).
- Повтор должности специалиста срезается детерминированно (`services/agent/title-dedup.js` — чистый модуль, тесты `agent-title-dedup.test.js`): правило «ДОЛЖНОСТЬ НАЗЫВАЙ ОДИН РАЗ» промпт выполнял нестабильно — «косметолог-эстетист Юлия» звучало в каждом сообщении подряд. Замена безопасна ТЕКСТУАЛЬНО: в русской конструкции «должность + Имя» падеж несёт ИМЯ, поэтому «у косметолога-эстетиста Юлии» → «у Юлии» остаётся грамматичным. Срезаются только имена, чья должность звучала в ПРОШЛЫХ репликах Милы (`namesWithTitle` по `priorAssistantText` — assistant-строки транскрипта БЕЗ строк с `OPERATOR_MARK`, режутся ПОСТРОЧНО: реплика администратора склеена `loadTranscript` в один блок с её собственными, и выбрасывать блок целиком значило бы потерять её же реплики); первое упоминание в текущей реплике не трогается. Место — ПОСЛЕ `stripStamp` и ДО address-guard и дописок приветствия. Должности — списком паттернов со склонением, а не «любое слово перед именем»; первая буква каждой — явным классом `[Кк]`/`[Вв]`/`[Гг]`, а НЕ флагом `i`: с `iu` свойства `\p{Lu}`/`\p{Ll}` замыкаются по case-folding и капитализация имени перестаёт проверяться вовсе («косметолог-эстетист свободна» захватывало бы «свободна» как имя). Разделители — `[^\S\n]`, а не `\s`: `\s` спанит перенос строки, и в вертикальном списке («Косметолог-эстетист\nЮлия — 12:00») пара склеивалась через строки и срезала заголовок списка. ДВЕ ПРАВКИ ПО РЕВЬЮ, обе про реальный текст: заглавное слово после должности далеко не всегда имя — «Записаться к врачу-косметологу Вы можете» давало пару «Вы», а срез превращал фразу в «К Вы можете» (это качественно хуже любого пропуска), поэтому слово короче 4 букв именем не считается вовсе плюс стоп-список местоимений — ценой того, что короткие настоящие имена («Ева», «Лия») не срезаются (прежнее поведение, а не поломка); и допуск на пробелы вокруг дефиса И на его отсутствие — в `staff_members.specialization` на проде разнобой («Косметолог- эстетист» у Гатауллиной Юлии, «Косметолог - эстетист» у Палий), без него фича была бы no-op ровно для тех, ради кого писалась (второе слово должности при этом остаётся ОБЯЗАТЕЛЬНЫМ, «Врач Юлия» парой не считается). Сверка имён — по ОБЩЕМУ ПРЕФИКСУ стемов, а не точным равенством: склонение живёт в хвосте, и у 4-буквенного имени «Юлия»/«Юлии» разошлись бы последней буквой. ИЗВЕСТНАЯ КОЛЛИЗИЯ, закреплённая тестом (чинить молча не надо): имена с общими тремя буквами склеиваются — «Александра» и «Алексей» считаются одним человеком, цена — лишний срез должности у второго мастера, тот же остаточный риск, что у `personRe` в reply-guard. ГОТЧА: `priorAssistantText` собирается по окну транскрипта `LIMIT 20`, а не «за весь диалог», поэтому в долгой переписке должность ЗАКОННО всплывает снова, когда первое упоминание из окна выпало. Рядом, но без резки, — ТЕЛЕМЕТРИЯ по «консультации в подарок»: `reply-guard.checkGiftRepeat` пишет нарушение `gift_repeat` в лог, когда подарок упомянут второй раз (`priorHasGift` считает оркестратор той же `GIFT_RE` по прошлым репликам Милы), но текст НЕ переписывает — фраза вплетена в предложение, а масштаб проблемы неизвестен (тот же подход, что у `offer_bypass`/`free_day_time`: сначала измерить). В `value` идёт ФАКТИЧЕСКАЯ клауза вокруг совпадения (кап 160 символов, разделитель предложения сохраняется в хвосте — видно и тон, и что именно повторено), а не константа «в подарок»: весь смысл сигнала — измерить, какую услугу и в какой формулировке модель дарит второй раз, и лог guard'а по этому правилу единственный источник.

### «Отдел заботы» (care-программы)
Плановые касания после состоявшегося визита («как самочувствие», Т+N дней): салон описывает программу (условия И/ИЛИ по мастеру/категории/услуге — тот же `evaluateRule` из notifications) и цепочку касаний; текст каждого касания пишет Мила одним LLM-вызовом без инструментов.

- Зачисление ТОЛЬКО событийное (вебхук в момент, когда визит стал состоявшимся): бэкфилла нет — программа, созданная сегодня, прошлые визиты не подхватит. Готча: правка старой записи в YClients перевыстреливает вебхук годы спустя, enrollment создаётся с `scheduled_at` в прошлом, а воркер арендует по `scheduled_at <= NOW()` без нижней границы → такое касание уходит немедленно. Защиты от протухших касаний нет.
- Таблицы (`migrations.js`): `care_programs` (conditions jsonb) → `care_touches` (delay_days, send_time, intent_text, text_mode) → `care_enrollments` (статусы `active|completed|declined|escalated|superseded|stopped`) → `care_touch_sends` — очередь+журнал в одной таблице (статусы `scheduled|sent|skipped|cancelled|failed`). DELETE программы каскадом уносит enrollments и весь журнал.
- Зачисление (`services/care/enroll.js`, хук в `routes/webhook.js` на resource=record): визит состоялся = `attendance=1` ИЛИ `paid_full=1` — НЕ кэшбэчный критерий «оплачено деньгами»: визит с оплатой бонусами тоже заслуживает заботы. `classifyRecordEvent` ПЕРВЫМ проверяет un-enroll (`status='delete'` / `deleted` / `attendance=-1` — предоплаченная неявка несёт `paid_full=1` одновременно с `attendance=-1`) → гасит активные цепочки записи. Повторный подходящий визит supersede'ит прежний активный enrollment той же программы по ДАТЕ ВИЗИТА, а не по порядку вебхуков (правка старой записи может перевыстрелить вебхук годы спустя — без сравнения `visit_at` она глушила бы живую цепочку). Дедуп — UNIQUE (program_id, yclients_record_id); self-heal: ретрай вебхука дозаполняет касания enrollment'а, вставленного до падения процесса. Телефон нормализуется `normalizePhoneKey`, ЧС клиента блокирует зачисление.
- Воркер (`services/care/worker.js`, тик 15с, guard от наслоения тиков — медленный прогон не пускает следующий): LEASE_SQL арендует до 5 due-строк `FOR UPDATE SKIP LOCKED` + attempts при аренде; колонки касания берутся СКАЛЯРНЫМИ ПОДЗАПРОСАМИ в RETURNING — JOIN на цель UPDATE в PG запрещён («invalid reference to FROM-clause entry»), юнит-моки db.any валидность SQL не проверяют → после правок LEASE_SQL обязателен живой EXPLAIN на дев-БД (SQL экспортируется именно для этого). Порядок детерминированных проверок до LLM: enrollment активен → программа включена → env-гейт агента → `isAllowed` (ОБЩИЙ гейт Милы: ЧС/режим/расписание) → диалог не на операторе → анти-спам «1 касание в день» (сдвиг scheduled_at на +24ч от max(scheduled_at, now()), не skip; паузу между сообщениями care-воркер НЕ держит — отправленные касания в счётчик темпа `send-pacing.js` входят, но ждут его только напоминания, см. раздел ниже) → повторный визит по условиям программы (fail-open при сбое YClients) → care-проход. Таймаут LLM 60с (< backoff аренды 120с); maxTokens — дефолт провайдера `AGENT_MAX_TOKENS` (инцидент 2026-08-03: ручной бюджет 1200 съедался reasoning-токенами gemini, JSON обрезался finish=length → `llm_no_json` и ВСЕ касания молча скипались).
- ОКНО РАСПИСАНИЯ НА КАСАНИЯ НЕ РАСПРОСТРАНЯЕТСЯ (2026-08-06): воркер зовёт гейт как `isAllowed(salonId, phone, { ignoreSchedule: true })` — опция гасит РОВНО сужение окном (`scheduleEnabled && !opts.ignoreSchedule` в `agent-settings.js`), чёрный список, режим whitelist и тумблер агента действуют в полном объёме. ЗАЧЕМ: окно проектировалось для ВХОДЯЩИХ («когда Мила отвечает клиентам»), а время касания задаёт САМ салон в программе (`send_time`) — это уже решение о том, когда писать пациенту. Прежний defer на сутки (фикс 2026-08-03) чинил терминальный skip, но при ПОСТОЯННОМ окне (ночное 22:00–09:30 на проде + касание в 11:00) сдвиг на +24ч сохраняет время суток → касание не уходило НИКОГДА и вечно висело scheduled в дашборде. Ветка `outside-schedule` в воркере оставлена СТРАХОВКОЙ (defer + WARN): при откате опции или подменённом гейте терминальный skip сжёг бы цепочку молча — at-most-once второго шанса не даёт. Тесты — `agent-settings-allowed.test.js` (окно нулевой длины `'10:00'-'10:00'`, чтобы «вне окна» было верно в любой момент прогона) + тест в `care-worker.test.js`, что боевой `defaultDeps.isAllowed` передаёт флаг (правка «унифицируем вызовы гейта» вернула бы дефект молча).
- ФИКС 2026-08-03 (интеграционное ревью): env kill-switch (`CHATPUSH_AGENT_ENABLED`) выключен — касание ОТКЛАДЫВАЕТСЯ на сутки тем же механизмом, что анти-спам (`deferTouch`: сдвиг scheduled_at, attempts=0), а НЕ терминальный skip: иначе цепочка молча сгорала бы навсегда (at-most-once, второго шанса нет), пока админ держит Милу выключенной на проде. Прочие причины гейта (whitelist/blacklist/disabled per-salon) — это «клиенту/салону нельзя», а не «сейчас нельзя», остаются терминальным skip как раньше. РЕШЕНИЕ: enrollment, остановленный эскалацией (`status='escalated'`), после «Вернуть боту» НЕ возобновляется — новая цепочка начнётся только со следующего подходящего визита.
- Доставка AT-MOST-ONCE (пропущенное касание дешевле дубля живому пациенту): mark-before-send — sent-маркер пишется ДО отправки условным `UPDATE … WHERE status='scheduled'`; условие — ФИНАЛЬНЫЙ гейт: арендованный enrollment_status в LIMIT-5 батче устаревает (stop_program по строке A уже отменил строку B того же enrollment). Флаги `delivered`/`terminalWritten` в catch: доставлено → статус НЕ откатывается никогда; терминальный skipped/cancelled записан → не перезаписывается; отправки не было → откат в scheduled с чисткой sent_at, после 3 попыток — failed. Любой терминальный исход последнего касания завершает enrollment (`maybeCompleteChain`) — иначе зомби-active в дашборде.
- care-проход: `buildCarePrompt` (`care-prompt.js`) — транскрипт и имя клиента КЛИЕНТ-КОНТРОЛИРУЕМЫ, всё проходит `sanitizeLine`/`sanitizeName` покомпонентно (перевод строки в сообщении пациента не может подделать реплику «Мила: …» отдельной строкой). `parseCareDecision` (`decision.js`) fail-safe: не-JSON / нестроковый `text` (массив коэрсился бы в правдоподобный текст) / пусто / >1500 символов / bidi-контролы → skip, не отправка. Действие `escalate` — осложнение в переписке: касание не шлём, диалог на оператора (зеркало `tools/escalate-to-operator.js`: upsert agent_dialogs + `emitAgentStatus`), эскалация ДО остановки цепочки — если упала, ретрай её повторит, а не потеряет. Ответы пациента на касание обрабатывает ОСНОВНОЙ агент (обычный вебхук-путь со всеми мед-границами); `rememberPending` подмешивает касание в транскрипт до эха Chatpush, для whatsapp — persist-on-send в chatpush_messages.
- Режим текста касания (`care_touches.text_mode`, дефолт `free`): `free` — `intent_text` это ЗАГОТОВКА СМЫСЛА, текст пишет Мила; `strict` — `intent_text` уходит ГОТОВЫМ ТЕКСТОМ (менять смысл, сокращать, дописывать эмодзи и вопросы запрещено, разрешена только подстановка обращения по имени; лимит санитизации поднят 400→1200 символов). Решение «слать ли вообще» в strict остаётся за LLM — мед-правила, эскалация при осложнении, skip при жалобе и stop_program работают как в свободном режиме (готовый текст не должен ложиться поверх «у меня отёк»). Неизвестный режим трактуется как `free`. UI — чипы «✍️ Мила пишет сама / 📋 Готовый текст» в редакторе касания.
- API `/api/care` (`routes/care.js`, owner/admin; JWT-поля `req.user.salonId`/`userId` — НЕ `salon_id`!): programs CRUD+toggle, дашборд `GET /enrollments` (next_touch_at/last_sent_at), журнал `GET /enrollments/:id/sends` (LEFT JOIN care_touches — touch_id NULL после удаления касания из программы), `POST /enrollments/:id/stop`, `POST /preview` (сухой прогон). Фронт — `frontend/js/pages/care.js` (страница «Забота»). Живые проверки: `scripts/care-e2e.js` (реальный LLM + РЕАЛЬНАЯ отправка на номер; чистка уносит sent-журнал каскадом, поэтому повторный прогон в тот же день отправит ещё раз — анти-спам свой прошлый прогон не увидит), `scripts/care-ui-e2e.js` (UI) и `scripts/care-preview-e2e.js` (превью + режим текста, API и UI; ничего не отправляет).
- Превью выборки (`services/care/preview.js`, `POST /api/care/preview`, кнопка «👁 Выборка» в карточке программы и в редакторе): «кто попал бы, если бы программа работала последние N дней» (1–90, дефолт 30). Нужно потому, что зачисление ЧИСТО СОБЫТИЙНОЕ — бэкфилла нет, и у только что созданной программы дашборд пуст: без превью не отличить «условия кривые» от «подходящих визитов не было». Тянет `/records/{cid}` за период и гоняет ТОТ ЖЕ `evaluateRule` и тот же критерий `isVisitCompleted`, что и enroll.js — расхождение превью с боевым отбором есть баг, правки условий идут в оба места. Ничего не пишет в БД и не отправляет. `matchVisits` чистая (тесты `care-preview.test.js`), сеть и ЧС — в маршруте; строки помечаются `skipReason` (`no_phone`/`blacklist`/`superseded` — из нескольких визитов клиента дожила бы цепочка только от самого позднего). Тело принимает либо `programId` (условия из БД), либо `conditions`+`touches` (черновик в редакторе, программа ещё не сохранена). Пустая карта категорий → `catMapFailed:true` в ответе (иначе «никто не подошёл» читается как «условия не те»).

### Напоминания о повторном визите
Отдельный модуль рядом с «Заботой», не её часть: правило = условия отбора визита (тот же формат `{logic, items}` и тот же `evaluateRule`, что у care-программ) + задержка в днях + текст (свободный или готовый) + необязательные ступени бонуса по балансу карты. На каждый подходящий состоявшийся визит заводится строка `reminder_queue` — очередь и журнал в одной таблице, статусы `scheduled|sent|skipped|cancelled|failed`.

- Таблицы (`migrations.js`): `reminder_rules` (conditions jsonb, delay_days, send_time, text_mode, text, attribution_days, bonus_enabled, bonus_tiers jsonb, backfill_max_per_day, send_interval_min) → `reminder_queue` (якорь визита: anchor_record_id/anchor_visit_at/anchor_staff_name/anchor_services, бонусная тройка balance_before/bonus_tier/bonus_accrued/bonus_txn_ok, атрибуция conversion_record_id/converted_at/visited_at, source `webhook|backfill`) → `reminder_suppressions` (анти-повтор, UNIQUE(rule_id, phone)). `reminder_queue.rule_id` — **`ON DELETE SET NULL`**, в отличие от каскада «Заботы»: история «кому что по какому правилу» обязана пережить удаление правила, отсюда денормализованный `rule_title`. Строки удалённого правила (`rule_id IS NULL`, ещё `status='scheduled'`) join воркера не вернёт и они висели бы вечно — их гасит `ORPHAN_SQL` (`UPDATE … SET status='cancelled'` на каждом тике, до аренды).
- Планирование ЧИСТО СОБЫТИЙНОЕ (хук в `routes/webhook.js` на `resource=record`, `services/reminders/enroll.js`, свой try/catch — падение не должно ронять «Заботу» и кэшбэк) — бэкфилла нет, у только что созданного правила очередь пуста. Критерий «визит состоялся» и классификация события переиспользуют `care/enroll.js` (`isVisitCompleted`, `classifyRecordEvent`): un-enroll (отмена/неявка/удаление) проверяется ПЕРВЫМ, потому что предоплаченная неявка несёт `paid_full=1` одновременно с `attendance=-1`. «Аналогичная услуга» (клиент уже записан/уже приходил повторно) — это ПОПАДАНИЕ ПОД ТЕ ЖЕ УСЛОВИЯ ПРАВИЛА, а не совпадение конкретной услуги: правило на категорию «Лазерная эпиляция» считает аналогичной запись на любую услугу категории. Снятие флага анти-повтора визитом стоит ДО планирования новой строки (иначе новая строка упёрлась бы в собственный `muted` от прошлого цикла) и бьёт только по `reminder_suppressions.source='auto'` — ручной отказ клиента (`source='manual'`) визитом не снимается, только человеком. Защита от вебхука не по порядку — двусторонняя, как в «Заботе»: (1) если по правилу+телефону уже есть ЖИВАЯ строка от БОЛЕЕ ПОЗДНЕГО визита, планирование по более старому визиту пропускается целиком (проверяется первой, раньше un-mute и cancel-stale); (2) прежние запланированные строки от БОЛЕЕ РАННИХ визитов отменяются при планировании новой. Дедуп — `UNIQUE(rule_id, anchor_record_id)`.

- Бонусная часть (`services/reminders/bonus.js` + `tiers.js`) — ГЛАВНЫЙ ИНВАРИАНТ: наружу не бросает никогда, любой сбой (нет карты нужного типа, YClients не ответил, начисление упало) деградирует в ступень `no_bonus`, и сообщение уходит без единого слова про бонусы — клиент не должен прочитать про бонусы, которых у него нет. Карта — СТРОГО типа, настроенного в салоне (`salon.yclients_card_type_id`, как `services/loyalty.js` и `routes/clients.js`), а не «с максимальным балансом»: у клиента могут быть карты других программ (например samosale), и начисление на чужую карту необратимо. Тип не настроен → `no_bonus` без единого вызова YClients. Следствие: `SELECT` салона в `defaultDeps.applyBonus` воркера обязан тянуть `yclients_card_type_id` — забытое поле молча выключает бонусы навсегда. Ступени (`pickTier`) — порог `up_to` ИСКЛЮЧАЮЩИЙ (ступень ловит баланс строго меньше своего порога), последняя ступень с `up_to:null` — «весь остаток»; начисление НЕОБРАТИМО, поэтому вызывающий обязан звать `applyBonus` не более одного раза на строку. Защита в воркере — НАМЕРЕНИЕ, записанное ДО вызова YClients: `UPDATE … SET bonus_tier='pending' WHERE id=$1 AND bonus_tier IS NULL`, и `applyBonus` зовётся, только если пометка легла. Одной проверки «`bonus_accrued IS NULL`» после начисления НЕ хватает: `ycAccrueCard` — ручная транзакция без ключа идемпотентности, и падение процесса (или обрыв БД) между успешным начислением и записью результата вернуло бы строку в `scheduled` с пустым `bonus_accrued`, а следующая аренда начислила бы деньги ВТОРОЙ раз. Строка, найденная в состоянии `pending`, трактуется как `no_bonus` (про сумму, которой может не быть, клиенту не говорим) + WARN в лог: прошлая попытка оборвалась ровно в этом окне, карту клиента надо проверить руками.
- Воркер (`services/reminders/worker.js`, тик 60с, тот же `_tickInFlight`-guard от наслоения, что в «Заботе»). Порядок внутри строки: детерминированные гейты → **бонусы** (считаются рано, потому что текст обязан содержать ФАКТИЧЕСКИ начисленную сумму, а не обещание; от двойного начисления защищает пометка `bonus_tier='pending'` ДО вызова YClients) → рендер текста (шаблон в `strict`, LLM-проход в `free`) → reply-guard → **захват строки условным `UPDATE … WHERE status='scheduled'`** (`SET status='sent'`) вплотную перед `sendMessage` → отправка → персист. Захват стоит ПОСЛЕДНИМ, а не сразу после аренды: ранний захват (как в первой версии плана) означал, что падение процесса (OOM, `pm2 restart`) между захватом и реальной отправкой оставляет строку `sent` без единого отправленного сообщения — `LEASE_SQL` арендует только `scheduled`, и такая строка терялась бы навсегда, выглядя в дашборде отправленной. Запас по времени: `LLM_TIMEOUT_MS` 60с строго меньше `RETRY_BACKOFF_S` 120с (тот же запас, что в care-воркере) — таймаут-ретрай не пересечётся с ещё живым прошлым вызовом в окне аренды; защита ПРОЦЕССНАЯ (один PM2-инстанс), не распределённая — при горизонтальном масштабировании нужен явный distributed lock или больший backoff. `LEASE_SQL` — тот же приём, что в «Заботе»: колонки правила берутся скалярными подзапросами в RETURNING (JOIN на цель UPDATE в PG запрещён), юнит-моки SQL не проверяют → после правок обязателен живой EXPLAIN на дев-БД. Аренда сортирует `ORDER BY scheduled_at ASC, id ASC` — тай-брейк по `id` ОБЯЗАТЕЛЕН: догон кладёт сотни строк на ОДИН `scheduled_at`, и решение владельца салона «первым получает тот, кто не был дольше всех» держалось на неспецифицированном порядке выдачи индекса; под этот ключ заведён `idx_reminder_queue_due2 (scheduled_at, id) WHERE status='scheduled'` (старый `idx_reminder_queue_due` оставлен — правило проекта «никогда деструктивно», он просто перестаёт быть выбором планировщика).
- В режиме `free` текст пишет Мила по СОБСТВЕННОМУ промпту напоминаний (`services/reminders/reminder-prompt.js`, тесты `reminders-prompt.test.js`), `intent_text` для него собирается уже с подставленными цифрами (`renderReminderText`). До 08.08.2026 тут переиспользовался care-промпт «Заботы», и это давало СИСТЕМАТИЧЕСКИЙ отказ писать: care-промпт описывает другой продукт («плановое касание заботы ПОСЛЕ ВИЗИТА, это НЕ продажа») и его правило «если пациент уже писал про эту процедуру — не отправляй бодрое касание поверх» модель обобщает на ЛЮБУЮ активность в переписке. ИЗМЕРЕНО на боевом провайдере (правило «Лазерная эпиляция», 79200255591, в окне транскрипта двухдневный вопрос про ботокс): care-промпт — skip 6 прогонов из 6 (и с якорём ПОД условия правила, и без), причины каждый раз новые («пациент в активной переписке о другой процедуре», «на прошлое касание не ответили», «пациент сам написал в чат»); тот же вход с рамкой «плановое напоминание» — send 3 из 3, care-промпт с ПУСТЫМ транскриптом — send 2 из 2. То есть дело было в рамке, а не в данных, и правкой одной формулировки не чинилось. Ключевое правило нового промпта — ЯВНОЕ «ВСЁ ОСТАЛЬНОЕ В ПЕРЕПИСКЕ — НЕ ПОВОД МОЛЧАТЬ» (чужая процедура, незакрытый диалог с администратором, недавнее сообщение клиники, отсутствие ответа): без него модель каждый раз изобретает новое основание для skip. Что СОХРАНЕНО и проверено живьём: skip, когда пациент сам обсуждает ИМЕННО эту услугу (2/2), и `escalate` при осложнении (2/2). Блока «БУДУЩИЕ ЗАПИСИ» в промпте намеренно нет: запись под условия правила отменяет строку детерминированно (`hasFutureMatchingBooking`) ДО вызова модели, а запись на другую услугу молчать не повод. «Сегодня …» в промпте ОБЯЗАТЕЛЬНО (и дописано заодно в care-промпт): без текущей даты модель судит о давности визита по своим представлениям — в прогоне 08.08.2026 она объявила визит от 31.07.2026 БУДУЩИМ и отказалась писать «после визита». Форматтер дат ОДИН на оба промпта (`care-prompt.fmtMskDate`). Промпт напоминаний нужен только режиму `free`: в `strict` воркер до LLM не доходит вовсе. Промпт инструктирует модель отвечать не только `send`, а ещё `escalate` и `stop_program` (`care/decision.js`), и оба варианта обязаны быть реально обработаны, а не просто схлопнуты в «текст пуст»: `escalate` (осложнение после процедуры) — касание НЕ отправляется, диалог переводится на оператора (`escalateDialog`, тот же приём, что `tools/escalate-to-operator.js`: upsert `agent_dialogs` + `emitAgentStatus`), строка `skipped`; `stop_program` (просьба «не пишите мне») — ставится флаг анти-повтора с `source='manual'` (визитом НЕ снимается — см. выше) и строка `cancelled`. Причина от модели (`decision.reason`) пишется в `decision_reason`, а не тонет в общей формулировке. Маркер `[сообщение администратора клиники]` (`OPERATOR_MARK` из `agent/history.js`) срезается из транскрипта ПЕРЕД сборкой промпта (`stripOperatorMark`, посимвольно с начала каждой строки серии) — ни промпт напоминаний, ни care-промпт про эту пометку не знают и отдали бы её клиенту дословно.
- Гейты воркера ДО бонусов и текста, по порядку: правило включено → env-гейт агента (выключен → `deferRow`, не терминально) → `isAllowed(salonId, phone, { ignoreSchedule: true })` — ОБЩИЙ гейт Милы (ЧС/режим/тумблер), но ночное окно расписания на плановые напоминания НЕ распространяется (симметрично «Заботе»: время задаёт сам салон в `send_time`); неожиданный `outside-schedule` вопреки `ignoreSchedule` — страховка, `deferRow` + WARN, а не терминальный skip → диалог не на операторе (эскалация Милы или ручная пауза — `deferRow` с `bumpDefers=true`, предел терпения `MAX_OPERATOR_DEFERS=3`, дальше терминальный skip: ждать бесконечно нельзя, напоминание протухнет по смыслу) → анти-повтор (`reminder_suppressions.muted`) → анти-спам «1 плановое сообщение в день» → **темп отправки** (см. ниже; стоит именно тут — ДО проверок YClients, ДО НЕОБРАТИМОГО начисления бонусов и ДО платного LLM-прохода) → живые проверки по YClients-записям (`hasFutureMatchingBooking` на будущих и на состоявшихся-после-визита записях; fail-open при сбое API — тот же размен, что в «Заботе»).
- Общий анти-спам `services/messaging/daily-limit.js` — «1 плановое сообщение клиенту в день», СЧИТАЕТ ОБЕ очереди (`care_touch_sends` UNION `reminder_queue`) одним запросом: две независимые очереди со своими воркерами легко сложились бы в два сообщения одному человеку в одно утро («как самочувствие» от «Заботы» и «пора повторить» от напоминаний). Это ЧТЕНИЕ ПЕРЕД ДЕЙСТВИЕМ без блокировки, не гарантия: два тика на один телефон, попавшие в одно окно, оба увидят «сегодня не слали» и оба отправят — размен осознанный (пропущенное сообщение хуже редкого дубля), окно сужено mark-before-send в обеих очередях, но не закрыто. РАСХОЖДЕНИЕ с соседним `send-pacing.js` НАМЕРЕННОЕ: тут ДВЕ очереди, там ТРИ (плюс `notification_sends`) — автоуведомление транзакционно и в лимит «планового клиенту» не входит (иначе запись на приём отменяла бы сегодняшнее касание «Заботы»), а темпу важен НОМЕР инстанса мессенджера, ему в счёт идёт всё исходящее.
- Темп отправки — пауза между плановыми сообщениями салона, поле правила `send_interval_min` (0–120, дефолт 3; явный 0 — законное «без паузы»). Счётчик — `services/messaging/send-pacing.js` (`lastPlannedSendAt`/`waitMsLeft`/`paceDeferMinutes`, тесты `messaging-send-pacing.test.js`), ОБЩИЙ на ТРИ плановые очереди САЛОНА (`reminder_queue`, `care_touch_sends`, `notification_sends`): WhatsApp блокирует НОМЕР, а не правило и не очередь, а автоуведомления — самый крупный источник пачки (их воркер арендует до 10 строк за тик). При этом ЖДЁТ паузу ТОЛЬКО воркер напоминаний: транзакционное «Вы записаны на приём» задерживать ради темпа нельзя, а у программ «Заботы» настройки темпа нет — асимметрия осознанная (обе очереди в счётчик ВХОДЯТ, но не троттлятся). ГОТЧА производительности: `max()` над `UNION ALL` PostgreSQL к «взять первую строку индекса» НЕ сводит (живой EXPLAIN показывал Append со сканом всех `status='sent'`), поэтому запрос написан как `greatest()` от трёх скалярных `max()` — под каждый заведён частичный индекс `(salon_id, sent_at DESC) WHERE status='sent'` (`idx_reminder_queue_sent`, `idx_care_touch_sends_sent`, `idx_notification_sends_sent`). Гейт в воркере — fail-CLOSED, и это осознанно расходится с общим fail-open остальных проверок: недоступный счётчик означал бы отправку ровно той пачкой, от которой пауза и защищает (не прочитали → откладываем на интервал). Битый/отсутствующий `send_interval_min` (`Number(null|'')` дал бы 0, то есть молча выключил защиту) → дефолт 3 + WARN.
- Пауза — гейт САЛОНА, а не строки, и это принципиально: `deferRowMinutes` переписывает `scheduled_at`, а аренда сортирует ПО НЕМУ первым ключом, поэтому построчное откладывание уводило отложенную строку в хвост за БОЛЕЕ СВЕЖИЕ визиты — решение владельца салона «первым получает тот, кто не был дольше всех» переставало соблюдаться ровно тогда, когда пачка не влезает в дневную ёмкость (при паузе 30 мин шаг доходил до ~150 строк). Теперь `processOne` на срабатывании паузы возвращает `RESULT_PACED`, а `processTick` откладывает ТОЛЬКО первую строку салона и остальные строки ЭТОГО салона в этом тике ПРОПУСКАЕТ без единого UPDATE по `scheduled_at`/`decision_reason` (множество `pacedSalons` живёт РОВНО один тик — пауза меряется минутами; строки других салонов обрабатываются как обычно, счётчик у них свой). ОСТАТОЧНОЕ ограничение: сама отложенная строка всё равно уезжает в хвост (≈2 строки «тонут» на каждую отправленную) — убрать это нельзя, иначе аренда возвращала бы ту же строку каждый тик до конца паузы.
- Бухгалтерия попыток при откладывании темпом: `deferRowMinutes` делает `attempts = GREATEST(attempts - 1, 0)` (откат РОВНО того инкремента, что добавила аренда), `defers` не трогает (на них висит `MAX_OPERATOR_DEFERS`, а у паузы предела нет по построению) и работает под `WHERE … AND status='scheduled'` (строку могли отменить прямо во время прогона — воскресить нельзя, а затереть чужой `decision_reason` можно). ЗАЧЕМ не «обнулять» и не «не трогать»: обнуление стирало бы НАСТОЯЩИЕ провалы (`final = attempts >= MAX_ATTEMPTS`) и строка с мёртвым каналом крутилась бы вечно, каждый круг оплачивая LLM-проход в режиме `free`; «не трогать» сжигало бы весь бюджет попыток на трёх откладываниях. Пропущенные строки салона получают ОДИН пакетный компенсирующий `UPDATE … attempts = GREATEST(attempts-1,0) WHERE id = ANY($1)` в конце тика — аренда инкрементит всем выданным строкам, а пропуск не попытка отправки; он намеренно НЕ двигает `scheduled_at`/`decision_reason`/`last_attempt_at` (последний держит backoff аренды).
- Дневной потолок темпа (`paceDeferMinutes`) — окно 09:00–21:00 МСК: если `now + пауза` попадает ВНЕ окна, строка переносится на ближайшее наступление `send_time` правила (считается от момента отправки, а не от now — иначе потолок СОКРАЩАЛ бы паузу); если САМ `send_time` лежит вне окна, салон выбрал это осознанно и потолок не применяется вовсе (туда же fail-open непарсящийся `send_time`). ГОТЧА: у двух проверок РАЗНЫЕ границы, это не копипаста — `inDayWindow` (момент отправки) конец ИСКЛЮЧАЮЩИЙ, `sendTimeInDayWindow` (`send_time` правила) ВКЛЮЧАЮЩИЙ: 21:00 — вероятное круглое значение формы, и читать его как «салон хочет ночную рассылку» неверно. Время последней отправки дня (`remPlanDayFinish`) — ОЦЕНКА по паузе правила: n-я строка уходит через (n−1) пауз после первой, всё, что попадает на 21:00 и позже, помечается ⚠️ и уезжает на следующий день (дневной потолок `paceDeferMinutes`, конец окна ИСКЛЮЧАЮЩИЙ). Считается ТОЛЬКО при выбранном одном правиле: пауза — настройка правила, и для «всех правил» единого числа нет. Блок строго вспомогательный — его сбой чистит панель, но журнал не прячет.
- Живая проверка `scripts/reminders-e2e.js` (создаёт правило и строку очереди на «сейчас», прогоняет один тик настоящего воркера, чистит за собой): по умолчанию отправка (`sendMessage`) и начисление (бонусы правила выключены при создании) застаблены, боевые пути включаются флагами `--send`/`--accrue`. Скрипт ОТКАЗЫВАЕТСЯ работать (кроме как с `--send` или явным `--allow-worker-running`), если pm2-процесс `loyalpro` сейчас `online`: его воркер тикает раз в минуту и, вставленная скриптом строка нарочно просрочена (`scheduled_at = NOW() - 1 минута`) для немедленной аренды, поэтому боевой тик может арендовать её первым и отправить сообщение по-настоящему. Готча прогона: с телефоном, у которого есть РЕАЛЬНАЯ история визитов в YClients (`loadClientRecords` не застаблен), строка законно уходит в `cancelled` («повторный визит уже состоялся» или «клиент уже записан на аналогичную услугу») — для демонстрации happy path нужен номер без истории у выбранного правила.

## Key constraints

- **Webhook handler must respond 200 immediately** before any async processing — YClients retries on timeout.
- **Advisory locks** are used in `processRecordEvent` to prevent race conditions on duplicate webhook deliveries — do not remove them.
- **Cashback accrual rule** — бонусы начисляются **только** если визит оплачен полностью деньгами: без применения бонусов и без скидок. Если клиент использовал бонусы или скидку — кэшбэк не начисляется (`finances_operation` type check в loyalty service).
- **`db.one` vs `db.oneOrNone`** — both exist, but they are byte-for-byte the same implementation (`db.js`: `return r.rows[0] || null`) — `one` does **not** throw on a missing row, it silently returns `null` just like `oneOrNone`. Code written expecting `one` to throw will instead keep running with `null` and blow up later as an unrelated `TypeError` (`Cannot read properties of null …`) far from the real cause. Treat both as `oneOrNone` and check the result explicitly wherever "not found" must be handled.
- **Timezone** — server runs TZ=Europe/Moscow. All date arithmetic must be Moscow-local. Use `AT TIME ZONE 'Europe/Moscow'` in SQL when comparing dates.
