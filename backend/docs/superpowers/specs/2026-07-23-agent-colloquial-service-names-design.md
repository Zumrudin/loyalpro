# Мила: распознавание бытовых названий процедур

Дата: 2026-07-23
Статус: одобрено к реализации

## Проблема

Пациенты называют процедуры бытовыми, сокращёнными или неофициальными словами:
«лазер», «био», «фото», «губы», «ботокс», «чистка». Сейчас на такой запрос Мила
трактует слово как «широкое направление» (Сценарий 2, Шаг 1) и задаёт открытый
уточняющий вопрос, перечисляя варианты процедур. Живой кейс:

> — Какие есть свободные окошки на лазер?
> — …уточните, какая именно процедура? Лазерная эпиляция, фотоомоложение Lumecca,
>   или что-то другое?

Для клиники «лазер» практически всегда означает **лазерную эпиляцию**. Открытое
перечисление всех процедур раздражает и тормозит запись.

Модель агента — Gemini Flash Lite (слабая), сама сленг→услуга не выведет; нужна
явная инструкция в промпте.

## Решение (2 компонента)

### Компонент 1 — Словарь бытовых названий + правило трактовки (промпт)

Новый блок в `services/agent/system-prompt.js`, сразу после правила
«ЕСТЬ ЛИ У НАС УСЛУГА — ТОЛЬКО ПО КАТАЛОГУ». Три части:

1. **Общий принцип.** Пациенты называют процедуры бытовыми/сокращёнными словами.
   Понимай их и переводи в конкретную услугу через `list_services`. Не заставляй
   пациента угадывать официальное название и НЕ вываливай весь список процедур.

2. **Словарь дефолтов (хардкод, PERI):** «обычно означает», не абсолют — итог всё
   равно сверяется с `list_services`, поэтому несуществующую услугу Мила не выдумает
   (старое правило каталога держит приоритет):
   - био → биоревитализация
   - губы → контурная пластика губ
   - фото → фотоомоложение (Lumecca)
   - ботокс / уколы красоты → ботулинотерапия
   - мезо → мезотерапия
   - чистка → чистка лица
   - лазер → чаще всего лазерная эпиляция (но есть и лазерное фотоомоложение Lumecca —
     неоднозначно, см. п.3)

3. **Неоднозначность.** Когда бытовое слово подходит под НЕСКОЛЬКО разных услуг
   каталога (напр. «лазер»):
   - если пациент повторный — сначала загляни в `get_client_visit_history`; если он
     раньше делал одну из подходящих процедур, веди именно её;
   - в ЛЮБОМ случае (в т.ч. первичный) подтверди ОДИН самый вероятный вариант
     да/нет-вопросом: «Вы имеете в виду лазерную эпиляцию?». НИКОГДА не открытый
     «какая именно процедура?» и не перечисление всех вариантов;
   - для однозначных слов (био, губы) — просто переводи и двигайся дальше, без
     лишнего подтверждения.

Экономия вызовов: `get_client_visit_history` зови только при реальной
неоднозначности И только для идентифицированного пациента.

### Компонент 2 — Новый инструмент `get_client_visit_history` (бэкенд)

`services/agent/tools/get-client-visit-history.js` — зеркалит
`list-client-bookings.js`, но возвращает ПРОШЛЫЕ визиты:

- schema: `get_client_visit_history`, без аргументов (телефон из `ctx.clientPhone`).
  Описание: «ПРОШЛЫЕ (уже состоявшиеся) визиты пациента — какие услуги делал раньше;
  помогает понять бытовое слово и подобрать услугу».
- `run(salonId, _input, ctx)`:
  - нет `ctx.clientPhone` → `{ visits: [], reason: 'no_phone' }`;
  - `identity.resolveYclientsClientId` → нет → `{ visits: [], reason: 'client_not_found' }`;
  - `salons` lookup; нет `yclients_company_id` → `{ visits: [], reason: 'no_yclients' }`;
  - `ycGetClientRecords(salon, ycClientId, { endDate: <сегодня по МСК> })`;
  - оставить ПРОШЛЫЕ, не удалённые, состоявшиеся (attendance !== -1),
    `datetime < nowMs`; сортировка по убыванию даты; лимит 10;
  - map → `{ datetime, services: [titles], staff_name }`; вернуть `{ visits }`.
- Регистрация в `services/agent/tools/index.js`.
