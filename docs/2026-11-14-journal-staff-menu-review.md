# Меню графика сотрудника: итог реализации и ревью, 14.11.2026

## Статус

Реализация завершена локально основным агентом по просьбе пользователя после
исчерпания квоты Kimi K3.1 Pro. По последующему разрешению пользователя код установлен на дев-стенд; штатные
миграции выполнены при запуске. См. `2026-11-14-journal-staff-menu-dev-deploy.md`.
Production не развёртывался.
730 тестов журнала проходят. Browser E2E и интеграционная проверка миграции на
PostgreSQL не выполнены: соответствующие MCP в сессии отсутствуют.

## Поведение

- Клик/касание заголовка сотрудника в дне или конкретного дня в неделе открывает
  меню. Работающий сотрудник: «Добавить перерыв», «Убрать рабочий день»;
  выходной: «Добавить рабочий день».
- Выходные сотрудники доступны после отключения «Только работающие». Сотрудник
  с локальным изменением графика остаётся доступен даже при включённом фильтре.
- Форма фиксирует сотрудника и дату; перерыв и рабочий день имеют начало/конец.
  Перерыв находится строго внутри одного рабочего интервала. Удаление дня
  требует подтверждения. Закрытие формы предлагает сохранить или отказаться.
- Изменение сохраняется локально; внешняя отправка — существующей кнопкой
  «Отправить в YClients». График учитывается в дне, неделе, календаре месяца
  и расчёте свободных окон. Статус отправки виден в заголовке.
- Постоянная кнопка «Изменения графика» показывает незавершённые изменения
  всех дат салона. Ошибку можно повторить или убрать локальную правку;
  перед её удалением перечитывается актуальный график YClients.
- Неопределённый результат не отправляется повторно. Владелец сначала
  подтверждает сверку через существующий интерфейс незавершённых операций,
  затем можно убрать локальную правку и загрузить действующий график.

## Исправления после первоначального ревью

1. Статус графика проходит из наложения через day/week в UI; failed-удаление
   рабочего дня не пропадает из интерфейса. Восстановление доступно независимо
   от даты и ранее закрытого окна отправки.
2. session_used больше не означает успех: форма остаётся открыта и объясняет,
   что новые значения не сохранены. Обычный повтор одинакового запроса
   возвращает тот же пакет; таймаут сохраняет ключ, двойной клик не дублирует запись.
3. Тестовый стенд загружает новый модуль меню. Добавлены тесты сервиса,
   маршрутов, YClients-адаптера, очереди, наложения, календаря и интерфейса.
4. Локальные изменения графика сериализованы с другими внешними изменениями
   журнала advisory lock салона. При failed/running-пакете того же сотрудника
   за день новая правка не принимается до разрешения предыдущей.
5. Перед внешней записью проверяются живой график, сотрудник, записи и занятые
   интервалы, а также локальные неотправленные записи. Pending-перенос/удаление
   не скрывает реально существующую запись от проверки конфликта.
6. Ошибка проверочного GET после успешного PUT — uncertain, даже если GET
   ответил 4xx. Такой результат нельзя ошибочно считать определённым отказом.
7. Возобновление обработчика после сохранённого done-шага восстанавливает
   кэш графика без повторного PUT.

## Безопасность и границы

- Маршруты под существующим auth и owner/admin; salonId и userId из авторизации.
  Чтение/вставки/восстановление scoped по салону, сотрудник проверяется в его списке.
- Идемпотентность локальной формы — session_id + request_hash; внешней операции —
  operation_id + request_hash. Pending-маркер записывается до внешнего эффекта.
- Полная длительность записей и их технические перерывы защищены от сокращения
  смены, включая переход через полночь в Europe/Moscow. Исходные записи не меняются.
- Официальный контракт проверен по сохранённой OpenAPI со страницы
  https://developers.yclients.com/: GET/PUT /company/{company_id}/staff/schedule,
  schedules_to_set/schedules_to_delete; busy_intervals допускает H:i:s.
  Синтетические контракт-тесты проверяют URL, query и payload. Live PUT не выполнялся.
- YClients не предоставляет compare-and-swap для графика: два чтения уменьшают,
  но не исключают гонку с изменением непосредственно в YClients между проверкой
  и PUT. Полной атомарности с внешней системой не заявляем.
- Сопутствующие изменения карточек, чата, лояльности и склада, существовавшие до
  задачи, сохранены. Реальные данные, сообщения, деньги и записи не изменялись.

## Миграция и выкладка

В backend/migrations.js добавлены nullable journal_outbox.schedule_key,
индекс (salon_id,schedule_key) и расширенный CHECK action со значением schedule.
Старые миграционные блоки защищены от повторного создания узких CHECK после v4.
Изменения идемпотентные, без backfill; ALTER CHECK может кратко блокировать таблицу.

Порядок выкладки: штатная миграция до старта нового обработчика/API, затем
новый backend и frontend вместе. Общие запросы очереди используют schedule_key.
Нельзя включать новый worker до миграции.

Откат: сначала остановить обработку/разрешить оставшиеся schedule-пакеты штатно,
затем откатывать код; колонку, индекс, CHECK и журнал операций оставить.
Старый worker не умеет исполнять шаг schedule — не отдавать ему такие пакеты.
По последующему разрешению выполнена выкладка на дев и штатная миграция.
Откат не выполнялся; подробности проверки — в отчёте установки.

## Проверки

Из backend:

```
npx jest journal --runInBand --silent
```

Итог: 28 наборов, 730 тестов прошли. Ранее при завершении Kimi было 11 падений;
они исправлены. В первом полном прогоне исправлена также ошибка нового
параметризованного теста адаптера. Предварительные прогоны из корня давали
предупреждения о дублирующихся package names; итоговый выполнен из backend
с проектным Jest config и Europe/Moscow.

Существующие тестовые mocks finance_operations печатают WARN; они были и до
задачи, не являются ошибками тестов или обращениями к рабочей базе.

`node --check` — 17 JS-файлов реализации, успешно.
`git diff --check` — успешно.

Не выполнены: browser E2E (Playwright MCP отсутствует), реальная миграция и SQL
интеграционные проверки (PostgreSQL MCP отсутствует), живая запись в YClients.
Мобильное приложение не менялось; mobile lint не запускался.
