# MAX: сервер бота программы лояльности

Реализовано 13.11.2026. В исходной конфигурации по умолчанию выключено.
По решению владельца сервисы ботов работают только на дев-сервере.
Первоначальная активация на production и последующий перенос описаны ниже.

## Текущее размещение: только дев-сервер

13.11.2026 MAX перенесён на дев `MyFinLandVPS`, рядом с Telegram-ботами.
Код: `/srv/loyalpro-max-bot/app`, отдельный пользователь `loyalpro`.
Node 22 закреплён копией бинарника `/srv/loyalpro-max-bot/node`, зависимости
скопированы в `app/node_modules` и не зависят от удаления релиза приложения.
Секреты и CA находятся рядом с `app`; файл окружения имеет права 0600.

- `loyalpro-max-bot.service`: enabled, Restart=always, RestartSec=5,
  StartLimitIntervalSec=0; запускается после `loyalpro-selectel-tunnel`.
- База остаётся прежней на Selectel: соединение через существующий туннель
  на `127.0.0.1:5441`. Регистрации, очередь и защита от повторных бонусов сохранены.
- `loyalpro-max-webhook-tunnel.service`: enabled, Restart=always; обратный SSH
  проброс production `127.0.0.1:3104` → dev `127.0.0.1:3104`. Подписка MAX
  `https://zumrudin.ru/max-loyalty/webhook` не меняется. На production только
  nginx и вход туннеля; обработчик бота выполняется на деве.
- На production MAX отключён (`disable --now`), установлен маркер
  `/srv/loyalpro-max-bot/MOVED_TO_DEV` и systemd condition в
  `loyalpro-max-bot.service.d/dev-only.conf`, запрещающий запуск при этом маркере.
- Telegram `mybot` и `birthday_bot`: active, enabled, Restart=always.
  Туннель БД также active/enabled с Restart=always.
- MAX не запускается из `backend/server.js`, webhook не монтируется в основном
  приложении. Единственная точка запуска — `backend/max-loyalty-server.js`.
  Выкладка основного приложения на production не запускает бот.

Systemd units в `backend/deploy/`. Для переустановки сначала подготовить
изолированный каталог, Node, зависимости, секреты, CA и SSH-ключ из unit;
затем `systemctl enable --now loyalpro-max-bot loyalpro-max-webhook-tunnel`.
При недоступности дева бот недоступен; резервный обработчик на production
намеренно отсутствует. Перезагрузка всего сервера для проверки не выполнялась.
Проверен перезапуск MAX и webhook-туннеля: после рестарта публичный health 200,
webhook без секрета 403. Перед коммитом прошли 81 unit/API/финансовый тест
и 9 интеграционных тестов на изолированном PostgreSQL (всего 90).
Секретные значения проверены на отсутствие в staged diff.

## Сценарий

### Исправление поиска существующего участника, 13.11.2026

Живая проверка обнаружила: `POST /company/{id}/clients/search` без `fields`
возвращает строки только с `id`. Проверка точного телефона ошибочно исключала
такую строку, а попытка создать существующего клиента завершалась `review` на
шаге `client_creating`. До карты и начисления выполнение не доходило.

В `services/max-loyalty/yclients.js` теперь явно запрашиваются `fields: ['id',
'phone']`; неполная идентификация в непустом ответе считается ошибкой, а не
отсутствием клиента. В `registration.js` добавлено узкое восстановление только
для `client_creating`: точное совпадение телефона и существующая карта нужного
типа позволяют завершить привязку с `welcome=false`. Неопределённый результат
создания карты/начисления таким способом не восстанавливается.

32 unit/API теста прошли. Два исправленных файла выложены, отдельный MAX-сервис
перезапущен, health 200. Read-only проверка восстановления с реальным ответом
YClients дала `done`, карта найдена, приветственное начисление отключено.
При проверке состояние production-регистрации не менялось, внешние записи
были запрещены. Пользователь завершает восстановление через `/start` и повторную
передачу контакта. Резервные файлы: `/srv/loyalpro-max-bot/backups/search-fields/`.

Аналог основного `/root/bot_project/bot.py`: `/start` → собственный контакт →
имя → дата рождения → клиент и карта YClients → 500 приветственных бонусов.
Карта существующего участника подключается сразу после подтверждения номера,
без повторной анкеты и без приветственного начисления. `/balance` и кнопка
«Бонусный баланс» показывают баланс и кешбэк; также доступны `/help`, `/cancel`.
Кешбэк берётся из программы «Программа лояльности», как в Telegram; пустое/нулевое
значение означает 5%. Тип карты — `salons.yclients_card_type_id`; если не задан,
ищется тип с названием `samosale` в этом филиале.

Дата рождения сохраняется в LoyalPro. Существующая дата клиента не затирается.
Отдельный Python-процесс поздравлений `birthday_bonus.py` здесь не дублируется:
новый ежедневный процесс начислений/рассылок не добавлен. Эта реализация покрывает
интерактивный бот регистрации и баланса, а не перенос админ-панели Python или
массовых рассылок. Нынешний MAX-аккаунт клиники в `gateway/` остаётся отдельным каналом.

## Размещение и конфигурация

Бот работает отдельным Node.js сервисом на дев-сервере. Отдельный Python-процесс и новая
зависимость не требуются. Один официальный бот на один салон в конфигурации
процесса; это не интерфейс управления несколькими ботами из админки.

| Переменная | Назначение |
| --- | --- |
| `MAX_LOYALTY_BOT_ENABLED` | Только `true` включает webhook и worker; иначе выключено |
| `MAX_LOYALTY_BOT_SALON_ID` | ID салона в LoyalPro, заданный оператором сервера |
| `MAX_LOYALTY_BOT_TOKEN` | Токен официального бота из кабинета MAX; только в секретном окружении |
| `MAX_LOYALTY_BOT_WEBHOOK_SECRET` | Случайный секрет: 32–256 символов `A-Za-z0-9_-` |
| `MAX_LOYALTY_BOT_WEBHOOK_URL` | Для setup-скрипта: публичный HTTPS URL с путём `/max-loyalty/webhook` |
| `NODE_EXTRA_CA_CERTS` | При необходимости путь к проверенному PEM доверенного CA Минцифры для исходящего HTTPS |

Используются существующие учётные данные YClients выбранного салона. Токен MAX
передаётся в `Authorization`, секрет вебхука — в `X-Max-Bot-Api-Secret`, не в URL.
Нельзя отключать проверку TLS. MAX API: `https://platform-api2.max.ru`.
Публичный вход — HTTPS/443 с доверенным сертификатом; за reverse proxy запрос
идёт в backend на `POST /max-loyalty/webhook`.

## Данные, очередь и начисления

В `backend/migrations.js` добавлены три таблицы:

- `max_loyalty_sessions`: состояние анкеты и связь MAX user ID с клиентом;
- `max_loyalty_events`: надёжная очередь событий и подготовленных ответов;
- `max_loyalty_registrations`: журнал создания клиента/карты/начисления по телефону.

Везде есть `salon_id`. Номер салона никогда не берётся из события, параметра
ссылки или сообщения. Индексы/ключи включают салон. Миграция additive/idempotent:
`CREATE ... IF NOT EXISTS`; старые таблицы не меняются и не переписываются.
Ожидаемая нагрузка — создание пустых таблиц/индексов и краткие metadata-locks.
Порядок выкладки: запуск отдельного сервиса на деве (MAX-миграция и worker) → регистрация webhook.
При отсутствии таблиц приём возвращает 503, чтобы MAX мог повторить доставку.

Webhook проверяет секрет, принимает только личные сообщения человека и события
start/stop. Контакт принимается только при корректном HMAC-SHA256 по VCF и
совпадении владельца с отправителем; пересланные контакты и произвольный текст
с номером не авторизуют клиента. В базе сохраняется нормализованное событие,
а не исходный MAX payload. После обработки тело события и ответ очищаются,
ключ дедупликации остаётся. Незавершённая анкета истекает через сутки.
Повторная привязка подтверждённого телефона к другому MAX ID отзывает прежнюю
MAX-сессию этого телефона только внутри салона.

200 возвращается после записи события в PostgreSQL; внешние вызовы выполняет
worker. События одного пользователя идут последовательно; одна ошибка не
блокирует остальных. Между ответами одному пользователю выдерживается минимум
600 мс. До шести попыток с задержками 5–300 секунд; после исчерпания попыток
обработки пользователю готовится сообщение о недоступности. Неотправленный
ответ после исчерпания попыток получает `failed`.

Session-level PostgreSQL advisory lock `(18342, salon_id)` исключает параллельную
обработку этим worker в нескольких процессах. Изменение анкеты и подготовка
ответа коммитятся одной транзакцией. Каждый необратимый запрос YClients имеет
сначала сохранённое намерение (`client_creating`, `card_creating`, `bonus_sending`).
После неоднозначного результата или перезапуска на таком шаге — `review`,
никаких автоматических повторных созданий/начислений. `uncertainStage` хранит
шаг для разбирательства. Обычные сбои чтения YClients повторяются и никогда не
трактуются как «клиента/карты нет».

Приветственные бонусы выдаются только карте, созданной этим выполнением:
проверяется тип и сгенерированный номер. Уже существующая карта, включая карту
Telegram-клиента, не даёт повторных 500. Успешная операция и локальный журнал
синхронизируются однократно; финансовые строки пишет существующий `finance-ops`.
Баланс учитывает `BONUS_LEDGER_PRIMARY` через `bonus-ledger`; дробный баланс
YClients сохраняется в прежнем режиме.

Граница гарантии: старый Python Telegram-бот не использует этот advisory lock.
Проверка существующей карты защищает обычный переход из Telegram в MAX, но
нельзя обещать атомарность двух строго одновременных ПЕРВЫХ регистраций через
независимые Python/Node процессы. Перед открытием двух каналов для такого
сценария нужна общая блокировка/единый сервис выдачи карт в обоих ботах.
На запуске проверить совместный сценарий; для строгой гарантии сначала
перевести выдачу карты Telegram в общий сервис. Python-репозиторий в этой
поставке не менялся.

Отправка ответов MAX — at-least-once: при потере ответа HTTP возможен повтор
текста. Этот повтор не запускает регистрацию или начисление заново.

## Подключение после модерации

1. Настроить секретное окружение, салон и YClients; проверить цепочку TLS.
2. Выполнить разрешённую выкладку и миграцию. Миграцию/рестарт production делать
   только после отдельного разрешения владельца.
3. Из каталога `backend` проверить токен и текущие подписки:
   `node scripts/max-loyalty-setup.js`. Это read-only обращение к MAX; токен,
   профиль и адреса подписок не выводятся.
4. После разрешения подключения выполнить
   `node scripts/max-loyalty-setup.js --apply`. Скрипт устанавливает команды через
   `PATCH /me/commands`, создаёт подписку на `bot_started`, `bot_stopped`,
   `message_created` и проверяет её наличие. Пациентские сообщения не отправляет.
   Если уже есть другой webhook URL, скрипт останавливается: второй обработчик
   нельзя подключать параллельно. Автоматической регистрации подписки при
   старте backend нет.
5. На согласованном тестовом клиенте проверить передачу собственного номера,
   регистрацию, повторный `/start`, баланс и существующую Telegram-карту.
   Проверки с созданием клиента/карты, реальным начислением и отправкой сообщений
   требуют отдельного разрешения. Пока бот на модерации, эти проверки не выполнены.

Не назначать токен другого бота старым сохранённым сессиям без отдельной миграции.
Откат: `MAX_LOYALTY_BOT_ENABLED=false` и разрешённый перезапуск. Таблицы оставить:
их удаление теряет защиту от повторных начислений. Для полной остановки доставки
событий отдельно снять подписку в MAX; иначе отключённый endpoint возвращает 503.

## Диагностика и восстановление

Логи `MaxLoyalty` содержат только внутренний ID события, фазу и результат
`retry/failed`. Исходные ошибки HTTP/SQL, токены, телефоны, анкеты и сообщения
не логируются. Сводку можно читать через PostgreSQL MCP, без выгрузки персональных
данных (параметр `$1` — разрешённый салон):

```sql
SELECT status, count(*) FROM max_loyalty_events
WHERE salon_id=$1 GROUP BY status;

SELECT state->>'stage' AS stage, state->>'uncertainStage' AS uncertain_stage, count(*)
FROM max_loyalty_registrations WHERE salon_id=$1 GROUP BY 1,2;
```

Для `review` сначала проверить фактического клиента, карту и историю начисления
в YClients. Нельзя просто удалить журнал или вернуть `bonus_sending` в предыдущую
стадию: неизвестный запрос мог исполниться. Исправление журнала/доначисление —
отдельная разрешённая операция по установленному результату, после неё пользователь
может снова пройти `/start` и подтвердить номер. Для временного сбоя чтения или
доставки повтор команды создаёт новое событие; журнал регистраций защищает эффекты.
