# Электронное подписание документов с пациентами через F.Doc — исследование

Дата: 24.10.2026. Источники: OpenAPI 1.2 `https://demo.fdoc.ru/spec-docs/` (47 путей + раздел шаблонов, 140 схем), PDF базы знаний F.Doc (`/swagger/schema_fdoc.pdf`, `/swagger/webhooksPackageStatus.pdf`, `/swagger/webhooksDocumentCreationInfo.pdf`, `/swagger/webhooksMessageDeliveryStatus.pdf`), сайт fdoc.ru (тарифы, интеграции, галерея шаблонов), дев-БД `loyalpro_test` (салон 1), код LoyalPro.

## 1. Вывод

Сделать можно. Техническая сложность — средняя: API стандартный (HTTPS + JSON, русскоязычная документация, есть демо-стенд без юридически значимых подписей), есть именно та функциональность, которую хочет клиника (шаблоны с подстановкой параметров, комплекты документов, маршрут «клиника → пациент», статусы, готовый PDF со штампом). Демо-стенд отвечает с дев-сервера (Хельсинки) за 0,3 с, гео-блокировки нет.

Главные трудности не в коде, а в данных и в праве:

1. У нас нет паспортных данных пациентов (ни в `clients`, ни в YClients). Их придётся либо собирать и хранить у себя (обязательства по 152-ФЗ), либо оставить сбор F.Doc: пациент вводит их сам в «окне клиента», в том числе фотографирует паспорт, а поля заполняются распознаванием.
2. ИДС (информированное добровольное согласие на медицинское вмешательство) по 323-ФЗ ст. 20 в электронном виде подписывается пациентом УКЭП или ПЭП через ЕСИА (Госуслуги) и медработником — УКЭП. Обычная SMS-ПЭП для ИДС не подходит. У F.Doc для этого отдельный «медицинский контур» (ЕСИА + КЭП организации) и отдельный тариф. Договор и согласие на обработку ПДн SMS-ПЭП подписывать можно.
3. Акт оказанных услуг — таблица с переменным числом строк, а параметры шаблона F.Doc скалярные (повторяющихся блоков нет). Акт проще собирать самим в PDF (библиотеки и шрифты в проекте уже есть) и отправлять как готовый файл.

Оценка MVP (договор + согласие ПДн при первом визите, акт по записи после процедуры, статусы, PDF в архив): 12–18 рабочих дней разработки плюс календарное время онбординга у F.Doc (заявка → установочная встреча → демо-доступ → прод-доступ, регистрация IP для вебхуков, тариф).

## 2. Что такое F.Doc и как подписывает пациент

- Сервис электронного подписания с физлицами, правообладатель ЗАО «ЦЦС», 63-ФЗ. Основной фокус — медицина (клиники, стоматология), есть готовые интеграции с МИС/CRM (1С, Битрикс24, amoCRM и др.), личный кабинет, «виртуальный принтер», REST API.
- Пациент: получает SMS со ссылкой, открывает «окно клиента» в браузере телефона, просматривает документы, вводит одноразовый код и подписывает (ПЭП). Ссылка клиента бессрочная, её можно переотправить (`POST /portal/api/v1/permalink/send`). В медицинском контуре — ПЭП через ЕСИА и КЭП клиники.
- Клиника: подписывает автоматически при отправке (`operatorAutoSign: true`) или кнопкой в «окне сотрудника» (ссылка живёт 30 минут). ФИО сотрудника, под чьим токеном идёт вызов, ложится на штамп и в журнал.
- При первом подписании F.Doc сам оформляет с пациентом «Согласие на пользование сервисом F.Doc» (вебхук `CreateDocument`, тип `AGREEMENT`), есть и отзыв согласия (`REJECTION`), и соглашение об аннулировании (`ANNUL_AGREEMENT`).

Тарифы по странице fdoc.ru/tariffs на 24.10.2026 (уточнять у F.Doc):

| Тариф | Цена | Объём | API |
|---|---|---|---|
| Стандарт | 21 900 ₽/год | 600–12 000+ док./год, до 20 пользователей | нет (только готовые модули) |
| Профи | 31 900 ₽/год | 600–12 000+ док./год, до 30 пользователей, верификация по паспорту | да |
| Старт для медорганизаций | 100 000 ₽ | 3 500 документов, ПЭП + КЭП, ЕСИА, интеграция с МИС | да |
| Индивидуальный | по запросу | под объём и ИТ-инфраструктуру | да |

SMS входят в тарифы. Для начала работы: заявка на сайте → установочная встреча → данные демо-стенда (`https://demo.fdoc.ru`) → переход на прод по запросу к сотруднику F.Doc.

## 3. Что даёт API (OpenAPI 1.2)

Базовые адреса: `/paperless-gateway/api/v1/…` (основной шлюз), `/paperless-gateway/portal/api/v1/…` (статусы, PDF, ссылка клиенту), `/additional-opengate/api/v1/…` (распознавание, верификация, КЭП для медицины).

### Аутентификация
- `GET /api/v1/verifyApiKey?apiKey=` (Basic: логин:пароль приложения) → `corpId`. Один раз, сохранить.
- `POST /api/v1/operator/accessToken` `{apiKey, grant, grantType: password|refreshToken|techAccount, app, corpId, employeeInitiator?}` → `accessToken` (живёт 3 минуты) + `refreshToken`. Все рабочие вызовы — `Authorization: Bearer <accessToken>` сотрудника. `techAccount` — техническая учётная запись организации; `password` — учётка конкретного сотрудника (его ФИО попадёт на штамп). Сотрудников можно регистрировать через `POST /api/v1/employees` (до 30 за раз, логин/пароль уходят им на почту и по SMS).

### Шаблоны документов
- Шаблон — DOC/DOCX/XLS/XLSX до 10 МБ с кодами параметров прямо в тексте: DOCX — `<<[code]>>` (пример `<<[client]>>`), XLSX — `&=$code`. Код: латиница и цифры, с буквы, до 16 символов; одинаковые коды — одно поле.
- `POST /api/v1/template` (создать с параметрами), `PUT` (править), `GET /api/v1/template?templateExternalId=` (параметры: `id`, `code`, `name`, `type`, `required`, `optionsName`, `autofillByPhoto`, условия и дочерние поля), `GET /api/v1/corp/templates` (список организации), галерея типовых шаблонов (`/template/library/*`), превью, экспорт/импорт.
- Типы параметров: текст `INPUT`/`TEXTAREA`; паспортные `PASSPORT` («1234 567890»), `AUTHORITY` (кем выдан), `AUTHORITY_CODE` («123-456»), `FIO`, `BIRTH_PLACE_NAT`, `BIRTH_DATE`, `PASSPORT_ISSUE_DATE`, `GENDER` — для них есть `autofillByPhoto` (пациент фотографирует паспорт в окне клиента, поля заполняются); `DATE`, `EMAIL`, `PHONE`, `ADDRESS` (подсказки ФИАС), `INN_FL`, `SNILS`, реквизиты юрлиц; `SELECT`, `MULTISELECT`, `RADIOBUTTON`, `YES_NO`, `CHECKBOX`.
- Значения, введённые пациентом, после подписания читаются назад: `GET /api/v1/template/values?documentGuid=` и `POST /api/v1/template/params`.
- Шаблоны по медицине в галерее F.Doc: договоры на медуслуги (с физлицом, представителем), ИДС, согласие на обработку ПДн, планы оказания услуг, акты оказанных медуслуг, отказ от вмешательства.

### Отправка на подписание
`POST /api/v1/document/withSigners`:
- `documents[]` — готовые файлы в base64 (doc, docx, xls, xlsx, pdf, png, jpg), до 15 МБ файл, до 50 МБ и 10 файлов на комплект, `unsignExpiredDate`, `stampView`.
- `documentTemplates[]` — `{id шаблона, name, autoSendToFill, templateParams: [{id, value | values, isNotEditableByClient}], templateFillers}`. Предзаполненные нами поля можно закрыть от правки пациентом. Форматы дат: `yyyy-MM-dd`, `dd.MM.yyyy` и др. При шаблонах первым в `signers` обязан стоять клиент.
- `package` — `{id (наш UUID), name, objectId (наш внешний объект, например id записи), needIdentification, identificationType, signers: [{type: corp|client, priority, operatorAutoSign, name, phone, id}]}`.
- Ответ: `url` окна сотрудника (30 минут) и `documentsFromTemplates[{templateId, documentId}]`.
- Прочее: аннулирование `POST /api/v1/employee/decline/package` (`DECLINE` / `DECLINE_PAPER`), окно сотрудника по клиенту/телефону/объекту `GET /api/v1/document?idType=package|client|object|clientPhone|employee|corporation`, запрос документов у клиента (`/package/by/client`), платёжная ссылка к комплекту.

### Статусы и вебхуки
- Статусы комплекта/документа: `PREPARED`, `CREATED_FROM_TEMPLATE`, `WAIT_FILL`, `SEND_LINK`, `WAIT_SIGN`, `SIGNED` (не конечный: может стать `ANNULED`), `ANNULED`, `CANCELED` (пациент отказался), `SIGNED_PAPER`, `SIGNING_EXPIRED` → `DELETED`, `ERROR_SEND`/`ERROR_SIGN`/`ERROR_ANNUL`.
- Опрос: `GET /portal/api/v1/document/status?id&idType&corpId`, пакетно до 10 — `POST /portal/api/v1/documents/status`, по подписантам — `…/workflow/signing/status`. В спеке у опроса `security: None`, но демо-стенд отвечает 401 без ключа — авторизация нужна, уточнить какая.
- Вебхуки: `PUT /api/v1/corp/webhooks` `{apiKey, channelTypeCode: 'API', events: [{code, url}], sendIntermediateStatuses}`. События: `SetStatus` (статус комплекта), `SetStatusPackageByClient`, `SetStatusMessage` (доставка SMS; на медицинском контуре НЕ работает), `CreateDocument`. Тело `SetStatus` — POST JSON `{employeeId? | clientId?, documentIds[], packageId, actionStatus?, status, statusName, comment?}`; заголовок `Authorization` передать нельзя — токен кладётся в URL (`…/webhook?key=…`); перед подпиской F.Doc регистрирует IP-адрес источника и проводит совместное тестирование. Нужны оба IP (дев в Финляндии, прод на Beget).
- Результат: `GET /portal/api/v1/document?packageGuid&documentGuid` → PDF со штампом; архивы за период/по id (`/corp/archives`, ссылка живёт 1 час).

### Дополнительно
- `POST /additional-opengate/api/v1/docs/by/client/recognize` — распознавание паспорта по фото (base64 до 6 МБ): серия, номер, дата выдачи, кем выдан, код подразделения, ФИО, дата и место рождения, пол, адрес; признаки уверенности и антиспуфинг (фото с экрана, распечатка).
- `POST …/identification/clients/status` — проходил ли клиент верификацию (по паспорту / ЕСИА). `POST …/person/identity-documents` — данные ДУЛ персоны, если она дала организации доступ.
- `POST …/med-docs/sign` — подпись документа КЭП сотрудника (`EMPLOYEE`) и/или организации (`RESPONSIBLE`), `ATTACHED`/`DETACHED`, результат вебхуком, скачивание `…/med-docs/signed`; для ЕГИСЗ. Доступно не всем организациям (403).
- `GET /api/v1/corp/tariff/active/info` — остаток документов в тарифе (для предупреждения в админке).
- Расхождения спеки и схемы интеграции: на диаграмме есть `POST /api/v1/document` (без маршрута) и `POST /api/v1/template/documents`, в OpenAPI их нет — пользоваться задокументированными `withSigners` и `template/params`.

## 5. Как это может выглядеть (MVP)

Бэкенд:
- `services/fdoc/client.js` — обёртка API: ключ → `corpId`, техучётка → токен с кэшем на салон и обновлением по истечении (3 минуты), единый разбор ошибок, таймауты, лог без ПДн.
- `services/edocs/` — чистые модули: сопоставление наших полей с кодами параметров шаблона (`fio`, `birth_date`, `passport`, `issued_by`, `authority_code`, `issue_date`, `address`, `phone`, `contract_no`, `contract_date`, …), сборка акта из записи (услуги с галочками, количество, суммы из `cost_to_pay`, врач, дата), рендер PDF акта, маппинг статусов F.Doc в наши.
- Таблицы: `edoc_settings` (на салон: ключ, техучётка, `corpId`, код приложения, карта шаблонов), `edoc_packages` (салон, клиент, запись, наш UUID = `package.id`, статус F.Doc, кто отправил, снимок параметров без паспорта), `edoc_documents` (`documentId`, статус, ключ PDF в S3), `edoc_events` (журнал вебхуков). Паспортные данные — отдельная таблица `client_identity` только если владелец решит хранить их у нас.
- `routes/edocs.js` (`/api/edocs`, owner/admin): клиенты и их данные, список шаблонов из F.Doc (кэш 60 с), отправка пакета, статусы, ссылка в окно сотрудника, скачивание PDF, аннулирование. `routes/fdoc-webhook.js` без JWT: токен в URL + проверка IP, идемпотентная запись статуса, ответ 200 сразу. Плюс крон-опрос статусов для незакрытых пакетов (страховка на случай потерянного вебхука).

Фронт: страница «Документы» (список пакетов и статусы), в карточке клиента — блок «Документы» с кнопкой «Оформить первичный пакет» (проверка/дополнение ФИО, даты рождения, паспорта вручную или по фото через распознавание; выбор шаблонов; предпросмотр; отправка), в записи после процедуры — кнопка «Акт» (галочки услуг → PDF → отправка). Пациент получает SMS, подписывает на телефоне; статус подтягивается вебхуком; подписанный PDF ложится в S3 и виден в карточке.

Рекомендации по спорным местам:
- Акт — свой PDF (как справки), а не шаблон F.Doc: таблица услуг в шаблоне не выражается.
- Договор и согласия — шаблонами F.Doc: клиника правит текст сама в кабинете F.Doc, а недостающие поля (паспорт, адрес) может заполнять пациент с фото паспорта (`autoSendToFill` + `autofillByPhoto`). Так паспорт можно не хранить у нас вовсе, а при необходимости читать назад через `template/values`.
- Подписант от клиники для MVP — техучётка (один штамп), персональные учётки администраторов — потом.
- Проверка: чистые модули под `jest`, живой скрипт на демо-стенде (`scripts/edocs-e2e.js`) по образцу остальных e2e.

Оценка трудозатрат (рабочие дни чистой разработки, в стиле проекта):

## 6. Риски и открытые вопросы

Владельцу:
1. ИДС: оформлять электронно через медицинский контур F.Doc (ЕСИА у пациента + КЭП клиники, отдельный тариф) или оставить на бумаге, а электронно подписывать договор, согласие ПДн и акты? Правовую позицию подтвердить у юриста (323-ФЗ ст. 20 ч. 7).
2. Хранить ли паспортные данные в LoyalPro (152-ФЗ: шифрование, доступ, срок хранения, цель) или оставить их в F.Doc, а у нас держать только ФИО, дату рождения, телефон и номер договора.
3. Кто ставит подпись от клиники — техническая учётка (один штамп) или каждый администратор под своим именем.
4. Приемлемо ли, что на каждый акт пациент получает SMS и вводит код. Альтернатива — подписывать в клинике на планшете по ссылке клиента (ссылка бессрочная; допустимость такого сценария уточнить у F.Doc).
5. Тариф и контур: API только с «Профи» и выше; медицинский контур — индивидуально; наш объём ~6 тыс. документов в год.

F.Doc (на установочную встречу):
1. Авторизация опроса статусов (в спеке `security: None`, стенд отвечает 401).
2. Что такое «согласие на электронное подписание, созданное на стороне Партнёра» (ошибка 500 у `permalink/send`): настройка организации или документ, и как его фиксировать нам.
3. Регистрация двух IP (дев и прод) для вебхуков, формат токена в URL, повторы при недоставке.
4. Доступность распознавания паспорта, `autofillByPhoto`, медицинского контура и `med-docs/sign` для нашей организации и в каком тарифе.
5. Поведение `unsignExpiredDate` → `SIGNING_EXPIRED` → `DELETED`: срок и возможность продления.
6. Галерея медицинских шаблонов: можно ли взять договор/ИДС/согласие как основу и править под клинику.

Технические готчи для реализации:
- `accessToken` живёт 3 минуты — обновлять перед каждой серией вызовов; `refreshToken` ротируется при каждом вызове.
- `templateParams[].id` — числовой и свой у каждого шаблона: перед отправкой читать `GET /api/v1/template` и сопоставлять по `code`; при правке шаблона в кабинете F.Doc id могут измениться — кэш с инвалидацией.
- Не больше 10 файлов и 50 МБ на комплект; PDF актов держать компактными.
- Вебхук без заголовка авторизации — секрет в URL и allowlist IP, обработчик идемпотентный (повторы при недоставке).
- Качество данных: ФИО одной строкой у 89 % карточек (разбор — `utils/person-name.js`), 20–25 % пришедших без даты рождения — форма проверки данных перед отправкой обязательна.
- Мультисалон: ключи, техучётка и шаблоны — на салон; у второго салона своя организация в F.Doc.

## 7. Что понадобится

- От F.Doc: заявка и установочная встреча; демо-доступ (API Key, техническая учётная запись, код приложения `app`); регистрация IP и совместный тест вебхуков; затем прод-доступ и тариф.
- От клиники: тексты договора, согласия на обработку ПДн, ИДС и акта в DOCX с согласованными кодами параметров (можно взять из галереи F.Doc); решения по пунктам 1–5 выше; реквизиты организации для шаблонов.
- От нас: модуль из раздела 5, переменные окружения/настройки салона, тесты, живой скрипт на демо-стенде, runbook переключения на прод.
