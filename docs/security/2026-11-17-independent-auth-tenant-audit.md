## Подтверждённые дефекты

### A1 — HIGH: чужой клиент в назначении домашнего ухода

`backend/routes/home-care.js:461–497` создаёт назначение с серверным salonId, но принимает client_id без проверки принадлежности. PUT `:502–529` также разрешает чужой client_id. `backend/migrations.js:131–135` содержит обычный FK по id, без составной границы салона. Чтение `home-care.js:295–300,311–323,447–457` ограничивает салон назначения, но присоединяет клиента только по id. В результате сотрудник салона A, включая специалиста, знающий/угадавший числовой id клиента B, может создать собственное назначение и прочитать имя/телефон B. POST также вызывает push для переданного клиента (`:22–38,497`); реальная отправка не проверялась.

Исправление первым: на POST/PUT проверять клиента и запись в текущем салоне, атомарно с записью; запретить побочные эффекты при отказе; ограничить JOIN и UPDATE салоном. Затем отдельно проверить существующие связи и добавить составные ограничения БД с миграционным планом. Негативный тест: чужой client_id → 404/400, никаких INSERT/UPDATE/push.

### A2 — HIGH: постоянная публичная ссылка на вложение чата

`backend/server.js:118–123` выдаёт frontend/uploads через express.static до mountRoutes. Gateway по умолчанию сохраняет вложения туда (`gateway/config.js:15–16`). Проверки пользователя и салона при скачивании нет. Известный URL работает без сессии и с токеном другого салона. Случайное имя (`gateway/lib/media.js:25–26`) затрудняет угадывание, но не ограничивает доступ после распространения ссылки; срок действия/отзыв не предусмотрен. Содержимое реальных файлов не запрашивалось; возможная чувствительность зависит от вложения.

Исправление: приватное хранилище, проверка владения файлом по серверному салону, защищённый download или короткоживущая подпись после проверки доступа. Учесть nginx/CDN, previews и загрузки провайдерами: закрытие только Express недостаточно, если edge выдаёт файлы напрямую. Публичные маркетинговые материалы отделить от приватных вложений.

### A3 — MEDIUM: межсалонная запись при синхронизации категорий

`backend/services/home-care.js:60–61` обновляет goods_sale_items по yclients_goods_id без ограничения через родительский goods_sales.salon_id. Исходный SELECT ограничен салоном, UPDATE — нет. При совпадающем внешнем id у двух салонов синхронизация A меняет категорию B. Достижимо через `routes/home-care.js:209–214` и фоновые задания. Совпадения в реальной БД не проверялись; подтверждена неограниченная запись, а не факт порчи production.

Исправление: UPDATE … FROM goods_sales с gsi.sale_id=gs.id AND gs.salon_id=текущий салон. Тест с одинаковым внешним id в двух салонах: меняется только A.

### A4 — MEDIUM: обязательная смена пароля обходится прямым API

`backend/routes/auth.js:94–107` выдаёт полноценную сессию даже при must_change_password=true. `backend/middleware/auth.js:28–45` не загружает и не проверяет флаг. Ограничение интерфейса не предотвращает прямой запрос с временным паролем и полученным токеном. Требуется уже знать временный пароль; это не вход без учётных данных.

Исправление: серверный режим ограниченной сессии до смены пароля; разрешить только необходимые auth endpoints. Проверить все роли и прямые API-запросы.

### A5 — MEDIUM: recovery CLI не отзывает сессии

`backend/reset-password.js:43–46` меняет пароль без удаления sessions. Ранее выданный украденный токен остаётся рабочим до истечения (обычно до 7 дней), если оператор сбрасывает пароль этим скриптом. Обычные операции смены пароля/роли в веб-интерфейсе имеют отзыв сессий; дефект относится именно к CLI. Дополнительно CLI принимает пароль в argv и выводит его (`:52,67–68`).

Исправление: транзакция изменения пароля и отзыва всех сессий; ввод секрета без argv и без печати. Проверка CLI в этом аудите статическая, скрипт не запускался.

## Проверенные защиты и ограничения

- Staff auth сверяет действующую сессию, текущие роль/салон, активность пользователя и салона. JWT из query не принимается.
- В проверенных clients, patient-portfolio, portfolio, chat, edocs и medical-cert маршрутах подтверждённого прямого межсалонного IDOR не найдено. Это не распространяется на найденную цепочку home-care.
- Mobile auth связывает JWT, сессию, клиента, телефон и серверный MOBILE_SALON_ID. Mobile home-care дополнительно проверяет clientId+salonId; найденная staff-цепочка не доказывает mobile bypass.
- Проверки Telegram contact/OTP и отзывов сессий выполнены на mocks. Живой OTP, реальные ограничения БД и внешний периметр здесь не тестировались.
- Дополнительная рекомендация: F.Doc webhook не имеет прикладного rate limit перед поиском секрета в БД; проверить edge limits и добавить ограничение/объединение повторных refresh. Это риск доступности, не установленный обход авторизации.
- Prefix allowlists желательно проверять по границе сегмента; реально доступного привилегированного маршрута с коллизией префикса не найдено.
