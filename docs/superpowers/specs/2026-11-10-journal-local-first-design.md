# Журнал записи: локальная работа и фоновая отправка в YClients — дизайн

Дата: 10.11.2026. Статус: реализовано на деве 10.11.2026 (план 2026-11-10-journal-local-first.md), не в git.
Предыдущие документы модуля: `2026-11-08-appointment-journal.md`, `2026-11-08-journal-payments.md` (раздел 09.11 — оплата через POST sale/payment).

## Зачем

Сейчас журнал работает «YClients-первым»: открытие дня — десятки живых запросов (график каждого мастера, записи ±1 день), поиск окон — ещё столько же, создание ждёт YClients, оплата с отметкой прихода — 5–7 с с проверками. Владелец хочет: форма создания / редактирования / оплаты закрывается сразу, без задержек и без текстов про сверку с YClients; в YClients данные уходят фоном, один пакет на одно открытие формы.

Решения владельца (10.11.2026):
- сбой фоновой отправки — красная пометка на карточке «Не передано в YClients: причина», правит человек, система сама ничего не меняет;
- ускоряется и чтение (день, окна), и запись;
- подход A: своя база + очередь отправки.

«Один раз» означает один пакет на сессию формы. В YClients это несколько вызовов подряд (создать запись → списать бонусы → отметить приход → оплатить кассу → перечитать для сверки): одним HTTP-запросом YClients это не принимает.

## Не цели

- LoyalPro не становится основной CRM: YClients остаётся главной системой (онлайн-запись, Мила, касса, уведомления). Изменения, сделанные в YClients, приходят к нам вебхуками и сверкой; спора «чья версия правее» нет — правее YClients.
- Нет офлайн-режима браузера.
- Нет автоматического разрешения конфликтов (перенос на другое время, повтор оплаты после неясного исхода).

## 1. Чтение из локальных данных

### 1.1 Записи

Источник — существующая таблица `records` (`raw_payload` = полная запись YClients), её уже пополняют вебхуки (`upsertRecordFromYc`) за секунды. Журнал перестаёт звать `GET /records` при открытии дня и поиске окон.

Копия сейчас неполна: на 10.11 не хватает до 5 из 13 будущих записей в день — созданных 11.10–01.11, в окно потери данных Beget (вебхуки по ним не повторялись, ночная сверка смотрит только `changed_after −2 дня`). Поэтому:
- разовый догон: `/records` за сегодня−1 … +120 дней, апсерт тем же `upsertRecordFromYc` (источник `journal_mirror`);
- сверка зеркала: каждые 10 мин окно сегодня … +14 дней, раз в ночь сегодня … +120. Запись есть у нас, но нет в выдаче YClients за её день → один `GET /record`; удалена → помечаем как удалённую тем же путём, что вебхук `delete`. Пропажа без подтверждения ничего не удаляет;
- статус свежести: время последней успешной сверки по салону. Старше 30 мин — в шапке журнала «Данные YClients обновлены ЧЧ:ММ» (без блокировки работы).

### 1.2 Графики мастеров

Новая таблица `journal_staff_schedule (salon_id, staff_id, date, is_working, slots jsonb, fetched_at)`, PK `(salon_id, staff_id, date)` — слоты целиком, с перерывами (существующая `staff_schedule` хранит только начало/конец и только прошлый/текущий месяц — для журнала не годится, её не трогаем). Фоновое обновление каждые 30 мин: сегодня … +60 дней, один запрос `/schedule/{cid}/{staff}/{from}/{to}` на мастера.

### 1.3 Справочники

Сотрудники, management-каталог услуг, ресурсы, кассы (`account_id`, название, наличные/безнал) и правило лимита бонусов — кэш в БД (`journal_reference_cache (salon_id, kind, payload jsonb, fetched_at)`), обновление раз в 30 мин и по кнопке «Обновить» журнала. Лимит бонусов: процент от чека из настроек типа карты YClients; если прочитать нельзя — форма показывает баланс без лимита, а окончательно сумму проверяет YClients при отправке (отказ → пометка).

### 1.4 Наложение несохранённого

День = зеркало + наложение пакетов очереди со статусом `queued | running | failed` (раздел 2): новая запись видна сразу (временный ключ `L<id пакета>`), правка/отмена — поверх зеркальной версии, оплаты — в счёте визита. Наложение пропадает, когда пакет `done` и вебхук принёс запись (у пакета есть `yclients_record_id`).

Поиск окон (`slotsFor`) считает по зеркалу + наложению + кэшу графиков и ресурсов — та же функция, другие входы.

## 2. Запись: пакет на сессию формы

### 2.1 Сессия формы

Браузер копит действия, сделанные за одно открытие формы: создание или правка записи, отмена/подтверждение, оплаты бонусами и в кассу (с отметкой прихода), удаление оплаты. Закрытие формы («Сохранить», «Оплатить», «Готово», крестик после изменений) — один `POST /api/journal/sessions` с `sessionId` (UUID) и списком действий. Сервер:
1. проверяет по локальным данным: окно свободно, сотрудник и услуги доступны, суммы не больше остатка к оплате, бонусы не больше баланса/лимита, права роли;
2. в одной транзакции пишет пакет в `journal_outbox` и отвечает 200 — без единого обращения к YClients;
3. повтор того же `sessionId` — тот же ответ (идемпотентность).

Отказ проверки (время уже занято по локальным данным, сумма больше остатка) — сообщение в форме сразу, как сейчас; форма не закрывается.

### 2.2 Очередь `journal_outbox`

Строка = пакет: `id, salon_id, session_id UNIQUE, user_id, record_key` (yclients id или `L<id>`), `yclients_record_id, status (queued|running|done|failed), steps jsonb, failed_step, error_code, error_text, attempts, next_attempt_at, created_at, updated_at`.

Шаг: `{kind, params, state: pending|done|failed|uncertain, result}`; виды — `create`, `update`, `cancel`, `confirm`, `pay_bonus`, `arrive`, `pay_account`, `remove_payment`. Порядок внутри пакета фиксирован кодом: запись → бонусы → отметка прихода → касса → удаления оплат (порядок, проверенный живым прогоном 09.11).

### 2.3 Фоновый обработчик

- Тик 2 с; по салону — один пакет за раз (тот же advisory-замок `17291`, что у текущих записей и оплат). Пакеты одной записи — строго по `created_at`; новый пакет записи ждёт завершения предыдущего.
- Каждый шаг исполняется существующим кодом, перенесённым из обработчиков HTTP: `mutate`-ядро (`yc.write`), `payments.pay`-ядро (`markArrived`, `POST sale/payment`, пауза 2 с, перечитывание и сверка, `remapBonusIds`). Финансовый журнал `journal_financial_transactions` и защита «намерение до внешнего эффекта» сохраняются как есть.
- Перед внешним вызовом шаг помечается в БД; после — `done` с результатом. Перезапуск процесса продолжает с первого не-`done` шага; `done`-шаги никогда не повторяются.

### 2.4 Сбои

| Ситуация | Действие |
|---|---|
| сеть до отправки, 429, 5xx на чтении | повтор с паузой 5 с → 30 с → 2 мин → 10 мин, до 6 попыток, потом `failed` |
| однозначный отказ YClients (4xx при записи: время занято, неверные данные) | `failed` сразу, без повторов |
| неясный исход записи денег или записи (таймаут ответа, оплата не найдена при сверке) | шаг `uncertain`, пакет `failed` с кодом «нужна сверка»; повтора нет никогда |
| отказ на середине пакета | уже выполненные шаги остаются; в пометке — на каком шаге остановилось |

Обработчик ничего не переносит, не отменяет и не «чинит» сам (решение владельца).

## 3. Интерфейс

- Формы закрываются сразу после ответа сервера (доли секунды). Убираются тексты и блоки про сверку с YClients, «Повторное проведение заблокировано», ожидание ответа оплаты.
- Карточка в сетке: «⏳» пока пакет `queued/running`; красная пометка «Не передано в YClients» при `failed`, в подсказке — причина и шаг. Открытие такой карточки показывает: что передано, что нет, причину; кнопки «Повторить отправку» (только для не-денежных и не-`uncertain` сбоев — новый пакет из невыполненных шагов) и «Изменить». Для `uncertain` — владельцу «Я проверил в YClients: проведено / не проведено» (перенос текущей сверки оплат).
- Статусы обновляются опросом раз в 5 с, пока на экране есть незавершённые пакеты (локальный запрос, без YClients).

## 5. Проверка

- Юнит-тесты: локальные окна с наложением; проверка сессии; порядок шагов; продолжение после рестарта с первого не-`done` шага; классификация сбоев (повтор / `failed` / `uncertain`); идемпотентность `sessionId`.
- Сквозной контракт-тест с синтетическим YClients (как `journal-account-contract.test.js`): создание + бонусы + приход + касса одним пакетом.
- Живой прогон на клиенте 79200255591 (по разрешению): создание с оплатой одним закрытием формы; занятое время (запись в то же окно, сделанная прямо в YClients) → красная пометка; рестарт процесса посреди пакета.
- Замер: открытие дня и поиск окон — без обращений к YClients (лог запросов), время ответа.

## Риски

- Между сохранением и отправкой время может занять Мила или онлайн-запись — пакет `failed` «время занято», правит администратор (принято владельцем).
- Зеркало отстаёт на время доставки вебхука (секунды) и до 10 мин при потерянном вебхуке — окна могут показать занятое время свободным; отказ YClients ловит это при отправке.
- Лимит бонусов из кэша может разойтись с YClients — отказ при отправке.
- Квота YClients: фоновая сверка (≈1–3 запроса / 10 мин) и графики (≈8 запросов / 30 мин) дешевле, чем нынешнее открытие дня.

## Редактирование карточки — dev, 10.11.2026

В карточке доступны четыре статуса (0 ожидание, 1 пришёл, −1 не пришёл,
2 подтвердил), а также изменение услуг, количества, цены, скидки и итога.
Статус и услуги сохраняются одним `edit` в `POST /api/journal/sessions`.
Выбор «Не пришёл» сохраняет длительность и состав; прежняя отдельная отмена
по-прежнему сокращает запись до пяти минут. Новые услуги выбираются из
внутреннего каталога с явным `yclientsId`, доступные текущему специалисту.
Длительность существующего визита сохраняется. При изменении состава или
количества повторно проверяются время, специалист и оборудование; прошедший
старт не позволяет менять состав через проверку свободных окон.

Редактирование доступно владельцу/администратору у сохранённого неоплаченного
визита, включая пришедший и «не пришёл». Оплаченные и удалённые визиты, а также
записи с незавершённым пакетом не редактируются в UI. Финансовые операции и
перенос нельзя объединять с edit. Сервер проверяет проведённые/неопределённые
оплаты прежними защитами. Перед отправкой worker сохраняет полный draft с
версией и ключом; повтор использует тот же draft. Версия карточки передаётся
в edit: несовпадение возвращает `edit_conflict`, без перезаписи свежих данных.
В overlay сохраняются полные строки услуг с количеством и ценой.

Миграция в migrations.js однократно заменяет ограничение допустимых действий
journal_operations, добавляя edit. Старые действия и строки сохранены.
ALTER требует короткой эксклюзивной блокировки таблицы; backfill отсутствует.
Применяется при старте до обработки запросов. При откате кода расширенное
ограничение оставить; накопленные edit-пакеты сначала обработать новой версией.
На dev подтверждены локальная loyalpro_test и ограничение
journal_operations_action_v2_check. Перезапущен только dev-процесс loyalpro.

Изменённые файлы: frontend/js/pages/journal.js, frontend/index.html;
backend/migrations.js, services/service-catalog.js,
services/journal/{model,index,sessions,overlay,outbox-worker,record-edit}.js;

### Исправление повторного изменения статуса — 10.11.2026

Причина: календарь опрашивал очередь, но открытая карточка сохраняла прежний
sync=queued/running и отключённые кнопки после завершения пакета. Карточка
теперь каждые 2 секунды перечитывается до завершения сохранения; полученная
версия заново подключает действия. Вместо «Скоро» показывается ожидание
сохранения. При закрытии или переходе в другую форму наблюдение отменяется;
запоздалый ответ не заменяет другую форму. Ошибка чтения повторяется, failed
показывает штатные действия восстановления. Оплаченные визиты по-прежнему
защищены; API, авторизация и внешние записи не менялись.

Файлы: frontend/js/pages/journal.js, frontend/index.html,
backend/journal-ui.test.js и этот документ. Проверка:

`node --check frontend/js/pages/journal.js`, `git diff --check` прошли.
