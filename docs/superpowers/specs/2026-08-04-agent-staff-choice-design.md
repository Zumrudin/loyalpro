# Выбор специалиста пациентом, а не моделью

Дата: 2026-08-04
Статус: спека утверждена, реализация не начата

## Проблема

Пациент пишет «хочу биоревитализацию на завтра», врача не называет. Сегодня промпт
Сценария 2 прямо разрешает Миле выбрать исполнителя самой:

- Шаг 2: «Определи специалиста (по желанию пациента или из тех, кто выполняет
  выбранную услугу в list_services)»;
- строка про запись: «"Любой специалист" — сама выбери любого мастера из поля staff
  нужной услуги (кто свободен), не спрашивая пациента».

Модель берёт одного мастера, зовёт `get_available_slots` под него и, если окна есть,
молча предлагает именно его. Пациент видит одно имя — и не знает, что процедуру ведут
двое.

Цена в PERI зависит от мастера (у главного врача она выше: 23 000 ₽ против 19 000 ₽ у
косметолога-эстетиста на одной и той же услуге). То есть «кого предложить по умолчанию»
— решение бизнеса, а не модели, и владелец решил: **выбор делает пациент**.

Существующее правило «АЛЬТЕРНАТИВНЫЙ СПЕЦИАЛИСТ» проблему не закрывает: оно срабатывает
только при ПУСТОЙ выдаче у выбранного мастера. Когда окна есть, альтернативы не
показываются вовсе.

## Решение

Пациент не назвал врача → Мила не выбирает за него. Она уточняет день, а код считает
свободные окна у ВСЕХ исполнителей услуги и отдаёт их списком. Мила одним сообщением
называет имя, должность и 1–2 времени каждого и спрашивает, к кому удобнее.

Пример целевой реплики:

> В четверг эту процедуру проводят Юлия, косметолог-эстетист — 12:00 и 14:00, и Пери
> Исамудиновна, главный врач — 15:00. К кому вам удобнее записать?

Дальше пациент корректирует выбор по имени или по времени — обычный ход диалога.

### Принятые решения

1. **Выбор и время — одним сообщением.** Не спрашиваем «к кому вам удобнее?» до
   уточнения даты: список считает код, и в нём только те, кто реально в смене и
   свободен. Иначе Мила предложит мастера, которого в этот день нет, и выбор придётся
   переигрывать.
2. **Цена в момент выбора НЕ звучит** — даже когда цены мастеров различаются. Имя и
   должность. Цену Мила называет по вопросу пациента, как и сейчас (правила
   «МУЖСКОЙ ПРАЙС» и per-master цены не меняются).
3. **История визитов не учитывается.** Даже если пациент раньше ходил к конкретному
   мастеру, но сейчас его не назвал — показываем весь выбор. Одно правило вместо ветки
   «свой мастер», меньше шансов, что слабая модель напутает.

## Изменения в коде

### `services/agent/tools/get-available-slots.js` — мультимастерный режим

`staff_yc_id` становится НЕобязательным. `service_yc_id` и `date` — по-прежнему
обязательны (без услуги неизвестна длительность, инцидент 2026-07-31).

Поведение без `staff_yc_id`:

1. Исполнители услуги — из `staffGuard.checkStaffPerformsService` (поле `staffList`,
   уже собирается для ветки альтернатив).
2. Скрытые пары «услуга-мастер» отсекаются `svcFilter.isBookable` — как в
   `findAlternativeStaff`.
3. Окна каждому считает существующий `computeStaffSlots` — те же lead-time,
   вычет занятого оборудования, fallback на график при выключенной онлайн-записи.
   Сбой по одному мастеру не валит ответ (как в `findAlternativeStaff`).
4. Мастера с пустым `slots` из выдачи выбрасываются — это и есть «в смене и свободен».

Ответ:

- `staff_options: [{ staff_yc_id, name, position, slots: [...] }]` + `hint`;
- сортировка по времени ПЕРВОГО свободного окна, тай-брейк по `yc_id` (детерминизм);
- `position` — из `staff.specialization` (одним SQL по списку `yc_id` салона). Без него
  должность модель придумает, а промпт обязывает её называть;
- пусто у всех → `{ slots: [], no_staff_available: true }` + hint «предложи другой день»;
- один исполнитель → `staff_options` из одного элемента + hint «выбора нет, просто
  предложи время и назови имя»;
- каталог не отдал исполнителей (fail-open `unknown` у `checkStaffPerformsService`) →
  ошибка-подсказка «укажи staff_yc_id» (прежнее поведение, не молчание).

Проверяем не больше 3 мастеров (тот же `MAX_ALT_STAFF`): до 3 запросов в YClients
вместо одного. Это осознанный компромисс по стоимости и задержке — в ветке альтернатив
он уже есть. Следствие: там, где исполнителей больше трёх, часть в список не попадёт,
поэтому промпт запрещает утверждать «это все наши специалисты».

Поведение С `staff_yc_id` не меняется вообще: та же предпроверка `staff_mismatch`, та же
ветка `alternative_staff` при пустой выдаче.

### Отвергнутая альтернатива

Отдельный инструмент `get_service_staff_slots`. Пришлось бы дублировать логику расчёта
окон, а модели — выбирать между двумя почти одинаковыми инструментами. Риск ошибки не
меньше, чем при необязательном параметре, а кода больше.

### `services/agent/system-prompt.js`

- Шаг 2 Сценария 2: пациент назвал мастера → как сейчас; НЕ назвал → не выбирай сама,
  зови `get_available_slots` БЕЗ `staff_yc_id`.
- Новое правило «ВЫБОР СПЕЦИАЛИСТА»: перечисли всех из `staff_options` — имя +
  должность + 1–2 времени ДОСЛОВНО из его `slots`, вопрос «к кому удобнее?». Никого не
  рекомендуй сама, цену не называй, «это все специалисты» не утверждай. Один элемент в
  списке — выбора не устраивай, просто предложи время.
- Строка «"Любой специалист" — сама выбери любого мастера» сужается: срабатывает только
  когда пациент САМ сказал «мне без разницы» — тогда берём того, у кого ближайшее окно.
- Правило «АЛЬТЕРНАТИВНЫЙ СПЕЦИАЛИСТ» остаётся без изменений — оно про случай, когда
  мастер назван, а окон у него нет.

## Границы

Не трогаем:

- `get_parallel_slots` и `get_sequential_slots` — там мастеров подбирает сам инструмент
  и уже называет их поимённо в вариантах;
- Сценарий 3 (перенос) — мастер существующей записи известен;
- цены, `get_service_masters`, правила мужского прайса.

## Проверка

- Юнит-тесты мультирежима (моки YClients): несколько мастеров с окнами; часть пустых;
  все пустые → `no_staff_available`; один исполнитель; сортировка по первому окну;
  скрытая пара `service-filter` не попадает в список; сбой по одному мастеру не валит
  ответ; вызов С `staff_yc_id` работает как раньше.
- `agent-system-prompt.test.js` — связка нового правила промпта с полями инструмента
  (`staff_options`, `no_staff_available`), чтобы правило не разъехалось с кодом.
- Живой прогон на тестовом номере (`/clear-history` перед прогоном): «хочу
  биоревитализацию на завтра» без имени врача → в ответе два мастера с должностями и
  временами, без цен.
