# Разовые рассылки через мессенджеры клиники: список, картинка, каскад, темп, лимиты, live-монитор

Дата: 2026-11-01. Статус: дизайн утверждён владельцем в переписке, реализация не начата.

## 1. Зачем

Сегодня разовая рассылка (`services/broadcast.js`, страница «Рассылки») умеет одно: текст подписчикам
Telegram-бота @PERICLINIC_bot через Bot API, получатели — клиенты из БД, найденные в базе бота
(`clients_peri.tg_id`), по фильтрам (сегменты, бонусы, давность визита, месяц ДР, пол, телефон), пауза
60 мс. Нужно:

1. рассылка по произвольному списку «имя + телефон»;
2. картинка в начале сообщения, под ней текст;
3. каскад мессенджеров клиники (Telegram-TDLib, WhatsApp, MAX) — как у автоуведомлений: сначала мессенджер
   последней переписки, иначе порядок из настроек салона;
4. пауза между сообщениями в один и тот же мессенджер;
5. лимит сообщений в один мессенджер на рассылку;
6. live-монитор рассылки: кто ушёл, кто ждёт, какой мессенджер на паузе, статистика по каналам.

Цель пунктов 4–5 — распределить поток по мессенджерам и не дать WhatsApp заблокировать номер клиники.

## 2. Решения владельца

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Бот | Остаётся как есть. У рассылки переключатель «Канал»: «Мессенджеры клиники» / «Telegram-бот». Новое — для мессенджеров; бот не меняется (картинка боту — вне scope, см. §9). |
| 2 | Получатель, чей мессенджер на паузе | **Ждёт свой мессенджер**; воркер шлёт тем, чей мессенджер свободен. Рассылка может растянуться. |
| 2a | Ночь | Отправка только в окне 09:00–21:00 мск (конец исключающий), ночью рассылка стоит. |
| 3 | Лимит | **На рассылку**, отдельно по каждому мессенджеру. |
| 4 | Исчерпан лимит | Выбор при создании: «в следующий мессенджер каскада» / «не отправлять». |
| 5 | Список | Вставка текстом И файл CSV/XLSX, разбор с отчётом до запуска. Номера не из базы — отправляем; чёрный список — по номеру. Имя из списка главнее имени карточки. |
| 6 | Монитор | На странице «Рассылки», открывается кликом по рассылке в истории. |

Решения исполнителя (не оспорены): картинка + подпись ОДНИМ сообщением; если текст > 1024 символов
(лимит подписи Telegram) — картинка, затем текст отдельным сообщением. Пауза и лимит считаются по
отправкам РАССЫЛОК салона; автоуведомления, напоминания, «Забота» их не расходуют и ими не задерживаются.

## 3. Архитектура

Подход: расширить существующие `broadcasts`/`broadcast_recipients`, у рассылки поле `transport`.
Старый воркер (`services/broadcast.js`) арендует только `transport='telegram_bot'` и иначе не меняется.
Новый код — каталог `backend/services/broadcast-messengers/`:

| Модуль | Ответственность | Зависимости |
|--------|-----------------|-------------|
| `list-parse.js` | Чистый разбор списка: текст (строки, разделители `; , \t` и пробел), CSV, строки XLSX (массив массивов) → `{rows:[{name, phone}], invalid:[{line, raw}], duplicates}`. Номер — общий `normalizePhoneKey`, годен только канон `7XXXXXXXXXX` (`notifications/cascade.canonPhone`). Колонки определяются по заголовку («имя/name/фио», «телефон/phone/номер»), без заголовка — та ячейка, что парсится как телефон, остальное — имя. | `agent-gate`, `notifications/cascade` |
| `audience.js` | Сборка получателей: по фильтрам — все клиенты салона с годным номером (те же фильтры, что у бота; ЧС исключён); по списку — строки списка, дотянутые карточкой клиента по номеру (`client_id`, бонусы, имя-фолбэк), ЧС по номеру. | `render.js` | Подстановки `{first_name}` (через `utils/person-name`, как у уведомлений), `{name}`, `{bonuses}` (не из базы → 0), `{salon}`. Разбиение «подпись / отдельный текст» по порогу 1024. | `utils/person-name` |

Роуты — расширение `routes/broadcasts.js` (owner/admin): см. §6. Фронт — `frontend/js/pages/broadcasts.js`
+ чистые помощники `broadcasts-monitor.js` (`node --test`), глобальные имена с префиксом `bc`/`BC_`.

## 4. Данные

Миграции только `IF NOT EXISTS`/`ADD COLUMN IF NOT EXISTS`; после выката сверить SQL-ом (миграции глотают ошибки).

`broadcasts` — новые колонки:
- `transport VARCHAR(20) NOT NULL DEFAULT 'telegram_bot'` (`telegram_bot|messengers`);
- `audience_source VARCHAR(10) NOT NULL DEFAULT 'filters'` (`filters|list`);
- `image_url TEXT` — `/uploads/broadcast_<salon>_<ts>.<ext>`;
- `cascade_enabled BOOLEAN NOT NULL DEFAULT TRUE`;
- `channel_settings JSONB NOT NULL DEFAULT '{}'` — `{tdlib|whatsapp|max: {enabled, delay_sec, limit|null}}`;
- `on_limit VARCHAR(12) NOT NULL DEFAULT 'next_channel'` (`next_channel|skip`);
- `paused BOOLEAN NOT NULL DEFAULT FALSE`, `pause_reason TEXT` — ручная пауза / авто-пауза при недоступном шлюзе;
- статусы рассылки дополняются: `pending|in_progress|completed|cancelled|failed` — без изменений, «ночная пауза» и «пауза» — вычисляемые/флаг, не статус.

`broadcast_recipients` — новые колонки:
- `phone VARCHAR(20)`, `cascade TEXT[]`, `step SMALLINT NOT NULL DEFAULT 0`, `channel VARCHAR(16)` — текущий
  (ожидание) или фактический (после отправки) мессенджер;
- `reason TEXT`, `delivery_id TEXT`, `account_id INTEGER`, `delivery_status VARCHAR(20)`
  (`accepted|delivered|undeliverable|unknown`), `checked_at TIMESTAMPTZ`, `cascade_log JSONB DEFAULT '[]'`,
  `sort_order INTEGER` — порядок списка/выборки.
- `telegram_chat_id` — `ALTER COLUMN DROP NOT NULL` (у мессенджерных строк его нет; старый уникальный индекс на NULL
  не срабатывает). Новый `CREATE UNIQUE INDEX IF NOT EXISTS uq_broadcast_recipient_phone ON broadcast_recipients
  (broadcast_id, phone) WHERE phone IS NOT NULL`.
- Статусы получателя для мессенджеров: `pending` (ждёт), `sending` (захвачен перед отправкой), `sent`, `failed`,
  `skipped`, `cancelled`. Причины в `reason`: `limit`, `no_recipient`, `blacklist`, `ambiguous_failure`, `all_rejected`.
- Индекс `(broadcast_id, status, sort_order)`.

Колонки `sent/failed/total` рассылки ведутся как и сейчас (+ `skipped INTEGER DEFAULT 0`). Статистика по каналам
монитора считается `GROUP BY channel, status, delivery_status` по получателям (тысячи строк — дёшево).

## 5. Алгоритм отправки

### 5.1 Состояние мессенджера (на тик, по рассылке)
- `lastSentAt[ch]` — max(`sent_at`) получателей этой рассылки с `channel=ch`, `status IN ('sent','sending')`;
- `sentCount[ch]` — их количество (лимит считается по отправленным, а не по доставленным);
- `free[ch] = now ≥ lastSentAt + delay_sec[ch]`, `limitHit[ch] = limit[ch] != null && sentCount[ch] ≥ limit[ch]`.

Активна одна рассылка на салон (самая ранняя `in_progress`, затем `pending`) — две параллельные рассылки обошли бы
паузу друг друга. Рассылки разных салонов идут независимо.

### 5.2 Тик (`scheduler.plan`)
1. Вне окна 09:00–21:00 мск, `paused` или `cancel_requested` — действий нет.
2. По мессенджерам с `limitHit` все ожидающие получатели этого мессенджера: `on_limit=next_channel` → `advance`
   на следующий шаг своего каскада (нет шага → `skip: limit`); `on_limit=skip` → `skip: limit`.
3. Обход ожидающих в `sort_order`: первый, чей текущий мессенджер `free` и не `limitHit`, получает `send`;
   мессенджер помечается занятым до конца тика. Итог — не больше одной отправки на мессенджер за тик.
   Остальные ждут (решение 2).

### 5.3 Исполнение `send`
1. Захват: `UPDATE … SET status='sending', sent_at=NOW() WHERE id=$1 AND status='pending'` — не легло → пропуск.
2. `authorship.remember(salon, phone, text, 'system')` ДО отправки (иначе эхо читается ответом администратора и ставит
   Милу на паузу — инцидент 04.08).
3. `transport.sendFile` (картинка, `caption` = текст или пусто при длинном тексте) / `transport.sendMessage`;
   длинный текст — вторым `sendMessage` в тот же мессенджер сразу за картинкой (вторая отправка паузу не ждёт и
   лимит не тратит: это одно сообщение рассылки).
4. Успех → `sent`, `channel`, `delivery_id`, `account_id`, `delivery_status='accepted'`, журнал каскада;
   `pendingReplies.remember`, для WhatsApp — `persistWhatsappOutgoing` (`authoredBy:'system'`). Всё после отправки
   глотает ошибки (at-most-once: ничего не возвращает строку в `pending`).
5. Однозначный отказ (`transport.isDefiniteRejection`, 4xx, нет аккаунта) → шаг каскада +1, `status='pending'`,
   `sent_at=NULL`, запись в `cascade_log` (нет шага → `failed: all_rejected`). Неудачная попытка паузу мессенджера
   не запускает (`sent_at` сброшен).
6. `ECONNREFUSED|ENOTFOUND|EAI_AGAIN` (шлюз недоступен) → получатель возвращается `pending` на ТОТ ЖЕ шаг,
   рассылка `paused=true, pause_reason='gateway_unreachable'`, предупреждение в мониторе; продолжить — кнопкой.
   ЗАЧЕМ: при лежащем шлюзе каскад откатил бы всех получателей в другие мессенджеры.
7. Неоднозначный сбой (таймаут, 5xx, `ECONNRESET`) → `failed: ambiguous_failure`, без отката — сообщение могло уйти,
   дубль хуже пропуска.
8. Рестарт процесса со строкой в `sending` (упал между захватом и ответом) — при старте такие строки старше 2 мин
   становятся `failed: ambiguous_failure`, не переотправляются.

### 5.4 Сверка доставки
Через 120 с после отправки — `transport.getDeliveryStatus(..., {accountId})`: статус 5 → `undeliverable`, иначе
`delivered`/`unknown`. **Только для монитора**: каскад по «не доставлено» не продолжается (в отличие от
автоуведомлений) — в разовой рассылке повтор в другой мессенджер через минуты выглядел бы спамом, а у шлюза статус 5
бывает и «исход неизвестен». Ошибка чтения — `unknown`.

### 5.5 Завершение
Нет `pending`/`sending` → `completed`, `finished_at`. Отмена → оставшиеся `pending` → `cancelled`, рассылка `cancelled`.

## 6. API (`/api/broadcasts`, owner/admin, `req.user.salonId`)

Статические пути — до `/:id`.
- `POST /list/parse` — multipart (файл CSV/XLSX ≤ 2 МБ, ≤ 5 000 строк) или `{text}` → отчёт разбора: распознанные,
  битые (номер строки + сырой текст), дубли, в ЧС, найдено в базе. XLSX читается зависимостью `exceljs`
  (новая зависимость бэкенда, только чтение первого листа); CSV — свой разбор (`;`/`,`, кавычки).
- `POST /image` — multipart, jpg/png/webp ≤ 5 МБ, тип по сигнатуре (`utils/upload-validator.validateImageBuffer`, как у прайс-фото)
  → `{imageUrl}`.
- `POST /forecast` — то же тело, что создание → `{byChannel:{tdlib, whatsapp, max, none}, durationMin, finishAt, nextDay}`.
- `POST /` — создание. Новые поля: `transport`, `audienceSource`, `list` (уже разобранные строки), `imageUrl`,
  `cascadeEnabled`, `channelSettings`, `onLimit`. Валидация: `delay_sec` 0–3600, `limit` пусто или 1–10 000, хотя бы
  один мессенджер включён, у салона есть аккаунт хотя бы одного включённого мессенджера (иначе 400), текст ≤ 4000.
  Бот (`transport='telegram_bot'`) — прежний путь без изменений.
- `POST /test` — то же тело + `testPhone` (поле в форме, запоминается в localStorage; у `users` колонки телефона нет)
  → отправка тем же кодом исполнения, без пауз и лимитов, не создаёт рассылку.
- `GET /:id/monitor` — шапка, карточки мессенджеров (`state: sending|paused_until|limit|disabled`, `pausedUntil`,
  счётчики по статусам и `delivery_status`, `advancedFrom`), `waiting` — первые 20 ожидающих в порядке отправки.
- `GET /:id/recipients?status&channel&q&offset&limit` — таблица получателей (кап 100 на страницу).
- `POST /:id/pause`, `POST /:id/resume`, `POST /:id/cancel` (есть).
- `POST /:id/retry-draft` — список «пропущенные + неотправленные» для новой рассылки в режиме «по списку».

## 7. Фронт

Модалка «Новая рассылка»:
1. Канал — чипы «💬 Мессенджеры клиники» / «🤖 Telegram-бот» (бот — прежняя форма).
2. Получатели — «По фильтрам» / «По списку» (textarea + «Загрузить CSV/XLSX», сводка разбора, раскрываемый список битых строк).
3. Картинка — загрузка с превью и кнопкой «убрать»; текст с подстановками; предупреждение про `{bonuses}` в режиме списка.
4. Доставка — тумблер каскада (порядок — ссылка на настройки автоуведомлений), таблица мессенджеров
   (вкл/пауза, сек/лимит; дефолты: WhatsApp 180 с, Telegram и MAX 60 с, лимит пусто), «При исчерпании лимита».
5. Прогноз (дебаунс 500 мс): распределение по мессенджерам и длительность.
6. «🧪 Тест на мой номер», «Запустить».

Монитор — панель по клику на строку истории, polling 5 с (останавливается при уходе со страницы): шапка с
прогрессом и кнопками, три карточки мессенджеров с обратным отсчётом паузы, блок «Сейчас ждут», таблица получателей
с фильтрами и поиском, итог с кнопкой «Новая рассылка по пропущенным». Правка JS/CSS — с бампом `?v=`.

## 10. Риски

- Широкая выборка «по фильтрам» теперь охватывает ВСЕХ клиентов салона с номером (у бота — только подписчиков):
  форма обязана показывать итоговое число перед запуском, а прогноз — длительность.
- Ответы клиентов приходят Миле обычным путём; в ночное окно Милы (22:00–09:30) первые утренние ответы она
  обработает, днём — администратор. Сообщение рассылки в транскрипте помечено `system` и видно Миле через `pendingReplies`.
- Неофициальные клиенты WhatsApp/MAX: пауза и лимит снижают, но не исключают риск блокировки.
