# Стоимость услуг и оплаты визита — 08.11.2026

Владелец запросил поля количества/цены/скидки/итога, формы оплаты, новую таблицу финансовых транзакций со связью с бонусами. Дополнительно явно выбрал отражение оплат и списаний в YClients.

## Договорённости и модель

Owner/admin могут изменять стоимость при создании записи: количество 1–100 (целое), цена за единицу, процент скидки, либо итог строки. Редактирование итоговой суммы переключает строку в режим явного итога, скидка рассчитывается; итог не выше суммы без скидки (повышение — через цену). Сервер независимо пересчитывает суммы в копейках, проверяет совпадение IDs строк и услуг. Ранее существовавшие запросы без lines совместимы. Количество умножает длительность услуги; поиск времени и проверка перед записью используют одинаковые количества. В YClients отправляются amount, cost_per_unit, first_cost (сумма до скидки), discount, cost (итог). Внутренние service IDs преобразуются на границе интеграции, как раньше.

Новый платёж не совмещается с созданием в одну неатомарную операцию: кнопки «Карта», «Наличные», «Все способы / бонусы» на форме создания сохраняют запись и открывают оплату. Администратор затем явно подтверждает фактически полученную сумму кнопкой «Провести оплату». Кассовая операция фиксирует расчёт в YClients; это не банковский эквайринг и не списание денег с банковской карты. Также форма доступна из существующей карточки визита. Смешанная оплата — последовательные подтверждённые операции (бонусы, затем наличные/карта) с обновлением остатка между ними. Сертификаты/абонементы, QR, оплата по ссылке явно помечены «Скоро».

Сведения о доступных кассах, бонусной карте и лимитах берутся из актуальной операции продажи YClients. В POST принимаются только method/account-or-card ID, сумма, версия и UUID; документ/компания выводятся из серверного салона и проверенной записи. Источник протокола — [официальная документация YClients](https://yclientsru.docs.apiary.io/reference/5/0/0), структурированная версия https://jsapi.apiary.io/apis/yclientsru: GET /company/{salon_id}/sale/{document_id}; POST того же пути + /payment с payment.method.slug=account|loyalty_card и соответствующим id. Документ выбирается из record.documents, type_id=7, с проверкой company_id/record_id. Неполный/неоднозначный ответ закрывает оплату, а не выбирает случайный документ.

## Долговечность и бонусы

Аддитивный JOURNAL_FINANCE_DDL создаёт journal_financial_transactions. PK salon_id+operation_id, сумма numeric, способ, источник компания/запись/документ, user_id, reviewed_by, состояние, HMAC запроса, идентификаторы транзакций до/после, снимок строк записи. FK record_id → records, client_id → clients, bonus_transaction_id → loyalty_card_transactions. Старая bonus_transactions не используется для нового учёта (историческая схема).

Салонный session advisory lock 17291 общий с операциями журнала. Pending AUTOCOMMIT сохраняется перед внешним POST. Точное повторение подтверждённой операции возвращает прошлый результат; новый ключ при pending блокируется. Перед POST проверяются HMAC текущего состояния, доступность метода, лимит и положительная сумма. Неопределённый ответ/ошибка сохранения результата оставляют pending: автоматического повторного POST нет. Только определённый HTTP отказ 400/401/403/404/422/429 помечается rejected. Ответ сверяется по новым transaction IDs и сумме; для бонусов только type_id=3, карта текущего способа, начисления исключены.

Сверка доступна только owner после явного подтверждения в UI: «проведена» — read-only сверка новых IDs/суммы и запись receipt; «не проведена» — снять блокировку только если новых транзакций выбранного метода в YClients не появилось. Никакого денежного действия при сверке не выполняется. Неопределённые оплаты также блокируют изменения записей через журнал. Отдельная интеграция/кассир в YClients этим локальным lock не блокируется: перед каждым запросом проверяется версия, а окончательный лимит контролируется YClients.

Бонусный баланс локально второй раз НЕ уменьшается. Новая таблица фиксирует результат внешнего списания; существующий webhook/reconciliation остаётся владельцем clients.bonus_balance и loyalty_card_transactions. При загрузке формы выполняется узкое связывание финансовых строк с tenant-scoped records, затем с уже поступившей строкой redemption по тому же салону, клиенту, визиту, карте и штатному заголовку «Списание бонусов при оплате визита #…». До прихода этой строки FK nullable, UI показывает ожидание связи. Это связь с бонусной записью визита; несколько частичных финансовых списаний могут ссылаться на агрегированную бонусную строку визита. Если штатная синхронизация не доставила такую строку, связь остаётся ожидающей — второе искусственное списание не создаётся. Новый журнал не прибавляется к revenue_operations в отчётах, иначе выручка задвоится.

Документированный PUT /visits/{visit_id}/{record_id} поддерживает new_transactions, но также изменяет содержимое визита. Возвращать прежний PUT с отсутствующим services нельзя. Полный путь требует сохранения услуг, товаров, количества, скидок, attendance и comment, проверки группового визита и независимого подтверждения сохранённого платежа. Текущий OpenAPI не объясняет генерацию new_transactions[].id и не описывает amount в services PUT; поэтому произвольный roundtrip и его сохранность пока не подтверждены живым тестом. В этом разборе финансовое поведение кода не менялось; исправлен вводящий в заблуждение комментарий адаптера. Тесты не перезапускались: изменены только комментарий и документация, исправление оплаты не заявляется.

## Исправление account-платежей после пользовательского разрешения

Этот раздел заменяет прежние варианты сохранения оплаты. Для оплаты в кассу больше не вызываются ни POST sale/payment, ни POST finance_transactions. Выполняется один документированный PUT /visits/{visit_id}/{record_id} с полным services, attendance, comment, пустыми goods_transactions/deleted_transaction_ids и одной new_transactions. Исходные cost, cost_per_unit, first_cost и discount берутся из записи; остаток cost_to_pay после бонусов не подставляется вместо цены. POST sale/payment сохранён только для существующего сценария оплаты бонусами. Источник контракта: https://developers.yclients.com/ru/ (раздел «Изменить визит»); схема GET visits также сверена с актуально загруженным официальным документом.

Поддерживается проверяемый поднабор: один record в визите, услуги с amount=1, без товаров, расходников и групповой записи. Остальные случаи отклоняются до финансового intent/HTTP-write с предложением оплатить в YClients; неоднозначные цены также не переписываются. include_consumables включается только при чтении платёжного контекста, чтобы не менять данные обычных переносов/подтверждений/отмен записей. План записи сверяет компанию, документ, визит и полный вложенный record с отдельным GET record. Перед записью повторно проверяется финансовое состояние sale.

Live GET выявил особенность YClients: top-level visit.datetime и record.datetime имеют одинаковые местные часы, но разные UTC offset (+04:00 и +03:00), при полностью совпадающих вложенном record и отдельном GET record. Top-level datetime не отправляется и не используется для сравнения; datetime вложенной записи и отдельного GET по-прежнему входят в строгий snapshot. Корректные ISO offset +0300 и +03:00 нормализуются одинаково. Значения комментария/посещения верхнего уровня и записи должны совпадать; неоднозначные случаи блокируются.

Pending фиксируется до единственного PUT. new_transactions.id — временный клиентский идентификатор из Date.now(), не receipt и не ключ безопасного повтора. При таймауте/неопределённом результате повторного write нет. После PUT независимо читаются record и sale: должны сохраниться услуги, цены, клиент, сотрудник, дата/длительность, ресурсы, комментарий, статус и другие защищённые поля; прежние кассовые операции и точный набор бонусных списаний должны сохраниться. Неожиданная операция другой кассы оставляет pending. Только новые сохранённые ID выбранной кассы с точной суммой подтверждают платёж. Пустой HTTP 200 сам по себе подтверждением не считается. При повторе уже confirmed операции проверяются именно её сохранённые external_ids, а также текущие компания и документ.

Изменённые файлы: backend/services/journal/{payments,yclients,visit-payment}.js; backend/journal-{payments,integration,visit-payment,account-contract}.test.js; этот документ. БД, UI и существующие финансовые данные не менялись. Добавлены регрессии реального адаптера с подменой только транспорта/БД: единственный PUT, intent до эффекта, сохранение цен после бонусов, receipt из независимого GET, отсутствие сохранения/потеря услуг/неожиданные операции оставляют pending, неподдерживаемые случаи не отправляют write. Проверены auth, tenant scope, отсутствие финансовых повторов и приватных данных в диагностике.

Проверки: `npx jest journal --runInBand --silent` — 9 наборов, 208 тестов прошли. Read-only подготовка нового payload на трёх активных записях dev прошла; использовались только SELECT в READ ONLY и GET YClients, remote writes=0. Это проверка подготовки и совместимости ответов, не подтверждение успешной реальной оплаты. Браузерный E2E не выполнялся: подходящего MCP нет; UI не изменялся. Мобильный lint неприменим.

Ограничения: YClients не предоставляет в этом контракте условную запись по версии; локальная блокировка не исключает одновременную правку непосредственно в YClients. Независимый readback обнаруживает расхождение и сохраняет pending. Полное сравнение документов намеренно консервативно. Старая отдельная финансовая операция и pending не очищены; последняя тестовая запись к моменту подготовки исправления уже удалена. Для финансового исправления старых данных требуется отдельное разрешение на конкретную операцию.

Операционный откат: отключить JOURNAL_ACCOUNT_PAYMENTS_ENABLED в dev и перезапустить только этот процесс; финансовый журнал и pending сохранить. Копии существовавших до исправления изменяемых файлов/тестов и документа находятся в /root/loyalpro-deploy-backups/journal-account-fix-before/. Возвращать старую двухшаговую отправку при включённой account-оплате нельзя.

Выкладка: на основании ранее данного разрешения перезапущен только dev PM2 loyalpro, без update-env. Проверено: runtime port=3001, БД loyalpro_test на локальном Postgres, account-флаг включён, новый процесс online и запущен после всех изменённых исходников; restart count 19→20. Главная отвечает 200, API журнала без авторизации — 401 JSON. В свежих логах отсутствуют ошибки запуска/подключения БД. Проверки синтаксиса всех семи JS-файлов, git diff --check и whitespace/conflict-check новых файлов прошли. Финансовые записи, повторные оплаты, удаление старой отдельной операции и сброс pending агентом не выполнялись. ## Повторный отказ после PUT: запись в ожидании

Пользовательский тест после restart20 в 21:35 МСК снова остановился на stage=saved_receipt. Предыдущее исправление не обеспечило сохранение этой оплаты. Проверена именно указанная пользователем активная запись на следующий день, без вывода номера/имени/идентификаторов в результаты диагностики. ## Оплата наличными/картой через POST sale/payment — 09.11.2026 (заменяет PUT /visits)

Причина всех отказов 08.11 установлена по `webhook_logs` и подтверждена контрольным опытом. YClients ПРИНИМАЕТ кассовую оплату визита в статусе «Ожидание» (attendance 0) и через ~0,3 с сам её удаляет: finances_operation create → record update attendance=0 → finances_operation delete. Так было на всех попытках 08.11, и через POST sale/payment, и через PUT /visits. Контроль 09.11 (тестовая запись клиента 79200255591): при статусе «Подтвердил» оплата 1 ₽ через POST sale/payment сохранилась; возврат той же записи в «Ожидание» удалил её с той же сигнатурой вебхуков. Вывод прошлого раздела «sale/payment — превью» был неверным: откатывал статус, а не метод.

Новый путь: касса оплачивается тем же `POST /company/{cid}/sale/{doc}/payment`, что и бонусы (`payment.method = {slug:'account', account_id}`). Состав визита (услуги, товары, расходники, количество) НЕ пересылается, поэтому ограничения «товары/расходники/количество >1 → оплатите в YClients» для визитов «Пришёл»/«Подтвердил» сняты. Для визита в «Ожидании» сначала, по явному «Оплатить и отметить приход», ставится attendance=1 полным `PUT /record` (короткий `{attendance}` YClients отвергает 422) — ДО финансового intent; после него проверяется, что изменился только статус (`visitPayment.snapshot`). Автоматическая отметка прихода ограничена прежним проверяемым поднабором (без товаров, расходников, количества >1, групп); остальные визиты в «Ожидании» получают «Отметьте приход клиента в YClients — после этого оплату можно провести здесь». После оплаты код ждёт 2 с (окно отката) и проверяет статус записи (1/2, не удалена) и сохранённую транзакцию в повторно прочитанном sale.

Вторая находка живого прогона: сохранение записи (наша отметка прихода или отметка в самом YClients) ПЕРЕСОЗДАЁТ бонусные списания визита под новыми id с той же картой и суммой (871653710 → 871653865). Без обработки проведённый бонус становился «не подтверждён» и блокировал оплату остатка. `remapBonusIds` (в `options` и `pay`) переписывает `external_ids` подтверждённого бонуса на незанятое живое списание той же карты и суммы; отметка прихода разрешает только такое пересоздание (кассовые операции должны совпасть точно, бонусы — по картам и суммам).

Живой прогон настоящего кода 09.11 (запись 2129147950 и 2129160940, клиент 79200255591, по 1 ₽): бонус → «Оплатить и отметить приход» картой — обе операции confirmed, оплата в кассе после паузы на месте, вебхука удаления нет; отмена оплаты и бонуса через журнал — confirmed; тестовые записи и операции удалены. Тесты: `npx jest backend/journal` — 9 наборов, 212 тестов. Резервная копия файлов до правки — /root/loyalpro-deploy-backups/journal-sale-payment-before-20261109/. Неизвестно: поведение отметки прихода полным PUT /record для визитов с товарами (поэтому автоматически не делается). В журнале остались 5 pending 08.11 по уже удалённым тестовым записям — касса по ним пуста (проверено GET /finance_transactions), блокируют только свои удалённые записи.
