# Экономика процедур: себестоимость и маржинальность по каждой услуге — дизайн

Дата: 2026-10-18. Статус: черновик на ревью владельца. Исследование и источники —
`docs/2026-10-18-procedure-margin-research.md`. Код не менялся.

## 1. Цель и границы

Владелец видит по каждой услуге за выбранный период: сколько визитов состоялось, сколько
заработано, сколько ушло по каждой статье (материалы, оплата врача, эквайринг, постоянные
расходы, аппараты) и что осталось. Данные о материалах берутся из YClients (техкарты,
списания, поступления), правила оплаты, постоянные расходы и аппараты ведутся в LoyalPro.

В первую версию НЕ входит: полный управленческий P&L салона, центры затрат по кабинетам,
кассовый учёт, расчёт налога на прибыль по правилам НК (минимальный налог, перенос убытков),
продажа косметики (товары «для продажи» — отдельный поток, здесь только расходники),
абонементы как отдельный продукт, изменение чего-либо в YClients (модуль только читает).

## 2. Решения владельца (18.10.2026)

| № | Вопрос | Решение | Следствие в модели |
|---|---|---|---|
| 1 | Налоговый режим | УСН «доходы минус расходы» | налог с оборота в переменных затратах НЕТ; налог УСН показывается ниже операционной прибыли как оценка 15 % от положительной прибыли |
| 2 | Персонал | в штате | на оплату врача начисляется множитель налогов на ФОТ (настройка, по умолчанию 1,30 — взносы 30 %) |
| 3 | Выручка | фактическая, бонусы списываются перед оплатой | выручка визита = стоимость услуг в записи после скидок − списанные бонусы; начисленные бонусы в затраты не идут (иначе двойной счёт) |
| 4 | Нормы расходников | YClients + LoyalPro, недостающие техкарты клиника закроет | источник норм — техкарты YClients; LoyalPro импортирует, показывает дыры, даёт временную норму для услуг без техкарты |
| 5 | Цена материала | последняя закупка | цена единицы = последнее поступление на дату визита; резерв — себестоимость YClients (`actual_cost`), затем ручная цена |
| 6 | Аппараты | список с сайта, цена — рыночная из интернета; насадки — в расходниках | реестр аппаратов с сидом из раздела 12; расходные части не дублируются |
| 7 | Постоянные расходы | в LoyalPro | помесячный бюджет по статьям |
| 8 | Драйвер распределения | «наверное поровну на визит? как правильнее» | по умолчанию ПО МИНУТАМ визита (обоснование в 3.6), «поровну на визит» — переключатель в настройках |
| 9 | Доступ | только владелец | `requireRole('owner')` на всём `/api/economics`, пункт меню `data-roles="owner"` |

## 3. Модель расчёта

Единица расчёта — **строка «запись × услуга»** состоявшегося визита (`records`,
`attendance = 1`, не удалена, `visit_date` в периоде). Запись с несколькими услугами даёт
несколько строк. Все суммы в рублях, две копейки.

### 3.1 Выручка

- `price = services[i].cost_to_pay` (после скидок и акций). Скидка = `first_cost − cost_to_pay`,
  показывается справочно, в затраты не входит.
- `bonus_redeemed` — списанные бонусы по записи (`loyalty_card_transactions`,
  `type='redemption'`, `record_id`), делятся между услугами записи пропорционально `price`.
- `cost_to_pay` в YClients — сумма к оплате ДЕНЬГАМИ: покрытое лояльностью (бонусы-как-скидка,
  абонемент) бывает уже вычтено в ней (Profhilo: cost 26000, cost_to_pay 23400, списано 2600),
  а бывает — нет (cost_to_pay = cost, бонусы — способом оплаты). Поэтому по записи
  `netted = max(0, Σcost − Σcost_to_pay)`, `bonus_in_revenue = max(0, bonus_redeemed − netted)`,
  делится между услугами так же; `revenue = price − bonus_in_revenue_share`. В строке хранятся
  оба поля: `bonus_redeemed` (фактически списано, для показа) и `bonus_in_revenue` (вычтено).
- Абонементный визит (cost_to_pay 0) при этом даёт выручку 0 — расходится с пунктом ниже,
  вопрос владельцу открыт.
- Оплата сертификатом/абонементом/депозитом считается выручкой визита (деньги уже получены
  при продаже); продажи абонементов и сертификатов в выручку услуг не входят.

### 3.2 Материалы

Три величины на строку, в отчёте видны все три:

- `materials_fact` — списания YClients по этой записи и услуге (`goods_transactions`,
  `type_id = 2` «Списание расходников», `record_id`, `service_id`, не удалённые):
  Σ `|amount| × unit_price(good, visit_date)`. Списание с `record_id`, но без `service_id`
  делится между услугами записи пропорционально `price`.
- `materials_norm` — норма: техкарта услуги (раздел 4.3) Σ `amount × unit_price`.
- `materials_used` = `materials_fact`, если по записи есть хотя бы одно списание, иначе
  `materials_norm` с флагом `estimated = true`; нет ни списаний, ни нормы → 0 и флаг
  `no_materials_data`.

`unit_price(good, date)`:
1. цена последнего поступления этого товара с датой ≤ `date`: `cost / amount` транзакции
   прихода (`type_id = 3`), то есть с учётом скидки поставщика (проверено: приход 10 шт по
   11 630 ₽ со скидкой 5 % даёт `cost` 110 485 → 11 048,5 ₽/шт);
2. иначе ручная цена из `goods_price_overrides`;
3. иначе `unit_actual_cost` из каталога YClients;
4. иначе 0 и флаг `no_price` на строке (в отчёте — предупреждение «товар без цены»).

Единицы: списание идёт в единице списания (`service_unit`: мл, ед., мг), приход — в
единице продажи (`unit`: флакон, упаковка); пересчёт через `unit_equals` каталога
(`unit_actual_cost = actual_cost / unit_equals`). Цена поступления всегда приводится к
единице списания делением на `unit_equals`.
Исключение (найдено на данных сентября 2026, ~943 из 2611 списаний): YClients хранит
`amount` части СПИСАНИЙ в единице продажи (0.1667 упаковки ватных дисков), хотя
`operation_unit_type=2`, а `cost_per_unit` — цена единицы списания. `price.writeoffQty`:
если `|amount|×unit_equals×cost_per_unit` сходится с `cost` (допуск max(0.05 ₽, 1 %)), а
`|amount|×cost_per_unit` — нет, количество умножается на `unit_equals`; иначе как есть.

Справочно хранится и `materials_yc_cost` — Σ `cost` списаний как посчитал YClients (средняя
себестоимость); расхождение с `materials_fact` — отдельная колонка в детализации.

### 3.3 Оплата врача

Правило выбирается по приоритету: услуга → категория услуги → сотрудник целиком → правило
салона по умолчанию; у каждого правила период действия. Поля: `percent`, `base`
(`gross` — от выручки, `net_of_materials` — от выручки минус `materials_used`),
`fixed_per_visit`. Для сотрудника без правила — оплата 0 и флаг `no_pay_rule`.

- `pay_base = revenue` или `revenue − materials_used`; настройка салона
  `pay_base_includes_bonuses` (по умолчанию `false`): при `true` базой служит `price`
  (до вычета бонусов) — так считают схемы YClients, если в них бонусы не исключены.
- `doctor_pay = (pay_base × percent / 100 + fixed_per_visit)`.
- `doctor_cost = doctor_pay × payroll_multiplier` (настройка, по умолчанию 1,30; подсказка
  в UI: если процент «на руки», ставить 1,494 = 1,30 / 0,87).

Сверка (этап 3): Σ `doctor_pay` по сотруднику за месяц против `salary` из
`GET /company/{cid}/salary/period/staff/{staff_id}/` — расхождение показывается в
«Оплате труда», ничего не пересчитывает.

### 3.4 Эквайринг

Оплаты записи — `revenue_operations` (`category='services'`, `yclients_record_id`), у каждой
касса (`account_title`). Настройка `acquiring` — процент по каждой кассе салона (список касс
берётся из `revenue_operations` за 12 месяцев; по умолчанию 0; подсказка: НДС 22 % на
комиссию по картам с 2026 года закладывать в процент). `acquiring_cost = Σ amount × pct/100`,
распределяется между услугами записи пропорционально `price`.
Нет привязанных оплат (сегодня 29 % визитов) → `revenue × avg_rate`, где `avg_rate` —
средняя доля эквайринга по визитам периода с привязанными оплатами; флаг `acquiring_estimated`.

### 3.5 Маржинальная прибыль

`contribution = revenue − materials_used − doctor_cost − acquiring_cost`,
`contribution_pct = contribution / revenue`. Это главная колонка отчёта: все слагаемые —
факты или нормы без модельных допущений.

### 3.6 Постоянные расходы и аппараты

Месячный бюджет `fixed_costs` (аренда, администраторы с налогами, уборка, коммунальные, ПО и
подписки, маркетинг, бухгалтерия, медотходы и стерилизация, прочее). Период отчёта может
накрывать несколько месяцев и части месяцев: сумма постоянных расходов периода = Σ по
месяцам `amount_month × доля дней месяца, попавших в период`.

Драйвер (`allocation_driver`):
- `minutes` (по умолчанию) — `rate = fixed_period / Σ minutes` всех строк периода;
  `overhead = minutes_row × rate`. Минуты строки — `seance_length` записи, делённый между
  услугами записи пропорционально длительности услуги в каталоге YClients (нет длительности —
  поровну). ЗАЧЕМ по минутам: аренду, администратора и уборку потребляет время кабинета;
  «поровну на визит» нагружает 15-минутную ботулинотерапию так же, как 90-минутную чистку, и
  делает короткие дорогие процедуры «прибыльнее», чем они есть. Это и есть TDABC-подход из
  исследования.
- `visits` — `rate = fixed_period / число строк периода`; `overhead = rate`.

Справочно рядом — ставка при плановой мощности: `fixed_period / Σ staff_schedule.work_minutes`
за период (сколько стоила бы минута при полной загрузке графика); разница с фактической
ставкой — цена простоя, она показывается на уровне периода, а не услуги.

Аппараты (`equipment`): `monthly_cost = (purchase_price × (1 − residual_pct/100)) /
useful_life_months + maintenance_monthly`; аппарат привязан к списку услуг (`service_ids`);
стоимость периода распределяется тем же драйвером, но только между строками его услуг.
Аппарат без привязки и услуга без аппарата — ноль. Расходные части (насадки, картриджи) —
в техкартах YClients, в реестре не дублируются; замена ламп и ТО — в `maintenance_monthly`.

`operating_profit = contribution − overhead − equipment_cost`;
`usn_estimate = 15 % × max(operating_profit, 0)` (оценка; настоящий налог — по салону в
целом, за периодом учёта модуль не следит); `profit_per_hour = contribution / hours_row`.

### 3.7 Агрегация

Отчёт по услуге за период: `visits`, `revenue`, `discounts`, `bonus_redeemed`,
`materials_used` (+ сколько из них оценка), `materials_norm`, `doctor_cost`, `acquiring_cost`,
`contribution`, `contribution_pct`, `overhead`, `equipment_cost`, `operating_profit`,
`operating_pct`, `usn_estimate`, `hours`, `profit_per_hour`, флаги покрытия (`% визитов со
списаниями`, `есть ли техкарта`, `есть ли правило оплаты`, `товары без цены`). Те же суммы
доступны в разрезе «услуга × сотрудник» и по визитам (детализация).

## 4. Источники данных и синхронизация

### 4.1 Товарные транзакции (списания, приходы, продажи, списания-потери)

- Вебхуки `goods_operations_consumable | receipt | sale | stolen` (`create | update |
  delete`) — новый обработчик в `routes/webhook.js` → `services/economics/goods-events.js`:
  `parseGoodsOperation(payload)` (чистая) + `upsertGoodsTransaction`. `delete` ставит
  `deleted_at`, строка не удаляется (форензика). Поля клиента (`client.name/phone`) в таблицу
  НЕ пишутся. Ответ 200 вебхуку уходит до обработки, как у остальных ресурсов.
- Ночная сверка `reconcileGoodsTransactions` — `GET /storages/transactions/{cid}?changed_after
  =<−2 дня>` с пагинацией `count=100` до пустой страницы (тот же приём, что
  `yclients-reconcile`): потерянные вебхуки и правки задним числом. Транзакции, которых больше
  нет в выдаче за свой день, помечаются удалёнными только разовым скриптом сверки, не кроном.
- Догон истории — `scripts/economics-backfill-goods.js --from=2025-10-01` помесячно, пауза
  между страницами, повтор на 429 через `withRateLimitRetry`; идемпотентен (UNIQUE по
  `yclients_txn_id`). Нужен один раз при включении: цены поступлений до 21.03.2026 у нас нет.

### 4.2 Каталог товаров и цены

- `yclients_goods_catalog` расширяется колонками `unit`, `service_unit`, `unit_equals`,
  `actual_cost`, `unit_actual_cost`, `stock` (jsonb по складам), `last_receipt_price`,
  `last_receipt_at`. Заполняется ночью из `GET /goods/{cid}?count=100&page=N` (5 запросов на
  467 товаров; НЕ через `category_id`, см. memory `ref_yclients_goods_pagination`). Существующий
  синк косметики (`yclients-goods-catalog.js`) не трогается — он про дерево «Уходов».
- `last_receipt_price` пересчитывается при каждом приходе (вебхук) и при сверке:
  `cost / amount / unit_equals` последнего по дате прихода.
- История цен не отдельная таблица: читается из `goods_transactions` (`type_id = 3`).

### 4.3 Техкарты и нормы

- Импорт `GET /technological_cards/{cid}/?count=100&page=N` → `tech_cards`
  (`yc_card_id`, `title`, `items` jsonb `[{good_id, amount, unit, price_at_sync}]`), ночью.
- Привязка техкарты к услуге (bulk-ручки у YClients нет, только по паре «сотрудник+услуга»):
  1. **обучение по факту** — ночью для состоявшихся вчера записей со списаниями зовётся
     `GET /technological_cards/record_consumables/{cid}/{record_id}/` (≈10–15 вызовов в
     сутки); пара `service_id → technological_cards[].id` пишется в `service_tech_cards`
     с `source='learned'`;
  2. **по запросу** — на вкладке «Техкарты» кнопка «Найти в YClients» для услуги без
     привязки: `default_for_staff_and_service/{cid}/{staff}/{service}` по каждому исполнителю
     услуги (≤ 4 вызова), `source='lookup'`;
  3. **вручную** — владелец выбирает техкарту из импортированных (`source='manual'`,
     главнее остальных) или заводит норму LoyalPro (`tech_cards.source='manual'`, редактор
     «товар из каталога + количество + единица»).
  Подсказка совпадений по названию (техкарта «Revi Silk 2 ml» ↔ услуга «Revi Silk 2 ml»)
  показывается, но без подтверждения не применяется.
- Покрытие: список услуг с визитами за период и у каждой — есть ли техкарта, доля визитов
  со списаниями. Это рабочий список для клиники «что заполнить в YClients».

### 4.4 Записи, оплаты, бонусы, график

Уже есть: `records` (услуги, `seance_length`, сотрудник, `attendance`), `revenue_operations`
(оплаты по кассам), `loyalty_card_transactions` (списания бонусов по записи),
`staff_schedule.work_minutes` (мощность), каталог услуг с длительностью (`ycGetServiceCatalog`,
кэш). Новых синков не нужно.

### 4.5 Лимиты YClients

Квота минутная и общая с Милой и «Заботой». Ночной проход модуля: ≤ 5 (каталог) + ≤ 3
(техкарты) + ≤ 10 (сверка транзакций) + ≤ 15 (обучение привязок) ≈ 33 запроса, крон
`5 5 * * *` мск — после сверки записей `35 4` и чистки `40 4`. Догон истории — только
ручным скриптом.

Все таблицы с `salon_id`; строки удалённого салона каскадом. Расчёт в v1 — на лету по

материализации; если отчёт за год превысит 1 с на живом EXPLAIN — завести таблицу
рассчитанных строк (вне scope v1).

## 6. Модули бэкенда (`backend/services/economics/`)

Чистые модули (без БД и HTTP, jest):
- `goods-events.js` — `parseGoodsOperation(payload)` → строка таблицы или `null`
  (неизвестный ресурс/битые поля), вырезание PII.
- `price.js` — `unitPriceAsOf(receipts, overrides, catalogRow, date)` по правилу 3.2.
- `pay-rules.js` — `pickRule(rules, {staffId, serviceId, categoryId, date})`,
  `doctorPay(row, rule, settings)`.
- `allocation.js` — `splitMinutes(seanceLength, serviceDurations)`,
  `periodFixedCosts(fixedCosts, from, to)`, `rate(driver, fixedSum, rows)`,
  `equipmentMonthly(eq)`, `allocate(rows, driver, sum, filterServiceIds)`.
- `calc.js` — `computeRow(input)` (3.1–3.6 для одной строки) и `aggregate(rows)` (3.7).
- `tech-cards.js` — `normCost(card, priceFn, date)`, `suggestLinks(cards, services)`.

IO-модули:
- `store.js` — SQL: загрузка строк периода (записи × услуги, списания, оплаты, бонусы,
  поступления, правила, бюджет, аппараты); SQL экспортируется ради живого EXPLAIN
  (`scripts/economics-explain.js` с реальными bound-параметрами — ГОТЧА проекта: EXPLAIN с
  литералами не ловит вывод типов параметров).
- `sync.js` — каталог, техкарты, сверка транзакций, обучение привязок; `runNightly(salon)`;
  `closeStale`-семантики нет, прогон идемпотентен.
- `report.js` — склейка store → calc → aggregate; кэш результата 60 с на ключ
  `salon+from+to` (один отчёт открывают несколько раз подряд).
- `routes/economics.js` — `/api/economics`, `requireRole('owner')`, период через тот же
  `resolvePeriod`, что у дашборда (кап 731 день).

## 9. Крон, флаги, ошибки

- Крон `5 5 * * *` мск: `sync.runNightly` для активных салонов с токенами. Ошибка одного шага
  — WARN и дальше; три ночи подряд без успеха — WARN «экономика: синк не проходит».
- Вебхуки `goods_operations_*`: исключение в обработчике логируется, 200 уже отдан; потерянное
  добирает ночная сверка.
- `ECONOMICS_SYNC=false` гасит крон (вебхуки и ручной `POST /sync` работают).
- Отчёт никогда не падает из-за отсутствия справочников: пустые правила/бюджет/аппараты дают
  нули и флаги, а не ошибку.

## 13. Риски и допущения

- Покрытие списаниями 53 % — до заполнения техкарт колонка «материалы» у части услуг —
  оценка по норме, и это видно в UI; услуги без нормы честно показывают «нет данных».
- Привязка техкарт учится по фактам, поэтому у услуг без визитов она появится только по
  запросу или вручную.
- `/storages/transactions` раньше ~2025 года может не отдать поступления; старые товары
  живут на `unit_actual_cost`/ручной цене.
- 29 % визитов без привязанных оплат — эквайринг у них оценочный.
- Налог УСН по услуге — оценка; минимальный налог 1 % и учёт расходов по правилам НК вне
  модуля.
- Цены аппаратов из интернета — ориентир; амортизация должна считаться от фактической цены
  покупки, которую вводит владелец.
