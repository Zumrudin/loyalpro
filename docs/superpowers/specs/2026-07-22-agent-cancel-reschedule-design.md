# Мила: отмена и перенос записи — дизайн

Дата: 2026-07-22
Ветка: feat/agent-service-filter

## Цель

Добавить ИИ-администратору «Мила» два новых сценария:

1. **Отмена записи.** Когда клиент просит отменить, Мила сначала вежливо
   предлагает перенести запись на другой день, чтобы не потерять её. Если клиент
   отказывается — отменяет.
2. **Перенос записи.** Когда клиент просит перенести, Мила сначала проверяет
   его записи; если клиент не указал явно какую именно — уточняет; затем уточняет
   дату переноса и предлагает слоты времени.

## Архитектурный принцип

Разговорный поток (предложить перенос до отмены, уточнить какую запись, спросить
дату, показать слоты) — **промпт-управляемый**, как уже сделан consent-gate для
`create_booking`. Инструменты остаются детерминированными действиями. Это
консистентно с текущей архитектурой агента (`services/agent/`) и покрывается
тестами системного промпта. Машину состояний в оркестраторе не вводим.

## Ключевые бизнес-решения

- **Механизм отмены — не удаление, а модификация записи** (`PUT /record`):
  - `attendance = -1` (статус «Клиент не пришёл»),
  - `seance_length = 300` (5 минут) — чтобы освободить место в графике мастера,
  - в список услуг записи добавляется услуга **«Запрет на отправку»** — при её
    наличии на записи YClients перестаёт слать уведомления по ней.
- **Услуга «Запрет на отправку»** ищется в каталоге (`list_services`) **по
  названию** (нормализованное совпадение). Отдельной настройки/поля не заводим.
- **Список записей клиента — живой запрос в YClients** (`GET /records?client_id=`),
  не локальная таблица `records` — для отмены/переноса критична актуальность.

## Новые инструменты (`services/agent/tools/`)

Каждый экспортирует `{ schema, run }`, регистрируется в `tools/index.js`.

### 1. `list_client_bookings`
Живой список **будущих** записей идентифицированного клиента.
- Резолвит `yclients_client_id` клиента: телефон из вебхука (`ctx.clientPhone`) →
  таблица `clients` (расширить выборку идентификации, чтобы отдавать
  `yclients_client_id`).
- `GET /records/{company_id}?client_id=…`; фильтр: только будущие
  (`datetime > now`) и не отменённые (`attendance != -1`).
- Возвращает массив: `record_id`, `datetime`, названия услуг, имя мастера
  (`staff_yc_id`).
- Если телефон неизвестен / клиент не найден / записей нет → пустой результат с
  причиной. Промпт реагирует: попросить телефон / предложить создать новую запись.

### 2. `cancel_booking`
Отмена = компаунд-модификация записи.
- Вход: `record_id`. **Проверка принадлежности** — record_id обязан быть в списке
  записей этого клиента (защита от отмены чужой записи).
- `GET /record/{id}` → текущие `staff_id`, `services`, `datetime`.
- Ищет в `list_services` услугу «Запрет на отправку» по нормализованному названию.
- `PUT /record/{company_id}/{record_id}`: `attendance = -1`, `seance_length = 300`,
  `services = существующие + { id: <«Запрет на отправку»> }`, staff/datetime без
  изменений.
- Если услуга «Запрет на отправку» не найдена в каталоге → отмена всё равно
  проходит (attendance −1 + 5 мин), но в результате инструмента ставится
  предупреждение (уведомления могли не заглушиться).
- Идемпотентность повторной отмены (запись уже `attendance = -1`) → без ошибки.
- Пишет `agent_events` kind `booking_cancelled`.

### 3. `reschedule_booking`
Перенос на новое время.
- Вход: `record_id`, новое `datetime`, опционально новый `staff_yc_id` (по
  умолчанию тот же мастер). Проверка принадлежности record_id клиенту.
- `PUT /record/{company_id}/{record_id}` с новым `datetime`; те же услуги, мастер,
  длительность (если staff не меняется).
- Пишет `agent_events` kind `booking_rescheduled`.

Оба пишущих инструмента (`cancel_booking`, `reschedule_booking`) добавляются в
`SIDE_EFFECT_TOOLS` (`orchestrator.js:20`), чтобы их результаты не терялись при
регенерации.

## YClients-хелперы (`services/yclients-records.js`)

- `ycGetClientRecords(salon, clientId)` — `GET /records/{company_id}?client_id=`.
- `ycGetRecord(salon, recordId)` — `GET /record/{company_id}/{record_id}`.
- `ycUpdateRecord(salon, recordId, body)` — общий `PUT /record/{company_id}/{record_id}`
  (существующий `updateAttendance` — частный случай, можно оставить или выразить
  через новый хелпер).

Все — через `ycHeaders(salon)`, с тем же swap на
`config.YCLIENTS_INTEGRATION_USER_TOKEN` и ретраем на 421, как в `ycCreateRecord`
(`services/yclients-booking.js`).

## Системный промпт (`services/agent/system-prompt.js`)

Новый **Сценарий 4: отмена / перенос**.

**Общие гейты (зеркало `create_booking`):**
- **Гейт личности** — отмена/перенос только для идентифицированного клиента
  (телефон известен). Если телефон неизвестен → попросить телефон или эскалация.
- **Гейт согласия** — перед вызовом `cancel_booking`/`reschedule_booking`
  подтвердить намерение словами.
- **⛔ Правило факта** — сообщать «отменила»/«перенесла» **только** после успешного
  ответа инструмента.

**Поток «клиент просит отменить»:**
1. Мила сначала вежливо предлагает перенести на другой день.
2. Если клиент отказывается → `cancel_booking`.

**Поток «клиент просит перенести»:**
1. `list_client_bookings`.
2. Если записей несколько и клиент не указал явно какую → уточнить, какую.
3. Уточнить дату переноса.
4. Показать слоты (`get_available_slots` для мастера+даты).
5. `reschedule_booking`.

**Крайние случаи:** записей нет → сказать вежливо, предложить создать новую; одна
запись → не переспрашивать.

## Обработка ошибок

- Чужая запись (record_id не в списке клиента) → инструмент отказывает.
- Только будущие записи; прошедшие не трогаем.
- YClients 421 → ретрай (как в `ycCreateRecord`).
- Идемпотентность повторной отмены (уже `attendance = -1`) → без ошибки.
