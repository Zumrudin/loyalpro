# Устойчивость агента к сбоям aitunnel: fallback на Claude + сохранение созданной записи

Дата: 2026-07-24
Ветка: `feat/agent-provider-fallback`

## Проблема

Инцидент 2026-07-24, диалог `79200255591`: клиент записал супругу на лазерную
эпиляцию, `create_booking` **успешно** создал запись (record_id 1864113480,
27.07 19:30). Через ~12 с диалог ушёл на оператора с сообщением
«Секунду, уточняю детали — передаю ваш вопрос администратору…».

Хронология из `agent_events`:
- `16:27:24` `booking_created` — запись реально создана в YClients.
- `16:27:36` `escalated`, reason: `сбой обработки: 421 Не удалось посчитать
  стоимость запроса, в ответе от провайдера отсутствует поле "usage"`.

### Корневая причина

aitunnel — биллинг-прокси. Он ищет в ответе Gemini поле `usage`, чтобы списать
оплату. Когда Gemini не кладёт `usageMetadata` (наблюдается на ответах после
tool-call — оба наших 421-инцидента были на добивочном вызове **после**
`create_booking`), прокси рубит валидную генерацию статусом **HTTP 421**.

Механика хода (`orchestrator.js`): в одном ходе модель сначала вызывает
`create_booking`, затем делается **ещё один** вызов LLM, чтобы прочитать
результат инструмента и написать клиенту «Готово, записала…». Этот второй вызов
получил 421, ретрай (`providers/aitunnel.js`, 5 попыток за ~4 с) не помог —
прокси флапал подряд. Исключение всплыло в catch-all диспетчера
(`dispatcher.js:110`) → `handOverSilently` → клиенту ушла страховочная фраза, а
статус стал `escalated`. Запись при этом **уже существовала**.

### Масштаб (из логов, all-time)

Терминальные сбои `AgentDispatcher`:

| Причина | Кол-во |
|---|---|
| `provider timeout` (aitunnel > 60 с) | 136 |
| `db down` | 68 |
| `421 … отсутствует поле usage` | 4 |

421 редка, но особенно болезненна: бьёт **после** оформленной брони. Fallback
заодно закрывает и таймауты — самую частую причину.

## Цели

1. Персистентная 421 (и таймаут/5xx) от Gemini не должна доходить до клиента,
   если запрос можно переиграть через надёжную модель.
2. Уже созданная запись не должна оборачиваться ложной эскалацией «передаю
   администратору» — клиент должен получить правдивое подтверждение.

Не-цели: чинить сам прокси aitunnel (чужой сервис); переводить основную модель
агента на Claude (отдельное решение, принимается позже по логам fallback'а).

## Решение

Две части, выкатываются вместе.

### Часть 1 — fallback-провайдер на Claude при транзиентном сбое

Живёт в `services/agent/providers/aitunnel.js`. aitunnel OpenAI-совместим и
отдаёт Claude тем же ключом/эндпоинтом (память `aitunnel_claude_upgrade`,
tool-calling у Claude проверен live) — значит fallback это тот же `createMessage`
с другим `model`; конвертация схем/ответа не нужна.

Поток в `createMessage`:
1. Основная модель (`AITUNNEL_CHAT_MODEL`, `gemini-3.1-flash-lite`) через
   существующий `createWithRetry` (5 попыток, ~4 с бэкоффа).
2. Если бросает **транзиентную** ошибку (`isTransient`: 421/usage, 429, 5xx,
   таймаут, сетевые) **и** задан `AITUNNEL_FALLBACK_MODEL` **и** это не та же
   модель — переиграть **тот же запрос** через fallback-модель
   (`claude-sonnet-4.6`, см. выбор ниже), **1 попытка** (Claude надёжен; полные
   5 не нужны) со
   **своим коротким таймаутом** (`AITUNNEL_FALLBACK_TIMEOUT_MS`, 30 000), чтобы
   не копить 60+60 с.
3. Fallback ответил → отдаём его ответ как обычный. Fallback тоже упал →
   пробрасываем (диспетчер эскалирует — реально лёг весь aitunnel).

Безопасность переигровки: 421 приходит на ответ, tool_calls из упавшего вызова
мы не получили — ничего не выполнилось. Гонки `create_booking` защищены
идемпотентным ключом в `booking.js`.

Наблюдаемость: `logger.warn('aitunnel fallback → <model> after <error>')` в момент
переключения — чтобы по фактам решать про полный переход на Claude.

### Часть 2 — не терять уже созданную запись

Живёт в `orchestrator.js` (`runDialog`).

1. Когда `WRITE_TOOL` отработал успешно, запоминаем `lastWrite`
   (`{ tool, datetime, clientName }`) из input инструмента.
2. Оборачиваем вызовы провайдера (основной в цикле tool-use **и** добивочный)
   в try/catch.
3. Провайдер бросил **после** успешной записи (`writeSucceeded === true`):
   не роняем ход — формируем **детерминированное подтверждение** из `lastWrite`
   и возвращаем его как единственную реплику. **Без эскалации** (решение
   пользователя): статус диалога остаётся `bot`, при следующем сообщении бот
   продолжит (fallback к тому времени, вероятно, снова живой).
4. Провайдер бросил, а записи в ходе не было (`writeSucceeded === false`):
   пробрасываем как раньше → диспетчер эскалирует (честно, ничего не сделано).

С fallback'ом из части 1 в п.3 мы попадаем только если **и Claude лёг**, т.е.
полный отказ aitunnel — тогда подтверждение из кэша ровно то, что нужно.

Текст подтверждения — детерминированный, без LLM:
- `create_booking`: `datetime` форматируется по Москве через `Intl` (ru-RU),
  `«Готово! Записала <имя|вас> на 27 июля в 19:30 ✅ Будем ждать 🤍»`.
- прочие write-инструменты: `«Готово, всё оформила ✅»`.

Имена мастера/услуги не реконструируем (в input только YClients-ID) — они уже
назывались клиенту в диалоге; дата+время достаточны и, главное, правдивы.

## Контракт между слоями

`orchestrator.runDialog` возвращает новое поле для части 2:
`degradedAfterWrite: true` + `replies: [<детерминированное подтверждение>]`,
`escalated: false`.

`dispatcher.process`: при `degradedAfterWrite` — просто отправляет `replies`
(это уже правдивое подтверждение), **не** зовёт `handOverSilently`,
**не** шлёт fallback-фразу. Фактически совпадает с обычной веткой «есть реплики»,
но флаг делает намерение явным и защищает от будущих правок логики ветвления.

## Конфиг (config.js)

- `AITUNNEL_FALLBACK_MODEL` — default `claude-sonnet-4.6`; пустая строка =
  fallback выключен.
- `AITUNNEL_FALLBACK_TIMEOUT_MS` — default `30000`.

### Выбор fallback-модели

Живой пилот (память `aitunnel_claude_upgrade`, 2026-07-22) на booking-флоу:
- `claude-haiku-4.5` — **ненадёжен для критичного booking**: галлюцинировал
  tool-id, один раз заявил «готово, перенесено» **не вызвав** инструмент
  (ложный успех).
- `claude-sonnet-4.6` — аккуратен: не выдумывал успех, переспрашивал при
  неоднозначности, без битых id.

Fallback может попасть на критичный вызов (модель решает вызвать
`create_booking`), а срабатывает редко (только когда Gemini флапает) — цена
Sonnet (600/3000 ₽ за 1M против 200/1000 у Haiku) в агрегате пренебрежима.
Поэтому default = `claude-sonnet-4.6`. Existing guard против ложного успеха
(`COMPLETION_CLAIM` + `writeSucceeded`) остаётся второй линией.

## Тесты

`providers/aitunnel` (unit, мок клиента):
- 421 на основной модели → вызван fallback-model, возвращён его ответ.
- `AITUNNEL_FALLBACK_MODEL` пуст → поведение как раньше, ошибка пробрасывается.
- не-транзиентная ошибка (напр. 400) → fallback НЕ зовётся.
- основная ответила с первой попытки → fallback не трогаем.

`orchestrator` (unit, мок провайдера):
- write успешен, следующий вызов провайдера бросает → `degradedAfterWrite`,
  реплика = детерминированное подтверждение с датой/временем, `escalated:false`.
- провайдер бросает без успешной записи → исключение пробрасывается (эскалация).

`dispatcher` (unit):
- `degradedAfterWrite` → отправлены `replies`, `escalate` НЕ вызван.

Регрессия: полный прогон `jest` (в т.ч. `agent-system-prompt`, память
`feedback_agent_prompt_test_guarded`).

## Затронутые файлы

- `backend/config.js` — два новых env-параметра.
- `backend/services/agent/providers/aitunnel.js` — fallback-модель.
- `backend/services/agent/orchestrator.js` — guard `degradedAfterWrite` +

- `backend/services/agent/dispatcher.js` — ветка `degradedAfterWrite`.
- тесты рядом с каждым модулем.
