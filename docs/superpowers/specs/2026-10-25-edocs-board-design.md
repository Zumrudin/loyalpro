# «Документы»: дашборд подписей, страница пациента, анкета и автоматизация — дизайн

Дата: 2026-10-25. Статус: макет одобрен владельцем 25.10.2026, решения по открытым вопросам — раздел 2.
Основа — модуль «Документы» (F.Doc) по `docs/superpowers/specs/2026-10-24-fdoc-esign-design.md`,
он на деве (merge `c054ab7` в `feat/notifications-own-module`), на проде нет; F.Doc на деве НЕ подключён
(`edoc_settings.enabled=false`, нет `corp_id`, ни одного комплекта, один шаблон договора).
Макет: PNG рядом (`2026-10-25-edocs-board-mockup/`), интерактивная версия —
https://dev.zumrudin.ru/peri-concepts/loyalpro-documents-20261025-bf513bb7/ (вымышленные данные).

## 1. Цель и границы

Администратор открывает «📄 Документы» и сразу видит, у кого из записанных пациентов не хватает
документов: карточки пациентов подсвечены цветом, зелёная карточка — всё обязательное подписано.
Клик по карточке открывает страницу пациента: данные для документов (свёрнуты, красный блок пульсирует,
пока не хватает обязательных полей), карточки документов с выбором на подпись и ручной правкой
каждого (акт — строки и суммы). Чтобы паспорт не вбивать на ресепшене, пациент заполняет данные сам
по ссылке (анкета). Рутинные отправки можно поручить автоматике (по умолчанию выключена).

Входит:
- дашборд по записям (Сегодня / Завтра / Неделя / Незакрытые) и вкладка «Вся база»;
- страница пациента вместо нынешнего мастера «Оформить»;
- отметка «Подписано на бумаге» со сканом;
- анкета пациента: публичная страница по ссылке (мессенджер или QR на экране администратора);
- автоматизация: договор и согласие перед визитом (или анкета, если данных не хватает), акт после
  оплаты, повтор неподписанной ссылки;
- автонумерация договоров;
- быстрое обновление статусов подписи.

Не входит: электронное ИДС (по-прежнему на бумаге — решение 24.10); SMS, кроме тех, что шлёт сам F.Doc;
дубль ссылки подписания F.Doc в мессенджер (у F.Doc нет API, отдающего ссылку пациента, — только
`permalink/send`, который сам шлёт SMS); загрузка вручную исправленного DOCX вместо шаблона;
запись номера договора и данных обратно в YClients; документы в мобильном приложении; перекраска
в Ivory & Brass (придёт с ребрендингом, решение 7).

## 2. Решения

Владелец (25.10.2026):

| № | Вопрос | Решение |
|---|---|---|
| 1 | Какие документы обязательны | договор и согласие на обработку ПД — до визита, один раз на пациента, бессрочно; акт оказанных услуг — сразу после визита, по каждой записи |
| 2 | Что на дашборде | записи «Сегодня / Завтра / Неделя»; вся база — отдельной вкладкой |
| 3 | Автоматизация | настраивается, по умолчанию выключена; ручная отправка доступна всегда |
| 4 | Бумажные договоры (номер в YClients у 796 карточек) | номер в YClients подписанным договором НЕ считается — каждый пациент один раз подписывает договор и согласие электронно; бумажный документ администратор отмечает вручную «Подписано на бумаге» |
| 5 | Анкета для самозаполнения | делать в этой работе |
| 6 | Номер договора нового пациента | автоматически: следующий после максимального в YClients (сейчас 1998 → 1999), стартовый номер владелец меняет в настройках; в YClients не пишем |
| 7 | Стиль страницы | текущий стиль админки (переменные `base.css`, светлая и тёмная тема); компоновка, цвета состояний и карточки — как в макете |

Решения дизайна (владелец не спрашивался, обоснование рядом):

| № | Решение | Почему |
|---|---|---|
| 8 | Акт нужен, когда у записи `status='arrived'` (attendance 1) И `raw_payload.paid_full='1'` | это и есть «перешла с оплатой в финальный статус»; за 45 дней 479 из 481 состоявшихся записей оплачены полностью; состоявшаяся, но неоплаченная запись показывает «ждём оплату» (акт по ней всё равно можно отправить вручную, как сейчас) |
| 9 | Акты обязательны для визитов начиная с `acts_required_from` (по умолчанию — дата выката) | иначе каждый прошлый визит без акта стал бы красным |
| 10 | Номер договора: свой номер пациента (данные для документов → поле YClients «Номер договора») главнее счётчика | электронная версия того же договора идёт под прежним номером; новый номер — только тем, у кого номера нет; так уже работает предзаполнение |
| 11 | В одном комплекте можно смешивать договор, согласие и акт (одна SMS вместо двух) | `prepare` это уже допускает; состояние документа теперь считается по ВИДУ документа (новая колонка `edoc_documents.kind`), а не по виду комплекта |
| 12 | Автоматические отправки идут от имени сотрудника, выбранного в настройках (его учётка F.Doc) | решение 24.10: у каждого пользователя своя учётка, в журнале F.Doc виден отправитель; без выбранного сотрудника автоматика, которой нужен F.Doc, не включается |
| 13 | Тихие часы и порядок мессенджеров — из настроек «Автоуведомлений» салона (`notification_settings.quiet_from/quiet_to`, `default_channels`, `prefer_last_channel`; дефолт 21:00–09:00) | одно место на салон; автоматика в тихие часы ждёт, ручные отправки — без ограничений |
| 14 | Дашборд, страница пациента, отметки «на бумаге» и анкета работают при выключенном модуле и неподключённом F.Doc; блокируются только электронная отправка и распознавание паспорта | клиника начинает учёт бумажных документов и сбор данных до подключения F.Doc; так же устроен нынешний мастер |
| 15 | Обновление: фронт перечитывает дашборд раз в 20 с, страницу пациента — раз в 10 с, пока что-то ждёт подписи или анкеты; бэкенд перечитывает в F.Doc комплекты, отправленные за последние 2 часа, раз в минуту (было — раз в 5 минут) | пациент подписывает у стойки — карточка должна позеленеть за ~1 минуту, а не за 5; вебхуки F.Doc ещё не подписаны (нужна регистрация IP) |
| 16 | Пульсирует только иконка блока данных пациента, при `prefers-reduced-motion` анимация выключена | прямая просьба владельца; план айдентики Ivory & Brass запрещает пульсацию — расхождение согласовать при ребрендинге |
| 17 | Безопасность дева: env `EDOCS_TEST_PHONES` — если задан, ЛЮБЫЕ отправки пациентам из модуля (ручные и автоматические, комплекты F.Doc, повторы ссылок, анкеты в мессенджер) уходят только на эти номера; на деве `79200255591`, на проде не задан | дев получает реальные вебхуки клиники и держит боевые аккаунты мессенджеров — включённая на деве автоматика написала бы живым пациентам; для F.Doc-демо уже есть такой же `EDOCS_DEMO_PHONES` |

## 3. Состояния документов и цвет карточки

Вся логика — в чистом модуле `services/edocs/board.js` (без БД и сети, исчерпывающие jest-тесты).
Фронт ничего не вычисляет — только рисует ответ сервера: одно правило, одно место.

### 3.1 Обязательные виды

- `contract`, `consent_pd` — до визита; `act` — после оплаченного визита (решение 8).
- Вид обязателен, только если у салона есть активный шаблон этого вида. Нет шаблона — вид не учитывается,
  в шапке дашборда предупреждение «Не загружен шаблон согласия — карточки его не проверяют»
  (владельцу/администратору — со ссылкой на настройки). Нет ни одного обязательного вида с шаблоном —
  карточки серые «шаблоны не настроены».

### 3.2 Состояние вида у пациента

Источник — комплекты пациента и их документы с `kind`. Для договора и согласия — любые комплекты
пациента; для акта — комплекты с `record_id` этой записи.

| Состояние | Когда | Текст на плитке |
|---|---|---|
| `signed` | есть комплект `signed` или `paper` с документом вида | «✓ 03.07.2025» / «✓ бумага» |
| `pending` | иначе последний комплект с документом вида — `sent` (или `draft` без ошибки моложе 5 минут — отправка идёт) | «отправлен 12 мин» |
| `problem` | последний — `error` или `draft` с `last_error` | «ошибка F.Doc» / «не ушло» |
| `lapsed` | последний — `declined`, `expired`, `annulled` | «отказ» / «срок истёк» / «аннулирован» |
| `missing` | комплектов с документом вида нет | «нет» |
| `later` | только акт: визит ещё не состоялся | «после визита» |
| `unpaid` | только акт: состоялся, не оплачен | «ждём оплату» |
| `off` | у салона нет активного шаблона вида | «—» |

`signed` побеждает всё (подписанный когда-то договор не портится новым неудачным комплектом).
«Плохие» состояния: `missing`, `lapsed`, `problem`.

### 3.3 Данные пациента

`complete`, если `placeholders.missingFor(identity, нужные шаблоны)` пуст. Нужные шаблоны — активные
шаблоны тех обязательных видов, которые сейчас в «плохом» состоянии (для акта — только если акт нужен).
При включённой автонумерации поле «Номер договора» недостающим не считается (раздел 9). Реквизиты
клиники (`org`) — не про пациента: их нехватка показывается баннером на дашборде, не на карточках.

### 3.4 Карточка = пациент × день

Записи пациента за день (`status` не `deleted`/`no_show`; `deleted` в `raw_payload` тоже отсекается)
сворачиваются в одну карточку: время первой записи, услуги, врач; две и больше записи — «2 визита»
(за 60 дней таких пациенто-дней 17 из 875). Акт считается по каждой записи; на карточке — худший.

Цвет (первое сработавшее правило):

1. **Красный** — акт нужен и в «плохом» состоянии; ИЛИ договор/согласие в «плохом» состоянии, и день
   карточки уже прошёл, или визит сегодня и до начала меньше 2 часов, уже начался или пациент пришёл.
2. **Оранжевый** — договор/согласие в «плохом» состоянии, визит позже.
3. **Синий** — «плохих» нет, но что-то `pending`, или отправлена анкета и данные ещё не получены.
4. **Зелёный** — все нужные сейчас виды `signed` (акт — только если уже нужен).

Подпись (первая подходящая): красный — «Ссылка истекла» / «Пациент отказался» / «Аннулировано»
(`lapsed`), «Не ушло в F.Doc» (`problem`), «Нужно до визита» (визит ещё не начался), «Нет договора
и согласия» / «Нет договора, согласия и акта» (пациент уже пришёл или день прошёл), «Акт не подписан»;
оранжевый — «Нужно до 16:30» (сегодня) / «Нужно до 27.10»; синий — «Ждём подпись» / «Ждём анкету»;
зелёный — «Документы готовы» (до оплаты визита) / «Всё подписано». Формулировки без рода:
«Готова/Готов» не используем. Анкета у пациента (активна, данных ещё нет) переводит «плохие»
договор и согласие из оранжевого в синий «Ждём анкету»; срочный визит остаётся красным.

Предупреждения под плитками: «⏱ первичный · через 40 мин», «нет паспорта и адреса», итог автоматики
(«автоотправка 09:00: анкета ушла в WhatsApp», «автоакт не отправлен: в записи нет врача»).

### 3.5 Главное действие карточки

| Ситуация | Кнопка | Что делает |
|---|---|---|
| договор/согласие «плохие», данных хватает | «Отправить N док.» | подтверждение → `POST /packages` с шаблонами по умолчанию для недостающих видов |
| договор/согласие «плохие», данных не хватает | «Заполнить данные» + ✉ | открыть страницу пациента с раскрытым блоком данных; ✉ — анкета пациенту (раздел 6) |
| акт нужен и «плохой» | «Отправить акт» | диалог: строки и итог акта, «Изменить» → страница пациента, «Отправить» |
| `lapsed` | «Отправить снова» | то же, что первая строка |
| `pending` | «Повторить ссылку» (контур) | `permalink` после подтверждения; недоступна первые 15 минут после отправки |
| анкета ждёт | «Повторить анкету» (контур) | повторная доставка той же ссылки |
| зелёная | — | — |
| модуль выключен / нет своей учётки F.Doc | «Открыть» | страница пациента; подсказка, что отправка заблокирована и почему |

Шаблон по умолчанию для вида — первый активный по `sort_order, id`.

## 4. Дашборд (`#edocs`)

Компоновка — как в макете:
- Шапка: заголовок, сегодняшняя дата, баннеры (модуль выключен / F.Doc не подключён у вас / нет
  шаблона вида / не заполнены реквизиты клиники / не задан ключ шифрования).
- Сводка: кольцо «Готовы: 3 из 10» и четыре плитки (Срочно / До вечера / Ждём подпись / Готово) по
  цветам выбранного периода; клик по плитке — фильтр.
- Переключатель периода со счётчиками: «Сегодня · 10», «Завтра · 14», «Неделя · 63» (сегодня + 6 дней),
  «Незакрытые · N» (прошлые 30 дней, не раньше `acts_required_from`, только не зелёные карточки —
  забытые акты и визиты без договора), «Вся база». Период — в hash (`#edocs/r/week`), F5 его сохраняет.
- Поиск по имени и телефону внутри периода (на «Вся база» — серверный).
- Фильтры-чипы со счётчиками: Все / Нет договора / Нет согласия ПД / Акт не подписан / Ждём подпись /
  Готово.
- Строка автоматики: «договор и согласие — вручную · акт — вручную · повтор через 2 ч — включён»,
  кнопка «⚙ Автоматизация» (владелец, администратор; кассир видит только строку).
- Группы «Требуют действия» (красные, затем оранжевые) / «Ждём пациента» (синие) / «Готово»
  (зелёные), внутри — по времени визита.
- Карточка (раздел 3): инициалы в кружке цвета состояния, имя, «10:30 · Биоревитализация · Пери И.»,
  подпись состояния, три плитки (Договор / Согласие ПД / Акт), предупреждение, подсказка и кнопка.
  Клик по карточке — страница пациента.
- Живое обновление (решение 15) только пока страница видима (`document.visibilityState`); карточка,
  ставшая зелёной, вспыхивает, всплывает тост «Елена В.: договор и согласие подписаны».
- «Вся база»: компактный список пациентов (50 на страницу, по последнему визиту), колонки «Договор»,
  «Согласие», «Незакрытые акты», «Последний визит»; чипы: все / без договора / без согласия /
  незакрытые акты / ждут подписи / всё есть; серверный поиск.
- Пусто / загрузка / ошибка — отдельные состояния; ошибка одного запроса не ломает остальную страницу.
- Телефон (≤ 700 px): плитки сводки 2×2, карточки в одну колонку, переключатель периода прокручивается.

## 5. Страница пациента (`#edocs/c/<clientId>[/<recordId>]`)

Заменяет мастер «Оформить». Прежние адреса `#edocs/new/<id>[/<recordId>]` перенаправляются сюда
(на них ссылаются карточка клиента, «Записи» и закладки).

1. «← Документы» (назад в историю, иначе на дашборд).
2. Шапка: инициалы, ФИО, телефон, ближайший или текущий визит, подпись состояния, четыре полоски
   «Данные · Договор · Согласие · Акт».
3. **Данные пациента** — свёрнутый блок. Красный с пульсирующей иконкой и текстом «не хватает 5
   полей: …», пока данных не хватает для нужных документов (раздел 3.3); зелёный «Данные заполнены»,
   когда хватает. Раскрытие подгружает расшифрованные данные существующим `GET /clients/:id/identity`
   (каждый показ — в журнал, как сейчас), поэтому само открытие страницы паспорт не расшифровывает.
   Внутри: кнопки «📷 Распознать паспорт» (нужен F.Doc), «↻ Подставить из YClients» (существующий
   prefill заполняет только ПУСТЫЕ поля), «✉ Анкета пациенту» (раздел 6); поля по группам (Личные
   данные / Паспорт / Адрес / Договор), недостающие подсвечены, у подставленных — источник; «Сохранить».
4. **Документы** — карточки: по одной на активный шаблон договора и согласия, акт по выбранной записи
   (по умолчанию — последний оплаченный визит без подписанного акта), прочие активные шаблоны,
   «＋ Другой документ». Карточка: состояние (раздел 3.2), галочка выбора (если документ можно
   отправить), 👁 предпросмотр (заполненный DOCX, существующий `/packages/preview`), ✎ правка,
   у подписанного — PDF и «Открыть комплект», у ждущего — «Повторить ссылку» и «Открыть в F.Doc»,
   «📎 На бумаге».
5. **Панель отправки** (липкая снизу): что выбрано, номер для SMS, почему нельзя отправить (нет данных —
   с перечнем полей; модуль выключен; нет учётки F.Doc), кнопки «Подписано на бумаге»,
   «Предпросмотр», «Отправить на подпись». В одном комплекте — не больше одного акта.
6. **Визиты и акты** — визиты с `acts_required_from` за 90 дней и будущие за 30 дней, состояние акта;
   клик выбирает визит для карточки акта.
7. **История** — `edoc_events` пациента (отправки, статусы, анкеты, автоматика, бумага, правки).

Правка:
- **Акт**: строки (галочка, название, количество, цена, сумма), «＋ Строка», «↺ Как в YClients»,
  итог; итог, отличный от записи YClients, подсвечивается предупреждением. Правленые строки уходят
  в `actLines` (как сейчас) и сохраняются снимком в `payload` комплекта — отдельного события нет.
- **Договор**: номер (с автонумерацией — «будет присвоен при отправке: 1999»), дата договора, дата
  документа, предпросмотр. Номер и дата договора — поля данных пациента (сохраняются туда же).
- **Согласие и прочие**: дата документа, предпросмотр.

Обновление (решение 15): страница перечитывает себя раз в 10 с, пока есть ждущий комплект или
активная анкета.

## 6. Анкета пациента

### 6.1 Поток

- Администратор: «✉ Анкета пациенту» (страница пациента или карточка дашборда) → окно со ссылкой,
  QR-кодом (пациент у стойки сканирует своим телефоном) и кнопкой «Отправить в мессенджер»; галочка
  «Сразу после заполнения отправить документы на подпись» (включена, если F.Doc готов).
- Автоматика перед визитом (раздел 7), когда для недостающих документов не хватает данных.
- Новая анкета гасит прежнюю активную анкету пациента (`revoked`) в той же транзакции, что и вставка новой.
- Просроченные активные анкеты крон автоматизации переводит в `expired` (событие `form_expired`).

### 6.2 Хранение — `edoc_patient_forms`

`id` UUID, `salon_id`, `client_id`, `record_id` (необязательно), `token_hash` (sha256, уникальный),
`status` (`active|submitted|revoked|expired`), `fields` JSONB (какие поля спрашиваем), `kinds` JSONB
(какие документы отправить после заполнения), `send_docs` bool, `sender_user_id` (чьей учёткой F.Doc
распознавать и отправлять), `source` (`manual|auto`), `created_by`, `expires_at` (по умолчанию +7 дней,
настройка), `delivered_via`, `delivered_at`, `opened_at`, `submitted_at`, `submit_attempts`,
`recognize_count`, `consent` JSONB (время, версия текста, адрес политики, хэш IP), `package_id`
(комплект, ушедший после заполнения), `last_error`, `created_at`, `updated_at`. Индексы
`(salon_id, client_id, created_at DESC)` и частичный уникальный `(client_id) WHERE status='active'`.

### 6.3 Ссылка и страница

- `<EDOCS_PUBLIC_URL>/anketa/<token>`; токен — 32 случайных байта base64url, в БД только хэш.
  Для автоматики `EDOCS_PUBLIC_URL` обязателен (нет — анкета автоматикой не создаётся, WARN раз в час);
  при ручном создании без него берётся адрес из запроса.
- Страница `frontend/anketa.html` + `frontend/js/anketa.js`, без зависимостей SPA, мобильная, в цветах
  клиники; вместо логотипа — монограмма из первой буквы названия клиники. Шаги: приветствие по личному имени
  (`resolveGivenName`) и дате визита → «📷 Сфотографировать паспорт» (если F.Doc доступен) или
  ручной ввод → поля → согласие → «Отправить» → «Спасибо! В течение пары минут придёт SMS для подписи
  документов» (или «Данные переданы в клинику», если документы не отправляются).
- Устаревшая, использованная или отозванная ссылка — дружелюбная страница «Ссылка больше не действует,
  попросите клинику прислать новую».

### 6.4 Публичные ручки (без JWT, монтируются рядом с `public-cert-request`)

- `GET /anketa/:token` — HTML; заголовки: строгий CSP (`default-src 'self'`, без встраивания),
  `Cache-Control: no-store`, `Referrer-Policy: no-referrer` (токен в адресе не должен утечь по ссылке
  на политику), `X-Robots-Tag: noindex`.
- `GET /api/public/anketa/:token` → `{clinic, greetingName, visit: {date, time} | null, fields: [{key,
  label, type, required}], canRecognize, policyUrl, status}`. Существующие данные пациента НЕ отдаются
  (кроме личного имени для приветствия): у кого ссылка, тот не прочитает паспорт.
- `POST /api/public/anketa/:token` — поля + `consent: true`. Проверка — та же `identity.validateIdentity`;
  обязательные поля из `fields` (`required: true`; отчество — нет) должны быть заполнены; телефон из анкеты
  не принимается (номер для SMS F.Doc меняет только клиника; пусто в данных — берётся из карточки
  клиента); слияние: присланные поля перезаписывают данные пациента, остальные сохраняются (читаем
  расшифрованную строку, накладываем, сохраняем целиком — нынешний upsert пишет все колонки);
  `source='patient_form'`. Затем `status='submitted'`, событие `form_submitted` (без ПДн), и если
  `send_docs` — отправка комплекта ФОНОМ под учёткой `sender_user_id` (ответ пациенту не ждёт F.Doc;
  итог — в `package_id`/`last_error` и в журнал).
- `POST /api/public/anketa/:token/photo` — фото паспорта (multer memory, `validateImageBuffer`, `sharp`
  как в нынешнем распознавании) → поля для формы пациента; фото не сохраняется; не больше 3 распознаваний
  на анкету (квота F.Doc).
- Лимиты (`cert-request.makeRateLimiter`, память процесса): GET — 60 за 10 минут на IP; POST — 10 в час
  на анкету и 30 в час на IP; фото — 10 в час на IP. Ошибка лимита — 429 с текстом для человека.
- Журнал: `form_created`, `form_sent`, `form_send_error`, `form_opened` (первое открытие), `form_photo`,
  `form_submitted`, `form_revoked`, `form_expired`; токен не пишется нигде (в логах — id анкеты).

### 6.5 Доставка в мессенджер — `services/edocs/form-delivery.js`

- Каскад как у автоуведомлений: порядок `default_channels` и «сначала мессенджер последней переписки»
  из `notification_settings`, адресаты `notifications/cascade.recipientFor`, переписка
  `notifications/rules.lastConversation`, отправка `messaging/transport.sendMessage`. К следующему
  мессенджеру — только после однозначного отказа (`transport.isDefiniteRejection` или сбой соединения
  до запроса); неоднозначный сбой — стоп (сообщение могло уйти, дубль хуже).
- Своё исходящее помечается ДО отправки: `outgoing-authorship.remember(..., 'system')` — иначе эхо
  читается ответом администратора и ставит Милу на паузу (инцидент 04.08); после — `pendingReplies`
  (Мила видит, на что отвечает пациент) и `persistWhatsappOutgoing` для WhatsApp.
- Текст — шаблон в настройках, плейсхолдеры `{имя}`, `{дата}`, `{время}`, `{ссылка}`; по умолчанию:
  «Здравствуйте, {имя}! Перед визитом в PERI CLINIC {дата} заполните, пожалуйста, данные для договора —
  это займёт 2 минуты: {ссылка}».
- Не доставлено ни одним мессенджером — администратор видит ошибку и может показать QR или скопировать
  ссылку. `EDOCS_TEST_PHONES` (решение 17) проверяется до отправки.

### 7.2 Крон `* * * * *` (мск) — `services/edocs/automation.js`

Один прогон на процесс (флаг «идёт»), салоны по очереди, сбой салона не останавливает остальных.
Каждое действие сначала «застолбляется» строкой журнала `edoc_auto_jobs`
(`INSERT … ON CONFLICT DO NOTHING RETURNING id`, UNIQUE `(salon_id, kind, ref)`) — at-most-once, как
в «Заботе» и уведомлениях: повторов не бывает, неудача остаётся в журнале с причиной, дальше — человек.
В тихие часы действие не застолбляется — его подберёт первый прогон после их окончания.

- **Перед визитом** (`kind='previsit'`, `ref=record_id`): записи `waiting`/`confirmed` с началом в
  ближайшие N часов; у пациента договор или согласие в «плохом» состоянии и нет активной анкеты;
  «первичный» = нет ни одной состоявшейся записи до этой. Данных хватает на ВСЕ недостающие виды →
  один комплект из них; не хватает хотя бы на один → анкета (`send_docs=true`, после заполнения уходят
  все недостающие виды разом) в мессенджер, если включено «отправить анкету»; иначе `skipped: нет данных`.
- **Акт** (`kind='act'`, `ref=record_id`): записи `arrived` + `paid_full='1'`, визит не раньше
  `acts_required_from` и не старше 3 дней, `records.updated_at` старше N минут (момент оплаты отдельно
  не хранится — приближение: последнее изменение записи), по записи нет ни одного комплекта с актом.
  Отказы `prepare` (нет врача, даты, данных) — `failed` с причиной на карточке.
- **Повтор** (`kind='remind'`, `ref=package_id` / `kind='remind_form'`, `ref=form_id`): комплект `sent`
  старше N часов и моложе 3 дней → `permalink` (F.Doc сам шлёт SMS); активная анкета старше N часов →
  повторная доставка той же ссылки.

Для F.Doc-действий нужны: модуль включён, `corp_id`, выбранный сотрудник с рабочей учёткой; иначе эти
шаги салона пропускаются с WARN раз в час. Анкете F.Doc не нужен. Все отправки проходят
`EDOCS_DEMO_PHONES`/`EDOCS_TEST_PHONES`.

## 8. Бумажные документы

- `POST /api/edocs/clients/:id/paper` (multipart): шаблоны (`templateIds[]`), запись для акта, дата
  подписания, необязательный скан (JPG/PNG/PDF до 10 МБ, сигнатура — `validateImageBuffer` и `%PDF`)
  и комментарий. Создаёт комплект `status='paper'`, `source='paper'`, документы с видом; скан —
  в S3 `edocs/<салон>/paper/<комплект>/<uuid>.<ext>`, в `payload.paper` — ключ, тип, размер, дата,
  комментарий; событие `paper`. F.Doc не нужен.
- `GET /api/edocs/packages/:id/scan` → presigned URL на 15 минут.
- Ошибочную отметку владелец или администратор снимает `POST /packages/:id/paper-revoke` (с причиной):
  комплект → `annulled`, событие `paper_revoke`. Кассир отмечает, но не снимает.

## 9. Нумерация договоров

- Таблица `edoc_counters (salon_id, kind, next_value, updated_at)`, PK `(salon_id, kind)`. Строка
  договора создаётся при первом обращении: `next_value` = максимум числовых номеров в YClients
  (`custom_fields['nomer-dogovra']`) и в `client_identity.contract_no` салона + 1 (сейчас 1999).
- Настройки: «Нумеровать договоры автоматически» (по умолчанию вкл, решение 6) и «Следующий номер»
  (владелец может поставить свой; предупреждение, если номер не больше уже выданного).
- Присвоение — при отправке комплекта с договором, если у пациента нет номера (решение 10: сначала поле
  данных, затем номер из YClients). Одной транзакцией: `UPDATE edoc_counters … RETURNING`, запись номера
  (и даты договора, если пусто, = дата документа) в `client_identity` с условием «номер ещё пуст» —
  ДО сборки DOCX; событие `contract_no`. Повтор отправки берёт уже записанный номер — дыр нет.
- Риск: если в YClients продолжат вручную раздавать номера бумажным договорам, номера могут совпасть.
  Клинике — перестать выдавать бумажные номера; владелец видит и правит «Следующий номер».

## 15. Риски

| Риск | Что делаем |
|---|---|
| В первый день почти все карточки красные (решение 4) | ожидаемо: каждый пациент подписывает один раз; «Отправить N док.» в один клик, анкета снимает ввод паспорта |
| Момент оплаты не хранится (автоакт по `updated_at`) | приближение достаточно для задержки «через N минут»; автоакт только по записям не старше 3 дней |
| Номер договора совпал с выданным вручную в YClients | «Следующий номер» правится владельцем; клинике — не выдавать бумажные номера |
| Ссылка анкеты попала к чужому | анкета ничего не показывает, кроме имени; один раз; 7 дней; отзыв; телефон из анкеты не меняется |
| Анкета не дошла до мессенджера (нет аккаунта у пациента) | ошибка видна, QR у стойки и копирование ссылки |
| Квота F.Doc на распознавание с публичной страницы | ≤ 3 на анкету, лимит на IP |
| Пульсация против правил айдентики | согласовать при ребрендинге (решение 16) |
| Цвета и подписи разъедутся между бэкендом и фронтом | считает только `board.js`, фронт рисует ответ |

## 16. Оценка

10–13 рабочих дней: состояния и доска — 2; страница пациента (API + фронт) — 2,5; бумага — 0,5;
нумерация — 0,5; анкета (публичная страница, ручки, доставка, безопасность) — 2,5; автоматизация — 1,5;
дашборд (фронт) — 1,5; тесты, визуальный стенд, живая проверка — 1,5. Электронная отправка, автоакт и
повтор проверяются живьём после подключения F.Doc.
