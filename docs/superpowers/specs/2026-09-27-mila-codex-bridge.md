# Мила: LLM-мост через Codex в Финляндии

Продовая Мила использует `AGENT_PROVIDER=codex-relay`: передаёт только системный
промпт, историю и схемы инструментов на HTTPS-мост. Модель закреплена как
`gpt-6-sol`, вход через существующую подписку ChatGPT. Инструменты, CRM,
tenant-проверки, история и отправка ответов выполняются штатной Милой на проде.
Мост не загружает конфиг приложения, не обращается к БД и не отправляет сообщения.
Тумблер Милы и её списки допуска переключение провайдера не меняет.

## Контракт и защиты

`POST /api/mila-codex/v1/message` принимает `{system, messages, tools}`.
Ответ: `{requestId, model, output:{text, toolCalls:[{name,arguments}]}}`.
Произвольные model/command/env/salon_id верхнего уровня запрещены. Содержимое
диалога передаётся только на stdin Codex, не в shell и не в аргументы процесса.
Каждый запрос — отдельная ephemeral-сессия без native-инструментов Codex.
Caller проверяет модель, requestId, имена и аргументы инструментов против
собственных схем. IDs tool calls формируются на caller и не разделяются между
диалогами. Мост не имеет tenant-owned хранилища: одна серверная интеграция,
авторизация которой не даёт доступа к данным других запросов.

Подпись HMAC-SHA256 связывает метод, фиксированный путь, timestamp, случайный UUID
и точные байты тела. Заголовки `X-Mila-Timestamp`, `X-Mila-Request-Id`,
`X-Mila-Signature`; окно 60 с, повтор UUID отклоняется. Секрет не менее 32 символов,
генерируется случайно, хранится только в приватных environment-файлах серверов.
HTTPS обязателен; редиректы запрещены. Ответы no-store; нет логов промптов,
ответов и секретов. Ошибки наружу обезличены.

Лимит тела и ответа 2 MiB, до 500 сообщений и 100 инструментов. Два параллельных
запроса, очередь максимум 8 с ожиданием до 20 с; 60 подписанных запросов/минуту.
Внешний nginx ограничивает частоту запросов до чтения тела приложением.
CLI: login до 10 с, генерация до 90 с; caller 125 с, nginx 130 с.
Нет автоматических повторов или переключения на другого провайдера: при ошибке
работает существующая обработка отказа Милы. При разрыве связи уже начатая
генерация может завершиться до своего таймаута; внешних инструментов у неё нет.

## Развёртывание и перенос

Отдельный сервис `mila-codex-bridge.service` слушает только 127.0.0.1:3012.
Nginx на dev публикует только точный путь API через HTTPS. `/health` доступен
локально и показывает модель, но не аккаунт или содержимое запросов.
Исходники сервиса в `/opt/mila-codex-bridge`, отдельная копия от рабочего дерева.
Unit: `backend/deploy/mila-codex-bridge.service`; конфиг `/etc/mila-codex-bridge.env`
с правами 0600, содержит PATH, HOME, CODEX_HOME, MILA_CODEX_BIN,
MILA_CODEX_RELAY_SECRET. Требуется установленный и авторизованный CLI 0.157.1.
Сервис использует существующую локальную авторизацию; файловая система read-only,
кроме приватного tmp и каталога Codex. Директории приложения/CRM скрыты unit'ом.
Это не отдельная машина: квота подписки и каталог авторизации пока общие с Codex
на деве. Самостоятельный сервер должен иметь отдельного сервисного пользователя
и обычный вход владельца подписки через Codex, без копирования ключей в репозиторий.

На caller задаются `AGENT_PROVIDER=codex-relay`,
`MILA_CODEX_RELAY_URL=https://dev.zumrudin.ru/api/mila-codex/v1/message`,
`MILA_CODEX_RELAY_SECRET`. У prod не требуется ни CLI, ни вход ChatGPT.
Для будущего переноса поднять тот же сервис с HTTPS на новом хосте, проверить
синтетический tool-cycle, поменять URL/секрет на caller и перезапустить только
Милу. Продовые миграции/изменения схем не нужны.

Откат: вернуть предыдущий AGENT_PROVIDER (`polza`) и перезапустить процесс Милы.
Старый провайдер и его секреты сохраняются. Переключение не меняет enabled/mode
в agent_settings. Не включать одновременно dev и prod для одного диалога.

## Проверки

`agent-codex-relay.test.js`: реальный локальный HTTP tool-cycle; неверная,
отсутствующая, просроченная и изменённая подпись; replay; запрет model/env/tenant
override; rate/concurrency/queue; размер; HTTPS; валидация ответа и tool args;
отсутствие ретраев и утечек ошибок. Дополнительно — существующие тесты адаптера.
Живой server-to-server smoke использует только синтетический диалог и фиктивный
инструмент, без отправки сообщений и изменений CRM.
