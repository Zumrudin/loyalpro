# Плановый синк с YClients (`runSync`): нужен ли, и чем его заменить

Дата: 2026-09-25. Продолжение разбора `docs/2026-09-25-cashback-accrual-bugs.md` (пункт 1;
пункт 2 — событийная привязка карты — уже исправлен и выкачен на прод коммитами
`b49402d`/`b10c6b0`).

Статус: **утверждён владельцем 25.09.2026** (вариант B, окно сверки 2 дня, после выката один ручной полный прогон ночью).

---

## 1. Что синк делает сегодня

`services/loyalty.js` `runSync(salon)`, крон `0 */3 * * *` (8 раз в сутки), плюс ручной
запуск из «Настроек» (`POST /api/sync`, кнопка «Синхронизировать»).

| Шаг | Что делает | Запросов к YClients |
|---|---|---|
| 1 | `/records` за **730 дней** страницами по 200 | ~50 (падает на 11–15-й) |
| 2 | `clients/search` — все id клиентов, по 25 | ~175 |
| 3 | на **каждого** из 4 313 клиентов: `/client/{id}` + `/loyalty/client_cards/{id}`; обновляет ФИО/телефон/почту/ДР/`yclients_data`, `total_spent`, `visits_count`, `last_visit_at`, привязку карты, баланс, `loyalty_level`; проходит по его записям из шага 1 (upsert в `records`, **начисление кэшбэка** `processCompletedRecord` для необработанных) | ~8 600 |
| хвост | bulk `last_visit_at` из `records`, привязка `record_id` к транзакциям карты | 0 |

Итого ≈ 8 800 запросов и **40–51 минута** на успешный прогон (по `sync_logs`).

## 2. Что показал прод

**Синк не работает с 26.06.2026.** `sync_logs` (salon 1): июль 4 ok / 244 err, август 2 / 247,
сентябрь 0 / 199. Последний успех — 04.08 18:00Z. Причина — лимит YClients на `/records`:
в каждом прогоне страницы 1–10 проходят за 13 секунд, на 11–15-й «Превышен лимит запросов»
(распределение по 47 падениям: стр. 11 ×5, 12 ×23, 13 ×15, 14 ×3, 15 ×1). Ретрай 3 с / 6 с
не спасает; исключение роняет прогон до шагов 2–3.

**Записи синк давно не поставляет.** `records` (13 528 строк) наполняется вебхуками: с мая
`source='sync'` — 5 строк, `source='webhook'` — 2 041. За 30 дней пришло 2 531 `record`-вебхуков,
ни одной записи без привязки к клиенту (`client_id IS NULL` с 04.08 — 0).

**Кэшбэк синк не начисляет.** `bonuses_accrued` во всех успешных прогонах с июня — 0: путь
вебхука (`processRecordEvent`) успевает раньше и ставит `bonus_processed`.

**Что реально протухает без синка:**
- `total_spent` / `visits_count` / `loyalty_level` — обновляются только самим начислением
  (`+paidAmount`, и только при успехе). Пример: клиент с 55 визитами — у нас 1 292 264 ₽ / 54,
  в YClients 1 373 824 ₽ / 55. Потребители: дашборд (сумма трат, «спящие»), список клиентов
  (фильтры/сортировка), сегменты, рассылки (`{bonuses}`, фильтр по балансу), уровень кэшбэка
  при начислении (пункт 7 плана), мобильное приложение (**1 клиент, последний вход 19.04** —
  фактически не используется).
- Новые клиенты, заведённые в YClients без записи (регистрация через бота): появляются у нас
  только на первом `record`-вебхуке. Для кэшбэка это не проблема (запись и создаёт клиента,
  карта подтягивается при начислении — фикс пункта 2).
- `yclients_data` (раздельные `surname`/`patronymic`, по ним агент выбирает обращение) —
  обновлялся только синком; 4 313 из 4 387 заполнены на 04.08, новые — нет.

**Синк вредит соседям.** Квота YClients общая на инстанс. Каждый старт на `:00` (runSync +
`syncGoodsCategories` в той же строке крона + `syncStaffData` + `syncGoodsSales` из соседнего
`0 * * * *`) выедает её; на проде **ежедневно в 12:00** воркер «Заботы» получает
«записи YClients недоступны (Превышен лимит запросов)» — 2–4 касания в день идут без проверки
повторного визита (fail-open). За неделю на проде 223 из 233 строк про лимит — от синка.
Если «починить ретрай» и вернуть 45-минутный прогон 8 раз в сутки (25 % времени ≈ 200 запр/мин),
под удар попадут живые вызовы Милы (`create_booking`/`reschedule_booking` — инцидент 19.09 с 429).

**Чем YClients уже кормит нас бесплатно (проверено на проде и живыми запросами):**
- `client`-вебхук приходит **на каждый оплаченный визит** (`status=update`; 118 событий за
  30 дней: 38 create / 80 update, 11 из 12 последних — рядом с `record`-событием) и несёт
  ровно поля шага 3: `spent`, `paid`, `visits`, `name`/`surname`/`patronymic`/`display_name`,
  `birth_date`, `email`, `phone`. Сегодня вебхук берёт из него только ФИО/телефон/почту/ДР.
- `/records?changed_after=YYYY-MM-DD` работает: за 2 дня — 79 записей, одна страница, 0,6 с.
  Это дешёвая сверка «не потеряли ли вебхук».
- `clients/search` сортировку по `last_change_date` НЕ поддерживает (проверено: список
  допустимых полей — id, name, …, last_visit_date, sold_amount, visits_count). Инкрементально
  по «изменённым клиентам» ходить нельзя — но и не нужно, см. выше.

## 3. Ответ на вопрос «нужен ли постоянный синк»

**Нет.** Всё, ради чего он писался, либо уже приходит вебхуками (записи, клиенты, карта при
начислении, баланс при финансовых операциях), либо приходит в `client`-вебхуке и просто не
сохраняется (`spent`/`visits`/раздельное ФИО). Полный обход 4 300 клиентов раз в 3 часа —
это 70 000 запросов в сутки ради данных, 99 % которых не изменились, и ровно он делает
квоту YClients дефицитной для «Заботы» и агента.

Полный прогон остаётся нужен в двух случаях: подключение нового салона (история за 2 года,
первичная привязка карт) и ручная сверка «после сбоя вебхуков на N дней». Оба — ручные и редкие.

## 4. Варианты

**A. Починить ретрай и оставить как есть** (ждать ≥60 с на лимите, сузить `SYNC_DAYS`).
Плюс: минимальная правка. Минус: возвращает 45-минутный прогон 8 раз в сутки и конкуренцию
за квоту с Милой и «Заботой»; сужение окна записей ничего не меняет — записи и так не из синка.
Не рекомендую.

**B. Событийное обслуживание + лёгкая ночная сверка; полный синк — только вручную.**
(Рекомендую.) Описано ниже.

**C. Полностью выключить синк, ничего не добавляя.** Плюс: одна строка. Минус: `total_spent`/
`visits_count`/уровень протухают навсегда, пропущенный вебхук не ловится никем, дашборд
показывает «Синхр.: 2 месяца назад».

## 5. Дизайн варианта B

### 5.1. `client`-вебхук сохраняет всё, что несёт (`routes/webhook.js`)
К текущему upsert добавить `total_spent = spent || paid`, `visits_count = visits`,
`yclients_data = data`, `loyalty_level = getLevel(spent, settings.levels)`, `synced_at=NOW()`.
YClients — источник правды, значения присваиваются, а не максимизируются: локальный
`+paidAmount` из начисления и `spent` из вебхука сходятся к одному числу (в случае отмены
платежа вебхук вернёт уменьшенное `spent`, и это правильно). Эти поля НЕ трогают `bonus_balance`
и карту (`balance` в `client`-вебхуке — депозит/долг, не карта лояльности).
Тот же разбор полей вынести в чистый хелпер (`services/client-upsert.js`), чтобы ночная сверка
и вебхук писали клиента одним правилом (тот же принцип, что `visitReallyHappened`).

### 5.2. Ночная сверка `reconcileDaily(salon)` (новый `services/yclients-reconcile.js`)
Крон `35 4 * * *` мск (в это время никто в YClients не ходит; `40 4` заняты чистками БД).
1. `/records?changed_after=<сегодня−2 дня>` постранично (ожидаемо 1–2 страницы). Для каждой:
   upsert в `records` тем же кодом, что шаг 3 синка (статус, `raw_payload`, сумма, услуги,
   мастер, `client_id`). **Кэшбэк отсюда НЕ начисляется**: деньги — только вебхук-путь.
   Если запись `completed`+`paid_full=1`, а в `finances_log` строки нет — **WARN** в лог
   («вебхук по записи N потерян») — видимый сигнал вместо тихого второго пути начисления с теми
   же дефектами (пункты 3–6 плана).
2. Собрать множество клиентов из п. 1 (на проде ≈ 55 в сутки). Для каждого, с паузой 500 мс:
   `/client/{id}` → тот же хелпер, что в 5.1; если у салона задан `yclients_card_type_id` и
   карта не привязана — `linkClientCard` (уже существует, пункт 2); если привязана —
   `ycGetClientCards` и обновить `yclients_card_balance`/`bonus_balance`. Ошибка по одному
   клиенту — лог и дальше (как в шаге 3 синка). Итого ≈ 110–170 запросов, 1–2 минуты.
3. Bulk `last_visit_at` из `records` и привязка `record_id` к транзакциям карты по дате визита
   (оба SQL уже есть в `runSync`, вынести в функции и звать из обоих мест — правило одно).
4. Строка в `sync_logs` с `sync_type='daily'` — дашборд («Синхр.: N ч назад») и
   `GET /api/sync/logs` продолжают работать без правок фронта.
Ретрай на лимите: `withRateLimitRetry` из `services/yclients-retry.js` с `delayMs: 60_000`,
`retries: 2` вокруг постраничного `/records` (минутный лимит — сообщение YClients «через 0
секунд» врёт, см. пункт 1 плана).

### 5.3. Полный синк — только вручную
- Убрать `runSync` из крона `0 */3 * * *` (`syncGoodsCategories` там остаётся, но уезжает на
  свою минуту `10 */3 * * *` — снять коллизию с `0 * * * *`, из-за которой «Забота» ловит лимит
  в 12:00).
- `runSync` остаётся за кнопкой «Синхронизировать» и `POST /api/sync`; в шаге 1 обернуть
  запрос страницы в `withRateLimitRetry({delayMs: 60_000, retries: 3})` — прогон снова
  проходит, но только когда его запустил человек. `SYNC_DAYS` не трогаем: полный прогон нужен
  именно ради истории.
- Ручной запуск при уже идущем прогоне — 409 (сейчас можно запустить два параллельно).

### 5.4. Наблюдаемость
- При старте процесса: `UPDATE sync_logs SET status='error', error_message='процесс
  перезапущен' WHERE status='running'` (27 зависших строк на проде с марта).
- Крон-обёртка сверки: три подряд `error` у `sync_type='daily'` → `WARN` в лог с текстом
  причины (три месяца тишины при красном синке — главный урок пункта 1).

### 5.5. Тесты
- `client-upsert.test.js` — разбор полей вебхука (spent vs paid, пустые поля, уровень).
- `yclients-reconcile.test.js` — на моках: множество клиентов из записей; WARN при потерянном
  вебхуке; кэшбэк не зовётся; ошибка одного клиента не роняет прогон; `sync_logs` пишется.
- Существующий `loyalty-card-link.test.js` не трогается (`linkClientCard` переиспользуется).
- Живая проверка на деве: `scripts/yclients-reconcile-e2e.js` — один прогон против реального
  YClients салона 1, вывод числа записей/клиентов, без записи денег.

### 5.6. Выкат
Один коммит + `pm2 restart` на проде. Первая ночь: сверить `sync_logs` (`daily`, success) и
лог на WARN про потерянные вебхуки. Откат — вернуть строку крона.

## 6. Вне scope (отдельные решения)
- Пункт 5 плана (`"0.00" === 0`, переигровка отказов) — по-прежнему решение салона: оживлённая
  ветка начислила бы и по картам, созданным после оплаты.
- Пункты 3, 4, 6, 7 плана — свои правки в `processRecordEvent`; пункт 7 (уровень по свежим
  тратам) после 5.1 закрывается наполовину сам: `total_spent` станет живым.
- Восстановление `total_spent`/`visits_count` по всей базе за период с 04.08 — один ручной
  `runSync` после выката (с починенным ретраем он пройдёт).

## 7. Решения владельца (25.09.2026)
1. Вариант B утверждён.
2. Окно сверки — 2 дня по `changed_after`.
3. После выката — один ручной полный `runSync` ночью, чтобы догнать `total_spent`/`visits_count`
   за 04.08–сегодня.
