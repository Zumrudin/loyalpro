# Внутренний каталог услуг — 08.11.2026

Запрос владельца: самостоятельный раздел услуг, вложенные категории, первоначальный каталог из YClients, внутренний источник услуг журнала и связь с экономикой.

## Поведение

Раздел «Услуги» доступен owner/admin. Дерево категорий, произвольная вложенность без циклов, создание/редактирование категории и её родителя, создание/редактирование услуг (название, категория, базовые цены, длительность, активность), поиск, архивирование через выключение активности. Удаления нет — идентичность и связи сохраняются.

Первичный и повторный импорт читает management services и service_categories через сервис интеграции. Сетевые чтения выполняются до транзакции. Импорт атомарный, сериализован с редактированием через tenant advisory xact lock 17292. UNIQUE salon/company/YC id и ON CONFLICT DO NOTHING предотвращают дубли и перезапись локальных правок. Повторный импорт добавляет отсутствующие позиции; не обновляет/удаляет ранее импортированные услуги, назначения сотрудников или их индивидуальные цены. Не выполняет обратных записей в YClients. Пустой/ошибочный источник не считается успешным импортом.

Услуги имеют собственный service_catalog.id; yclients_id вместе с company id хранится отдельно от внутреннего ID. Категории также имеют собственные ID. Услуга без внешней связи хранится внутри LoyalPro, но не участвует в создании записей через YClients. Внешняя связь существующих строк не меняется через редактор. Индивидуальные цены/длительности сотрудников первоначально импортированы и имеют приоритет над базовыми значениями, что явно указано в редакторе.

Связь с экономикой: economics_yc_id из существующей модели финансового раздела. При импорте автоматически равен исходной услуге. Редактор позволяет выбрать связанную услугу текущего салона, включая связь для новой внутренней услуги. Кнопка «Экономика» открывает действующую детализацию себестоимости/маржинальности выбранной связи. Расчёты и финансовые данные не копируются и не меняются. Нативная экономика услуг без внешнего источника фактических визитов — последующий этап.

## Журнал

GET /day получает каталог и категории из PostgreSQL, а сотрудников/расписание/записи — пока из YClients. Каталог содержит только активные услуги с соответствующей текущей company связью. serviceSource=internal различает внутренние ID от прежних внешних. /slots и /create принимают этот признак, разрешают локальные ID строго по salon_id и company_id и проверяют активность/назначение сотрудника. Перед записью используется свежий management-каталог для проверки наличия услуги, назначения специалиста и ресурсов; расписание/конфликты также проверяются свежими. Длительность и цена новой записи берутся из внутреннего каталога (с индивидуальными значениями сотрудника). Во внешний payload идут только YClients IDs. Старые запросы без serviceSource совместимы и продолжают использовать внешние ID; перенос старых записей сохраняет исходные услуги/стоимость. Идемпотентность и блокировка неопределённых операций не изменены.

## Схема и выкладка

Аддитивный SERVICE_CATALOG_DDL в backend/migrations.js создаёт service_categories и service_catalog. В каждой таблице salon_id, составные внешние ключи салон+категория и салон+родитель, уникальная внешняя связь салон+company+id. Индексы по салону/категории/родителю. Существующие таблицы и записи не перестраиваются. Новые таблицы пусты до явного импорта; автоматического backfill на старте нет. Ожидаемое влияние блокировок — создание двух новых таблиц, короткая транзакция импорта нескольких сотен строк. Перед использованием нового кода выполнить миграции обычным запуском backend; до миграции новый каталог возвращает ошибку, а не внешний fallback.

Порядок на деве: резервный снимок → проверки → перезапуск только loyalpro (миграции) → явный импорт каталога текущего салона → read-only smoke каталога и журнала. Создание реальных визитов и финансовые операции для тестов не выполняются. Прод не затрагивается.

Откат: восстановить изменённые старые файлы из `/root/loyalpro-deploy-backups/services-20261108T143353Z/before/`, перезапустить только dev loyalpro. Новые таблицы и импортированные строки сохранить; новые файлы останутся неиспользуемыми. Предварительно проверить последующие изменения. Удаление таблиц не требуется и не разрешено этим сценарием.
