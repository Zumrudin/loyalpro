# ИИ-агент-администратор (диалог + запись клиентов) — дизайн

**Дата:** 2026-07-18
**Статус:** черновик, на согласовании
**Ветка контекста:** `feat/admin-chat-page`

## Цель

Диалоговый ИИ-агент, который **автономно** отвечает на входящие сообщения
клиентов (WhatsApp / Telegram / MAX через chatpush), ведёт переписку,
консультирует по услугам и специалистам и **доводит клиента до записи**,
самостоятельно создавая запись в YClients.

Границы автономности (утверждено на брейншторме 2026-07-18):
- **Автономность:** полностью автономный. Оператор подключается только по
  эскалации.
- **Запись:** агент создаёт запись сам через YClients API.
- **LLM-движок:** Claude с tool-calling (function calling).
- **Эскалация на оператора:** (а) по явной просьбе клиента (позвать
  человека / жалоба / конфликт); (б) когда в базе знаний нет ответа /
  низкая уверенность — не выдумывать, а передать оператору.

Источники данных:
- **Услуги и специалисты** — из нашей базы знаний (`kb_articles`,
  `kb_categories`) + каталог персонала.
- **Свободные слоты и создание записи** — из YClients.

## Контекст (что уже есть)

- **Приём входящих:** `routes/chatpush-webhook.js` принимает события
  chatpush, отвечает `200` сразу, пишет в `chatpush_events` (сырой лог) и
  `chatpush_messages` (нормализованные, идемпотентно
  `ON CONFLICT (salon_id, external_message_id) DO NOTHING`), матчит клиента
  по телефону. Секрет в `?key=` (тело chatpush не подписывает).
- **История диалога:** `chatpush_messages`, индексы
  `idx_chatpush_messages_dialog (salon_id, phone, msg_ts DESC)` и
  `idx_chatpush_messages_dialogkey (salon_id, COALESCE(NULLIF(phone,''), chat_id), msg_ts DESC)`.
  Ключ диалога = `phone`, либо `chat_id` для каналов без телефона (Telegram/MAX).
- **Отправка ответа:** `chatpush.sendMessage(instanceToken, {text, phone|chat_id, dispatchRouting, replyToMessageId})`
  и `chatpush.replyRoutingFor(channel)` (`telegram_bot → telegram`).
- **Заглушка агента:** `services/chatpush-agent.js` `generateReply(msg)` —
  сейчас эхо, за флагом `CHATPUSH_AGENT_ENABLED` (=false). Вызывается из
  `routes/chatpush-webhook.js`.
- **RAG по базе знаний:** `services/kb-assistant.js` — `retrieveArticles()`
  (полнотекст `to_tsquery('russian')` + ILIKE-фолбэк по `kb_articles`),
  `ask()` (собирает контекст ≤12k символов, зовёт Gemini напрямую или через
  relay). Векторного поиска нет — только keyword/FTS.
- **YClients:** `services/yclients.js` `ycGet(salon, endpoint, params)`
  (partner + user Bearer токены), синк персонала (`staff_members`),
  расписание `GET /schedule/{cid}/{staff}/{from}/{to}` (рабочие часы, но
  **без** вычета занятости), `updateAttendance` (PUT статуса).
  **Нет** функций расчёта свободных слотов и создания записи.
- **Состояния диалога/памяти агента нет.** Есть только история сообщений в
  `chatpush_messages` + аудит KB в `kb_chat_logs`.

## Выбранный подход

**ReAct-цикл Claude с детерминированным гейтом на создание записи (подход C).**

Claude ведёт весь диалог и свободно вызывает read-инструменты (база знаний,
каталог, слоты). Единственное необратимое действие — создание записи —
проходит через жёсткий guard: эхо деталей клиенту → явное согласие →
создание под advisory-lock с идемпотентностью. Автономность разговора +
защита критичного действия (в стиле advisory-локов в `processRecordEvent`).

Отклонённые варианты: чистый ReAct без гейта (риск «молча пробить бронь по
галлюцинации» и двойных броней на ретрае вебхука); явный конечный автомат с
Claude только для формулировок (много кода, хрупко к живым диалогам).

## Архитектура

### Поток данных

```
Клиент (WhatsApp / Telegram / MAX)
    │  входящее
    ▼
[1] chatpush-webhook  ──ACK 200 сразу──►  chatpush_events + chatpush_messages   (ЕСТЬ)
    │  (после сохранения — отдаём в диспетчер, не в generateReply напрямую)
    ▼
[2] Dispatcher / Debouncer  — ждёт ~4–6с тишины по dialog_key, склеивает серию
    │                          сообщений; advisory-lock на диалог (анти-дубль);
    │                          если статус = escalated → молчит
    ▼
[3] Agent Orchestrator  — грузит состояние + историю, крутит Claude-цикл tool-use,
    │                      сохраняет обновлённое состояние и реплики
    │        ┌─────────────────────────────────────────────┐
    │        │ [4] Claude Messages API (tools)              │
    │        │   loop: ответ | tool_use → выполнить → назад │
    │        └───────────────┬─────────────────────────────┘
    │                        ▼
    │              [5] Tools layer  (каждый scoped по salon_id)
    │   search_knowledge_base · list_services · list_staff ·
    │   get_available_slots · create_booking(gate) ·
    │   get_client · escalate_to_operator
    │                        │
    │        ┌───────────────┴───────────────┐
    │        ▼                               ▼
    │   kb-assistant/RAG (ЕСТЬ)      yclients.js: book_times / POST records (НОВОЕ)
    ▼
[6] Reply pipeline → chatpush.sendMessage(routing) (ЕСТЬ) + запись outgoing
    │
    ▼
[7] agent_dialogs / agent_events — состояние диалога + аудит вызовов инструментов (НОВОЕ)
```

### Компоненты

**[1] Ингест — есть.** Меняется только хвост `routes/chatpush-webhook.js`:
после сохранения входящего вызываем диспетчер `[2]` вместо `generateReply`
напрямую.

**[2] Диспетчер / дебаунсер — новое (`services/agent/dispatcher.js`).**
Копит входящие по `dialog_key` (`salon_id` + `phone|chat_id`), запускает
агента после N секунд тишины (дефолт ~4–6с), чтобы не отвечать на каждую
строку серии. Один процесс PM2 → in-memory таймер-мапа + `pg_advisory_xact_lock`
на время обработки диалога. Диалог в статусе `escalated` — не обрабатывается.

**[3] Оркестратор — новое (`services/agent/orchestrator.js`).** Собирает
контекст: системный промпт (роль, правила, часы работы, тон салона),
состояние из `agent_dialogs`, транскрипт из `chatpush_messages` (последние M
реплик, `direction:outgoing`-эхо не дублируем), профиль клиента. Крутит цикл
Claude ↔ инструменты с лимитами (макс. итераций и токенов на ход). По
завершении сохраняет состояние и реплики.

**[4] Claude-клиент — новое (`services/agent/claude.js`).** Anthropic
Messages API, модель `claude-opus-4-8` или `claude-sonnet-4-6` (скорость/цена),
с `tools`, ретраи на 429/5xx (по образцу двухключевого фолбэка в
`kb-assistant.js`). Env: `ANTHROPIC_API_KEY`.

**[5] Слой инструментов — новое (`services/agent/tools/*`), каждый =
JSON-schema + функция, всё scoped по `salon_id`:**

| Инструмент | Источник | Статус |
|---|---|---|
| `search_knowledge_base(query)` | `kb-assistant.retrieveArticles` (FTS по `kb_articles`) | переиспользуем |
| `list_services(query?)` / `list_staff(service?)` | KB + `staff_members` / YClients | частично есть |
| `get_available_slots(service_id, staff_id?, date_range)` | YClients `GET /book_times/{cid}/{staff}/{date}` + `/book_dates` | **новое** |
| `create_booking(...)` | YClients `POST /records/{cid}` (partner+user токен) | **новое + gate** |
| `get_client(phone)` | `clients` / YClients client | частично есть |
| `escalate_to_operator(reason)` | флип `agent_dialogs.status = escalated` + нотификация | **новое** |

Правила фактов: цены, слоты, мастера агент **обязан** брать только из
инструментов; в системном промпте — запрет выдумывать. Свободные слоты берём
через `book_times` (уже вычитает занятость), а не через сырой `/schedule`
(только рабочие часы, без учёта записей).

**Гейт `create_booking`.** Инструмент отдаёт модели «черновик» (услуга,
мастер, дата/время, цена, длительность) и требует, чтобы агент подтвердил
детали у клиента текстом. Реальное создание — только после явного согласия
клиента, под `pg_advisory_xact_lock(salon, dialog)` + идемпотентный ключ
`(dialog + service + datetime)`, чтобы ретрай/дубль вебхука не породил две
брони.

**Эндпоинт создания записи.** Management API `POST /records/{company_id}`
(использует существующие partner+user токены из `yclients.js`, создаёт
запись напрямую, без SMS-кода). Альтернатива — booking-flow
`POST /book_record` с `book_code` (SMS-подтверждение клиентом): «честнее» с
точки зрения онлайн-записи, но добавляет шаг с кодом. **Решение по
умолчанию:** management `POST /records`.

**[6] Отправка — есть.** `chatpush.sendMessage(...)` + `replyRoutingFor(channel)`.
Оркестратор может слать 1–2 сообщения за ход.

**[7] Состояние и аудит — новое (2 таблицы через `migrations.js`,
`ADD COLUMN IF NOT EXISTS`-стиль):**
- `agent_dialogs` — `salon_id, dialog_key, status (bot|escalated|closed),
  collected (jsonb: intent + частичная бронь), watermark_ts, dirty,
  last_activity, escalated_reason, assigned_operator` — по строке на диалог.
- `agent_events` — аудит каждого вызова инструмента и решения (для отладки
  «почему записал не туда»).

### Эскалация

Бот отдаёт диалог оператору при: (а) явной просьбе клиента; (б) когда
`search_knowledge_base` не вернул релевантного / низкая уверенность. При
эскалации: статус → `escalated`, бот замолкает, оператору — уведомление и
баннер на существующей странице «Чат» (`feat/admin-chat-page`) + тумблер
«бот ↔ оператор» на диалоге для возврата управления боту.

## Конкурентность и дедупликация

Сценарий: клиент прислал сообщение, агент начал готовить ответ, в этот
момент клиент дописывает ещё сообщения. Поведение разное **до** старта
прогона и **во время** него.

### Окно 1 — сообщения пришли до старта прогона

Их склеивает дебаунсер `[2]`: таймер тишины перезапускается на каждом
входящем, агент не стартует, пока клиент печатает серию. В оркестратор
приходит вся пачка как один контекст. Покрывает большинство случаев.

### Окно 2 — сообщение пришло во время прогона (Claude в полёте / выполняются инструменты)

Работают три механизма вместе.

**1. Сериализация.** `pg_advisory_xact_lock(salon, dialog_key)` держится
весь прогон. Новое входящее не запускает второй агент-цикл параллельно —
только помечает диалог и ждёт лок. Двух Claude на один диалог не бывает.

**2. Watermark + dirty-флаг.**
- На старте прогон запоминает водяную метку — `max(msg_ts)` прочитанных
  входящих.
- Любое входящее во время прогона ставит `agent_dialogs.dirty = true` и
  перевзводит дебаунс.
- Перед отправкой ответа прогон перечитывает: есть ли входящие новее
  watermark?

**3. Решение по коммиту.**

```
Пришло новое сообщение во время прогона
         │
         ▼
  Прогон уже сделал side-effect (create_booking)?
    ├─ НЕТ (текстовый черновик ответа)
    │     → ЧЕРНОВИК ВЫБРАСЫВАЕМ, не отправляем
    │     → сразу перезапускаем прогон с полным контекстом
    │       (клиент видит ОДИН связный ответ, а не два)
    │
    └─ ДА (запись уже создана)
          → бронь закоммичена и идемпотентна — откатывать нечего
          → следующий прогон обрабатывает новые сообщения поверх
            («уже записал вас на 15:00; хотите перенести?»)
```

Выбросить недоотправленный текстовый черновик дёшево, поэтому предпочитаем
«отменить и перегенерировать», а не слать устаревший ответ. Ломающий
сценарий: «хочу на маникюр» → агент начал отвечать → «ой нет, на педикюр».
Наивная система ответит про маникюр; наша — выкинет черновик и ответит про
педикюр.

**Безопасность записи в гонке.** Единственное необратимое действие
`create_booking` за гейтом: происходит только сразу после явного «да»
клиента, под тем же advisory-локом и с идемпотентным ключом
`(dialog + service + datetime)`. Дубль-вебхук или лишнее сообщение во время
подтверждения не создадут второй записи; гонка максимум добавит уточняющий
ход.

**Опционально (не для MVP).** Передавать в Claude-клиент `AbortController` и
прерывать вызов в полёте при новом входящем — экономит секунды и токены на
перегенерации. Прерывать только между шагами цикла и только до любого
пишущего инструмента, чтобы не оборвать создание записи на полпути.

## Guardrails

- Цены/слоты/мастера — только из инструментов; запрет галлюцинаций в
  системном промпте.
- `create_booking` — эхо деталей + явное согласие клиента + advisory-lock +
  идемпотентность.
- Лимиты итераций и длины хода; фильтр `direction:outgoing` (эхо своих
  отправок) при сборке истории.
- Русский язык, тон салона, часы работы — в системном промпте.

## Обработка ошибок

- Вебхук всегда `200` сразу (YClients/chatpush ретраят на таймаут) —
  обработка агента полностью асинхронна после ACK.
- Ошибка Claude (429/5xx) — ретрай; при исчерпании — тихая эскалация на
  оператора (не молчим в никуда).
- Ошибка YClients (слоты/запись) — агент сообщает клиенту о невозможности и
  эскалирует; запись не помечается созданной без успешного ответа API.
- Все вызовы инструментов и решения логируются в `agent_events`.

## Тестирование

- Юнит: слой инструментов (моки YClients/KB), гейт `create_booking`
  (идемпотентность, отказ без согласия), сборка контекста/watermark-логика.
- Интеграция: симуляция вебхука (как в текущем `chatpush` — приём/дедуп),
  сценарий гонки (сообщение во время прогона → один ответ), полный путь
  «консультация → слоты → подтверждение → запись в YClients» на тестовой
  компании.
- Ручное: dev-сервер, реальный входящий из Telegram/WhatsApp, флаг
  `CHATPUSH_AGENT_ENABLED` включён локально.

## Что явно вне scope (YAGNI)

- Векторный/семантический поиск по базе знаний (остаётся FTS).
- Мультиинстансная оркестрация на нескольких PM2-процессах (in-memory
  дебаунс рассчитан на один процесс).
- Триггеры эскалации по оплате/возвратам/медвопросам (не выбраны; при
  желании добавляются в список триггеров).
- Голосовые/медиа-ответы агента (только текст на этом этапе).
