# Бонусный довод в напоминании Милы о себе

**Дата:** 2026-09-20
**Статус:** спека утверждена салоном (решения 1–6 ниже), не реализована
**Родительская спека:** `2026-08-11-agent-followup-waiting-status-design.md`

## Задача

Мила ответила пациенту, записи нет, пациент замолчал. Через `followup_delay1_min` минут
уходит напоминание о себе (`services/agent/followup-worker.js`, stage 0). Сейчас это
нейтральное «мягко вернуться к вопросу». Нужен дополнительный довод довести до записи:

- у держателя бонусной карты — напомнить про баланс («на карте N бонусов, ими можно оплатить
  часть визита»);
- у пациента без карты программы лояльности — напомнить, что при регистрации дарят
  приветственные баллы.

Довод уместен не всегда, и уместность решает КОД по детерминированным признакам, а не модель.

## Решения салона (2026-09-20)

1. **Ступень:** только напоминание stage 0 (через 15 мин). Финальный шаблон stage 1 не трогается:
   он задуман как точка в разговоре, а не ещё одна попытка продать.
2. **«Первичный» = нет карты программы лояльности** типа, настроенного в салоне
   (`salons.yclients_card_type_id`), а не «нет визитов». Пациент с историей визитов, но без
   карты, законно получает приветственные баллы при регистрации.
3. **Порог баланса:** ниже него баланс не упоминаем. Настройка салона, дефолт 100.
4. **Фразы пишет салон** в настройках агента (два шаблона). Модель бонусные фразы не пишет и
   в промпт напоминания факт о балансе не попадает.
5. **Частота:** не больше одного упоминания за переписку и не чаще раза в 7 дней на номер.
6. **Ситуации:** довод только в классах «выбор времени/специалиста» и «цена». Всё остальное
   (уточнение, перенос/отмена, медицинский маршрут, чистая справка) — без довода.

## Почему детерминированно, а не промптом

- У прохода напоминания нет инструментов, и его промпт (`followup-prompt.js`, правило 2)
  запрещает называть новые факты. Баланс — живые данные (Сценарий 5 основного промпта:
  «никогда по памяти»). Значит, баланс читает код.
- Правило «упомяни, только если уместно» — ровно тот класс промпт-правил, который на этом
  проекте проигрывал живым прогонам (мораторий в CLAUDE.md). Уместность решает классификатор.
- Инвариант из напоминаний о повторном визите (`services/reminders/bonus.js`) наследуется
  целиком: **пациент не должен прочитать про бонусы, которых у него нет.** Любой сбой чтения
  → напоминание уходит БЕЗ бонусной фразы.

Рассмотренные альтернативы:

- *Факт в промпт, модель вплетает сама* — естественнее, но требует нового промпт-правила и
  числового guard'а. Отложено: если живой прогон покажет, что дописка звучит пришитой, этот
  вариант можно добавить поверх — гейты и чтение баланса останутся теми же.
- *Бонус только в финальном шаблоне через плейсхолдер* — проще всего, но лучший момент (15 мин)
  упускается, а финал не про продажу.

## Где довод уместен

Строка ожидания заводится только когда реплики доставлены, записи в этом ходу нет, диалог не
эскалирован и Мила не промолчала сознательно (`followup-queue.shouldAwaitReply`). Внутри этого
множества класс ситуации считает чистый модуль `services/agent/followup-situation.js` по двум
источникам: журнал инструментов хода-якоря (`agent_tool_events` по `turn_id`) и собственная
последняя реплика Милы (последний assistant-блок транскрипта без строк с `OPERATOR_MARK`).

Классы, первое совпадение сверху побеждает:

| Класс | Признак | Довод |
|---|---|---|
| `modify` | вызван `reschedule_booking` / `cancel_booking` / `modify_booking_services` (в т.ч. с hint-ответом) ИЛИ реплика Милы содержит «перенес/перенос/отмен» | нет |
| `clarify` | `create_booking` / `book_chain` вернул hint-флаг: `needs_phone`, `generic_service_hint`, `too_soon`, `unverified_slot`, `needs_confirmation`, `wrong_service` | нет |
| `choice` | любой из `get_available_slots` / `get_available_dates` / `get_sequential_slots` / `get_parallel_slots` без `is_error` с непустой выдачей (`slots`, `offer_slots`, `staff_options`, `alternative_staff`, `options`, `schedule` или `free_day:true`) | да |
| `price` | вызван `get_service_masters` или `send_price_list` без `is_error`, ИЛИ реплика Милы содержит сумму с валютой (`\d[\d\s]*\s?(₽\|руб)`) | да |
| `unknown` | всё остальное (справка из КБ, маршрут в консультацию, ответ без инструментов и без цены) | нет |

`unknown` без довода — сознательно консервативно для первой версии: там же живёт медицинский
маршрут («решает врач на консультации»), который детерминированного признака в коде не имеет.
Расширять после замера по журналу.

Дополнительные гейты (все обязаны пройти), в порядке от дешёвых к дорогим:

1. фича включена: соответствующий шаблон в настройках непуст;
2. `row.phone` известен (канал без номера — ни баланса, ни ветки регистрации: пациент со
   скрытым номером в Telegram может быть золотым клиентом);
3. класс ситуации ∈ {`choice`, `price`};
4. бонусы ещё не звучали в окне транскрипта (любая роль, `/бонус|лояльност/i`) и не звучат в
   тексте напоминания, который написала модель;
5. по этому номеру в салоне за 7 дней не было напоминания с бонусной фразой
   (`agent_followups.bonus_kind IS NOT NULL AND nudge1_at > now() - interval '7 days'`);
6. чтение карты (см. ниже) дало определённый результат.

## Чтение баланса

Новый общий модуль `services/card-balance.js`, `readCardBalance(salon, phone, deps)`:

```
{ status: 'ok', balance, cardId }   карта типа салона есть
{ status: 'no_card' }               клиент в YClients есть, карты типа салона нет → ветка welcome
{ status: 'no_client' }             клиента в YClients нет вовсе → ветка welcome
{ status: 'unavailable' }           нельзя утверждать ничего → без фразы
```

Шаги:

1. `salon.yclients_card_type_id` не задан → `unavailable` + WARN (один раз на процесс).
   Без типа карты нельзя отличить «нет карты» от «карта другой программы».
2. `yclients_client_id`: сначала `clients` по суффиксному LIKE (как `get_bonus_balance`),
   при промахе — живой `POST /company/{cid}/clients/search` по телефону (тот вызов, что в
   `services/loyalty.js`). Пусто в живом поиске → `no_client`. Ошибка поиска → `unavailable`.
   Живой поиск обязателен: настоящий новый пациент в нашей БД не существует до 3-часового
   синка, и без него ветка регистрации не срабатывала бы именно у тех, для кого она написана.
3. Карты — СТРОГО через вариант, который БРОСАЕТ при ошибке. `ycGetClientCards` глотает
   исключения и возвращает `[]` — для этой фичи `[]` при сбое сети означало бы «карты нет» и
   приглашение зарегистрироваться держателю карты. В `services/yclients.js` добавляется
   `ycGetClientCardsStrict` (тело запроса то же, без try/catch); существующие потребители не
   меняются.
4. Карта типа салона: фильтр по `type.id` (число/строка, как в `reminders/bonus.js`),
   тай-брейк по максимальному балансу. Нет → `no_card`.

`services/reminders/bonus.js` переводится на тот же `readCardBalance` (рефакторинг без
изменения поведения; сьют `reminders-bonus.test.js` остаётся зелёным). Начисление в этой фиче
НЕ делается: здесь только чтение.

## Выбор фразы

Чистый модуль `services/agent/followup-bonus.js`,
`chooseBonusLine({ situation, card, settings, alreadyMentioned, recentlySent, nudgeText })` →
`{ kind: 'balance'|'welcome', text, balance? } | null`.

- `card.status === 'ok'` и `balance >= followupBonusMinBalance` → шаблон
  `followup_bonus_text`, подстановка `{balance}` (целое, разряды через неразрывный пробел:
  «3 024»). Баланс ниже порога → `null` (ни баланса, ни регистрации: карта уже есть).
- `card.status ∈ {no_card, no_client}` → шаблон `followup_welcome_text`.
- `unavailable` → `null`.
- Пустой шаблон нужной ветки → `null` (ветка выключена, вторая продолжает работать).
- После `{balance}` шаблон проходит общий `notifications.renderTemplate` (`{first_name}`,
  `{salon}` — как финальный текст).

Итоговое сообщение: текст модели, пустая строка, бонусная фраза. Одно сообщение, а не два:
второе исходящее подряд заводило бы у Chatpush отдельную доставку и удвоило бы след в «Чате».

## Изменения в существующем коде

### Схема (`migrations.js`, только `ADD COLUMN IF NOT EXISTS`)

`agent_settings`:

| Поле | Тип | Дефолт | Смысл |
|---|---|---|---|
| `followup_bonus_text` | TEXT | NULL | шаблон держателю карты, `{balance}` |
| `followup_welcome_text` | TEXT | NULL | шаблон пациенту без карты |
| `followup_bonus_min_balance` | INTEGER NOT NULL | 100 | порог упоминания |

`agent_followups`:

| Поле | Тип | Смысл |
|---|---|---|
| `anchor_turn_id` | TEXT | `turn_id` хода-якоря — по нему классификатор читает журнал |
| `bonus_kind` | TEXT | `balance` / `welcome`, пишется в момент ЗАХВАТА строки |
| `bonus_balance` | INTEGER | баланс, названный пациенту (журнал, правило 7 дней) |

### Настройки (`services/agent-settings.js`, `routes/agent-settings.js`)

Три поля в `DEFAULTS`, `rowToSettings`, `getSettings`, `updateSettings`. Контракт — щадящий, как
у `followupFinalText`: `undefined`/`null` = «не передано, оставить», пустая строка = очистка.
Тексты — кап `FOLLOWUP_TEXT_MAX` (1200). Порог — целое 0..100000, `''`/`null`/`undefined` =
оставить текущее; bool/массив/объект → `BAD_FOLLOWUP`. ГОТЧА роута сохраняется: фронт шлёт весь
объект, `enabled`/`mode` по-прежнему трактуются как «выключено/all» при отсутствии.

### Очередь (`followup-queue.js`, `dispatcher.js`)

`schedule(...)` получает `opts.turnId` и пишет `anchor_turn_id` (и в INSERT, и в ON CONFLICT).
Диспетчер передаёт `turnId` из той же точки, где ставит вердикт `markDelivered` — переменная там
уже есть. `turnId` может быть `null` (ранние выходы) — тогда классификатор видит пустой журнал
и решает по тексту реплики.

### Журнал инструментов (`tool-events.js`)

Новая `loadTurn(turnId)` → `[{tool, input, result, is_error}]` по `turn_id`. Best-effort с
логом (в отличие от `loadRecent`): пустой журнал даёт класс по тексту, а не падение
напоминания.

### Воркер (`followup-worker.js`, только ветка stage 0)

Порядок внутри `processOne` после успешного `buildNudgeText`:

```
nudge = текст модели (после guard'ов и среза приветствия)
bonus = await tryBonusLine(...)      // best-effort, любое исключение → null + WARN
text  = bonus ? `${nudge}\n\n${bonus.text}` : nudge
захват: UPDATE ... SET stage=1, ..., rendered_text=$3, bonus_kind=$4, bonus_balance=$5
отправка
```

Бонусная фраза считается ПОСЛЕ LLM-прохода: `skip` модели не должен стоить похода в YClients.
`reply-guard.hardViolations` и `hasInventedTime` проверяют текст МОДЕЛИ до дописки — шаблон
салона, как и финальный текст, не линтуется. `bonus_kind`/`bonus_balance` пишутся в том же
условном UPDATE, что и захват: журнал отражает только реально ушедшие фразы. Строка лога
отправки дополняется `bonus=balance:3024` / `bonus=welcome` / `bonus=none:<причина>`.

`LEASE_SQL` получает три новых скалярных подзапроса из `agent_settings` и
`salons.yclients_card_type_id` в `RETURNING` → после правки обязателен живой `EXPLAIN` на
дев-БД (правило проекта: юнит-моки SQL не проверяют).

### Фронт (`frontend/index.html`, `frontend/js/pages/agent-settings.js`)

В блок «Напоминания о себе» модалки «⚙️ Агент» добавляются: textarea «Довод про бонусы
держателю карты» (подсказка про `{balance}` и `{first_name}`), textarea «Приглашение в
программу лояльности» (для пациентов без карты), число «Минимальный баланс для упоминания».
Пустое поле = ветка выключена. Бамп `?v=` у скрипта обязателен (память проекта: старая копия
`.js` живёт в браузере месяц).

Рекомендуемые заготовки-плейсхолдеры (салон правит под себя):

- держателю: «Кстати, на вашей бонусной карте {balance} бонусов — ими можно оплатить часть
  визита 🤍»
- без карты: «Кстати, при регистрации в нашей программе лояльности дарим 500 приветственных
  баллов — регистрация в Telegram-боте или по QR на сайте.»

## Чего фича не делает

- **Не начисляет** бонусы и не обещает начисления: только называет баланс либо факт
  приветственных баллов из шаблона салона.
- **Не работает** без известного номера и при незаданном типе карты салона.
- **Не трогает** финальный шаблон и промпт напоминания.
- **Не даёт** довода в классе `unknown` (справка, консультация врача) — расширение после
  замера.
- **Не защищена** от гонки с синком: карточка, созданная в YClients минуты назад, найдётся
  живым поиском, но карта лояльности могла ещё не быть выпущена — тогда ветка `welcome`
  честна по данным на момент проверки.
- **Не дедупит** бонусную тему глубже окна транскрипта (`LIMIT 15`) — за это отвечает правило
  7 дней по журналу.
- Фича спит вместе с родительской: пока `followup_delay1_min = 0`, строки очереди не заводятся.
