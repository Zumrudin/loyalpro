# Перенос существующих записей через book_chain

## Причина

В тестовом диалоге обсуждался перенос двух существующих записей. После
подтверждения модель вызвала `book_chain`, который до этого умел только
создавать записи. Проверка выбранного времени и специалистов прошла, но
исходные записи остались на месте: тип операции не проверялся кодом.

## Поведение

- `list_client_bookings` дополнительно возвращает `service_yc_ids`; прежние
  поля сохранены. Оркестратор передаёт прочитанные сервером записи в контекст
  инструментов, отдельно от аргументов модели.
- `chain-reschedule.js` сопоставляет услуги выбранной цепочки с существующими
  записями по ID услуг. Уникальное соответствие один-к-одному привязывается к
  варианту в кэше данного салона и диалога. Сопоставление по названию запрещено.
- Если последнее предложение ясно обозначает перенос, обычная проверка
  подтверждения цепочки разрешает выполнить его. Если было только «Записать?»,
  сервер сначала спрашивает именно о переносе существующих записей. Согласие
  на создание не становится автоматически согласием на изменение.
- Выполнение вызывает существующий `reschedule_booking` для каждого исходного
  `record_id`. `create_booking` и добавление услуг при переносе не вызываются,
  даже если новый вариант рассчитан как одна запись у одного специалиста.
  Исходные отдельные записи сохраняются отдельными.
- Доказательство слотов строится из подтверждённой цепочки с прежним TTL.
  Сохраняются проверки владельца, минимального срока, услуги и мастера.
  Непосредственно перед PUT повторно проверяются владелец, активное состояние
  и точный состав услуг записи. Повтор уже выполненного переноса не делает PUT.
- При частичном отказе ответ перечисляет только успешные переносы. Повтор
  использует те же исходные ID. Исчезнувшая запись не заменяется другой.
  После отказа выполнение пакета инструментов прекращается, включая создание
  записей, которое модель могла запланировать следом. Журнал и подтверждение
  описывают перенос, а не создание.

## Консервативные ограничения

Несколько исходных записей на одну услугу, объединённая запись с несколькими
услугами, смесь переноса и добавления, неизвестные ID услуг или ошибка чтения
CRM блокируют действие до обращения к администратору. Создавать новую цепочку
на те же услуги вместо имеющихся без отдельного разбора система не будет.
Обычная новая цепочка без существующих совпадений и добавление новых услуг
после закреплённого визита сохраняют прежний путь. Перенос чужого пациента
через сопоставление записей владельца диалога запрещён; для другого номера
остаётся прежний отдельный путь создания.

Автоматически исправлять уже созданные дубли этот фикс не должен. Изменение
таких записей требует отдельного разрешения владельца. Миграций БД нет.

## Файлы и проверка

Рабочие изменения: `chain-reschedule.js`, `tools/book-chain.js`,
`tools/list-client-bookings.js`, `tools/reschedule-booking.js`,
`booking-modify.js`, `orchestrator.js`, `chain-confirmation.js`,
`tool-memory.js`, `recent-write.js` в `backend/services/agent/`.
Новые и дополненные тесты проверяют сопоставление источников, подтверждение,
tenant/TTL, неизменность ID, отказ до записи, частичный результат, повтор,
переименование операции в памяти и прекращение пакета инструментов.

Команда из `backend/`:

```sh
AGENT_CATALOG_IN_PROMPT=false ./node_modules/.bin/jest agent-chain-reschedule agent-book-chain agent-chain-confirmation agent-orchestrator agent-reschedule-booking agent-booking-modify agent-tools agent-sequential-offers agent-tool-memory agent-slot-evidence agent-recent-write --runInBand --silent
```

Внешние записи/переносы в тестах заменены заглушками. Браузерный прогон не
требуется: UI не меняется. Живой тест с записью в CRM не выполняется.
Итог: 495 тестов в 11 наборах прошли; `git diff --check` и проверки синтаксиса
изменённой логики без ошибок. Новые регрессии до реализации падали на попытках
создания вместо переноса. По ранее выданному разрешению владельца на перезапуск
дев-стенда выполнен `pm2 restart loyalpro` без изменения окружения. Перед
перезапуском проверена БД `loyalpro_test`; после — статус `online`, HTTP 200
главной страницы и HTTP 401 защищённой ручки диалогов без авторизации.
Откат: отменить только изменения этого исправления и перезапустить дев-процесс;
схема и старые поля ответов совместимы. Откат возвращает риск создания дублей,
поэтому сценарий переноса цепочки до нового исправления проверяет администратор.
