# «Отдел заботы»: программы заботы (post-care + retention)

Дата: 2026-08-02 · Статус: утверждено пользователем

## Цель

Автоматические касания клиентов после состоявшегося визита: забота о самочувствии
(Т+1/Т+14) и возвращаемость (месяцы), с LLM-проходом Милы перед КАЖДОЙ отправкой —
касание не тупой шаблон, а решение с учётом переписки и будущих записей. Ответы
клиентов обрабатывает существующий контур Милы (мед-границы, эскалация осложнений).

## Утверждённые решения

- Вариант C: полноценные «программы заботы» (не расширение notification_rules).
- Состав v1: база цепочек + retention-касания + статусы и дашборд «Клиенты».
  Фото-контроль реабилитации — v2.
- Care-касания подчиняются ТОМУ ЖЕ гейту допуска Милы (`isAllowed`: тумблер,
  чёрный/белый список) — пилот автоматически сужается до белого списка; клиент,
  которому Мила не ответит, касание не получает.
- Перед отправкой Мила проверяет последнюю переписку (клиент мог уже писать про
  процедуру — жалоба, вопрос) и будущие записи (уже записан на докоррекцию →
  «хотите записаться?» неуместно).

## Сущности (migrations.js, IF NOT EXISTS / DO NOTHING)

`care_programs` — программа:
- `id, salon_id, title, is_enabled BOOL DEFAULT TRUE`
- `conditions JSONB` — тот же формат и `evaluateRule`, что в автоуведомлениях:
  `{logic:'and'|'or', items:[{type:'staff'|'category'|'service', ids:[…]}]}`
- `created_by, created_at, updated_at`

`care_touches` — касание в цепочке программы:
- `id, program_id FK, salon_id, title` («Т+1 самочувствие»)
- `delay_days INT` (retention = большая задержка, напр. 120), `send_time TIME DEFAULT '10:30'` (мск)
- `intent_text TEXT` — заготовка-ЦЕЛЬ касания для Милы, не финальный текст
- `sort_order INT`

`care_enrollments` — прохождение программы клиентом:
- `id, salon_id, program_id FK, client_id, phone` (канонизированный `normalizePhoneKey`)
- якорный визит: `yclients_record_id BIGINT, visit_at, staff_yc_id, staff_name`
  (имя врача для «по поручению вашего доктора …»)
- `status: active | completed | declined | escalated | superseded | stopped`, `status_reason`
- `UNIQUE (program_id, yclients_record_id)`, `created_at, updated_at`

`care_touch_sends` — очередь + журнал (по образцу `notification_sends`):
- `id, salon_id, enrollment_id FK, touch_id FK, scheduled_at TIMESTAMPTZ`
- `status: scheduled | sent | skipped | cancelled | failed`, `attempts, error`
- `decision_reason TEXT` — решение/причина Милы или детерминированной проверки
- `rendered_text, routing JSONB, channel_used, delivery_id, sent_at, created_at`
- `UNIQUE (enrollment_id, touch_id)`

## Зачисление (enrollment)

Триггер — вебхук записи, визит состоялся: `attendance=1` ИЛИ `paid_full=1`
(именно ИЛИ — кэшбэчный критерий не годится: визит с оплатой бонусами тоже
заслуживает заботы). Совпавшие по `conditions` программы (маппинг
serviceId→categoryId — существующий кэш из services/notifications.js) →
enrollment + все касания цепочки в `care_touch_sends` со
`scheduled_at = дата визита + delay_days` на `send_time` мск.

Повторный подходящий визит при живом enrollment той же программы (курсовой
клиент): старый → `superseded`, его будущие касания → `cancelled`, цепочка
стартует заново от нового визита.

Записи, созданные самой Милой, тоже якорят программу — это уместно.

## Воркер отправки

Отдельный care-воркер по образцу notification-воркера (тик, `FOR UPDATE SKIP
LOCKED`, аренда с бэкоффом, MAX_ATTEMPTS=3). Все проверки — В МОМЕНТ
срабатывания, не при постановке.

1. Детерминированные проверки (порядок важен, причина → `decision_reason`):
   - программа включена, enrollment `active`;
   - гейт Милы `isAllowed(salonId, phone)` (fail-closed);
   - клиент не в чёрном списке;
   - диалог не эскалирован на оператора (иначе `skipped`);
   - анти-спам: не больше ОДНОГО care-касания клиенту в день; второе due
     сдвигается на завтра (перенос `scheduled_at`, не skip);
   - retention-проверка: был новый визит той же категории/услуги после якоря →
     enrollment `completed` («цель достигнута сама»), касание `cancelled`.
2. Care-проход Милы: отдельный лёгкий промпт (БЕЗ каталога услуг), контекст:
   интент касания, услуга/дата/врач якорного визита, хвост транскрипта
   (`history.loadTranscript`, ~15 сообщений), будущие записи клиента
   (сервисная часть `tools/list-client-bookings.js`). Выход — строгий JSON
   `{action: 'send'|'skip'|'stop_program', text?, reason}`.
   - Невалидный/неразобранный ответ LLM → fail-safe `skipped`, НЕ отправка.
   - `stop_program`: отказ клиента в переписке («не пишите») → `declined`;
     «уже записан/уже решено» → `completed`. «Правило одного пинга» работает
     без нового инструмента в диалоге — решает pre-send проход.
   - Текст — через существующий `reply-guard`.
3. Отправка: `chatpush.sendMessage`, каскад каналов как в автоуведомлениях
   (последний входящий канал клиента первым, `resolveRouting`). Касание
   персистится в `chatpush_messages` как исходящее Милы (persist-on-send +
   дедуп эха по delivery_id — существующий механизм) → видно в чате админки,
   попадает в транскрипт и `pending-replies`: ответ клиента Мила поймёт в
   контексте, повторный прогон не потеряет касание.

## Ответы и красные флаги

Ответ клиента идёт обычным контуром Chatpush → Мила. Мед-границы уже в промпте:
осложнение («болит», «отёк», «асимметрия»…) → немедленный `escalate_to_operator`,
диалог краснеет и всплывает вверх списка чатов. Новый маленький хук: эскалация
из диалога, у phone которого есть активные enrollments → их `status='escalated'`
(красный флаг на дашборде).

## UI: страница «Забота» (nav, owner/admin), две вкладки

- «Программы»: список (тумблер, условия, счётчики), модалка: название,
  конструктор условий (переиспользовать компонент из broadcast-rules), цепочка
  касаний (строки: задержка + время + заготовка; добавить/удалить/сортировка).
- «Клиенты» (дашборд): enrollments — клиент, программа, якорный визит, врач,
  статус-бейдж, следующее касание; фильтр по статусу; клик → deep-link
  `/#chat/<key>`; раскрытие строки — журнал касаний с `decision_reason`.

Бамп версий ассетов обязателен.

## API `routes/care.js` → `/api/care` (owner/admin)

- `GET/POST/PUT/DELETE /programs[/:id]` — программы вместе с касаниями
  (цепочка сохраняется целиком в PUT), `POST /programs/:id/toggle`
- `GET /enrollments?status=&program_id=` — дашборд
- `GET /enrollments/:id/sends` — журнал касаний
- `POST /enrollments/:id/stop` — ручная остановка (`stopped`)
- Словари пикеров — существующий `GET /api/notification-rules/dictionaries`

## Тесты

- Чистые модули: расчёт `scheduled_at` (мск, send_time, retention-месяцы),
  парс care-решения (fail-safe skip), анти-спам «1 в день» (сдвиг, не skip),
  superseded-логика, матчинг условий (переиспользует протестированный
  `evaluateRule`).
- Живой смоук `scripts/care-e2e.js`: синтетический enrollment на тестовый
  номер, ускоренный `scheduled_at`, реальный care-проход LLM, доставка,
  чистка за собой (по образцу `agent-price-probe.js`).

## Границы v1 (сознательно)

- Без фото-контроля реабилитации (Т+1/Т+3/Т+7 с фото врачу) — v2, туда же
  приём медиа из Chatpush.
- Разметка сообщений не адаптируется под канал.
- Догоняющих сообщений при молчании клиента нет; следующее касание цепочки —
  плановое, не «догоняющее».
