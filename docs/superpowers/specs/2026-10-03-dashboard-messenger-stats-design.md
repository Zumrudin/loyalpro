# Статистика переписок в мессенджерах на дашборде — дизайн

Дата: 2026-10-03. Статус: утверждён владельцем (определения и макет).

## Зачем

Салон хочет видеть на странице «Обзор», сколько клиентов пишут в мессенджеры
первыми и сколько из них в тот же день записываются, суммарно и по каждому
каналу (WhatsApp, Telegram, MAX). Сегодня эти данные есть только в сырых
таблицах переписки и записей, и для ответа на вопрос «работает ли канал»
приходится писать SQL руками.

## Утверждённые определения

Все даты — московские (`Europe/Moscow`), как у остального дашборда.

- **Диалог** — пара «собеседник + календарный день», в которой есть хотя бы
  одно сообщение, кроме автоуведомлений (`authored_by = 'system'`). День,
  состоящий только из автоуведомлений («Вы записаны…», «Напоминаем…»),
  диалогом не считается. Групповые чаты исключены (`chat_id LIKE '-%'`,
  `… LIKE '%@g.us'`, `… LIKE '%@broadcast'`). Собеседник определяется тем же
  ключом, что и в «Чате» (`DIALOG_KEY_SQL` из `services/chat.js`: номер,
  иначе `chat_id`).
- **Клиент написал первым** — первое за день неслужебное сообщение диалога
  (по `msg_ts`) имеет `direction = 'incoming'`. Ответ клиента на
  автоуведомление считается «написал первым». Канал диалога — канал этого
  первого сообщения.
- **Записался в тот же день** — у клиента с телефоном диалога есть запись в
  `records`, у которой дата СОЗДАНИЯ в YClients совпадает с днём диалога и
  `status <> 'deleted'`. Дата создания берётся из `raw_payload->>'create_date'`
  (строка вида `2026-10-03T18:31:10+0300`, московское локальное время,
  присутствует у 100 % строк); день — `left(raw_payload->>'create_date', 10)`.
  `records.created_at` НЕ годится: это время вставки нашей строки (у
  `source='sync'` — время синка). Записи со статусами `no_show`, `waiting`,
  `confirmed`, `arrived` считаются: бронь была создана.
- **Единица счёта** всех трёх показателей — диалог-день. Один собеседник,
  писавший в понедельник и в среду, даёт два диалога.
- **Период** — общий переключатель дашборда (Сегодня / Неделя / Месяц /
  Период), границы включительно, парсятся существующим `resolvePeriod`.

Дополнительные цифры, которые показываются рядом:

- **Без номера** — диалоги «клиент первым», у которых телефон скрыт
  (Telegram/MAX). Их нельзя сопоставить с записью, и пользователь должен
  видеть этот зазор, а не принимать его за «не записались».
- **Оформила Мила** — сколько из записей «в тот же день» создал агент:
  `agent_events.kind = 'booking_created'`, `payload->>'record_id'` =
  `records.yclients_record_id`.

Замер на дев-базе за 30 дней до 03.10.2026: Telegram 201 → 81, WhatsApp 102 → 39,
MAX 83 → 34 (клиент первым → записались в тот же день), конверсия ≈ 40 %.

## Чего фича НЕ утверждает

Запись «в тот же день» не доказывает, что она пришла из переписки: клиент мог
позвонить, а администратор — внести запись руками. Подпись под таблицей
говорит об этом явно («запись создана в тот же день, кем угодно»). Отдельная
цифра «оформила Мила» — единственная часть, где источник записи известен.

## Архитектура

Вариант «отдельная ручка» (утверждён): дашборд СТАРТУЕТ запрос статистики
переписок параллельно основному (`/api/analytics/dashboard`) и дожидается его
перед каскадом карточек — в отличие от графика бонусов
(`/api/analytics/bonuses`), который на деле грузится ПОСЛЕДОВАТЕЛЬНО, уже после
основного ответа. Сбой или медленный запрос по переписке не ломает
остальные карточки (свой try/catch внутри `loadMessengerStats`; текст ошибки
ручки показывается в подписи плитки «Диалогов за период»). Предрасчёт в таблицу отвергнут: объёмы (~15 тыс.
сообщений, ~450 записей в месяц) считаются на лету за доли секунды.

### Бэкенд

**`backend/services/messenger-stats.js`** — новый модуль.

- `MESSENGER_STATS_SQL` — экспортируемая константа с запросом (экспорт нужен
  для живого `EXPLAIN` на дев-БД, как у `LEASE_SQL` воркеров). Параметры:
  `$1` salon_id, `$2` from, `$3` to (даты `YYYY-MM-DD`).
- `loadMessengerStats(salonId, from, to, deps = { db })` — выполняет запрос,
  возвращает сырые строки.
- `summarize(rows, { from, to })` — ЧИСТАЯ функция: строки → ответ API
  (сводка, разрез по каналам, ряд по дням с нулями на пустые даты). Тестируется
  без БД.
- `channelLabel(channel)` — `tdlib → Telegram`, `whatsapp → WhatsApp`,
  `max → MAX`; незнакомое значение возвращается как есть.

Структура запроса (один SQL, CTE):

1. `m` — сообщения салона за период, не группы, не `system`:
   `dkey` = `DIALOG_KEY_SQL`, `d` =
   `(to_timestamp(msg_ts) AT TIME ZONE 'Europe/Moscow')::date`, `p10` =
   последние 10 цифр `phone` (или NULL, если номера нет), `channel`,
   `direction`, `msg_ts`. Фильтр по периоду — `d BETWEEN $2::date AND $3::date`.
2. `dd` — диалог-дни: `GROUP BY dkey, d`; первое сообщение дня —
   `DISTINCT ON (dkey, d) … ORDER BY dkey, d, msg_ts` даёт `first_dir` и
   `first_channel`; `p10` — любой непустой номер диалога за день.
3. `cl` — клиенты по номерам: `clients.phone = ANY(ARRAY['+7'||p10, '7'||p10,
   '8'||p10, p10])` (сравнение равенством, использует `idx_clients_phone`;
   98,7 % карточек хранят `+7XXXXXXXXXX`). Берутся `id` и `yclients_client_id`.
4. `rec` — записи, созданные в периоде: `left(raw_payload->>'create_date',10)
   BETWEEN $2 AND $3`, `status <> 'deleted'`; поля `client_id`,
   `yclients_client_id`, `cd` (день создания), `yclients_record_id`,
   флаг `by_agent` через `EXISTS` в `agent_events`.
5. Итог: по `(d, first_channel)` — `dialogs`, `client_first`,
   `client_first_no_phone`, `booked_same_day` (есть `rec` с `cd = d`, связь по
   `client_id` ИЛИ по `yclients_client_id`), `booked_by_agent`.

`summarize` складывает строки в три разреза; на уровне салона и канала
`dialogs ≥ client_first ≥ booked_same_day` по построению.

**Маршрут** — `GET /api/analytics/messengers` в `backend/routes/api.js`, рядом
с `/analytics/bonuses`: `auth`, `req.user.salonId`, `resolvePeriod(req)`,
ответ `summarize(...)`. Ошибка — `500 {error}`; фронт её глотает сам.

Ответ:

```json
{
  "period": { "from": "2026-09-04", "to": "2026-10-03" },
  "totals": { "dialogs": 716, "clientFirst": 386, "clientFirstNoPhone": 30,
              "bookedSameDay": 154, "bookedByAgent": 61 },
  "byChannel": [
    { "channel": "tdlib", "label": "Telegram", "dialogs": 382, "clientFirst": 201,
      "clientFirstNoPhone": 27, "bookedSameDay": 81, "bookedByAgent": 30 }
  ],
  "daily": [ { "date": "2026-09-04", "clientFirst": 12, "bookedSameDay": 5 } ]
}
```

`byChannel` отсортирован по `dialogs` убыванию; `daily` покрывает каждый день
периода, пустые дни — нулями (график без дыр). Проценты считает фронт.

Индексы не добавляются: выражение по `raw_payload` с приведением к
`timestamptz` не `IMMUTABLE`, а строковый `left(...,10)` на 13 тыс. строк
`records` и 15 тыс. строк `chatpush_messages` читается последовательно за
десятки миллисекунд. Живой `EXPLAIN ANALYZE` на дев-БД — обязательный шаг
плана; порог — не более 300 мс на месячном периоде.

### Фронт

**`frontend/index.html`** — новый блок между рядом карточек
(`.sg` с «Клиентов в базе…») и `.g32` с «Выручка по дням», по макету
`2026-10-03-dashboard-messenger-stats-mockup.html` (рядом с этой спекой;
скриншоты обеих тем снимаются из него headless-Chrome):

- заголовок «Переписки в мессенджерах» + подпись периода и каналов справа;
- три плитки `.sc`: «Диалогов за период», «Клиент написал первым» (+ доля от
  диалогов, + «N из них без номера телефона»), «Записались в тот же день»
  (+ конверсия от написавших первыми, + «N оформила Мила»);
- `.g32`: слева карточка с графиком `canvas#msgChart` (столбики по дням, две
  серии: «Написали первыми» синий `#3b82f6`, «Записались в тот же день» зелёный
  `var(--a)`; в тёмной теме зелёный `#00a87c`, палитра проверена валидатором
  dataviz в обеих темах; легенда в заголовке карточки; тултип с конверсией
  дня); справа карточка «По мессенджерам» — таблица: канал (бейдж TG/WA/M),
  диалогов, первым, записались, конверсия с полоской, строка «Все каналы»
  итогом, подпись с определениями под таблицей.

**`frontend/js/pages/dashboard-messengers.js`** — новый файл, подключается
обычным `<script>` после `dashboard.js` с бампом `?v=` (правка без бампа не
доезжает до браузера — известная готча). Делит глобальную область с другими
страницами: никаких верхнеуровневых `const` с именами существующих функций
(класс дефекта `chat-wait-status.js`).

- Чистые помощники (тестируются `node --test` в `vm`, как
  `chat-wait-status.test.js`): `msgPct(part, whole)` → `'40%'`/`'—'`;
  `msgChannelRows(byChannel, totals)` → массив строк для таблицы;
  `msgChartSeries(daily)` → `{labels, first, booked}`;
  `msgTileTexts(totals)` → подписи трёх плиток.
- `loadMessengerStats(q)` — `api('GET', '/api/analytics/messengers' + q)`,
  рендер плиток/таблицы/графика. Экземпляр графика — глобальная `msgCh`,
  уничтожается перед перерисовкой (как `rCh`/`bfCh`). Цвет серий выбирается по
  `document.documentElement.getAttribute('data-theme')`.
- Пустые данные (0 диалогов) — плитки «0», таблица «Нет данных», график пустой.

**`frontend/js/pages/dashboard.js`** — `loadDashboard` после основного ответа
зовёт `loadMessengerStats(q)` в своём `try/catch` (сбой → `console.warn` +
пустой блок, дашборд живёт); `showDashSkeleton` получает id новых плиток.

Мобильная вёрстка: плитки в столбик при ≤ 900 px (`.msg-tiles`), `.g32` уже
складывается существующим правилом при ≤ 1100 px.

### Права

Маршрут под общим JWT-гейтом `routes/index.js`; специалисты на дашборд не
попадают по существующей ролевой фильтрации меню и префиксов, отдельной
проверки не нужно — ровно как у `/analytics/dashboard`.

## Крайние случаи

- **Диалог без номера** — попадает в «диалоги» и «клиент первым», в
  «записались» попасть не может; считается в `clientFirstNoPhone`.
- **Собеседник сменил канал в течение дня** — диалог один (ключ общий по
  номеру), канал — у первого сообщения дня.
- **Один клиент, две записи в день** — диалог-день засчитывается один раз
  (`EXISTS`), «оформила Мила» тоже один раз.
- **`authored_by IS NULL`** у исходящих до 05.08.2026 — считается
  неслужебным (ошибка в сторону лишнего диалога; на периодах после выката
  авторства не влияет).
- **Запись удалена в YClients после создания** — `status='deleted'`, из
  «записались» выпадает задним числом. Осознанно: удалённая бронь — не бронь.
- **Сегодняшний день** — запись могла ещё не прийти вебхуком; цифра за
  сегодня растёт в течение дня, как и «Выручка за период».
- **Телефон в карточке в нестандартном формате** (1,3 % карточек) — связка
  не найдётся, диалог считается незаписавшимся. Принято.

## Вне scope

- Атрибуция записи к переписке (не доказуема данными).
- Воронка внутри диалога (ответила Мила / администратор / тишина) — отдельная
  задача, см. `docs/2026-10-02-mila-sales-funnel-analysis.md`.
- Экспорт/детализация до конкретных диалогов из дашборда.
