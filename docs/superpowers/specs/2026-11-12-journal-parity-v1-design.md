# Журнал записи: паритет с YClients, v1 — дизайн

Дата: 12.11.2026. Статус: утверждён владельцем (границы и подход), реализация — ветка `feat/journal-local-first`, дев-стенд, прод не затрагивается.
Контекст: программа «функции YClients у нас» (решения владельца 12.11.2026: порядок журнал → финансы → склад → сертификаты/абонементы; для новых областей LoyalPro главный, YClients копия). Журнал остаётся local-first (спека `2026-11-10-journal-local-first-design.md`): сохранение локально сразу, отправка в YClients пакетами по кнопке «Отправить в YClients».
Входы: инвентаризация `docs/2026-11-12-journal-current-inventory.md`, карта API `docs/2026-11-12-yclients-api-capability-map.md`.

## 1. Цель и границы

Цель — администратор работает в нашем журнале так же, как в журнале YClients, не открывая YClients для рутинных операций с записями.

Включено (v1):
- Сетка: вид «Неделя» (один мастер × 7 дней) рядом с «Днём»; календарь выбора даты с индикацией загруженности дней; перенос записи перетаскиванием; изменение длительности растягиванием; цвет и метки записи; значки «онлайн-запись», «новый клиент», «оплачено», «есть комментарий»; перерывы и технический перерыв как отдельные ячейки; печать дня; мобильный день (≤700px — один мастер с переключателем).
- Карточка: телефон клиента; правка комментария; правка длительности; смена клиента; удаление записи; технический перерыв; флаг «не уведомлять клиента»; метки и цвет; «Записать повторно»; история изменений; панель клиента (визиты, неявки, бонусы, абонементы).

Не включено (отдельные подпроекты): групповые события (activity), лист ожидания, повторяющиеся записи, товары в визите (склад), сертификаты и абонементы как способ оплаты, ресурсы отдельными колонками (в зеркале есть `resource_instance_ids`, но запись их через `PUT /record` для обычной записи не подтверждена), печать чека, роли specialist/admin_cashier (доступ остаётся owner/admin).

Эксплуатационная заметка: оплата наличными и картой уже включена на деве (`JOURNAL_ACCOUNT_PAYMENTS_ENABLED=true` в `.env`), отдельной задачи нет.

## 2. Архитектура фронта: разрезание `journal.js`

`frontend/js/pages/journal.js` (1125 строк, 92 КБ) делится на файлы одной глобальной области (как `dashboard.js` + `dashboard-messengers.js`), все с префиксом `jr`:

| Файл | Содержимое |
|---|---|
| `journal.js` | состояние `journal`, `jrApi`, `loadJournal`, навигация по датам, вид (день/неделя), опрос очереди, точка входа из `nav.js` |
| `journal-grid.js` | сетка дня и недели: ячейки, дорожки (`jrLayout`), блоки записей, значки, цвет/метки, перерывы, drag-and-drop и растягивание, печать |
| `journal-card.js` | карточка записи, статусы, редактор услуг, правка комментария/длительности/клиента/меток/цвета/технического перерыва, удаление, история, панель клиента, «Записать повторно» |
| `journal-forms.js` | форма создания и переноса, поиск клиента, календарь выбора даты, вопрос при закрытии |
| `journal-payment.js` | форма оплаты (как сейчас) |
| `journal-dispatch.js` | «Отправить в YClients», сверка операций |

Правила: первая задача — чистое разрезание без изменения поведения; `journal-ui.test.js` грузит ВСЕ файлы журнала одним `vm`-контекстом (как `notifications.test.js` грузит все `<script>` `index.html`) — иначе верхнеуровневый `const` с именем функции другого файла пройдёт тест и сломает страницу (готча из `chat-wait-status.js`). Каждый новый файл подключается в `index.html` отдельным `<script>` с `?v=`; правка JS/CSS — с бампом `?v=`.

## 3. Сетка

### 3.1 Виды
- Переключатель «День | Неделя» в тулбаре. Неделя — один мастер (выбор из фильтра мастера; если выбран «все» — первый работающий), колонки = 7 дней с понедельника. Высота и шаг сетки общие с днём.
- `GET /api/journal/week?date&staffId` → `{ staff, days:[{date, workRanges, working, records:[…]}] }` из зеркала и кэша графиков, без YClients. Внутри — тот же построитель дня, что у `GET /day`, по 7 датам.
- Календарь выбора даты (всплывающий месяц) с загруженностью: `GET /api/journal/month?month=YYYY-MM` → `{ days:[{date, records, workingStaff}] }` из зеркала (`records` без удалённых) и `journal_staff_schedule`. Плотность рисуется точками 0/1/2/3 по доле `records / (workingStaff × 8)`.
- Мобильный день: порог 700px продублирован в CSS (`journal.css`) и JS (`JR_MOBILE_MAX`), менять только вместе (как `CHAT_MOBILE_MAX`). На телефоне показывается один мастер, сверху — чипы мастеров; неделя на телефоне не предлагается (кнопка скрыта).

### 3.2 Блок записи
- Цвет: `custom_color` записи (hex) главнее цвета по статусу; текст — `custom_font_color`, иначе автоконтраст. Метки (`record_labels`) — кружки цветом метки в шапке блока, заголовок в `title`.
- Значки: 🌐 `online=true`; ✦ `client.is_new`; 💳 оплачено (`paid_full`); 💬 комментарий непустой; ⏸ технический перерыв (`technical_break_duration>0`) — отдельная полоса под записью той же ширины, цвет `off`.
- Перерывы мастера (разрывы между интервалами `slots` графика) — ячейка класса `break` с подписью «Перерыв», отличная от `off` (до начала/после конца смены).
- Печать: кнопка «Печать» → `window.print()`; `@media print` скрывает тулбар и меню, сетка дня — в ширину листа, цвета сохраняются (`print-color-adjust: exact`).

### 3.3 Перетаскивание и растягивание
- Перенос: pointer-события на блоке (не на кнопках внутри); при отпускании над свободной ячейкой другого времени/мастера — подтверждение «Перенести запись Имя на 12:30 к Юлии?» → та же сессия формы с `move` (`POST /sessions`). Без подтверждения ничего не меняется. Сетка 5 минут (как у слотов), занятость считается по текущим данным сетки (блок нельзя бросить поверх другой записи того же мастера), окончательную проверку делает сервер (`busy` → сообщение, блок возвращается).
- Растягивание: ручка внизу блока; при отпускании — подтверждение «Длительность 60 → 75 мин?» → сессия с `edit.seanceLength`. Доступно при тех же условиях, что перенос (без оплаты, без блокирующего пакета, статус не «пришёл»/«не пришёл»).
- Блоки записей из очереди (`sync.status` queued/running) и «Продолжение» не перетаскиваются.

## 4. Карточка

### 4.1 Новые поля и действия
| Действие | Клиент | Сервер (сессия `edit`) | В YClients (шаг) |
|---|---|---|---|
| Комментарий | textarea, ≤1000 | `edit.comment` | `PUT /record` `comment` |
| Длительность | поле мин. (кратно 5, 5…720) + растягивание | `edit.seanceLength`; проверка окна с явной длительностью | `seance_length` |
| Сменить клиента | тот же поиск по базе, что в создании | `edit.client {name, phone}` (телефон 11–15 цифр) | `client {phone, name}` — YClients перепривязывает по телефону |
| Цвет | палитра YClients (8 цветов) + «без цвета» | `edit.customColor` (hex или null) | `custom_color` |
| Метки | мультивыбор из справочника салона | `edit.labelIds` (id из кэша `labels`) | `record_labels` |
| Технический перерыв | 0/5/10/…/60 мин | `edit.technicalBreak` (сек, кратно 300, ≤3600) | `technical_break_duration` |
| Не уведомлять клиента | чекбокс (по умолчанию уведомлять) | `edit.notifyClient` / `create.notifyClient` | см. 4.3 |
| Удалить запись | кнопка + подтверждение «удалить насовсем, в отличие от отмены» | `status:'delete'` → шаг `delete` | `DELETE /record/{cid}/{id}` |
| Записать повторно | кнопка → форма создания с тем же клиентом и услугами, дата пустая | обычный `create` | `POST /records` |
| Телефон клиента | в карточке, кликабельный `tel:` + «копировать» | `GET /records/:id` отдаёт `clientPhone` (owner/admin — роутер и так пускает только их) | — |

Условия правки те же, что сегодня: без проведённой оплаты, без блокирующего пакета, не удалена; смена клиента, длительность и удаление — дополнительно статус не «пришёл». Комментарий, цвет, метки, флаг уведомления правятся при любом статусе, кроме удалённой записи.

Наложение (`overlay` пакета `patch`) несёт новые поля, карточка и сетка показывают их сразу, до отправки. Удаление в наложении — блок исчезает из сетки, в карточке по id — «удалена (ждёт отправки)».

### 4.2 История изменений
`GET /api/journal/records/:id/history` → список событий по убыванию времени, объединение двух источников:
- `webhook_logs` (`event_type='record'`, `resource_id=:id`, `salon_id`): по каждому событию `payload.status` (create/update/delete) и разница значимых полей с предыдущим событием: время, мастер, состав услуг, длительность, статус, комментарий, цвет, метки, оплата, удаление. Автор — `payload.data.created_user_id`/ имя из `payload.data.staff` недоступно; показывается «YClients».
- `journal_outbox` пакеты записи (`record_key`/`yclients_record_id`): время, пользователь (`users.name` по `user_id`), шаги и их состояние, ошибка. Автор — «LoyalPro: Имя».
Без новой таблицы. Кап 200 событий. В ответе нет телефона и email.

### 4.3 Уведомления клиенту
В YClients всегда `send_sms:false` (как сейчас). Уведомления клиенту шлёт наш модуль (`services/notifications`) по вебхукам; флаг «не уведомлять» должен его остановить:
- Таблица `journal_record_prefs (salon_id, yclients_record_id, notify_client boolean NOT NULL DEFAULT true, outbox_id, updated_at)`, PK `(salon_id, yclients_record_id)`.
- Для существующей записи воркер пишет строку ДО `PUT` (вебхук приходит после).
- Для новой записи id неизвестен до ответа `POST /records`, а вебхук `create` может опередить нашу запись строки, поэтому `create` уходит с `api_id` = числовой id пакета (`'43'`; YClients хранит `api_id` ТОЛЬКО числом — строку `lp-outbox-43` он сохранил как `"0"`, живой прогон 13.11.2026; поле принимает `POST /records`, вебхук возвращает его в `data.api_id`), и `notifications/enroll.js` проверяет: строка `journal_record_prefs` по id записи, иначе `api_id` (1–15 цифр, не `0`) → пакет `journal_outbox` этого салона → `steps[create].params.notifyClient`. Числовой `api_id` могут прислать и чужие источники (онлайн-запись, другие интеграции), поэтому пакет считается нашим, только если у него есть шаг `create` и его `yclients_record_id` пуст или равен id записи из вебхука; иначе флаг не применяется. `false` → job ставится `skipped` с причиной `journal_opt_out`. Флаг действует на все семь типов правил по этой записи (создана, перенесена, напоминание, опрос и т.д.), снять можно тем же чекбоксом.
Правило «записи Милы получают "Вы записаны" как все» не меняется: по умолчанию `notify_client=true`.

### 4.4 Панель клиента
`GET /api/journal/clients/summary?phone=…` (или `?ycClientId=`) → `{ name, phone, visits:{ success, fail }, bonusBalance, loyaltyLevel, totalSpent, lastVisits:[{date, staffName, services, attendance}] (10), abonements:[{title, balance, expires}] | null, bonusesSource }`:
- `visits` — из `client.success_visits_count/fail_visits_count` зеркала записи, иначе подсчёт по `records`;
- баланс и уровень — из `clients` (при `BONUS_LEDGER_PRIMARY` — наш баланс, иначе показание карты);
- `lastVisits` — из `records` салона по `yclients_client_id`/телефону;
- абонементы — живой `GET /loyalty/abonements?company_id&phone` (кэш 60 с по телефону; сбой → `null`, UI пишет «не удалось прочитать»).
Телефон отдаётся только owner/admin (роутер). Карточка рендерит панель лениво (по открытию), ошибки панели не ломают карточку.

## 5. Сервер

- `sessions.js`: `parseSession` принимает новые поля `edit`, `status:'delete'`, `create.notifyClient`; валидация значений (длина, кратность, hex, id меток из кэша). `buildSteps`: `delete` — последний шаг после статусов, несовместим с оплатами; `edit` с `seanceLength` → проверка окна `index.availability` с переданной длительностью (сейчас длительность всегда из услуг — добавляется параметр `durationOverride`, учитывается и технический перерыв).
- `record-edit.js`: `patch` собирает `comment`, `seance_length`, `client`, `custom_color`, `record_labels`, `technical_break_duration`.
- `outbox-worker.js`: шаг `delete` → `DELETE /record` (409/404 от YClients — «запись уже удалена» → `done`), запись `journal_record_prefs` перед `PUT` при наличии `notifyClient` в параметрах.
- `model.js` `normalizeRecord`: добавить `online, isNew, comment, customColor, fontColor, labels, technicalBreak, clientPhone, visitCounts`; `recordsForDay` учитывает технический перерыв в занятости (слоты).
- `reference-cache.js`: вид `labels` (`GET /labels/{cid}`), обновляется с остальными справочниками; `GET /day` отдаёт `labels`.
- Новые маршруты (`routes/journal.js`, owner/admin, no-store): `GET /week`, `GET /month`, `GET /records/:id/history`, `GET /clients/summary`.
- Миграция: только `CREATE TABLE IF NOT EXISTS journal_record_prefs`; индексов сверх PK нет.
- Безопасность: все запросы по `salon_id`; телефон — только в ответах роутера журнала; тексты YClients наружу не отдаются (502 `unavailable`); `api_id` формируется кодом, не из тела запроса.

## 6. Ошибки и крайние случаи
- Перенос/растягивание на занятое время по данным сервера → `busy`/`slot_taken`, форма показывает причину, блок возвращается на место.
- Удаление записи с оплатой → 409 «сначала удалите оплаты» (как у правки).
- Смена клиента у записи, созданной онлайн (`online=true`) — разрешена, как в YClients.
- `DELETE` после того, как запись уже удалили в YClients, → шаг `done` (идемпотентно).
- Метка, удалённая в YClients после сохранения, → `PUT` вернёт 4xx → пакет `failed` с причиной (правит человек, принцип 10.11).
- История: вебхуки до 04.11.2026 (переезд на Selectel) отсутствуют — список начинается с имеющихся.
