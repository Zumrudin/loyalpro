# Напоминания о повторном визите — дизайн

Дата: 2026-08-07
Статус: утверждён пользователем, готов к планированию реализации

## Задача

Процедуры вроде лазерной эпиляции требуют регулярного повторения: эффект
держится, пока клиент приходит примерно раз в месяц. Сейчас никто об этом не
напоминает — клиент выпадает молча.

Нужен модуль, который после состоявшегося визита ждёт заданный срок и, если
клиент к тому моменту не записался на аналогичную процедуру, пишет ему
напоминание. К напоминанию привязывается бонусная механика: если бонусов мало —
начислить и сказать об этом, если много — напомнить, что накопленное можно
потратить. Всё отправленное попадает в журнал с отметкой, записался ли клиент в
итоге.

Модуль живёт на существующей странице «Забота» отдельными вкладками.

## Решения, утверждённые при обсуждении

| Вопрос | Решение |
|---|---|
| Бонусные пороги | Настраиваемые ступени, а не два зашитых порога |
| Клиент не ответил на напоминание | Молчим до следующего состоявшегося визита |
| «Аналогичная услуга» | Совпадение по условиям правила (мастер/категория/услуга) |
| Конверсия | Отслеживаем и запись, и состоявшийся визит; окно 30 дней, настраивается |
| Текст | Два режима: готовый шаблон и «Мила пишет сама» |
| Порядок начисления | Начислить до отправки, отката нет |
| Нет карты / сбой YClients | Отправить напоминание без бонусной части |
| Ручной тумблер | В строке истории, по паре клиент+правило |
| Догон по базе | Кнопка с превью и капом на день |
| Размещение | Отдельный модуль `reminders`, «Заботу» не переписываем |

## Архитектура

Рассмотренные варианты:

- **A (выбран)** — отдельные таблицы, отдельный воркер, общие хелперы с «Заботой».
- **B** — дискриминатор `kind` в таблицах «Заботы». Отвергнут: enrollment у
  напоминания вырожденный (одно касание, нет supersede-цепочки, нет
  `maybeCompleteChain`), каждая из этих веток стала бы `if (kind === …)` в самом
  нагруженном файле боевого модуля, а колонки под бонусы и атрибуцию всё равно
  пришлось бы добавлять.
- **C** — общий движок плановых сообщений с переписыванием «Заботы». Отвергнут:
  переписывание работающего на проде модуля ради соседней фичи.

Переиспользуется без изменений: `evaluateRule` и `getServiceCategoryMap`
(`services/notifications.js`), `agentSettings.isAllowed`, `care/context.js`
(живые записи клиента из YClients), `care/schedule.js` (`computeScheduledAt`,
`parseVisitAt`, `plusOneDay`), `notifications.resolveRouting` +
`chatpush.sendMessage`, `outgoing-authorship`, `pendingReplies`,
`chat-persist.persistWhatsappOutgoing`, `care/care-prompt.js` для free-режима,
`utils/person-name.resolveGivenName`, `ycGetClientCards`, `ycAccrueCard`.

## Модель данных

Все три таблицы добавляются в `migrations.js` в стиле `CREATE TABLE IF NOT
EXISTS` / `ADD COLUMN IF NOT EXISTS`, без деструктивных операций.

### `reminder_rules`

```
id, salon_id → salons(id) ON DELETE CASCADE,
title, is_enabled BOOLEAN DEFAULT TRUE,
conditions JSONB DEFAULT '{"logic":"and","items":[]}',
delay_days INTEGER NOT NULL,
send_time VARCHAR(5) DEFAULT '11:00',
text_mode VARCHAR(10) DEFAULT 'strict',      -- 'strict' | 'free'
text TEXT NOT NULL,                          -- базовый текст/интент
attribution_days INTEGER DEFAULT 30,
bonus_enabled BOOLEAN DEFAULT FALSE,
bonus_tiers JSONB DEFAULT '[]',
backfill_max_per_day INTEGER DEFAULT 30,
created_by, created_at, updated_at
```

Формат `conditions` — тот же, что у `care_programs`, чтобы работал общий
`evaluateRule` и общий конструктор условий в интерфейсе.

Формат `bonus_tiers` — массив, отсортированный по возрастанию `up_to`,
у последней ступени `up_to: null` (бесконечность):

```json
[ {"up_to": 500,  "action": "accrue",  "amount": 300, "text": "…начислили 300 бонусов…"},
  {"up_to": 1000, "action": "none",    "amount": 0,   "text": ""},
  {"up_to": null, "action": "mention", "amount": 0,   "text": "…у вас {balance} бонусов…"} ]
```

Баланс попадает в первую ступень, для которой `balance < up_to` (последняя
ступень с `up_to: null` принимает всё). Пустой `text` ступени означает «взять
базовый `text` правила». Действия: `accrue` — начислить `amount` и сказать об
этом; `mention` — не начислять, назвать текущий баланс; `none` — обычное
напоминание без упоминания бонусов.

### `reminder_queue`

Очередь и журнал в одной таблице — как `care_touch_sends`.

```
id BIGSERIAL, salon_id,
rule_id INTEGER REFERENCES reminder_rules(id) ON DELETE SET NULL,
rule_title VARCHAR(255),                     -- денормализовано: журнал переживает удаление правила
client_id, phone VARCHAR(20), yclients_client_id BIGINT,
anchor_record_id BIGINT, anchor_visit_at TIMESTAMPTZ, anchor_services JSONB,
scheduled_at TIMESTAMPTZ NOT NULL,
status VARCHAR(20) DEFAULT 'scheduled',      -- scheduled|sent|skipped|cancelled|failed
attempts INTEGER DEFAULT 0, defers INTEGER DEFAULT 0,
last_attempt_at, error, decision_reason,
rendered_text TEXT, routing JSONB, channel_used VARCHAR(30),
delivery_id TEXT, sent_at TIMESTAMPTZ,
balance_before INTEGER, bonus_tier VARCHAR(20),   -- accrue|mention|none|no_bonus
bonus_accrued INTEGER, bonus_txn_ok BOOLEAN,
conversion_record_id BIGINT, converted_at TIMESTAMPTZ, visited_at TIMESTAMPTZ,
source VARCHAR(20) DEFAULT 'webhook',        -- webhook|backfill
created_at,
UNIQUE (rule_id, anchor_record_id)
```

Индексы: частичный `(scheduled_at) WHERE status='scheduled'` для аренды;
`(salon_id, phone, sent_at DESC)` для атрибуции и анти-спама;
`(salon_id, rule_id, created_at DESC)` для истории.

`rule_id` — `ON DELETE SET NULL`, а не `CASCADE` (в отличие от «Заботы»):
пользователь явно просил историю «кому что по какому правилу», и удаление
правила не должно её стирать. Поэтому же денормализован `rule_title`.

`UNIQUE (rule_id, anchor_record_id)` даёт дедуп повторных доставок вебхука.
После удаления правила `rule_id` становится NULL и ограничение на такие строки
не действует — это допустимо, планировать по несуществующему правилу нечего.

### `reminder_suppressions`

```
id, salon_id, rule_id → reminder_rules(id) ON DELETE CASCADE,
phone VARCHAR(20), muted BOOLEAN DEFAULT TRUE,
reason TEXT, source VARCHAR(10),             -- 'auto' | 'manual'
muted_at, reset_at, updated_at,
UNIQUE (rule_id, phone)
```

Отдельная таблица, а не вычисление флага из журнала: ручной тумблер требует
хранимого состояния, а явная таблица делает правило «клиенту сейчас можно/нельзя»
читаемым одним запросом.

## Жизненный цикл

Планирование — чисто событийное, через существующий хук вебхука
`resource='record'` в `routes/webhook.js`, рядом с вызовом `care/enroll.js` и в
собственном `try/catch`: падение напоминаний не должно ронять «Заботу» и
начисление кэшбэка.

**1. Визит состоялся** (`attendance=1` ИЛИ `paid_full=1` — тот же критерий, что в
`care/enroll.isVisitCompleted`; визит, оплаченный бонусами, тоже считается):

для каждого включённого правила салона, чьи условия совпали с визитом,
в этом порядке:

1. снять `muted` в suppressions (`muted=false, reset_at=NOW()`) — клиент дошёл,
   цикл замкнулся;
2. отменить прежние `scheduled` строки этого правила и телефона от **более
   ранних** визитов (`cancelled`, причина «новый визит перепланировал») — как
   supersede в «Заботе»; более поздний активный якорь этот визит не глушит;
3. вставить строку очереди на `computeScheduledAt(visit_at, delay_days,
   send_time)` с `ON CONFLICT (rule_id, anchor_record_id) DO NOTHING`.

Порядок 1→3 обязателен: снятие флага должно предшествовать планированию, иначе
новая строка тут же упрётся в собственный `muted` от прошлого цикла.

Телефон нормализуется `normalizePhoneKey`; клиент в чёрном списке не планируется.

**2. Запись отменена или неявка** (`status='delete'`, `deleted=true`,
`attendance=-1` — проверяется первым, предоплаченная неявка несёт `paid_full=1`
одновременно с `attendance=-1`): строки `scheduled` с этим `anchor_record_id`
переводятся в `cancelled`.

**3. Атрибуция конверсии.** На любом событии записи: если у телефона есть строка
`status='sent'` с `sent_at >= NOW() - attribution_days`, `conversion_record_id IS
NULL`, и новая запись подходит под условия того же правила — проставляются
`conversion_record_id` и `converted_at`. Когда по этой записи придёт
`attendance=1` — проставляется `visited_at`. Запись, созданная раньше
напоминания, конверсией не считается: она же гасит напоминание проверкой «есть
будущая запись».

`attribution_days` и условия берутся из правила по `rule_id`. У строк с
удалённым правилом (`rule_id IS NULL`) атрибуция не считается — сверять новую
запись не с чем; в истории такая строка остаётся с текстом и `rule_title`, но
без отметки конверсии.

## Воркер

`services/reminders/worker.js`, тик 60 с, guard от наслоения тиков, аренда
`FOR UPDATE SKIP LOCKED` с `LIMIT 5` и инкрементом `attempts`, backoff 120 с,
`MAX_ATTEMPTS=3`. Все внешние зависимости инжектируются — юнит-тесты без БД и
сети, по образцу `care-worker.test.js`.

Арендный SQL обязан пройти живой `EXPLAIN` на дев-БД: на алиас цели `UPDATE`
нельзя ссылаться из `ON`-условий джойнов, колонки правила берутся скалярными
подзапросами в `RETURNING`. Юнит-моки `db.any` невалидный SQL не ловят — «Забота»
на этом уже обжигалась.

### Порядок проверок (до любых затрат на LLM и YClients)

1. правило выключено → `skipped`;
2. env kill-switch `CHATPUSH_AGENT_ENABLED` выключен → **отложить на сутки**
   (`deferTouch`-аналог: сдвиг `scheduled_at`, `attempts=0`). Терминальный skip
   сжёг бы напоминание молча, пока администратор держит Милу выключенной;
3. гейт `isAllowed(salonId, phone, {ignoreSchedule: true})` — чёрный список,
   режим whitelist и тумблер агента действуют, ночное окно расписания не
   действует (время отправки задаёт салон в правиле, ровно как у касаний
   «Заботы»). Причина `outside-schedule` при `ignoreSchedule` прийти не может;
   если пришла — WARN и отложить, а не сжечь;
4. диалог на операторе (`agent_dialogs.status='escalated'`) → отложить на сутки,
   `defers++`; при `defers >= 3` → `skipped`. Писать поверх живого разговора
   администратора нельзя, но и терять напоминание из-за паузы, которая обычно
   снимается вечерним sweep'ом, не нужно;
5. `muted` в suppressions → `cancelled`;
6. общий анти-спам «одно сообщение в день» → отложить на день;

Откладывание везде работает одинаково: `scheduled_at` сдвигается на сутки от
`max(scheduled_at, now())` (просроченная строка уезжает в будущее одним шагом,
а не по дню за тик), `attempts` обнуляется, строка остаётся `scheduled` и видна
в интерфейсе. Счётчик `defers` инкрементится **только** на шаге 4 — у паузы
оператора есть предел терпения, у остальных откладываний его нет: выключенный
агент и анти-спам это временные состояния, которые пройдут сами.

7. есть будущая запись под условия правила → `cancelled` («клиент уже записан»).
   `muted` при этом **не** ставится: флаг вешается только за фактически
   отправленное сообщение;
8. был повторный подходящий визит после якоря → `cancelled`.

Шаги 7–8 работают на данных `care/context.loadClientRecords`. Сбой YClients →
WARN и продолжение без этих проверок (fail-open, как в «Заботе»): перманентная
недоступность API не должна молча остановить все напоминания. Цена — редкое
лишнее сообщение клиенту, который только что записался.

### Анти-спам, общий с «Заботой»

`sentTodayExists(salonId, phone)` выносится в общий хелпер и считает отправки
**обеих** очередей — `care_touch_sends` и `reminder_queue`. Без этого клиент в
один день получит и «как самочувствие», и «пора повторить». Это единственная
правка в боевом `care/worker.js`: подмена SQL в `defaultDeps.sentTodayExists`.

### Отправка и бонусы

Порядок сознательный, он закрывает гонку за строку, двойное начисление и ложь о
бонусах:

1. **Захват строки:** `UPDATE reminder_queue SET status='sent', sent_at=NOW()
   WHERE id=$1 AND status='scheduled'`. `rowCount=0` — строку перехватил другой
   исход, молча выходим, ничего не откатывая.
2. **Бонусы**, только если `bonus_accrued IS NULL` (ретрай второй раз не
   начислит): читаем карты `ycGetClientCards` → баланс → `pickTier(balance,
   tiers)` → при `action='accrue'` зовём `ycAccrueCard(salon, cardId, +amount,
   'Бонусы по напоминанию «…»')` → **сразу** пишем в строку `balance_before`,
   `bonus_tier`, `bonus_accrued`, `bonus_txn_ok`. Нет карты, сбой чтения или
   сбой начисления → ступень `no_bonus`, базовый текст правила: сообщение
   уходит, но про бонусы в нём нет ни слова. Начисление — до отправки, отката
   нет: клиент никогда не прочтёт про бонусы, которых у него нет.
3. **Рендер текста** с фактической суммой. `strict` — подстановки в шаблон
   ступени; `free` — вызов LLM с точными цифрами в промпте и проверкой
   `replyGuard.hardViolations` на результате.
4. **Отправка** `chatpush.sendMessage` с маршрутом `notifications.resolveRouting`.
   Провал → строка возвращается в `scheduled` на ретрай; бонусы **не**
   откатываются и повторно не начисляются (пункт 2 их уже записал). Исчерпание
   попыток → `failed`.
5. **Успех** → `muted=true` (`source='auto'`) в suppressions, дозапись
   `delivery_id`/`channel_used`, `pendingReplies.remember` + журнал авторства
   `system` + `persistWhatsappOutgoing` для WhatsApp. Последнее обязательно:
   иначе клиент, ответивший на напоминание, придёт к Миле без текста, на который
   отвечает.

Доставка at-most-once: пропущенное напоминание дешевле дубля живому клиенту —
та же философия, что в «Заботе».

## Догон по базе

Две ручки, по образцу «Выборки» в «Заботе»:

- `POST /api/reminders/rules/:id/backfill/preview` — тянет `/records/{cid}` за
  последние N дней (1–90, по умолчанию 30), гоняет тот же `evaluateRule` и тот же
  `isVisitCompleted`, что и штатное планирование, и возвращает список с
  причинами отсева: `no_phone`, `blacklist`, `muted`, `already_queued`,
  `future_booking`, `superseded` (из нескольких визитов клиента берётся самый
  поздний). Ничего не пишет и не отправляет.
- `POST /api/reminders/rules/:id/backfill` — ставит подтверждённые строки в
  очередь с `source='backfill'`, раскладывая по ближайшим дням в `send_time`
  правила с капом `backfill_max_per_day` (по умолчанию 30). Веерная рассылка
  сотне клиентов в одну минуту исключена по построению.

Расхождение превью с боевым отбором — это баг: правки условий идут в оба места.

## API

`routes/reminders.js`, монтируется как `/api/reminders`, `requireRole('owner',
'admin')`. Поля JWT — `req.user.salonId` и `req.user.userId` (не `salon_id`!),
как в `routes/care.js`.

```
GET    /rules                       список со счётчиками (в очереди, отправлено, конверсия)
POST   /rules                       создать
PUT    /rules/:id                   изменить
POST   /rules/:id/toggle            вкл/выкл
DELETE /rules/:id                   удалить (история остаётся)
POST   /rules/:id/backfill/preview  превью догона
POST   /rules/:id/backfill          выполнить догон
GET    /queue                       запланированные отправки
POST   /queue/:id/cancel            отменить запланированную
GET    /history                     журнал с фильтрами и пагинацией
POST   /suppressions/toggle         ручной тумблер {ruleId, phone, muted}
```

Все запросы скоупятся по `salon_id`.

## Интерфейс

Страница «Забота» получает четыре вкладки: *Программы заботы · Прохождения ·
Напоминания · История напоминаний*.

Редактор правила повторяет редактор программы «Заботы»: заголовок, конструктор
условий, задержка в днях, время отправки, чипы «📋 Готовый текст / ✍️ Мила пишет
сама», блок ступеней бонусов (порог → действие → сумма → текст) и кнопка
«Догнать за N дней» с превью.

Конструктор условий сейчас живёт внутри `frontend/js/pages/care.js` (около 80
строк). Он выносится в общий модуль и подключается к обеим вкладкам — вместо
копии. Поведение существующего редактора при этом не меняется.

История — таблица: дата, клиент, правило, ступень и начисленные бонусы, текст
сообщения, статус, «записался» (дата и услуга), «дошёл», кнопка тумблера
«Разрешить снова / Запретить» в строке.

## Подстановки шаблона

`{first_name}`, `{name}`, `{услуга}`, `{мастер}`, `{дней}` (сколько прошло с
визита), `{бонусы}` (фактически начислено), `{баланс}` (текущий баланс),
`{салон}`.

`{first_name}` резолвится существующим `utils/person-name.resolveGivenName` —
подставлять первое слово карточки нельзя: на боевой базе PERI 73.5% карточек это
«Фамилия Имя Отчество» одной строкой, и клиенту ушло бы «Вихарева, пора
повторить». Осиротевшая запятая в начале строки схлопывается, как в
`notifications.renderTemplate`.

## Тестирование

Вся содержательная логика выносится в чистые модули без БД и сети:

- `services/reminders/tiers.js` — `pickTier(balance, tiers)`: границы ступеней,
  пустой список, баланс неизвестен → `no_bonus`, ступень с `up_to: null`.
- `services/reminders/template.js` — подстановки, `{first_name}` через
  `resolveGivenName`, схлопывание осиротевшей запятой, пустой текст ступени →
  базовый текст правила.
- `services/reminders/eligibility.js` — `hasFutureMatchingBooking(future,
  conditions, catMap)`.
- `services/reminders/backfill.js` — раскладка по дням с капом.
- `services/reminders/attribution.js` — подбор строки-кандидата под новую запись.

Воркер — юнит-тесты с инжектированными зависимостями. Обязательные сценарии:

1. повторная попытка не начисляет бонусы дважды (`bonus_accrued IS NOT NULL`);
2. сбой отправки не откатывает начисление и возвращает строку в `scheduled`;
3. `muted` ставится только при фактической отправке, но не при `cancelled`
   «клиент уже записан»;
4. перехваченная строка (`rowCount=0` на захвате) не отправляется;
5. каждый гейт из порядка проверок даёт свой исход (skip / defer / cancel);
6. сбой YClients на проверке будущих записей не блокирует отправку.

Живые проверки: `scripts/reminders-e2e.js` (реальная отправка на тестовый номер;
бонусная транзакция под флагом `--accrue`, по умолчанию заглушена — начисление
необратимо), `scripts/reminders-ui-e2e.js`, и `EXPLAIN` арендного SQL на дев-БД.

## Что затрагивается в существующем коде

Исчерпывающий список — это вся зона риска:

- `migrations.js` — три таблицы и индексы;
- `routes/webhook.js` — вызов планировщика и атрибуции рядом с care, в
  собственном `try/catch`;
- `server.js` — старт воркера;
- `services/care/worker.js` — одна правка: `defaultDeps.sentTodayExists` считает
  обе очереди;
- `frontend/js/pages/care.js` — вкладки и вынос конструктора условий;
- `routes/index.js` — монтирование `/api/reminders`;
- `frontend/index.html` — подключение нового js-файла страницы.

## Чего модуль сознательно не делает

- Не отслеживает выручку по приведённому визиту — только факт записи и визита.
- Не гасит начисленные бонусы, если клиент так и не пришёл.
- Не шлёт повторное напоминание тому, кто промолчал: разблокировать может только
  новый состоявшийся визит или рука администратора.
- Не задаёт срок сгорания бонусов — ручная транзакция YClients такого поля не
  имеет.
- Не применяет address-guard и медицинские границы к тексту: тексты в режиме
  `strict` пишет салон, как и шаблоны автоуведомлений.
