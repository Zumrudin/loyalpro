# Память Милы о результатах инструментов между ходами

**Дата:** 2026-08-04
**Статус:** дизайн утверждён

## Проблема

Транскрипт диалога собирается из текстов `chatpush_messages` (`history.loadTranscript`):
в него попадают только реплики клиента и финальные ответы Милы. Весь tool-цикл хода
(`convo` в `orchestrator.runDialog` — вызовы инструментов и их результаты) живёт один
прогон и выбрасывается. На следующем ходе модель не помнит, какие слоты показывала,
какие цены называла, что читала в истории визитов — и гадает по собственному тексту.

Два существующих костыля латают частные случаи ровно этой дыры:
- `sequential-offers.js` — дописывает живые варианты стыковки в хвост промпта
  (in-memory, умирает при рестарте pm2);
- `pending-replies.js` — подмешивает только что отправленные реплики до прихода эха.

## Решение (гибрид)

Полный сырой лог tool-цикла — в БД (форензика, разбор инцидентов). В промпт — только
детерминированная компактная выжимка фактов, блоком в волатильном хвосте (обобщение
подхода sequential-offers).

### 1. Таблица `agent_tool_events` (сырой лог)

Через `migrations.js` (`IF NOT EXISTS`, не деструктивно):

```
id        bigserial PK
salon_id  int NOT NULL
dialog_key text NOT NULL          -- тот же ключ phone || chat_id, что во всём чате
turn_id   uuid NOT NULL           -- группирует события одной попытки runDialog
ts        timestamptz NOT NULL DEFAULT now()
tool      text NOT NULL
input     jsonb                   -- полный (PII допустима: та же БД, где chatpush_messages)
result    jsonb                   -- кап ~64 КБ, при обрезке маркер truncated:true
is_error  bool
delivered bool                    -- NULL до вердикта, см. жизненный цикл
```

Индекс `(salon_id, dialog_key, ts DESC)`. Чистка тем же кроном `40 4 * * *`, что чистит
`outgoing_authored`; хранение 30 дней.

**Жизненный цикл `delivered`** — главная тонкость:
- Оркестратор буферизует события по ходу tool-цикла и флашит батчем в конце попытки.
  Строго best-effort: сбой БД не роняет ход (паттерн outgoing-authorship).
- Попытка, выброшенная перегенерацией (`hasIncomingAfter` → continue), флашится сразу
  с `delivered=false`: эти факты пациент не видел, в выжимку они не попадают.
- Диспетчер после успешной отправки реплик помечает turn `delivered=true` (без await).
  Черновик, выброшенный rerun'ом до отправки, — `false`.
- Fail-open при краше между флашем и отметкой: `delivered IS NULL` → в выжимку не
  попадает, КРОМЕ событий write-инструментов (`create_booking`, `book_chain`,
  `cancel_booking`, `reschedule_booking`, `modify_booking_services`) — запись в YClients
  существует независимо от того, ушла ли реплика, и забыть её опаснее всего.

### 2. Выжимка: `services/agent/tool-memory.js`

Чистый модуль (без HTTP; БД — через переданный интерфейс), юнит-тесты
`agent-tool-memory.test.js`.

Выборка: события диалога за последние **48 часов**, только `delivered=true`
(+ write-события с любым значением флага). Кап ~30 событий, жёсткий потолок рендера
**~1500 токенов**; при переполнении приоритет — свежие и write-события; о срезанном
факт срезания в лог (правило «no silent caps»).

Пер-инструментные экстракторы + **дефолтный фолбэк** (имя инструмента + скалярные
аргументы без PII-полей `client_phone/client_name/comment` + решающие поля результата —
расширенный `summarizeToolInput/Result`), чтобы новый инструмент автоматически получал
минимальную запись:

- write-инструменты — самое ценное: «[вчера 19:03] создала запись record_id=…
  “Услуга” у Мастера на 5 августа 14:00»;
- `get_service_masters` — названные цены: «цена “X”: Юлия 19 000, Пери 23 000»;
- `get_client_visit_history` / `list_client_bookings` — компактная сводка прочитанного;
- `get_available_slots` / `get_available_dates` / `get_sequential_slots` /
  `get_parallel_slots` — **защита от протухания**: конкретные времена рендерятся только
  если событию < 30 минут; старше — только факт «смотрела слоты “Услуги” у Мастера на
  дату D», без времён. Иначе память воспроизведёт инцидент со стухшими слотами
  (`TIME_UNAVAILABLE_RE`, 2026-07-31);
- `search_knowledge_base` — только заголовок найденной статьи, не текст.

Рендер строго детерминирован (сортировка по ts, стабильные форматы) — требование
префикс-кэша.

### 3. Место в промпте

Блок «ЖУРНАЛ ТВОИХ ДЕЙСТВИЙ В ПРЕДЫДУЩИХ ХОДАХ» в волатильном хвосте
`system-prompt.js`, рядом с «АКТИВНЫЕ ВАРИАНТЫ СТЫКОВКИ». Инвариант кэша тот же:
промпт без блока обязан остаться префиксом промпта с блоком. В шапке блока правило:
«это твоя память для связности разговора; времена слотов из журнала не предлагать без
перепроверки инструментом».

Сбой чтения журнала / рендера — fail-open: ход идёт без блока (как activeOffers).

### 4. Судьба костылей

- **Фаза 1** (этот дизайн): костыли не трогаем, журнал и выжимка работают рядом.
- **Фаза 2** (отдельно): `sequential-offers` переезжает хранением на журнал (полный
  `result` jsonb уже там; заодно закрывается боль in-memory — pm2-рестарт убивает
  варианты). `pending-replies` остаётся: он про тексты исходящих реплик, журнал его
  не заменяет.

### 5. Тесты и живые проверки

- Юнит (`agent-tool-memory.test.js`): детерминизм рендера; PII не течёт в промпт;
  stale-слоты без времён; потолок токенов и приоритезация; фолбэк-экстрактор;
  фильтр `delivered` (write-исключение).
- Оркестратор/диспетчер: буферизация, флаш с нужным `delivered`, best-effort при
  сбое БД (моки).
- Живая: `scripts/agent-tool-memory-e2e.js` по образцу `agent-sequential-e2e.js` —
  ход 1 называет цену через инструмент; ход 2 «а сколько, вы говорили, стоит?» —
  ответ без повторного вызова; ход 3 после имитации рестарта процесса (память
  DB-backed, обязана пережить).

## Принятые риски

- Выжимка — интерпретация, не полный контекст: модель видит «смотрела слоты», но не
  каждое поле ответа. Спорные случаи разбираются по сырому jsonb в БД.
- +0.5–1.5k токенов к волатильному хвосту: при ~5.4 ₽/ход (gemini на polza) —
  единицы процентов стоимости.
- `delivered IS NULL` у read-событий при краше = потерянная память одного хода —
  осознанно дешевле, чем показать модели «факт», которого пациент не видел.
