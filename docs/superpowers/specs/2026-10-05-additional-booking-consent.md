# Подтверждение дополнительного визита при сохранении прежней записи

## Текущее решение: структурированное предложение (05.10, после handoff)

По согласованному варианту 3 добавлен `prepare_additional_booking` для одиночного
дополнительного визита основного пациента. Модель определяет намерение и смысл
согласия. Сервер связывает согласие с конкретной операцией и параметрами.
Описание ниже этого раздела — история предыдущего кандидата с регулярками.

### Протокол

1. Модель выбирает дополнительный визит с сохранением прежних записей и вызывает
   `prepare_additional_booking` с услугой, специалистом, ISO datetime и, если
   известна, длительностью. При неоднозначном намерении сначала уточняет его.
2. Инструмент проверяет серверный список существующих записей, доказательство
   слота именно для услуги/специалиста, минимальный срок, фильтр услуг и каталог.
   Названия берутся из каталога. Сервер генерирует ID и пациентский текст с
   точными параметрами и явным сохранением ВСЕХ прежних записей. CRM не меняется.
3. Оркестратор завершает ход этим текстом. Остальные вызовы из того же пакета
   модели не выполняются. Диспетчер активирует предложение только после
   успешной отправки всех реплик с receipt.id и сохранением исходного текста.
4. На следующем ходе сервер проверяет салон, диалог, пациента, срок предложения,
   совпадение с последней репликой клиники и новое входящее ПОСЛЕ отправки.
   ID и параметры появляются в системном контексте. Созданный в этом же ходе
   черновик не может дать право на создание записи.
5. Модель оценивает ответ: только согласие именно на это дополнительное посещение
   позволяет `create_booking(proposal_id, patient_confirmed:true, ...)`.
   Отказ, неясность, вопрос об условиях или изменение варианта требуют ответа/
   уточнения; новые параметры — нового prepare и нового согласия.
6. Сервер сверяет ID, услугу, специалиста, точную строку datetime, длительность,
   пациента и актуальный снимок существующих записей. Отрицания в свободном
   тексте больше не отменяют подтверждение этого структурированного варианта.
   Остальные проверки create_booking и идемпотентность booking.js сохранены.

Согласие на дополнительный визит нельзя использовать для book_chain, переноса,
отмены, изменения услуг или create_booking без того же proposal_id. При смене
операции сначала требуется новое предложение и ответ пациента.

Существующий точный дополнительный визит, появившийся после предыдущей попытки,
возвращается как duplicate с ID из CRM, если прежние записи не изменились.
Другие изменения снимка требуют нового предложения. Повтор одного отклонённого
create_booking в том же ходе возвращает сохранённый отказ без повторного запуска
обработчика. Новые аргументы проверяются заново.

### Хранение, совместимость и ограничения

- Кэш в памяти процесса: один вариант на salon_id + dialogKey, TTL 30 минут,
  максимум 500 диалогов. Это существующий архитектурный подход sequential-offers.
  Рестарт, вытеснение, новый вариант или другой последний ответ клиники требуют
  повторного предложения; согласие из JSON модели не восстанавливается.
- Отправка означает приём сообщения провайдером с receipt.id. Это не подтверждение
  прочтения: Chatpush доставляет асинхронно. Дополнительно требуется новое входящее
  после времени отправки и семантическое согласие. Времена входящих имеют точность
  до секунды; ответ в ту же секунду консервативно не авторизует запись.
- Модель по-прежнему может ошибиться в оценке согласия. Сервер ограничивает
  последствия точным предложением, но unit-тесты не доказывают качество модели.
- Автоматическое требование нового протокола действует в оркестраторе для
  одиночного create_booking при уже существующей записи на ту же услугу.
  Подготовить дополнительный визит можно и на другую услугу. Гостевые записи и
  цепочки не переведены на этот протокол; прежние внутренние вызовы совместимы.
- HTTP API и схема БД не изменены. Для нескольких процессов потребуется общее
  хранилище предложений; сейчас промах кэша безопасно требует нового согласия.
- Новые диагностические причины содержат только коды, без реплик пациента.

## История предыдущего кандидата

## Подтверждённый дефект

Дополнительная запись использовала `transferConfirmed`. Отрицание переноса
прежнего визита («не переносим», «без переноса») проверялось во всей реплике
и блокировало согласие на новый визит. Дефект воспроизведён детерминированно.
Для первого неуспешного живого прогона точная сработавшая ветка не сохранена:
считать этот дефект доказанной исторической причиной того отказа нельзя.

## Изменение

В `booking-write-guard.js` дополнительный визит проверяет отдельная функция
`additionalConfirmationRejection`. Обычный перенос и проверка цепочек сохраняют
прежнее поведение. Публичные аргументы инструментов и схема БД не меняются.

Из проверки нового визита исключаются только явно сформулированные фрагменты
о сохранении существующего визита. Дата и, если указано, время такого фрагмента
должны совпадать с одной живой записью из серверного `ctx.liveBookings`. Без даты
допускается только явное указание на прежнюю/старую/существующую запись при
непустом проверенном списке. Неизвестные формулировки остаются в тексте и могут
потребовать уточнения; это не универсальный семантический разбор.

Новый визит требует предложения дополнительной записи, согласия и совпадения
даты/времени. Отказ, отмена, вопрос вместо согласия, другая дата/время и
неоднозначный выбор блокируют создание. Время старого сохраняемого визита не
может подтвердить время нового. Внутренние вызовы без `patient_confirmed`
сохраняют консервативную текстовую проверку согласия.

В отказ добавлено совместимое поле `confirmation_reason` и конкретная подсказка
модели: отсутствие флага/контекста, отрицательное предложение, непредложенная
дата/время, конфликт даты/времени, неоднозначность. Полные реплики и персональные
данные в новые диагностические поля не попадают. Перед живым прогоном тестовый
отчёт должен сохранять этот код и безопасные признаки условий проверки.

## Безопасность

Tenant scope, идентификация владельца, проверка слота и доступности услуги
остаются в существующем обработчике. Совпадение уже созданного визита возвращает
его ID без повторной записи. Создание вместо переноса по-прежнему блокируется.
Снятие отрицания о старом визите не снимает отказ от нового визита.

## Проверки и границы готовности

Новые регрессии на исходной реализации: 12 падений, включая ошибочное принятие
просьбы отменить дополнительный визит. После изменения проходят тесты обработчика
создания с заглушкой CRM и оркестратора с реальной проверкой согласия; отдельные
проверки покрывают неправильную дату/время сохраняемого визита, отрицание нового
визита, неоднозначное предложение и совместимость старого контракта.

Команда из `backend/`:

```sh
AGENT_CATALOG_IN_PROMPT=false ./node_modules/.bin/jest agent-booking-write-guards agent-chain-confirmation agent-orchestrator agent-tools agent-create-booking-slot-evidence agent-create-booking-generic agent-create-booking-client-name agent-reschedule-booking agent-book-chain agent-chain-reschedule --runInBand --silent
```

Живые вызовы модели и изменения CRM для этой версии не выполнялись. Перед
выкладкой нужен живой прогон с сохранением причины каждого отказа, включая
варианты «сохраняем», «не переносим», «не трогаем» и «без переноса».
UI и мобильный код не менялись; браузер и mobile lint не требуются.

Откат: вернуть изменение `booking-write-guard.js`; миграций или отката данных нет.
Откат возвращает известную зависимость подтверждения от формулировки сохранения.

## Живая проверка 05.10 — кандидат пока не готов к выкладке

После описанных автоматических проверок кандидат загружен в отдельный процесс
на прод-сервере через временную копию модуля. Основной сервис не изменён.
Использованы боевой провайдер модели, реальные чтения и создания в CRM,
изолированная история тестового номера; доставки через мессенджер не было.

- Исходный тестовый визит создан успешно.
- Дополнительный визит с формулировкой «запись не переносим» создан после одного
  дополнительного подтверждения. Первый отказ — `additional_not_offered`:
  предложение модели не обозначало дополнительный визит явно.
- Второй дополнительный визит с формулировкой «без переноса записи» не создан.
  После обсуждения недоступной даты и выбора альтернативы оба подтверждения
  дали суммарно шесть отказов `negative_proposal`, при `patient_confirmed:true`.
  Сохранявшиеся записи не изменились. Сам отрицательный фрагмент предыдущего
  ответа не сохранён; его точную формулировку по этому отчёту восстановить нельзя.

Таким образом, новая диагностика различает причины, но проверка отрицания
предыдущей реплики всё ещё блокирует живой диалог. Перед выкладкой требуется
доработка с проверкой принадлежности отрицания конкретному предложению.
