# Журнал записи поверх YClients — первая версия

Дата: 2026-11-08. Направление подтверждено пользователем: первый этап — свой интерфейс с YClients как источником записей. Реализация выложена на дев-стенд по отдельному разрешению пользователя 08.11.2026; результаты ниже. Рабочие записи при проверке не изменялись.

## Поведение

Отдельный раздел «Журнал записи» (`#journal`) для владельца и администратора. Прежний раздел «Записи» сохранён. Календарь дня по сотрудникам, выбор даты, фильтр сотрудника, поиск по имени/услуге, карточка визита. Пересечения отображаются отдельными полосами. Данные берутся непосредственно из YClients, обновление вручную; время загрузки показывается явно. Даты и время — Europe/Moscow, независимо от пояса браузера. API читает соседние календарные дни и фильтрует по московскому времени: пояс компании YClients может отличаться. Переходящий через полночь визит отображается продолжением.

Действия:
- Создать запись: имя, телефон с кодом страны, сотрудник, 1–10 услуг, дата, выбранное свободное время, комментарий. Длительность определяет сервер по каталогу; персональная seance_length сотрудника при наличии имеет приоритет. Телефон используется YClients для связи клиента по существующему контракту создания записи.
- Перенести: те же клиент, услуги и цены, новое время/сотрудник; длительность существующей записи сохраняется.
- Подтвердить: attendance=2.
- Отменить: существующая в LoyalPro конвенция attendance=-1 и seance_length=300. При наличии добавляется услуга «Запрет на отправку». Это не удаление: остаётся пяти минутный блок. UI явно объясняет семантику до действия.
- Пришедшие, оплаченные, отменённые и удалённые визиты доступны для просмотра; изменение в этой версии через YClients. Касса, оплаты, начисления бонусов и редактирование состава существующего визита не входят в версию.

## Проверки и ограничения интеграции

Свободное время строится по актуальному management-графику, всем страницам записей соседних дней и требуемым аппаратам. Полная длительность должна помещаться в рабочее окно; шаг стартов 5 минут, прошедшее время исключено. Каталог management позволяет выбирать услуги, скрытые из онлайн-записи. Привязка к сотруднику должна быть явно указана в staff услуги. Неизвестные данные о длительности/оборудовании блокируют действие, а не означают свободное время. При отсутствии instance ids у существующего визита консервативно блокируются экземпляры общих аппаратов, определённых по услугам.

Перед записью проверка повторяется. Карточка имеет HMAC-версию значимых полей; изменение между открытием и сохранением вызывает 409. Перед отправкой PUT запись перечитывается ещё раз. Нет атомарного compare-and-swap с внешней CRM: конкурентные изменения из YClients или Милы остаются ограничением интеграции; окончательный отказ при занятости — через save_if_busy=false. Новые вызовы внешнего API находятся в services/journal/yclients.js. Сетевые ошибки не возвращают клиенту upstream-тексты.

Запросы POST/PUT не повторяются автоматически. send_sms=false не отменяет существующие вебхуки и правила уведомлений: они продолжают работать при реальных изменениях, как для других источников записи. Локальные копии records обновляются существующим webhook/reconcile-путём, сам календарь читает YClients напрямую. Модуль не пишет agent_events, поэтому действия администратора не учитываются как записи Милы.

## API и доступ

Все пути под `/api/journal`; глобальная проверка живой JWT-сессии плюс auth/requireRole в роутере. salonId и userId только из проверенного JWT. Салон для вызовов YClients загружается по этому salonId. Доступа specialist/admin_cashier нет. Ответы Cache-Control:no-store. Новых публичных endpoints нет.

- GET /day?date=YYYY-MM-DD — календарь и справочники.
- GET /records/:id — карточка и версия, без телефона в ответе.
- GET /slots?date&staffId&serviceIds=... либо &recordId=... — свободные старты и длительность.
- POST /create, /move, /confirm, /cancel — action определяется маршрутом, operationId UUIDv4 обязателен; изменения требуют recordId/version.
- GET /operations/pending и POST /operations/review — только owner. Для review нужны operationId и checkedInYclients=true.

Клиентские имена/тексты экранируются. Тело новой записи не сохраняется в localStorage. Форма закрывается только после окончания запроса; при потере ответа повтор использует тот же ключ и тело. Устаревшие ответы календаря, карточки и поиска времени игнорируются.

## Миграция и идемпотентность

`backend/migrations.js`, экспорт JOURNAL_DDL: CREATE TABLE IF NOT EXISTS journal_operations. PK (salon_id, operation_id); user_id, reviewed_by, action, record_id, HMAC request_hash, state, result с recordId, временные метки. Имена, телефоны и комментарии в этой таблице отсутствуют.

Новая таблица создаётся без backfill и без изменения существующих таблиц/данных. Краткие блокировки системного каталога и ссылочных таблиц при CREATE TABLE; сканирования исторических records нет. Изоляция операций — session advisory lock (17291, salonId), общий между процессами журнала; при занятом замке возвращается 409 без ожидания. Неисправное соединение при unlock удаляется из пула.

pending фиксируется отдельным autocommit ДО внешней записи. done записывается после подтверждения YClients; повтор возвращает сохранённый результат. Определённые HTTP-отказы 400/401/403/404/422/429 переводят в rejected. Таймаут, 5xx, неполный ответ или ошибка фиксации успеха сохраняют pending. Новый ключ также блокируется при pending в салоне — перезагрузка страницы не обходит защиту.

Восстановление: владелец открывает «Сверить незавершённые операции», проверяет фактический результат в YClients и явно подтверждает проверку. Только после этого состояние становится reviewed, сохраняется reviewed_by и снимается блокировка новых операций. Старый ключ навсегда остаётся неповторяемым. Автоматического повторения или удаления записи нет. При невозможности установить результат блокировку оставляют.

Порядок выката: применить миграцию штатным способом, затем включить новую версию backend/frontend. До миграции запись fail-closed с 503, прежние API не меняются. Для проверки существования таблицы достаточно read-only `SELECT to_regclass('public.journal_operations');`; запрос здесь не выполнялся. Откат — вернуть код и пункты меню, таблицу оставить: она сохраняет сведения о неоднозначных операциях. Удалять pending/таблицу при откате нельзя до сверки. Применение миграции, перезапуск и выкладка в рабочую среду требуют отдельного разрешения по AGENTS.md.

## Окно создания: услуги и существующие клиенты — 08.11.2026

Создание выделено в отдельную компоновку по второму образцу: слева сотрудник, дата, проверенное время, рассчитанные окончание/длительность и комментарий; в центре выбор услуг плитками с поиском и раскрываемым полным списком; справа поля клиента, поиск и последние клиенты. Блок оплаты и инструменты существующего визита в создании убраны. Услуги фильтруются по специалисту; показываются индивидуальные длительность и цена, при отсутствии — общие значения каталога. Первые три услуги не выдаются за статистически популярные.

Поиск/последние клиенты используют существующий GET /api/clients (tenant определяется авторизацией, limit=6, сортировка last_visit_at). Выбор заполняет имя, телефон, email, количество визитов и бонусный баланс. ФИО выбранного клиента при отправке сохраняется в точности, даже если отображение разделено на три поля: POST /records может переименовать карточку по телефону. Поля выбранного клиента защищены от случайного редактирования, смена/очистка доступны отдельной кнопкой. Email только отображается; редактирование остаётся в разделе клиентов.
