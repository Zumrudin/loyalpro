# Самозаявка на справку об оплате медуслуг (Wix → LoyalPro) — Design Spec

**Дата:** 2026-06-18
**Связано:** [генерация PDF справки](2026-06-17-medical-cert-pdf-design.md), [визуальный редактор координат](2026-06-17-medical-cert-coords-editor-design.md)

## Цель

Дать пациенту/плательщику подать с сайта клиники (Wix) заявку на справку об оплате
медицинских услуг для налогового вычета (КНД 1151156): он сам вводит недостающие у
клиники данные (паспорт, ИНН, кто плательщик/пациент, степень родства, отчётный год),
сразу скачивает готовое «Заявление» для подачи в клинику, а данные попадают в LoyalPro
в раздел «Заявки на справки», откуда сотрудник одним кликом открывает существующий
генератор справок с предзаполненными полями.

## Контекст и ограничения

- Генератор справок КНД уже реализован в LoyalPro (`routes/medical-cert.js`,
  `services/medical-cert-*`, `frontend/js/pages/medical-cert.js`). Эту фичу **переиспользуем**.
- Таблица `clients` уже хранит `phone`, `name`, `birthday`, `yclients_client_id`
  (синхронизируется из YClients). Сопоставление пациента — **локально по телефону**, без
  доп. запросов в YClients.
- YClients-сервис сейчас только читает (карты/транзакции/финансы); сущности «заявка на
  справку» в YClients нет. Заявка хранится **только в LoyalPro** (решение пользователя).
- Ванильный JS SPA для staff; статика отдаётся бэкендом (правки живут на reload, без сборки).
- Мультисалон: каждый запрос строго скоупится по `salon_id`.
- Бэкенд за HTTPS, helmet/CSP включены. Сервер TZ=Europe/Moscow.

## Размещение на Wix

Форму **хостим у себя**: бэкенд отдаёт страницу `GET /cert-request/:slug`. На Wix —
элемент «HTML iframe / Embed» с `src` нашей страницы. Velo и CORS не нужны (API
same-origin внутри iframe), PDF «Заявление» скачивается с нашего бэка. Минус (фикс.
высота iframe) решаем разумной версткой и `postMessage` для авто-высоты (опционально).

## Сопоставление по телефону

Сумма за год считается по **пациенту** (он получал услуги, есть в `clients`):

- **плательщик = пациент** → матчим по его телефону.
- **плательщик ≠ пациент** → матчим по **телефону пациента**; телефон плательщика — контакт.
- Телефон нормализуем в цифры (`replace(/\D/g,'')`), сравниваем по нормализованному виду.
- **Не нашли** → заявку всё равно принимаем (`status='new'`, `matched_client_id=null`),
  сотрудник сопоставляет/обрабатывает вручную. Публично факт совпадения **не раскрываем**
  (защита от перебора базы по номерам). Ответ всегда одинаковый «заявка принята».

## Модель данных

Новая таблица `cert_requests` (миграция в `migrations.js`, паттерн `IF NOT EXISTS`):

| поле | тип | назначение |
|---|---|---|
| `id` | serial PK | |
| `salon_id` | int NOT NULL FK salons | скоуп клиники |
| `status` | varchar(20) NOT NULL default `'new'` | `new` / `in_progress` / `done` / `rejected` |
| `report_year` | int NOT NULL | отчётный год |
| `payer_is_patient` | boolean NOT NULL | плательщик == пациент |
| `payer_last/first/middle` | varchar | ФИО плательщика (получателя справки) |
| `payer_birthdate` | date | |
| `payer_inn` | varchar(12) | |
| `payer_doc_type_code` | varchar(2) | код вида документа |
| `payer_doc_serie_number` | varchar(20) | серия+номер (как ввёл) |
| `payer_doc_issue_date` | date | |
| `payer_phone` | varchar(20) | нормализованные цифры |
| `payer_email` | varchar(190) | для связи |
| `patient_last/first/middle` | varchar | ФИО пациента (если ≠ плательщик) |
| `patient_birthdate` | date | |
| `patient_inn` | varchar(12) | при наличии |
| `patient_doc_type_code` | varchar(2) | |
| `patient_doc_serie_number` | varchar(20) | |
| `patient_doc_issue_date` | date | |
| `patient_phone` | varchar(20) | нормализованные цифры (для матчинга) |
| `relationship` | varchar(20) | степень родства (если ≠ плательщик) |
| `matched_client_id` | int NULL FK clients | результат матчинга по телефону |
| `computed_amount` | numeric(12,2) NULL | подсказка суммы за год (если сопоставлён) |
| `consent_at` | timestamptz NOT NULL | момент согласия 152-ФЗ |
| `ip` | varchar(64) | аудит |
| `user_agent` | varchar(400) | аудит |
| `created_at` / `updated_at` | timestamptz default now() | |

Индексы: `(salon_id, status, created_at DESC)`, `(salon_id, matched_client_id)`.

Колонка у салона: `ALTER TABLE salons ADD COLUMN IF NOT EXISTS cert_request_slug varchar(40)`
(уникальный публичный идентификатор формы; генерим из id, если пуст).

`relationship` — фиксированный набор: `spouse` / `parent` / `child` / `ward`
(супруг(а)/родитель/ребёнок/подопечный) с человекочитаемой подписью на фронте и в заявлении.

## Компоненты

### 1. `services/cert-request.js` (чистая логика + сборка)
- `normalizePhone(raw)` → строка из цифр.
- `validateInn(inn)` → bool (контрольные цифры 10/12-значного ИНН). Чистая, тестируемая.
- `matchPatient({ db, salonId, phone })` → `{ clientId|null }` (поиск в `clients` по
  нормализованному телефону, скоуп salon).
- `computeYearAmount({ db, salonId, clientId, year })` → сумма из `revenue_operations`
  (переиспользуем логику `medical-cert-defaults.sumPaymentsForYear`).
- `buildApplicationPdf(request)` → Buffer «Заявления» (pdf-lib + тот же шрифт
  `assets/fonts/PTSans-Regular.ttf`). Чистая относительно БД (принимает готовый объект).

### 2. `routes/public-cert-request.js` (публичный, монтируется ДО JWT-мидлвари)
- `GET /cert-request/:slug` → HTML-страница формы (отдаёт `frontend/cert-request.html`).
- `GET /api/public/cert-requests/:slug/config` → `{ clinicName, years:[...], relationships:[...], policyUrl }`.
  Неизвестный slug → 404.
- `POST /api/public/cert-requests/:slug` → приём заявки. Honeypot + rate-limit по IP.
  Валидация (телефон, ИНН, паспорт, даты, обязательное согласие). Матчинг → сумма →
  `INSERT cert_requests`. Ответ: `{ ok:true, applicationToken }` (одинаковый при матче и без).
- `GET /api/public/cert-requests/:slug/application/:token` → отдаёт PDF «Заявления».
  Токен короткоживущий (TTL, напр. 30 мин), непредсказуемый, привязан к конкретной заявке,
  не содержит ПДн в URL; в пределах TTL допускает повторное скачивание.

**Монтирование:** публичный роутер подключается в `routes/index.js` **до** inline-JWT-мидлвари,
чтобы не требовать токен (надёжнее точечного добавления в `config.API_PUBLIC`, который
сверяет полный путь и не работает со slug-параметром).

### 3. Расширение `routes/medical-cert.js` (staff, `requireRole('owner','admin')`)
- `GET /api/medical-cert/requests?status=` → список заявок салона (с `matched_client_id`,
  кратким ФИО, годом, статусом, флагом сопоставления).
- `GET /api/medical-cert/requests/:id` → полная заявка.
- `PUT /api/medical-cert/requests/:id/status` → смена статуса (`in_progress`/`done`/`rejected`).
- `PUT /api/medical-cert/requests/:id/match` → ручная привязка `matched_client_id` (по поиску
  клиента), пересчёт `computed_amount`.
- `GET /api/medical-cert/requests/:id/prefill` → отдаёт значения в формате формы генератора
  (год, payer/patient блоки, подсказка суммы) для предзаполнения существующего генератора.

### 4. Фронт-форма `frontend/cert-request.html` + `frontend/js/cert-request.js`
Самостоятельная страница (НЕ часть staff-SPA): загружает `/config`, рисует форму (период,
блок плательщика, тумблер «пациент — это я», условный блок пациента + степень родства,
согласие 152-ФЗ, honeypot), отправляет POST, по успеху показывает экран «Заявка принята» с
кнопкой «Скачать заявление» (ссылка на `/application/:token`). Своя минимальная CSS
(адаптив под iframe). Используем хелперы валидации параллельно серверным.

### 5. Раздел staff `frontend/js/pages/cert-requests.js` + нав-пункт
Список заявок (бейдж количества `new`), фильтр по статусу, карточка заявки с данными и
индикатором сопоставления; кнопки: «Сопоставить клиента» (если не сопоставлено), «Создать
справку» (открывает существующий генератор `medical-cert` с предзаполнением через `/prefill`),
смена статуса. Переиспользуем общие классы стат-фронта.

## Поток данных

```
Wix iframe → /cert-request/:slug (наша страница)
   → GET /api/public/.../config  (название клиники, годы, политика)
   → POST /api/public/.../:slug  (данные формы)
        → normalizePhone → matchPatient → computeYearAmount
        → INSERT cert_requests (status=new)
   ← { ok, applicationToken }
   → GET .../application/:token  → PDF «Заявление» (скачивание)

Staff LoyalPro → раздел «Заявки на справки»
   → GET /requests (список, бейдж new)
   → открыть заявку → [Создать справку] → /requests/:id/prefill
        → существующий генератор medical-cert (staff правит код1/код2, № справки, подписанта)
        → POST /api/medical-cert/generate → КНД-PDF
   → PUT /requests/:id/status = done
```

## «Заявление» (PDF для клиента)

Серверный A4-PDF (pdf-lib + PTSans). Текст:

> **Заявление**
> Я, {ФИО плательщика}, паспорт {серия номер}, выдан {дата}, ИНН {инн},
> прошу подготовить справку об оплате медицинских услуг для представления в налоговый
> орган за **{год}** год
> — *(если за себя)* за оказанные мне медицинские услуги.
> — *(если за пациента)* за медицинские услуги, оказанные {ФИО пациента}, являющемуся(ейся)
> мне {степень родства}.
> Контактный телефон: {телефон}. Дата: «___» ________ 20__ г. Подпись: __________

Точный финальный текст — в реализации; пользователь утвердит при ревью.

## Безопасность и приватность

- Публичный роутер изолирован, JWT не требует; всё остальное `/api/*` остаётся под JWT.
- **Анти-спам:** скрытое honeypot-поле (заполнено → тихо игнорируем) + rate-limit по IP
  (например 5 заявок/час на IP, in-memory счётчик с TTL).
- **Согласие 152-ФЗ:** обязательный чекбокс, фиксируем `consent_at`, `ip`, `user_agent`.
- **Без enumeration:** ответ не зависит от факта совпадения телефона.
- **Доступ к ПДн:** заявки видят только `owner`/`admin` своего салона.
- **Валидация на сервере** (не доверяем клиенту): телефон (10–11 цифр RU), ИНН (контрольные
  цифры), паспорт (цифры/длина), даты (ISO, не из будущего для дат рождения/выдачи), год из
  допустимого списка, обязательные поля по ветке плательщик=пациент.
- **Токен заявления** короткоживущий (TTL), непредсказуемый, не содержит ПДн, не позволяет
  листать чужие заявки.

## Обработка ошибок

- Неизвестный slug → 404 (и страница, и API).
- Невалидные данные → 400 со списком полей (для своей формы; нейтрально).
- Honeypot/rate-limit → 200 «принято» (не палим анти-спам) либо 429 для явного флуда.
- Ошибка матчинга/суммы не валит приём заявки — сохраняем как несопоставленную.
- Сбой генерации «Заявления» → заявка всё равно сохранена; на экране ссылка «повторить
  скачивание».

## Тестирование

- **Юнит (`node:test`)** для `services/cert-request.js`: `normalizePhone`, `validateInn`
  (валидные/невалидные 10/12-значные), `matchPatient` (есть/нет, скоуп salon, ветка
  плательщик≠пациент → телефон пациента), `computeYearAmount`, формирование объекта для
  `buildApplicationPdf` и непустой PDF на выходе.
- **Интеграция:** POST публичного эндпоинта (валид/невалид/honeypot/rate-limit), создание
  строки, ответ без раскрытия матчинга; staff list/detail/prefill скоупятся по salon.
- **Ручная/Playwright smoke:** заполнение формы в iframe-режиме, скачивание заявления,
  появление заявки в разделе staff, кнопка «Создать справку» предзаполняет генератор.

## Вне скоупа (YAGNI)

- Онлайн-оплата.
- Уведомления клиенту по SMS/email о готовности (только in-app бейдж для staff).
- Мультигодовые/диапазонные заявки (только один год).
- Шифрование полей ПДн на уровне БД (хранение в PG c SSL и ограничением доступа; усиление —
  отдельной задачей при необходимости).
- Нативная Wix/Velo-форма.
- Автосоздание сущностей в YClients.
