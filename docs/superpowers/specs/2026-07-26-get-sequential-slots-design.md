# get_sequential_slots — детерминированная стыковка нескольких услуг подряд

Дата: 2026-07-26. Статус: дизайн утверждён.

## Проблема

Сценарий «две процедуры подряд одним визитом» требует пересечения окон нескольких
услуг/мастеров — интервальной арифметики, которую сейчас выполняет модель в голове.
Сильные модели (sonnet-4.6) справляются, слабые (deepseek-v4-flash) галлюцинируют
слоты, обещают несуществующие варианты и ходят кругами, не выполняя перенос
(разбор тестовой переписки 26.07: «био в 16:00» — слота нет; «1 августа к Татьяне» —
мастер в этот день не работает). Для параллельной записи двух гостей аналогичный
детерминированный инструмент уже есть (`get_parallel_slots`); для последовательной
цепочки одного клиента — нет.

## Решение

Новый инструмент агента `get_sequential_slots`: код (не модель) подбирает время,
когда клиент может пройти несколько услуг подряд, с приоритетной лестницей
назначения мастеров и авто-сканом ближайших дней.

## Вход

```json
{
  "services": [{ "service_yc_id": 9536674 }, { "service_yc_id": 9536777 }],
  "date": "2026-07-27",
  "preferred_staff_yc_id": 5708379
}
```

- `services` — 2+ услуг в желаемом порядке выполнения. Порядок фиксирован,
  перестановки не пробуем (YAGNI).
- `date` — с какого дня искать.
- `preferred_staff_yc_id` — необязателен: текущий мастер клиента (у кого уже есть
  запись). Приоритет — сохранить запись у него.

Мастеров-исполнителей инструмент подбирает сам из каталога (`list_services`,
поле `staff[]` собрано per-staff запросами) — модель не назначает мастеров вслепую.

## Приоритетная лестница кандидатов

1. **`same_staff`** — preferred-мастер делает все услуги: одна запись двумя+
   услугами (суммарный `seance_length`).
2. **`other_staff`** — другой мастер, работающий в этот день и делающий все услуги
   («перенести всё к Юлии»).
3. **`mixed`** — на каждую услугу свой исполнитель, встык (био у Астемира, сразу
   после чистка у Юлии). Preferred-мастер получает те услуги, которые делает.
4. **`with_gap`** — булев флаг варианта (не отдельный `type`): тот же день, но с
   перерывом (`gap_minutes` в каждом старте), когда встык в запрошенный день не
   сходится. Считается для той же лестницы мастеров; в выдаче не более одного.

## Алгоритм

Чистая логика — модуль `backend/services/agent/sequential.js` (юнит-тестируемый,
без сети/БД, по образцу `agent-gate.js`); обёртка-инструмент —
`backend/services/agent/tools/get-sequential-slots.js`.

1. Каталог: исполнители каждой услуги, длительность (`equipment-context.durationMin`,
   дефолт 60 мин), фильтр скрытых пар `svcFilter.isBookable` (скрытая пара → мягкий
   пустой ответ `filtered`, как в существующих инструментах).
2. Скан дней `date … date+7` (горизонт 7 дней, утверждено). По каждому дню для
   каждого кандидата: свободные окна из `ycGetStaffSeances` минус занятость
   аппаратов услуги (`equipment-context.busyForService`, `eq.subtractRanges`).
   Для последовательной цепочки общий аппарат услуг — не блокер (интервалы не
   пересекаются), вычитается только занятость другими записями.
3. Цепочечная подгонка: старт `t` годится, если услуга₁ помещается целиком в
   `[t, t+d₁)` в окнах своего мастера, услуга₂ — в `[t+d₁, t+d₁+d₂)` и т.д.
   Допуск стыка 0–15 мин (выравнивание к чистой сетке 30 мин, как в
   `rangesToSlots`). Прошедшее время сегодняшнего дня отсекается (москва,
   `moscowNow`).
4. `with_gap`: если встык в запрошенный день нет — добавить вариант этого дня с
   минимальным суммарным перерывом и явным `gap_minutes`.
5. Ранний стоп: найден `same_staff` на день X → дни после X не сканируются.
   Графики кэшируются в рамках одного вызова (мастер+день запрашивается один раз).

## Выход

```json
{
  "requested_date": "2026-07-27",
  "variants": [
    { "type": "other_staff", "date": "2026-07-30",
      "staff": [{ "yc_id": 1914276, "name": "Гатауллина Юлия" }],
      "starts": [
        { "time": "10:00", "gap_minutes": 0, "booking_mode": "single_record", "chain": [
          { "service_yc_id": 15394035, "service_title": "Novacutan Ybio",
            "staff_yc_id": 1914276,
            "datetime": "2026-07-30T10:00:00+03:00", "seance_length": 1800 },
          { "service_yc_id": 9536777, "service_title": "Комбинированная чистка лица",
            "staff_yc_id": 1914276,
            "datetime": "2026-07-30T10:30:00+03:00", "seance_length": 5400 }
        ] }
      ] }
  ],
  "preferred_staff_cannot": ["Комбинированная чистка лица"],
  "performers_by_service": { "9536777": ["Гатауллина Юлия", "Богатырева Татьяна"] },
  "hint": "…"
}
```

- Сортировка: `same_staff` → `other_staff` → `mixed`; встык-варианты раньше
  помеченных `with_gap: true`; внутри — по дате.
- Лимиты выдачи: ≤3 подходящих даты, ≤4 старта на вариант, ≤6 вариантов суммарно
  (`MAX_VARIANTS`; весь ответ ~1–2k токенов — крупные дампы слотов вредят слабым
  моделям).
- `preferred_staff_cannot` + `performers_by_service` — модель обязана озвучить,
  кто делает каждую процедуру.
- Сбои получения графиков не глушатся молча: флаг `schedule_degraded` + оговорка
  в `hint` (список может быть неполным / «времени нет» не утверждать).
- Пустая выдача — всегда с машинной причиной (`no_combo_in_horizon` или
  `filtered` — все исполнители услуги скрыты фильтром) и `hint`-предписанием
  (предложить по отдельности/другие дни; эскалация — крайняя мера). Случай
  «никто один не делает всё» отдельной причиной не является — его закрывают
  `mixed`-варианты.

## Исполнение выбранного варианта

Новых инструментов записи не нужно: `chain` содержит готовые
`datetime/seance_length/staff_yc_id`. Способ исполнения инструмент считает сам и
кладёт в каждый старт поле `booking_mode` — модель не решает это эвристикой:

- `booking_mode: 'single_record'` — один мастер И `gap_minutes == 0`: одна запись
  со всеми услугами — `create_booking` по первому элементу chain + затем
  `modify_booking_services` с `add_service_yc_ids` = `service_yc_id` остальных
  элементов (как в успешной сессии sonnet-4.6 26.07: запись 30.07 10:00 с двумя
  услугами встык).
- `booking_mode: 'separate_records'` — разные мастера ИЛИ `gap_minutes > 0`:
  отдельный `create_booking` на каждый элемент chain.

Почему перерыв нельзя схлопывать в одну запись: `modify_booking_services`
пересчитывает длительность визита как непрерывную сумму услуг от старта и не
выражает внутренний зазор; а его проверка наложения смотрит только другие записи
ТОГО ЖЕ мастера и слепа к занятости аппарата. Одна непрерывная запись поверх
`with_gap`-варианта стёрла бы перерыв и могла молча занять аппарат, забронированный
в это время чужой записью. Поэтому любой `gap_minutes > 0` → `separate_records`.

## Изменения промпта (`system-prompt.js`)

Блок стыковки нескольких услуг переписывается:

- арифметику окон модель не считает — зовёт `get_sequential_slots`;
- варианты предлагаются в порядке выдачи инструмента (приоритет — текущий мастер);
- всегда называть, кто выполняет каждую процедуру;
- конкретное время озвучивать только из последнего результата инструмента;
- `with_gap` подавать честно, с длительностью перерыва.

Промпт защищён тестами — `agent-system-prompt.test.js` дополняется под новый блок
(память: не срезать промпт, гонять jest после правок).

## Тестирование

- **Юнит** — `sequential.test.js`: чистая подгонка цепочки (стыки, допуск 15 мин,
  вычет аппаратов, перерывы, границы дня, ранний стоп, лимиты выдачи) — без
  сети/БД.
- **Промпт** — jest `agent-system-prompt.test.js`.
- **Интеграция** — прогон сценария 26.07 с тестового номера (79200255591) на деве:
  ожидание — Мила сразу отвечает «встык у Юлии не выйдет ни 27-го, ни 1-го;
  ближайшее встык — …; либо 27-го с перерывом (чистка 20:30)», и после согласия
  клиента выполняет перенос инструментом.

## Риски и ограничения

- До ~20–30 запросов графика к YClients в худшем случае (7 дней × кандидаты);
  смягчение — ранний стоп и кэш графиков в рамках вызова.
- Каталог недоступен → fail-open по образцу `staff-service-guard` (unknown не
  блокирует, ошибку ловит `create_booking`).
- Порядок услуг фиксирован; «в разные дни» инструмент не подбирает — это обычные
  одиночные слоты.
