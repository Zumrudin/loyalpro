# Меню графика сотрудника в журнале

Статус: реализовано локально. После остановки Kimi K3.1 Pro из-за квоты
пользователь поручил завершение основному агенту; замечания ревью исправлены.
28 наборов / 730 тестов проходят. По последующему разрешению установлен
на dev.zumrudin.ru, выполнена штатная миграция и read-only smoke.
Browser E2E не выполнен (MCP отсутствует).
Отчёт: `docs/2026-11-14-journal-staff-menu-review.md`.

## Запрос

По клику на сотрудника открыть меню: добавить перерыв, убрать рабочий день,
добавить рабочий день. Реализацию пользователь поручил Kimi, последующее
независимое ревью — основному агенту.

## Поведение

- В дне меню открывается из заголовка сотрудника для выбранной даты.
- В неделе действия относятся к конкретному дню выбранного сотрудника.
- Для работающего сотрудника доступны перерыв и удаление дня; для выходного —
  добавление дня. Выходные сотрудники доступны через существующий фильтр
  «Только работающие», после его отключения.
- Перерыв задаётся временем начала/окончания внутри смены; рабочий день —
  началом/окончанием. Дата и сотрудник явно видны в форме.
- Удаление рабочего дня требует подтверждения в интерфейсе.
- Пересечения с активными записями, их техническими перерывами и локальными
  неотправленными изменениями блокируют сокращение графика. Записи не отменяются.
- Escape и клик снаружи закрывают меню; управление доступно с клавиатуры и касанием.

## Реализация

1. Изучить AGENTS.md, CLAUDE.md, спецификации журнала 08/10/12 ноября.
   Сохранить все существующие незакоммиченные изменения.
2. Подтвердить контракт изменения графика по официальной документации YClients.
   Не угадывать URL, метод и тело запроса. Не выполнять реальные записи в API.
3. Добавить отдельный сервис графика, валидацию дат/интервалов, проверку сотрудника
   и конфликтов; маршруты owner/admin с salonId из авторизованного пользователя.
4. Сохранение должно следовать существующей модели: локально, затем явное
   «Отправить в YClients». Учесть наложение графика на кэш при обновлении,
   окна записи, день, неделю, месяц, очередь, последовательность операций,
   повтор и неоднозначный результат внешней записи. Сверять актуальный график
   и записи перед отправкой; не перетирать внешние изменения молча.
5. Если нужна схема, использовать только additive/idempotent изменения в
   backend/migrations.js и навык db-migration. Миграции на рабочих БД не запускать.
6. Добавить меню и формы отдельным frontend-модулем, подключить в index.html,
   минимально изменить journal-grid.js и journal.css, обновить кэш-версии.
7. Добавить направленные тесты API, сервиса, очереди и UI. Синтетические данные,
   внешние вызовы замоканы. Покрыть соседние интервалы, неверные даты/время,
   конфликт, чужой салон/роль, двойное сохранение, повтор после таймаута,
   переключение даты при открытой форме и доступность выходного сотрудника.
8. Независимое ревью diff и повторный запуск релевантных Jest-наборов.
   Browser-проверка через Playwright MCP при наличии. Отдельно перечислить
   невыполненные проверки и оставшиеся риски.

## Ограничения

Не развёртывать, не перезапускать сервисы, не менять реальные графики/записи,
не отправлять сообщения и не выполнять финансовые операции. Не включать
секреты или данные пациентов в отчёты. Действующий механизм журналирования
и интеграционные контракты сохраняются обратно совместимыми.
