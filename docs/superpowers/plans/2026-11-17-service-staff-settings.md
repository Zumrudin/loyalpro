# Услуги: специалисты, индивидуальные цены и длительность

Дата: 17.11.2026. Статус: реализация, выкладка и перенос на dev завершены; production не менялся. Итоговые результаты ниже.
Основание: запрос владельца и приложенный пример карточки Yclients.
Предыдущая спецификация: `docs/superpowers/specs/2026-11-08-internal-services.md`.

## Что уже есть

- `backend/services/service-catalog.js`: базовые `price_min/price_max`, длительность в минутах, категории, активность, внешние ID и связь с экономикой.
- Назначения и индивидуальные значения импортируются в `service_catalog.staff` как JSON Yclients. Редактор и `saveService` не умеют менять их.
- Повторный импорт делает `ON CONFLICT DO NOTHING`: актуальные назначения существующих услуг не переносит. Этот контракт нельзя молча заменить перезаписью.
- Журнал уже использует локальный каталог и индивидуальные параметры, но проверяет доступность назначения также по живому Yclients.
- AI-каталог в `backend/services/agent/catalog-data.js` пока использует отдельные источники Yclients и правила видимости. Изменение только редактора приведёт к расхождению каналов.
- `journalService` использует `Number(price) || null`: нулевая индивидуальная цена теряется. Это требуется покрыть регрессионным тестом.
- Локальные сотрудники находятся в `staff_members`; внешняя идентичность — `salon_id + yclients_staff_id`. Локальный ID сотрудника нельзя подменять внешним.

Живой каталог Yclients в рамках подготовки этого плана не считывался. Исторические количества из документации не являются актуальной инвентаризацией. Первый этап ниже обязан установить текущие количества и фактический формат полей.

## Целевое поведение

1. В карточке услуги: название, категория, базовая цена или существующий диапазон, базовая длительность, активность, прежняя связь с экономикой.
2. Ниже — «Специалисты, оказывающие услугу»: назначить существующего сотрудника, снять назначение, задать его цену и длительность.
3. Для цены и длительности отдельные переключатели «Использовать базовую». Отсутствие override означает наследование; ноль — допустимая цена, но не отсутствие значения. Длительность — целое число 1–1440 минут.
4. Изменение базы обновляет только наследуемые значения. Явные индивидуальные значения сохраняются, даже если прежде совпадали с базовыми.
5. В строке сотрудника видны фактические значения и признак наследования. Один специалист не может быть добавлен дважды.
6. Без назначенных активных специалистов услугу можно сохранить, но нельзя предложить для новой записи; показать понятное предупреждение.
7. Снятие назначения и правка прайса не изменяют существующие визиты, оплаты, историю и уже зафиксированные суммы. Для новых визитов используются актуальные параметры.
8. Администратор и владелец редактируют только свой салон; неактивного специалиста нельзя назначить для новых записей.
9. После первоначальной сверки редактируемые настройки ведёт LoyalPro. Повторная сверка с Yclients показывает различия; применение изменений явно отделено от просмотра и обычного импорта.
10. Для внешней записи обязательна корректная связь услуги и специалиста с Yclients. Локальное назначение само по себе не создаёт назначения в Yclients; при расхождении блокируется внешняя операция с понятной причиной. Автоматической обратной синхронизации в этом этапе нет.

Границы: создание сотрудников внутри карточки услуги, групповые услуги, ресурсы, техкарты и прочие вкладки со скриншота не входят в этот запрос. Используем существующих специалистов.

## Предлагаемая модель и совместимость

- Аддитивная таблица `service_staff_assignments`: `salon_id`, `service_id`, `staff_member_id`, nullable индивидуальные `price_min/price_max`, nullable `duration`, источник изменения, временные метки. Уникальность пары в салоне и составные FK к услуге и сотруднику. Для FK сотрудника потребуется уникальность `(salon_id,id)` в `staff_members`.
- Базовые значения остаются в `service_catalog`. Сохраняется поддержка диапазонов. Для индивидуальной цены наследуется вся пара min/max; комбинации частично заданного диапазона отклоняются или нормализуются по заранее закреплённому контракту.
- Общий resolver возвращает назначение, effective price/duration, происхождение значений и внешние ID. Журнал, редактор, AI и booking используют одну семантику.
- Добавить явную отметку завершённой миграции назначений по услуге. Пустой новый список после миграции означает «никто не назначен», а не возврат к старому JSON.
- Пока потребители переводятся, JSON остаётся совместимым представлением, обновляемым в одной транзакции с назначениями. Старые API-запросы без поля назначений не стирают их. Новые поля ответа аддитивны.
- Сохранение базы и назначений атомарно, под существующей блокировкой салона; версия карточки защищает от потери параллельных правок, устаревшая версия — 409.
- До миграции сохраняется прежний режим через контролируемое переключение. Новый функционал включается только после проверки схемы и переноса; исключения БД не должны скрываться произвольным fallback.

**T06 / Kimi:** менять только `frontend/js/pages/service-catalog.js`, `frontend/css/service-catalog.css` и согласованные UI-тесты после фиксации API. ## Перепривязка актуальных услуг

1. Получить свежий полный снимок management-каталога и специалистов через существующий сервис Yclients; зафиксировать время, company и fingerprint. Ошибочный/частичный источник не считать пустым каталогом.
2. Сопоставлять услуги по `(salon_id, company_id, yclients_id)`, сотрудников — по внешней идентичности в текущем салоне. Не связывать автоматически по похожим именам. Проверить случай смены подключённой компании.
3. Построить preview: новые/изменённые/снимаемые назначения, изменённые базы и overrides, неизвестные сотрудники, неактивные услуги, услуги без внешнего ID. Ничего не удалять по отсутствию в неполном ответе.
4. Равенство индивидуального значения базовому не доказывает наследование в Yclients. Если источник не отдаёт соответствующий признак, сохранять явное значение; перевод в наследование — отдельное действие.
5. Неизвестных или неоднозначных сотрудников отправить в список исключений. Создание/синхронизация локального сотрудника — явный пункт переноса с повторной проверкой; не скрытое угадывание.
6. Сохранить резервное состояние затрагиваемых настроек. Применить проверенный diff транзакционно по салону, с контрольной версией каталога и идемпотентным run ID. Если каталог изменён после preview — новый preview, не перезапись.
7. Повторный apply того же run ID — no-op. Ошибка в середине не оставляет частично обновлённую карточку. Возобновление и отчёт различают применённые изменения и исключения.
8. Итоговая сверка: каждая исходная допустимая пара сопоставлена либо явно отражена в исключениях; нет межсалонных связей/дубликатов; цены и длительности равны выбранному diff. Сводка «до/после», без персональных данных.

Обычная кнопка импорта сохраняет прежнее поведение «добавить отсутствующие». Актуализация существующих параметров — отдельный preview/apply. Не вводить автоматическую ночную перезапись локальных правок.

## Проверки и критерии готовности

- Наследование цены/длительности независимо, изменение базы, сброс override, нулевая цена, диапазон, ошибочная и отсутствующая длительность.
- Запрет назначения сотрудника другого салона и неактивного сотрудника; дубликаты; отсутствие назначения; права owner/admin и отказ specialist.
- Атомарность сохранения, параллельное редактирование, старый клиент без назначений, защита от устаревшего preview.
- Импорт: пустой/частичный/ошибочный ответ, повтор, неизвестный ID, архив, различие local/external ID, смена company, корректное преобразование времени.
- Новая запись/слоты/AI используют одинаковые параметры. Смена специалиста пересчитывает только значения, которые должны следовать настройкам; ручные согласованные цены и существующие визиты не перезаписываются молча.
- История, оплаты, экономика и уже сформированные операции остаются неизменными. Удаление назначения не ломает просмотр старой записи.
- Начальные suites: `service-catalog`, `service-catalog-routes`, `service-catalog-ui`, `journal-service`, `journal-ui`, `yclients-booking`, `agent-service-fact`, `agent-slots-staff-options`, `agent-slots-staff-check`, `agent/service-filter`. Точный набор расширяется по фактически изменённым путям.
- Отдельная PostgreSQL-проверка миграции/FK и повторного переноса; браузер: назначение двух специалистов с разными параметрами, сохранение/повторное открытие, конфликт, архив, узкий экран и новая запись с синтетическими API. Использовать qa-e2e и security-privacy-review.

## Выкладка и откат

Порядок: тесты → резервная копия → аддитивная схема → совместимый backend → пробный перенос на dev → UI и потребители → сверка → production preview → разрешённые выкладка и apply → повторная сверка.

Оценить блокировки создания индекса staff_members и объём снимка на T01; сетевые чтения вынести за короткую транзакцию, перенос сериализовать существующим tenant lock. Не выполнять backfill автоматически при старте приложения.

Откат приложения сохраняет новые таблицы и совместимый JSON. Откат данных восстанавливает только затронутые настройки из сохранённого снимка при отсутствии более поздних правок; при конфликте требуется отдельный diff. Не удалять таблицы и не откатывать визиты/финансы.

AGENTS.md требует явного разрешения на точную production-операцию и restart/deploy. На этой стадии разрешение не запрашивается: сначала нужно подготовить реализацию, проверки и конкретный diff. Перепривязка будет считаться завершённой только после применения и сверки, а не после написания скрипта.
