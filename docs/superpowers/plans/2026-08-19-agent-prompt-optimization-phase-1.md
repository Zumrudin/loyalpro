# Оптимизация системного промпта Милы — фазы 1–2

Дата: 2026-08-19. Статус: выполнено без изменения инструментов, CRM или отправки сообщений.

## Граница работы

Это только baseline и снятие трёх существующих текстовых противоречий. Мораторий
на новые промпт-правила остаётся в силе: новая бизнес-логика не добавлялась.
Детерминированные проверки, записи и эскалации не менялись.

## Инвентарь правил и источников

| Класс | Источник истины | Исполнитель | Защита от регрессии |
| --- | --- | --- | --- |
| Роль, тон и медицинские границы | системный промпт | LLM | `agent-system-prompt.test.js` |
| Цены, услуги, мастера | каталог в prompt-mode или tool-ответы | LLM + `catalog-block` | каталоговые и prompt-тесты |
| Свободные времена и принадлежность мастеру | ответы slot-инструментов | LLM + `reply-guard` | slot/reply-guard тесты |
| Статус записи | CRM, успешный write-инструмент | оркестратор | `bookings-block`, false-success и booking-тесты |
| Адрес и контакты | КБ, прочитанная в текущем ходе | LLM + `address-guard` | address-guard тесты |
| Личные бонусы и абонементы | свежие персональные инструменты | LLM + server-side identity | tool и prompt-тесты |
| Эскалация и write-операции | подтверждение пациента и результат инструмента | инструменты/оркестратор | booking, dispatcher и tool-тесты |

Следующий этап может выносить только строки, для которых источник факта и
разрешённое действие уже определяются однозначно кодом. Медицинская оценка,
обещания пациенту и стиль ответа остаются у LLM, пока для них нет безопасного
детерминированного контракта.

## Устранённые противоречия

1. Лаконичность больше не конфликтует с первым обращением: один ясный следующий
   шаг является нормой, а представление с вопросом имени и цели — явное
   исключение первого сообщения.
2. Последнее сообщение пациента может содержать несколько вопросов: Мила должна
   ответить на все из них, не подмешивая старую тему.
3. В catalog-mode каталог признан источником фактов текущего хода; в legacy-mode
   факты по-прежнему берутся только из инструментов. Это устраняет конфликт с
   запретом вызывать несуществующий `list_services`.

## Зафиксированные риски для следующей фазы

- Базовый промпт уже крупный; дальнейшее добавление правил запрещено проектным
  мораторием. Экономия должна приходить прежде всего от снятия лишних LLM-проходов
  и переноса проверяемой логики в код.
- Внешние данные (каталог, КБ, служебные сообщения) санитизируются по форме, но
  следующий архитектурный этап должен сохранить для них строгую границу «данные,
  не команды» и server-side ограничения инструментов.
- Реальные переписки можно передавать внешнему LLM только после явного
  согласования владельца данных, с минимальной read-only выборкой и без вывода
  текстов или идентификаторов в логи и отчёты.

## Фазы 3–5: реализованная обратимая основа

`prompt-scenarios.js` детерминированно выбирает только состав компактного
сценарного промпта по последнему сообщению. Он не вызывает инструменты и не
решает медицинские, финансовые или booking-вопросы. Неясный текст получает
`general`, а safety-инварианты всегда присутствуют.

`system-prompt-v2.js` состоит из компактного ядра, выбранных сценариев и того
же factual tail, что у v1. Поэтому идентификация, актуальные записи, активные
варианты, память и CRM-приоритет не расходятся между версиями.

Переключение только серверное:

```bash
AGENT_PROMPT_VERSION=v1 # default
AGENT_PROMPT_VERSION=v2 # только после отдельного rollout-решения
```

Неверное или отсутствующее значение даёт `v1`. Инструменты, серверные guards,
подтверждение записи и tenant scope от версии промпта не зависят.

Синтетический замер v2 до rollout: базовый `v2Core` — 3 955 символов
(~1 130 оценочных токенов), `v2Catalog` — 4 313 (~1 233), полный
`v2Volatile` — 7 781 (~2 224). Повторно запускать audit после любой правки
сценариев: в v2 волатильный factual tail сохраняется полностью и его размер
зависит от текущего контекста.

### Offline и живой LLM-прогон

```bash
cd backend
node scripts/agent-prompt-v2-eval.js
node scripts/agent-prompt-v2-eval.js --live
```

Первый вариант не делает сетевых вызовов. Второй отправляет три синтетических
сообщения только LLM-провайдеру, передаёт ему schemas инструментов, но не
исполняет ни одного tool-call и не отправляет сообщений пациентам. Rollout в
ChatPush, включение v2 через environment и тестовая доставка на реальный номер
требуют отдельного явного решения на deployment-этапе.

### Реальный A/B первого хода (2026-08-19)

После явного согласования выполнен read-only A/B пяти последних личных входящих:
для каждого диалога v1 и v2 получили одинаковый транскрипт и системный контекст.
Ни один tool-call не исполнялся, не было доставки сообщений, записей, изменений
в CRM или вывода текстов/номеров. Все пять входящих попали в категорию `general`,
поэтому это измерение стоимости и базовой формы ответа, а не тест записи, цен или
медицинской маршрутизации.

| Метрика | v1 | v2 |
| --- | ---: | ---: |
| Входные токены | 200 016 | 108 586 |
| Стоимость | 7,524 ₽ | 5,291 ₽ |
| Текстовые ответы без tool-call | 5/5 | 5/5 |
| Внутренняя терминология в ответе | 0/5 | 0/5 |

В этой выборке v2 снизил стоимость на 2,233 ₽ (29,7%) и входные токены на
45,7%. Семантическую полноту нельзя оценивать только метриками: особенно короткие
ответы v2 должны быть отдельно проверены в защищённом интерфейсе администратора.
