# Форма продажи косметики по скриншоту

Статус: реализовано и проверено 15.11.2026. Luna подготовила стили, Terra — форму, Sol — API; ведущая модель выполнила ревью всех изменений, исправления и интеграционные проверки. Установлено на дев 15.11.2026; миграция применена только к loyalpro_test. Отчёт: [установка на dev](../../2026-11-15-stock-sale-form-dev-deploy.md).

## Цель и исходное состояние

Привести диалог «Продажа товара» к предоставленному пользователем изображению: дата и время, данные клиента, сотрудник и склад, таблица товаров, итог, комментарий и две кнопки сохранения.

Основа: `frontend/js/pages/stock-sale.js`, диалог в `frontend/index.html`, стили `frontend/css/stock.css`. Общие редакторы строк находятся в `frontend/js/pages/stock-docs.js` и используются другими складскими операциями.

Сервер уже принимает `docDate` и `comment`; поиск каталога поддерживает название, артикул и штрихкод. Продажа сейчас требует существующего клиента и полной оплаты наличными/картой либо оформляется как подарок с нулевым итогом. Отдельного сценария неоплаченной продажи нет. Контракт формы не сохраняет ФИО/email.

Источник действующих ограничений: `docs/superpowers/specs/2026-11-13-stock-goods-design.md` и `docs/superpowers/plans/2026-11-13-stock-goods.md`.

## Порядок выполнения

1. Luna готовит визуальную структуру; Terra описывает состояние формы и события; Sol фиксирует API-контракт. Исследование этих частей уже делегировано параллельно.
2. Использовать утверждённые пользователем решения ниже; при реализации обновить действующую спецификацию под проведённую продажу с долгом.
3. Передать Terra готовую визуальную структуру для интеграции поведения. Luna и Terra не редактируют `stock-sale.js` одновременно.
4. Sol реализует серверные изменения параллельно с интеграцией фронтенда после фиксации контракта.
5. Terra выполняет проверки; ведущая модель принимает результат и делает итоговое ревью.

## Утверждённые пользователем решения (15.11.2026)

- **«Сохранить без оплаты»**: провести продажу (`posted`), сразу списать товар и зафиксировать долг в размере неоплаченного итога. Денежные проводки до фактической оплаты не создавать. Предусмотреть последующую оплату того же документа без повторного списания товара; долг уменьшается на фактически внесённую сумму. Не использовать черновик для этого действия. Sol отвечает за контракт, атомарность, защиту от повторов и тесты этого сценария.
- **ФИО и email**: показывать данные выбранного клиента только для чтения. Выбор/смена клиента обновляет поля; отсутствующие значения оставлять пустыми. Форма не создаёт и не редактирует ФИО/email в карточке клиента или YClients. Terra отвечает за загрузку и отображение; Luna — за оформление полей.
- Сохранить доступность существующего сценария «Подарок» и единиц товара; расположение дополнительных настроек согласовать с новой компоновкой. Склад брать из настроек, а не жёстко задавать названием с изображения.

## Файлы и проверки

Основные файлы: `frontend/js/pages/stock-sale.js`, `frontend/css/stock.css`, точечные изменения `frontend/index.html`; при необходимости адаптация `frontend/js/pages/stock-docs.js`. Сервер: `backend/services/stock/sales.js`, `model.js`, `store.js` и соответствующий роут после определения контракта.

Проверки при реализации:

- Из `backend`: `npx jest stock-ui stock-sales stock-model stock-documents --runInBand`.
- Из `backend`: `node scripts/stock-ui-e2e.js` после проверки его безопасного тестового окружения. Использовать синтетические данные и изолированную тестовую БД.
- Браузерное сравнение с исходным изображением при размере 928×577, затем узкий экран; ошибки валидации, Esc/крестик, фокус, длинные названия, несколько строк.
- Для новых финансовых сценариев: неоплаченный документ не создаёт фиктивную выручку, последующая оплата не повторяет движение товара, повтор запроса не создаёт дубль, чужой салон недоступен, старый сценарий полной оплаты работает.

В рабочем дереве уже есть сторонние изменения, включая `frontend/index.html`, `backend/migrations.js` и `backend/scripts/stock-ui-e2e.js`; сохранять их и проверять дифф перед интеграцией. Продакшен, реальные продажи и данные клиентов при подготовке и проверках не изменять.

## Результат и проверки реализации

- Форма повторяет компоновку образца; данные выбранного клиента только для чтения, смена клиента отдельной ссылкой. Поля количества и скидки доступны на узком экране. Сохранены подарок и выбор единиц.
- Неоплаченная продажа сразу списывает товар; частичная/полная оплата доступна в карточке документа. Оплата не создаёт повторного складского движения.
- Создание идемпотентно по requestId, погашение — по paymentId; при неопределённом ответе или сбое обновления карточки фронтенд сохраняет ключ и исходную сумму оплаты.
- Основные файлы: `frontend/js/pages/stock-sale.js`, `stock-docs.js`, `frontend/css/stock.css`, оболочка и версии ресурсов `frontend/index.html`; `backend/routes/stock.js`, `backend/services/stock/{sales,store,model,documents}.js`, три аддитивных DDL-операции в `backend/migrations.js`.
- Тесты: `backend/stock-{ui,sales,model,documents}.test.js`, `backend/scripts/stock-e2e.js`, `backend/scripts/stock-ui-e2e.js`. Фикстуры учитывают текущую проверку сессий; auth middleware не менялся в рамках этой задачи.

Выполнено из `backend`:

1. `npx jest stock-sales stock-model stock-documents stock-routes stock-operations-api finance-ops --runInBand --silent` — 6 наборов, 151 тест PASS.
2. `npx jest stock-ui stock-operations-ui clients-purchases-ui journal-ui --runInBand --silent` — 4 набора, 211 тестов PASS.
3. `node scripts/stock-e2e.js --sale --cleanup` — реальный PostgreSQL/API PASS: долг, повтор создания, конфликт ключа, частичная оплата, повтор оплаты, переплата, чужой салон/роль, погашение, отмена, старые операции.
4. `node scripts/stock-ui-e2e.js` — браузер/реальный API PASS: выбор клиента, readonly данные, список товаров, расчёт скидки, продажа в долг, частичная/полная оплата и отмена; прежние сценарии склада и журнала. Светлая/тёмная темы, ширины 928 и 390; горизонтального переполнения формы нет.
5. `git diff --check` и `node --check` для изменённых JS приложения — PASS.

E2E использует только `loyalpro_test`, TEMP-таблицы и синтетические записи, внешние вызовы заблокированы, завершение — ROLLBACK. Рабочие таблицы и их последовательности не изменяются. Миграционные поля проверены в TEMP-таблице. Фото формы: `/tmp/stock-sale-light-928.png`, `/tmp/stock-sale-dark-928.png`, `/tmp/stock-sale-light-390.png`, `/tmp/stock-sale-dark-390.png`.

Ревью ведущей модели: исправлены гонка одинакового paymentId на разных документах, нечувствительность UUID к регистру, потеря точности в хэше цены, повтор оплаты после ошибки обновления карточки, устаревшие результаты поиска клиента и скрытые мобильные поля. После исправлений блокирующих замечаний в проверенном объёме нет.

В ходе реализации не выполнялись реальные продажи, внешние интеграции, полный репозиторный suite и mobile lint (mobile не менялся). Последующая установка на dev и проверки собранного релиза описаны в отчёте выше. Перед запуском нового API требуется штатная миграция request_id/request_hash/index; откат к прежнему коду не требует удаления этих полей. Старый API без requestId совместим, но не получает новую защиту повторного создания.
