### 1.1 Модуль «Фото-кейсы пациентов» (полный)
Внутренний клинический инструмент для staff-фронта: фотодокументация работ с пациентом — до / в процессе / после по каждому визиту YClients, привязка к специалисту, опциональные курсы лечения, плоский тред комментариев, поиск по пациенту.

- **Спека:** `docs/superpowers/specs/2026-05-30-patient-photo-cases-design.md`
- **План реализации:** `docs/superpowers/plans/2026-05-30-patient-photo-cases.md`

- **Cron:** ежедневная чистка зависших S3-объектов (`s3_orphans` ≥ 5 попыток → отказываемся).

### 4.2 Yandex S3 бакет
Бакет `loyalpro` уже настроен (мы использовали его для smoke в предыдущих сессиях). В `backend/.env` на проде должны быть `S3_*` переменные. Проверить:
```bash

grep -c "^S3_" /root/loyalpro_new/backend/.env
# Ожидается 7 (ENDPOINT, REGION, BUCKET, ACCESS_KEY, SECRET_KEY, FORCE_PATH_STYLE, URL_TTL_SECONDS)
```
Если меньше — донастроить по образцу `.env.example`.

### 4.3 Ротация S3-ключа
Текущий ключ доступа к Yandex Object Storage **попал в чат** ранее по сессии. Рекомендую:
1. В Яндекс IAM → Сервисные аккаунты → удалить старый ключ.
2. Создать новый.
3. Обновить `/root/loyalpro_new/backend/.env` на проде (заменить `S3_ACCESS_KEY` и `S3_SECRET_KEY`).
4. `pm2 restart loyalpro`.


**ВАЖНО про БД при откате:**
- Таблицы `case_*` и `s3_orphans` останутся (`CREATE TABLE IF NOT EXISTS` — не дропаются на откате кода). Пустые таблицы никому не мешают.
- Колонка `users.staff_member_id` останется. Тоже не мешает.
- Если очень хочется — можно вручную удалить:
  ```sql
  DROP TABLE case_comments, case_photos, case_visits, case_courses, s3_orphans CASCADE;
  DROP TYPE case_photo_stage;
  ALTER TABLE users DROP COLUMN staff_member_id;
  ```
  Но фото из S3 надо чистить отдельно (через консоль Яндекса или скрипт).

**Файлы в S3** при откате кода **не удаляются** автоматически. Если откат окончательный — почистить вручную:
```
yc storage s3 rm s3://loyalpro/salon_*/ --recursive
```
