# MAX через свой шлюз — есть ли такая возможность (исследование)

Дата: 2026-10-13. Автор: Claude Fable 5.1 по запросу владельца. Вопрос: можно ли перевести MAX на прямую интеграцию так же, как Telegram (TDLib, `gateway/lib/telegram-client.js`, на проде с 12.10) и WhatsApp (Baileys, `gateway/lib/whatsapp-client.js`, на проде с 13.10). Кода и плана здесь нет — только факты и варианты.

## 1. Коротко

Да, технически возможно, но ТОЛЬКО тем же неофициальным путём, что и WhatsApp: официального API для «номерного» аккаунта (аккаунт клиники по номеру телефона, в котором живут все нынешние переписки) у MAX нет и не анонсировано. Три пути:

| Путь | Что это | Подходит для диалогов Милы и «Чата»? |
|---|---|---|
| A. Неофициальный клиент пользовательского протокола | То, что делают Chatpush, Wappi и др.: реверс-протокол `wss://api.oneme.ru/websocket` / TCP, вход по QR или номеру+SMS | Да, 1:1 замена Chatpush (как Baileys для WhatsApp). Риск блокировки номера выше, чем у WhatsApp |
| B. Официальный Bot API (`dev.max.ru`) | Бот компании; верификация юрлица/ИП; бот не пишет первым, только тем, кто нажал «Начать» | Нет как замена: другой продукт (пациенты пишут боту, не номеру клиники; администратор не может отвечать из приложения). Возможен как ДОПОЛНИТЕЛЬНЫЙ «белый» канал |
| C. Официальные сервисные уведомления по номеру | Через операторов «большой четвёрки»/агрегаторов (edna, Messaggio…): односторонние уведомления, OTP, папка «Полезные уведомления» | Нет для диалогов. Кандидат для модуля уведомлений (замена слоя A Chatpush) вместо/рядом с YClients-каналом MAX |

«Программа разработчиков MAX» для сторонних клиентов (анонс 07.08.2026: API + исходники клиента + аудит кода, только для IT-компаний с опытом крупных проектов, сроков нет) — не наш масштаб; ждать её нельзя.

## 2. Как это устроено у Telegram/WhatsApp и что переиспользуется

Шлюз `gateway/` выбирает класс клиента по `messenger_accounts.channel` (`registry.clientClassFor`: `tdlib` → TelegramClient, `whatsapp` → WhatsappClient). Интерфейс клиента: `start()`, `authStep(step)`, `status()`, `sendText()`, `sendFile()`, `logout()`, `close()`, поля `id`/`authState`/`closed`, статический `dirsFor()`. Входящие уходят в бэкенд вебхуком в форме Chatpush, бэкенд их уже разбирает (`services/chatpush.js envelope()`), транспорт `services/messaging/transport.js` выбирает аккаунт по салону и каналу, админка «Настройки → Мессенджеры» ведёт подключение (QR у WhatsApp, номер/код/пароль у Telegram) и переключает канал по `auth_state='ready'`.

Для MAX бэкенд уже знает: плоскую форму события `max_incoming_msg` (`chat_id` = id собеседника для лички, отрицательный у групп, `chat_type person|group`, `timestamp` на уровне payload), адресацию `recipientParams('max')` = `phone` + `max_user_id` (= `chat_id`), канал файлов `max`, метку канала в админке (`MSG_ACC_CHANNEL.max`). То есть новый клиент встаёт в существующий контракт без правок бэкенда, кроме прокидывания `max_user_id` в `/api/v1/delivery` шлюза и списка каналов в `accounts-repo.listActive`/`createGatewayAccount`.

## 3. Что у MAX есть на самом деле

### 3.1 Пользовательский протокол (путь A)

- Транспорт: WebSocket `wss://api.oneme.ru/websocket` (веб-клиент `web.max.ru`) или TCP (мобильный). Пакет: 10-байтный заголовок + msgpack, LZ4-сжатие, без прикладной криптографии (только TLS). Задокументировано ~177 opcodes (AUTH/LOGIN, GET_QR, MSG_SEND, PHOTO_UPLOAD, CONTACT_INFO_BY_PHONE, NOTIF_MESSAGE…). Источник: `farafonoff/max-web-protocol-sniffer`, `max-account-api` (160+ опкодов из декомпилированного клиента).
- Вход: QR «Профиль → Устройства → Подключить устройство» (веб-сессия, как WhatsApp Web) ИЛИ номер + SMS-код (+ облачный пароль 2FA) как Android-устройство (полная сессия, как TDLib). SMS-вход и phone-auth заблокированы по гео: нужен RU-IP (прод на Beget подходит, дев-бокс — нет).
- Умеет всё нужное нам: входящие в реальном времени, отправка текста/фото/файлов, скачивание вложений по временным URL, поиск пользователя по номеру (`getUserByPhone`), чаты/группы, реакции, редактирование, сессии устройств.
- Библиотеки на Node.js (наш стек шлюза):
  - `webmaxsocket` 1.2.7 (Tellarion; 14★, 6 форков; npm 05.08.2026, репозиторий 28.08.2026; deps `@msgpack/msgpack`, `lz4js`, `ws`) — QR/token/SMS+2FA, WS и TCP, медиа, звонки, `getUserByPhone`. Самая полная Node-реализация.
  - `max-account-api` 0.1.1 (maxsos1; 10★; TypeScript; npm 18.06.2026) — вход по номеру + QR-bind, медиа, группы, `client.raw(opcode)`; с июня без обновлений.
  - `vkmax` 1.0.4 (Grovvik, порт Python-клиента; 1★; ноябрь 2025) — слабый.
- Эталон на Python: `MaxApiTeam/PyMax` (274★, 59 форков, активен 25.09.2026, есть «maintained fork»): TCP и WS, SMS и QR, обновляемый каталог fingerprints мобильного клиента. Полезен как спецификация протокола для сверки Node-библиотеки.
- Эксплуатационная готча: MAX требует «свежий» клиент — при устаревшем `APP_VERSION`/`BUILD_NUMBER` отвечает «Приложение устарело» (webmaxsocket чинил это в 1.2.7, PyMax держит каталог fingerprints). То есть клиент нужно ОБНОВЛЯТЬ вслед за релизами MAX, иначе сессия перестаёт логиниться.

Риски пути A (выше, чем у WhatsApp):
1. Блокировка аккаунта. С 01.10.2025 «Центр безопасности MAX» блокирует вход через сторонние клиенты (моды reMAX, Komet, WhiteMAX); блокировка «временная или постоянная», восстановление по исходному номеру не гарантировано. Библиотеки прямо пишут: «использование может нарушать условия сервиса… ответственности за блокировки не несём»; Wappi советует свои HTTP-прокси. Номерной аккаунт MAX — это номер клиники (79250177778): блок ударит и по приложению администраторов, не только по интеграции.
2. Протокол меняется без предупреждения («уже менялся под библиотекой не раз» — автор моста MAX↔Telegram, 05.10.2026). Сообщество в разы меньше, чем у Baileys (14★ против тысяч), поддержка может прекратиться — тогда чинить придётся нам по PyMax/снифферу.
3. Юридически: MAX — «национальный мессенджер» с госучастием; правила запрещают массовые рассылки по номерам, жалобы получателей ведут к блокировке «пожизненно». Наш трафик — ответы на входящие и единичные служебные сообщения, но формальный риск нарушения условий остаётся.
4. Тот же класс риска уже реализуется у Chatpush: MAX-сессия клиники там «подключена» (`max_session=2`), но с 10.10.2026 21:54 не доставляет и не принимает ничего (13.10 два касания «Заботы» в MAX — «Невозможно доставить»). Свой клиент от такого не застрахует, но даст видимость причины и управление сессией.

### 3.2 Официальный Bot API (путь B)

- Регистрация на `dev.max.ru`: юрлица, ИП и самозанятые — резиденты РФ; верификация через Госуслуги или T-Business ID/Alfa ID; до 5 ботов у организации; карточка бота проходит модерацию (сайт `https://`, логотип 500×500, пользовательское соглашение и политика в интерфейсе бота). С 19.07.2026 API на `platform-api2.max.ru`, токен только в заголовке `Authorization`.
- Возможности: `POST /messages` по `user_id`/`chat_id`, вложения (фото до 50 МБ, видео 250 МБ, файлы до 4 ГБ), webhook (HTTPS 443, доверенный сертификат или Минцифры, ответ 200 за 30 с, секрет в `X-Max-Bot-Api-Secret`, 10 повторов, автоотписка через 8 ч без 200) или long polling; лимиты 30 rps, 2 сообщения/с в диалог, 4000 символов. Официальный npm `@maxhub/max-bot-api` (обновлён 08.10.2026).
- Ограничение, из-за которого это не замена: бот — ВХОДЯЩИЙ канал. Пишет только тем, кто сам нажал «Начать» (`bot_started`); по номеру телефона адресовать нельзя, номер пользователя выдаётся только через `requestContact()` в диалоге. Чаты бота не видны в приложении MAX на телефоне клиники — администратор отвечал бы только из нашего «Чата». Текущие ~200 MAX-диалогов пациентов с номером клиники в бота не переедут.
- Где уместен: «белый» канал для новых обращений (ссылка/QR на бота в уведомлениях и на сайте), Мила отвечает в боте через наш бэкенд напрямую (без Chatpush; у нас уже есть обвязка `max_bot` для Chatpush-формы). Это новый продукт, не миграция.

### 3.3 Официальные уведомления по номеру (путь C)

- 12.05.2026: МТС, Билайн, МегаФон, T2 подключают MAX к сервисным уведомлениям, кодам подтверждения и транзакционным сообщениям бизнеса/госорганов — в папки «Коды подтверждения»/«Полезные уведомления», «в рамках существующих договоров операторов с бизнес-клиентами». Агрегаторы (edna — сертифицированный партнёр, Messaggio, Devino, evatelecom) продают то же: Messaggio — предварительно 8,5–12,2 ₽ за клиента/мес, «прямое подключение пока недоступно».
- Односторонний канал: ответы пациента («Подтверждаю», «5») в наш вебхук не вернутся (если конкретный агрегатор не даёт двусторонний API — проверять при выборе). У YClients есть собственный бесплатный канал MAX с нередактируемыми шаблонами (см. спеку уведомлений §2.2).
- Уместен только для модуля уведомлений (`docs/superpowers/specs/2026-10-13-yclients-notifications-own-module-design.md`, §7 п.1), где MAX — 30 % служебных отправок.

## 5. Что потребуется сделать по пути A (если владелец примет риск)

1. **Спайк 1–2 дня, до любого дизайна** (как `gateway/scripts/whatsapp-spike.js`): на тестовом номере 79200255591, с RU-IP (прод-бокс или прокси), библиотека `webmaxsocket` (запасная — `max-account-api`, сверка по PyMax). Проверить: вход по QR с телефона и по номеру+SMS; сохранение сессии и рестарт без кода; входящее 1:1 в реальном времени; ЭХО своего сообщения, набранного в приложении на телефоне (на нём держится пауза «ответил оператор»); видимость номера собеседника и id для лички/группы (сверить с форматом Chatpush: `chat_id` = id собеседника, у групп «-…»); отправка по номеру пациенту, который ещё не писал (`getUserByPhone`); фото и файл в обе стороны; поведение при «Приложение устарело»; реконнект. Без зелёного спайка путь A закрывается.
2. **Дизайн по образцу** `docs/superpowers/specs/2026-10-12-whatsapp-gateway-design.md`: `gateway/lib/max-client.js` с тем же интерфейсом, `max-mapper.js` → плоская форма `max_incoming_msg` с `provider='gateway'`, `delivery_id` у своих отправок (синтез эха, как у WhatsApp), `gateway_deliveries` со статусами 2/5, сессия в `data/acc-<id>/max`, `registry.clientClassFor('max')`, `accounts-repo.listActive` + `max`, `/api/v1/delivery` принимает `max_user_id`, `createGatewayAccount(salonId,'max')`, кнопка «Подключить MAX напрямую» с QR и формой номер/код/пароль, переключение канала `activateAccount` и откат на Chatpush.
3. **Эксплуатация**: пин версии библиотеки, регламент обновления fingerprint (следить за «Приложение устарела»), алерт на разлогин (его нет и для WhatsApp — предложено 13.10), темп и дневные лимиты как у WhatsApp, никаких массовых проверок номеров.
4. **Выключение MAX в Chatpush** после переключения (иначе две сессии и двойные события; автоуведомления YClients по-прежнему идут через Chatpush — та же оговорка, что у Telegram/WhatsApp).

Объём сопоставим с WhatsApp-шлюзом: спека + ~10 задач, 2–3 дня subagent-driven плюс живой прогон.

## 6. Решения владельца

1. Принимаем ли риск неофициального клиента на боевом номере клиники (блок номера = потеря MAX и для администраторов)? Альтернатива — оставить MAX на Chatpush (тот же риск, но чужими руками, и сейчас канал там не работает) или не вести диалоги в MAX вовсе (каскад на Telegram/WhatsApp/SMS).
2. Нужен ли параллельно официальный бот MAX как «белый» канал для новых пациентов (требует верификации клиники на `dev.max.ru`, сайта и политики, и это другой продукт).
3. Для уведомлений: официальный канал по номеру (операторы/агрегатор, платно, без ответов) или канал MAX у YClients (бесплатно, шаблоны не редактируются) — решение из спеки уведомлений §7.
